8. Testing as you go

In this chapter you will write your first test blocks, run them with zig test, and learn the handful of assertion functions in std.testing that the rest of this book relies on. You will also read a real failure message slowly, so that when your own tests fail later you know exactly where to look. From here on most exercises are test files: you fill in a function, run one command, and the file tells you whether you are done.

8.1 Why testing comes this early

Most books put testing near the end, as a good habit to pick up once you know the language. Zig makes the opposite order natural. A test is not a separate framework, a separate folder, or a separate runner: it is a block of code in the same file as the thing it checks, and the compiler itself knows how to run it. Writing one costs three lines.

That matters for a learner more than for anyone else. Every exercise from now on is a file with a // TODO and a few tests at the bottom. You run zig test, read what fails, fix it, run it again. No printing values to eyeball, no guessing whether an edge case works. The compiler is the grader, and it is a strict one.

It matters for IRON LEDGER too. The game has 224 tests spread across its modules, and its rule is simple: every module carries its own. When a rule about salaries or contracts changes, the test next to it changes in the same commit. You will read some of those tests in Part 5; today you learn to write the small ones.

8.2 Your first test block

A test is the keyword test, a name in quotes, and a block. Put it in any file, next to the function it checks.

first_test.zig

const std = @import("std");

fn add(a: i32, b: i32) i32 {
    return a + b;
}

test "add works" {
    try std.testing.expect(add(2, 3) == 5);
}

Notice there is no main. A test file does not need one. Run it with zig test instead of zig run:

1/1 first_test.test.add works...OK
All 1 tests passed.

Read the first line carefully, because you will see thousands like it. 1/1 means test one of one. first_test.test.add works is the full name: the file, the word test, then the name you wrote in quotes. Then OK. The last line is the summary.

Inside the block, std.testing.expect takes a boolean. If it is true the function returns normally; if it is false it returns an error, and the try in front of it makes the test fail. That is all a test failure is in Zig: an error returned from the test block. This is also why every assertion line starts with try. Forget it and the compiler complains that you are ignoring an error value, which is Zig's usual rule for error unions (Chapter 16 covers this properly).

Add a second function and a second test:

two_tests.zig

const std = @import("std");

fn add(a: i32, b: i32) i32 {
    return a + b;
}

fn double(x: i32) i32 {
    return x * 2;
}

test "add works" {
    try std.testing.expect(add(2, 3) == 5);
}

test "double works" {
    try std.testing.expectEqual(@as(i32, 8), double(4));
}
1/2 two_tests.test.add works...OK
2/2 two_tests.test.double works...OK
All 2 tests passed.

Tests run in the order they appear in the file. Each one is independent: a failure in one does not stop the others from running.

8.3 What a failure looks like

Now break something on purpose. Change add to subtract:

failing.zig

const std = @import("std");

fn add(a: i32, b: i32) i32 {
    return a - b; // bug: should be a + b
}

test "add works" {
    try std.testing.expectEqual(@as(i32, 5), add(2, 3));
}
1/1 failing.test.add works...expected 5, found -1
FAIL (TestExpectedEqual)
<zig>/lib/std/testing.zig:118:17: in expectEqualInner__anon_36361 (test)
                return error.TestExpectedEqual;
                ^
<zig>/lib/std/testing.zig:83:5: in expectEqual (test)
    return expectEqualInner(T, expected, actual);
    ^
ch08/failing.zig:8:5: in test.add works (test)
    try std.testing.expectEqual(@as(i32, 5), add(2, 3));
    ^
0 passed; 0 skipped; 1 failed.

There is a lot of text, but only three lines matter, and they are always in the same places:

  • The first line, after the test name: expected 5, found -1. That is the diagnostic. It tells you what the test wanted and what it got.
  • The line naming your own file: failing.zig:8:5, followed by the source line. That is where the assertion is. Line 8, column 5.
  • The summary: 0 passed; 0 skipped; 1 failed.

Everything in between is a stack trace through std/testing.zig. It shows how the failure travelled up from expectEqualInner to your test. You can ignore those lines until you are debugging something deep; your eye should learn to skip to the line with your file name in it.

Compare this with the same bug caught by plain expect:

failing_expect.zig

const std = @import("std");

fn add(a: i32, b: i32) i32 {
    return a - b; // bug
}

test "add works" {
    try std.testing.expect(add(2, 3) == 5);
}
1/1 failing_expect.test.add works...FAIL (TestUnexpectedResult)
<zig>/lib/std/testing.zig:615:14: in expect (test)
    if (!ok) return error.TestUnexpectedResult;
             ^
ch08/failing_expect.zig:8:5: in test.add works (test)
    try std.testing.expect(add(2, 3) == 5);

Same failure, but the diagnostic line is gone. You know that add(2, 3) == 5 was false, not what add actually returned. That difference is the whole reason the more specific assertion functions exist. Use expect for genuinely boolean questions (is this even?) and a more specific function whenever you are comparing two values.

8.4 The assertion family

You need five functions. Learn their names now; you will type them hundreds of times.

expectEqualStrings(expected, actual)comparing textboth strings, with the first difference marked

Finally, expectError. It takes an error value and an error union, the kind of value a function returning !T gives you. It passes when the union holds exactly that error.

errors.zig

const std = @import("std");

const ParseError = error{Empty};

fn firstByte(s: []const u8) ParseError!u8 {
    if (s.len == 0) return error.Empty;
    return s[0];
}

test "empty input is an error" {
    try std.testing.expectError(error.Empty, firstByte(""));
}

test "non-empty input works" {
    try std.testing.expectEqual(@as(u8, 'a'), try firstByte("abc"));
}
1/2 errors.test.empty input is an error...OK
2/2 errors.test.non-empty input works...OK
All 2 tests passed.

Note the second test: to compare the successful value you first have to unwrap it with try. try firstByte("abc") is a u8; firstByte("abc") on its own is a ParseError!u8, and expectEqual would refuse to compare a plain u8 to that.

8.5 The @as(T, literal) convention

Look back at the tests above and you will see a pattern that looks fussy:

try std.testing.expectEqual(@as(i32, 8), double(4));

Why not just expectEqual(8, double(4))? In older Zig versions that did not compile: a bare 8 has the type comptime_int, and expectEqual insisted that the actual value be converted to the type of the expected one, which is impossible for a runtime i32. Every tutorial and most codebases, IRON LEDGER included, wrap the expected value in @as(T, ...) to give it a concrete type.

In Zig 0.16 the function was changed to use peer type resolution, the same rule that decides the type of if (c) 1 else x. A bare literal and an i32 now resolve to i32, so this compiles and passes:

const std = @import("std");

fn add(a: i32, b: i32) i32 {
    return a + b;
}

test "literal trap" {
    try std.testing.expectEqual(5, add(2, 3));
}

So why keep writing @as? Two reasons. First, you will read it everywhere, so you need to recognise it. Second, it still catches mistakes: if you write expectEqual(300, small()) where small returns a u8, the compiler stops you with type 'u8' cannot represent integer value '300', which is exactly the kind of bug a test is for. This book writes @as(T, value) in solutions so they match the style you will see in real code, and you may drop it in your own tests when the types are obvious.

The real trap: expectEqual on strings. Two slices are "equal" to expectEqual when they point at the same memory and have the same length. It does not look at the bytes. So this fails even though both strings say hi: 
const std = @import("std");

fn label(buf: []u8) []const u8 {
    buf[0] = 'h';
    buf[1] = 'i';
    return buf[0..2];
}

test "expectEqual on strings compares pointers" {
    var buf: [8]u8 = undefined;
    try std.testing.expectEqual("hi", label(&buf));
}

test "expectEqualStrings compares contents" {
    var buf: [8]u8 = undefined;
    try std.testing.expectEqualStrings("hi", label(&buf));
}
1/2 slicetrap.test.expectEqual on strings compares pointers...expected slice ptr u8@10026955c, found u8@16fce9d70
FAIL (TestExpectedEqual)
<zig>/lib/std/testing.zig:133:25: in expectEqualInner__anon_36825 (test)
                        return error.TestExpectedEqual;
                        ^
<zig>/lib/std/testing.zig:83:5: in expectEqual (test)
    return expectEqualInner(T, expected, actual);

The diagnostic says it plainly: expected slice ptr ..., found .... Two different addresses. Whenever you compare text, use expectEqualStrings; whenever you compare slices, use expectEqualSlices. (Arrays, as opposed to slices, are compared element by element, which is why expectEqual([3]u8{...}, arr) works fine in later chapters.)

8.6 Naming tests and running a subset

Test names are free-form strings. Use them as sentences about behaviour, not as function names: "empty input is an error" tells the reader more than "firstByte". A common convention is a prefix for the area, which makes the next feature useful.

filter.zig

const std = @import("std");

test "math: addition" {
    try std.testing.expect(1 + 1 == 2);
}

test "math: multiplication" {
    try std.testing.expect(2 * 3 == 6);
}

test "text: length" {
    try std.testing.expect("abc".len == 3);
}

--test-filter runs only the tests whose full name contains the given text:

$ zig test filter.zig --test-filter math
1/2 filter.test.math: addition...OK
2/2 filter.test.math: multiplication...OK
All 2 tests passed.

Notice the numbering changed to 1/2 and 2/2: the third test was not compiled into this run at all. When a big file has one stubborn failure, filtering down to it makes the edit-run loop much faster.

8.7 Tests live next to the code

In Zig the normal place for a test is the same file as the function it exercises, usually right below it or gathered at the bottom. Nothing stops you from making a separate _test.zig file, but you then have to @import the code under test and mark everything pub, and you lose the ability to test private helpers. Same-file tests can see everything.

Test blocks are only compiled by zig test. When you zig run or zig build the same file, they vanish. There is no runtime cost and no separate build configuration.

One consequence of Zig's laziness deserves a callout. The compiler only analyses functions that something actually calls. A function nobody references can contain nonsense and still build:

refall_ok.zig

const std = @import("std");

pub fn unusedHelper(x: u32) u32 {
    return x + "oops"; // never called, so never checked
}

test "something else" {
    try std.testing.expect(true);
}
1/1 refall_ok.test.something else...OK
All 1 tests passed.

That is convenient while sketching, and dangerous in a library: a helper can rot for months without anyone noticing. The fix is a nameless test that references every declaration in the file:

refall.zig

const std = @import("std");

pub fn unusedHelper(x: u32) u32 {
    return x + "oops"; // never called, so normally never checked
}

test {
    std.testing.refAllDecls(@This());
}
refall.zig:4:14: error: incompatible types: 'u32' and '*const [4:0]u8'
    return x + "oops"; // never called, so normally never checked
           ~~^~~~~~~~
refall.zig:4:12: note: type 'u32' here
    return x + "oops"; // never called, so normally never checked
           ^
refall.zig:4:16: note: type '*const [4:0]u8' here
    return x + "oops"; // never called, so normally never checked
               ^~~~~~
referenced by:
    refAllDecls__anon_36346: <zig>/lib/std/testing.zig:1216:14
    test_0: refall.zig:8:28

@This() means "the type of the thing I am inside", which at file scope is the file itself (files are structs, as Chapter 30 explains). refAllDecls touches every public declaration so the compiler has to type-check them. IRON LEDGER has exactly this test in its root file, and every exercise solution in this book ends with one when it has pub functions. A test with no name shows up in the output as test_0.

8.9 The rhythm from here on

Every exercise from this chapter forward follows the same loop:

  1. Open the starter file. Read the tests at the bottom first; they are the specification.
  2. Replace each // TODO with code. Remove the _ = x; lines that were only there to keep the starter compiling.
  3. Run zig test filename.zig.
  4. Read the first failure. Find the line with your file name. Fix. Repeat.

Compile errors come before test failures. If you see error: with a file and line but no 1/3 counter, the file did not compile and no test ran yet. Unused variables, wrong types, and missing try are the usual suspects at this stage.

In IRON LEDGER. The dice module keeps its tests directly under the type they exercise. This one checks that drawing a thousand numbers from one random stream does not disturb another, which is what makes the game's replays reproducible (Chapter 49): 
// src/sim/rng.zig
test "streams are independent and deterministic" {
    var a = Rng.init(42);
    var b = Rng.init(42);

    // Draw heavily from one stream in `a` only; another stream must still
    // match the untouched twin exactly.
    for (0..1000) |_| _ = a.roll2d6(.maintenance);
    for (0..10) |_| {
        try std.testing.expectEqual(b.roll2d6(.battle), a.roll2d6(.battle));
    }
}

test "2d6 stays in range" {
    var r = Rng.init(7);
    for (0..1000) |_| {
        const v = r.roll2d6(.events);
        try std.testing.expect(v >= 2 and v <= 12);
    }
}

Note the choice of assertion in each: expectEqual where two values must match (a failure would print both rolls), expect for a range check. The root file src/root.zig ends with the nameless refAllDecls(@This()) test, so that the 31,000 lines are all type-checked on every zig build test, even the paths no test walks.

Exercises

Exercise 8.1 · Your first test file warm-up

Fill in max and isEven so that the tests pass. Then deliberately break max (return a always) and read the failure output before fixing it again. Name the file: exercises/08-testing/ex1_first_tests.zig.

Solution 
//! Chapter 08, exercise 1: your first test file.
//! Run with:  zig test ex1_first_tests.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Returns the larger of two integers.
fn max(a: i32, b: i32) i32 {
    return if (a > b) a else b;
}

/// Returns true when n is even.
fn isEven(n: i32) bool {
    return @rem(n, 2) == 0;
}

test "max picks the larger" {
    try std.testing.expectEqual(@as(i32, 7), max(3, 7));
    try std.testing.expectEqual(@as(i32, 7), max(7, 3));
    try std.testing.expectEqual(@as(i32, -1), max(-1, -5));
}

test "isEven" {
    try std.testing.expect(isEven(0));
    try std.testing.expect(isEven(10));
    try std.testing.expect(!isEven(7));
    try std.testing.expect(isEven(-4));
}

@rem is used instead of % because % on signed integers is a compile error when the operand might be negative (Chapter 4). @rem(-4, 2) is 0, so the negative case passes.

Exercise 8.2 · Pick the right assertion warm-up

Every test in the starter uses plain expect. Replace each one with the most specific assertion that fits, so a failure would print a useful message. The tests must still pass. Name the file: exercises/08-testing/ex2_pick_assertion.zig.

Solution 
//! Chapter 08, exercise 2: pick the right assertion.
//! Run with:  zig test ex2_pick_assertion.zig
//! Goal: replace every `expect(...)` with the most specific assertion that fits,
//! so that a failure prints a useful message. All tests must still pass.
const std = @import("std");

const ParseError = error{ Empty, NotADigit };

fn digit(s: []const u8) ParseError!u8 {
    if (s.len == 0) return error.Empty;
    const c = s[0];
    if (c < '0' or c > '9') return error.NotADigit;
    return c - '0';
}

fn shout(buf: []u8, word: []const u8) []const u8 {
    for (word, 0..) |c, i| buf[i] = std.ascii.toUpper(c);
    return buf[0..word.len];
}

fn firstTwo(xs: []const u32) []const u32 {
    return xs[0..2];
}

test "digit parses a single digit" {
    try std.testing.expectEqual(@as(u8, 7), try digit("7"));
}

test "digit rejects empty input" {
    try std.testing.expectError(error.Empty, digit(""));
}

test "digit rejects letters" {
    try std.testing.expectError(error.NotADigit, digit("x"));
}

test "shout upper-cases" {
    var buf: [16]u8 = undefined;
    try std.testing.expectEqualStrings("LANCE", shout(&buf, "lance"));
}

test "firstTwo slices" {
    const data = [_]u32{ 5, 6, 7 };
    try std.testing.expectEqualSlices(u32, &[_]u32{ 5, 6 }, firstTwo(&data));
}

The starter's expect(digit("") == error.Empty) works but says nothing useful on failure. expectError prints which error was actually returned. Likewise expectEqualStrings shows both strings with a caret at the first difference, where expect(std.mem.eql(...)) only says "false".

//! Chapter 08, exercise 3: read a failure, fix the bug.
//! Run with:  zig test ex3_fix_the_bug.zig
//! Goal: the tests are correct; the functions have bugs. Read the failure output,
//! find each bug and fix it. Do not edit the tests.
const std = @import("std");

/// Sum of the first n positive integers: 1 + 2 + ... + n.
fn triangle(n: u32) u32 {
    var total: u32 = 0;
    var i: u32 = 1;
    while (i <= n) : (i += 1) total += i;
    return total;
}

/// Number of characters in s that equal c.
fn countChar(s: []const u8, c: u8) usize {
    var n: usize = 0;
    for (s) |ch| {
        if (ch == c) n += 1;
    }
    return n;
}

/// Clamp x into [lo, hi].
fn clamp(x: i32, lo: i32, hi: i32) i32 {
    if (x < lo) return lo;
    if (x > hi) return hi;
    return x;
}

test "triangle numbers" {
    try std.testing.expectEqual(@as(u32, 0), triangle(0));
    try std.testing.expectEqual(@as(u32, 1), triangle(1));
    try std.testing.expectEqual(@as(u32, 10), triangle(4));
    try std.testing.expectEqual(@as(u32, 5050), triangle(100));
}

test "countChar" {
    try std.testing.expectEqual(@as(usize, 3), countChar("banana", 'a'));
    try std.testing.expectEqual(@as(usize, 0), countChar("banana", 'z'));
    try std.testing.expectEqual(@as(usize, 0), countChar("", 'a'));
}

test "clamp" {
    try std.testing.expectEqual(@as(i32, 5), clamp(5, 0, 10));
    try std.testing.expectEqual(@as(i32, 0), clamp(-3, 0, 10));
    try std.testing.expectEqual(@as(i32, 10), clamp(42, 0, 10));
}

Three classic bugs: an off-by-one in the loop condition (< should be <=), a stray break that stops the loop after the first character, and swapped return values in clamp. The diagnostic expected 1, found 0 for triangle(1) is the hint for the first one: the loop never ran.

Exercise 8.4 · Write the tests yourself practice

The functions are given and correct. Write at least three tests for each, including one edge case each (zero, empty string, negative numbers). Give the tests sentence-like names. Finish with a nameless refAllDecls test. Name the file: exercises/08-testing/ex4_write_tests.zig.

Solution 
//! Chapter 08, exercise 4: write the tests yourself.
//! Run with:  zig test ex4_write_tests.zig
//! Goal: the functions are given. Write at least three tests for each, including
//! one edge case (zero, empty, negative). Finish with a refAllDecls test.
const std = @import("std");

pub fn absDiff(a: i32, b: i32) u32 {
    return if (a > b) @intCast(a - b) else @intCast(b - a);
}

pub fn isPalindrome(s: []const u8) bool {
    if (s.len < 2) return true;
    var i: usize = 0;
    var j: usize = s.len - 1;
    while (i < j) : ({
        i += 1;
        j -= 1;
    }) {
        if (s[i] != s[j]) return false;
    }
    return true;
}

test "absDiff: ordinary values" {
    try std.testing.expectEqual(@as(u32, 4), absDiff(7, 3));
    try std.testing.expectEqual(@as(u32, 4), absDiff(3, 7));
}

test "absDiff: negatives and zero" {
    try std.testing.expectEqual(@as(u32, 0), absDiff(5, 5));
    try std.testing.expectEqual(@as(u32, 10), absDiff(-5, 5));
    try std.testing.expectEqual(@as(u32, 2), absDiff(-7, -5));
}

test "isPalindrome: true cases" {
    try std.testing.expect(isPalindrome("racecar"));
    try std.testing.expect(isPalindrome("abba"));
    try std.testing.expect(isPalindrome("x"));
}

test "isPalindrome: empty string is a palindrome" {
    try std.testing.expect(isPalindrome(""));
}

test "isPalindrome: false cases" {
    try std.testing.expect(!isPalindrome("lance"));
    try std.testing.expect(!isPalindrome("ab"));
}

}

Edge cases are where bugs hide. isPalindrome("") is worth its own test because s.len - 1 would underflow on an empty slice if the early return were missing; a test documents that the function handles it.

Check your understanding

  1. What is a test failure, in language terms?
    AnswerAn error returned from the test block. The assertion functions return an error on failure, and try propagates it out of the test.
  2. Why must every assertion line begin with try?
    AnswerBecause the assertion functions return error unions, and Zig will not let you silently discard an error. try unwraps on success and returns the error on failure.
  3. You see expected 3, found 4 but you know the function should return 3. What went wrong?
    AnswerMost likely the arguments are swapped: the function returned 3 (printed as "expected") and the literal 4 was in the actual position. Expected goes first.
  4. Why does expectEqual("hi", someSlice) fail even when someSlice holds hi?
    AnswerFor slices, expectEqual compares the pointer and the length, not the contents. Use expectEqualStrings for text or expectEqualSlices for other element types.
  5. How do you run only the tests whose names contain "parse"?
    Answerzig test file.zig --test-filter parse.
  6. What does test { std.testing.refAllDecls(@This()); } catch that other tests do not?
    AnswerType errors in declarations that nothing calls. Zig only analyses code that is referenced; this test references every public declaration in the file so all of it gets checked.
  7. The output says All 1 tests passed. and then 1 tests leaked memory. and the command fails. Which allocator was in use?
    Answerstd.testing.allocator. It tracks every allocation and reports the ones never freed, failing the run even though the test body returned normally.
What you learned.
  • test "name" { ... } blocks live next to the code they check and run with zig test file.zig.
  • A failure is an error returned from the block; every assertion needs try.
  • Use expectEqual, expectEqualStrings, expectEqualSlices and expectError over plain expect so failures print what they saw. Expected value first.
  • @as(T, literal) gives the expected value a concrete type. Zig 0.16 no longer requires it for plain integers, but you will see it everywhere.
  • expectEqual on slices compares addresses, not bytes.
  • Read a failure by finding the diagnostic line and the line with your file name; skip the std/testing.zig frames.
  • --test-filter text runs a subset. refAllDecls(@This()) forces every declaration to be type-checked. std.testing.allocator fails tests that leak.
