31. The build system

In this chapter you will stop typing zig run file.zig and start describing your program in build.zig: a Zig program that builds a graph of steps. You will create a project with zig init, read every line it generates, add modules, options, run and test steps, choose optimisation modes, and finally read IRON LEDGER's real build script from top to bottom.

31.1 zig init

There is one tool, zig. It compiles, tests, formats and runs. For anything bigger than one file it reads build.zig, and the quickest way to get a correct one is to let it write one. In an empty directory:

$ mkdir init && cd init && zig init
info: created build.zig
info: created build.zig.zon
info: created src/main.zig
info: created src/root.zig
info: see `zig build --help` for a menu of options

Four files. build.zig.zon is the package manifest you met in Chapter 28. src/root.zig is a library with one function and a test. src/main.zig is an executable that imports the library. And build.zig is about 150 lines, most of them comments, describing how the two fit together. Trimmed of its comments it is this:

const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const mod = b.addModule("init", .{
        .root_source_file = b.path("src/root.zig"),
        .target = target,
    });

    const exe = b.addExecutable(.{
        .name = "init",
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/main.zig"),
            .target = target,
            .optimize = optimize,
            .imports = &.{
                .{ .name = "init", .module = mod },
            },
        }),
    });
    b.installArtifact(exe);

    const run_step = b.step("run", "Run the app");
    const run_cmd = b.addRunArtifact(exe);
    run_step.dependOn(&run_cmd.step);
    run_cmd.step.dependOn(b.getInstallStep());
    if (b.args) |args| {
        run_cmd.addArgs(args);
    }

    const mod_tests = b.addTest(.{ .root_module = mod });
    const run_mod_tests = b.addRunArtifact(mod_tests);
    const exe_tests = b.addTest(.{ .root_module = exe.root_module });
    const run_exe_tests = b.addRunArtifact(exe_tests);

    const test_step = b.step("test", "Run tests");
    test_step.dependOn(&run_mod_tests.step);
    test_step.dependOn(&run_exe_tests.step);
}

The rest of this chapter explains each of those lines, with a slightly smaller project of our own so the output fits on a page.

31.2 A build script does not build

Read the signature: pub fn build(b: *std.Build) void. When you type zig build, the compiler first compiles this function into a small program called the build runner, runs it, and the function describes the work by adding steps to b. Nothing is compiled while build() executes. Only after it returns does the runner look at the graph, decide which steps the user asked for, work out what is cached, and execute the rest, in parallel where dependencies allow.

That is why the calls are named the way they are: addExecutable, addTest, addRunArtifact. Each adds a node. dependOn adds an edge. b.step("name", …) creates a named entry point the user can type. Everything else is plumbing between nodes.

31.3 Anatomy of build.zig

Here is the project for this chapter: a library module money in lib/, an executable in src/, two options, build-time constants, and run and test steps. Every line is numbered by the comment above it.

ledger/build.zig

const std = @import("std");

pub fn build(b: *std.Build) void {
    // 1. Options the user can pass on the command line.
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});
    const verbose = b.option(bool, "verbose", "Print every transaction") orelse false;
    const company = b.option([]const u8, "company", "Company name baked into the binary") orelse "Unnamed";

    // 2. A library module other code can import as "money".
    const money = b.addModule("money", .{
        .root_source_file = b.path("lib/money.zig"),
        .target = target,
    });

    // 3. Build-time constants, visible in code as @import("build_options").
    const opts = b.addOptions();
    opts.addOption(bool, "verbose", verbose);
    opts.addOption([]const u8, "company", company);

    // 4. The executable: its own root module that imports the library.
    const exe = b.addExecutable(.{
        .name = "ledger",
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/main.zig"),
            .target = target,
            .optimize = optimize,
            .imports = &.{
                .{ .name = "money", .module = money },
                .{ .name = "build_options", .module = opts.createModule() },
            },
        }),
    });
    b.installArtifact(exe);

    // 5. `zig build run -- args`
    const run_cmd = b.addRunArtifact(exe);
    run_cmd.step.dependOn(b.getInstallStep());
    if (b.args) |args| run_cmd.addArgs(args);
    const run_step = b.step("run", "Run the ledger");
    run_step.dependOn(&run_cmd.step);

    // 6. `zig build test`: one test binary per module.
    const lib_tests = b.addTest(.{ .root_module = money });
    const exe_tests = b.addTest(.{ .root_module = exe.root_module });
    const test_step = b.step("test", "Run all tests");
    test_step.dependOn(&b.addRunArtifact(lib_tests).step);
    test_step.dependOn(&b.addRunArtifact(exe_tests).step);
}

ledger/lib/money.zig

//! The "money" module: C-bills as integers, never floats.
const std = @import("std");

pub const CBills = i64;

pub fn fromCbills(n: i64) CBills {
    return n * 100;
}

pub fn format(buf: []u8, amount: CBills) ![]u8 {
    const sign: []const u8 = if (amount < 0) "-" else "";
    const abs: u64 = @abs(amount);
    return std.fmt.bufPrint(buf, "{s}{d}.{d:0>2} C-bills", .{ sign, abs / 100, abs % 100 });
}

test "format" {
    var buf: [64]u8 = undefined;
    try std.testing.expectEqualStrings("12.05 C-bills", try format(&buf, 1205));
    try std.testing.expectEqualStrings("-0.50 C-bills", try format(&buf, -50));
}

ledger/src/main.zig

const std = @import("std");
const money = @import("money");
const build_options = @import("build_options");

pub fn main(init: std.process.Init) !void {
    var buf: [256]u8 = undefined;
    var w = std.Io.File.stdout().writer(init.io, &buf);
    const out = &w.interface;

    var balance: money.CBills = money.fromCbills(1000);
    var it = std.process.Args.Iterator.init(init.minimal.args);
    _ = it.next();
    while (it.next()) |arg| {
        const delta = try std.fmt.parseInt(i64, arg, 10);
        balance += delta;
        if (build_options.verbose) try out.print("  {s:>8} -> {d}\n", .{ arg, balance });
    }
    var fbuf: [64]u8 = undefined;
    try out.print("{s}: {s}\n", .{ build_options.company, try money.format(&fbuf, balance) });
    try out.flush();
}

test "main module compiles and sees the library" {
    try std.testing.expectEqual(@as(money.CBills, 200), money.fromCbills(2));
}

1. Options. b.standardTargetOptions registers -Dtarget and -Dcpu, so anyone can cross-compile your project without editing the script. b.standardOptimizeOption registers -Doptimize. b.option(T, name, description) declares your own flag; it returns ?T, null when the user did not pass it, and you supply the default with orelse. Supported Ts include bool, integers, []const u8, enums, and lists of strings.

2. Modules. A module is a tree of source files with one root, plus the settings needed to compile it. b.addModule("money", …) creates one and makes it available under that name to other packages that depend on yours. b.createModule(…) creates one that is private to this build. Both take the same options: root_source_file, target, optimize, and an imports list that says which other modules this one may @import by name.

3. Build options. b.addOptions() creates a step that writes a tiny generated Zig file, and addOption(T, name, value) adds a constant to it. opts.createModule() turns that into a module you can import. In the source, @import("build_options").verbose is then a compile-time bool, and if (build_options.verbose) compiles to nothing at all when it is false.

4. The executable. b.addExecutable takes a name and a root_module. The root module is where main lives, and its imports list is how the source's @import("money") finds the library. b.installArtifact(exe) says "when the user runs the default step, copy this into the install prefix", which is zig-out/bin/ unless changed.

5. Run. b.addRunArtifact(exe) creates a step that executes the built program. Making it depend on the install step means it runs the installed copy. b.args is the optional list of words after -- on the command line, forwarded with addArgs. Finally b.step("run", …) creates the entry point and dependOn wires it to the run step.

6. Tests. b.addTest compiles a module as a test binary. A test binary covers one module, so a project with a library and an executable makes two and runs both under one test step. Steps run in parallel when nothing orders them.

31.5 Optimisation modes

The -Doptimize flag chooses one of four modes, and the choice changes what the language guarantees:

ModeSpeedSafety checksUse it for
Debug (default)slowon: overflow, bounds, null, leak detectiondevelopment, every test run
ReleaseSafefaston: overflow, bounds, null still panicshipping software that must fail loudly
ReleaseFastfastestoff: undefined behaviour on overflowbenchmarks, code you have tested to exhaustion
ReleaseSmallfastoff, plus size over speedembedded, downloads where size matters
$ zig build -Doptimize=ReleaseSmall --prefix /tmp/ledger-small
$ zig build -Doptimize=ReleaseFast -p /tmp/ledger-fast
$ ls -l zig-out/bin/ledger /tmp/ledger-small/bin/ledger /tmp/ledger-fast/bin/ledger
2065784 zig-out/bin/ledger
 396936 /tmp/ledger-fast/bin/ledger
 165272 /tmp/ledger-small/bin/ledger

The same program is two megabytes in Debug (full debug info and safety code), 400 KB in ReleaseFast, and 165 KB in ReleaseSmall. --prefix (short form -p) redirects the install from zig-out to any directory, which is how you produce a release tree.

Do not test in ReleaseFast. The safety checks that make Debug and ReleaseSafe catch overflow and out-of-bounds are switched off in ReleaseFast. A bug that panics in Debug may silently corrupt memory there. Develop and test in Debug, ship ReleaseSafe unless you have measured a need for more, and use std.math.add-style checked functions for arithmetic that must be correct in every mode (Exercise 31.4).

31.6 The cache and the output directory

Two directories appear beside build.zig. zig-out/ is the install prefix: bin/ for executables, lib/ for libraries, whatever installDirectory adds. It is yours to ship or delete. .zig-cache/ holds compiled objects keyed by a hash of their inputs, so a second zig build that changes nothing does nothing. There is also a global cache (~/.cache/zig on this machine, see zig env) for the standard library and fetched packages. Both caches are safe to delete; the next build simply takes longer. Add both directories to .gitignore.

31.7 Data files and C libraries

Two more module calls round out the vocabulary. module.addAnonymousImport("name", .{ .root_source_file = path }) binds a file anywhere on disk to an import name; you saw it in Chapter 28 for ZON tables. And for C:

mod.link_libc = true;
mod.linkSystemLibrary("sqlite3", .{});

The first links the C standard library into the module; the second asks the system linker for libsqlite3. Chapter 35 shows what the Zig side of such a binding looks like. Both are set on the module, and any executable or test that uses the module inherits them, which is why IRON LEDGER's tests can open a database without repeating the linker flags.

31.8 Reading IRON LEDGER's build.zig

Now comes the real thing, game/build.zig. It is the zig init template grown up, and you can read it in the order the template used. Comments are trimmed.

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const mod = b.addModule("game", .{
        .root_source_file = b.path("src/root.zig"),
        .target = target,

The simulation core is a module named game, rooted at the root.zig you read in Chapter 30. Then the data tables:

    const data_dir = b.option([]const u8, "data", "Directory overlaying data/*.zon and data/tables/*.zon (mod support)");
    const DataFile = struct { import_name: []const u8, rel: []const u8 };
    const data_files = [_]DataFile{
        .{ .import_name = "chassis_zon", .rel = "chassis.zon" },
        .{ .import_name = "planets_zon", .rel = "planets.zon" },
        .{ .import_name = "parts_zon", .rel = "parts.zon" },
        .{ .import_name = "tuning_zon", .rel = "tables/tuning.zon" },
        // … nine more
    };
    var overlaid = std.ArrayList([]const u8).empty;
    for (data_files) |f| {
        var path: std.Build.LazyPath = b.path(b.fmt("data/{s}", .{f.rel}));
        if (data_dir) |dir| {
            const candidate = b.pathJoin(&.{ dir, f.rel });
            const exists = if (std.fs.path.isAbsolute(candidate))
                std.Io.Dir.accessAbsolute(b.graph.io, candidate, .{})
            else
                b.build_root.handle.access(b.graph.io, candidate, .{});
            if (exists) |_| {
                path = if (std.fs.path.isAbsolute(candidate)) .{ .cwd_relative = candidate } else b.path(candidate);
                overlaid.append(b.allocator, f.rel) catch @panic("OOM");
            } else |_| {}
        }
        mod.addAnonymousImport(f.import_name, .{ .root_source_file = path });
    }

This is build.zig as a program, not a config file. A table of thirteen data files, a loop, and inside the loop a real file-system check (access through the build's own io) to see whether a mod directory supplies a replacement. Whatever path wins is bound with addAnonymousImport. The list of overlaid files is collected so the binary can report it:

    const build_options = b.addOptions();
    build_options.addOption(?[]const u8, "data_dir", data_dir);
    build_options.addOption([]const []const u8, "data_overlays", overlaid.items);
    mod.addImport("build_options", build_options.createModule());

    mod.link_libc = true;
    mod.linkSystemLibrary("sqlite3", .{});

And the run and test steps are the template's, with one addition worth learning from:

    const test_step = b.step("test", "Run tests");
    test_step.dependOn(&run_mod_tests.step);

A test step that also depends on install means "the tests passed and the binary builds". That line exists because of a real afternoon lost to a green test suite and a stale executable. Build scripts accumulate this kind of knowledge, and because they are ordinary Zig, the comment can sit right next to the fix.

In IRON LEDGER. The commands you will use daily in the game/ directory are zig build (compile and install to zig-out/bin/game), zig build test --summary all (every test block in both modules, plus the install), zig build run -- --tui (build and launch the terminal client), and zig build -Ddata=mymod (overlay tables from a mod directory). Run zig build --help there: the -Ddata and -Dbundle-music options you see are the two b.option calls above, and Zig generated the help text from their descriptions. The whole script is game/build.zig; read it once with this chapter beside you and it will hold no surprises.

Exercise 31.2 · Options become constants practice

In exercises/31-build-system/ex2_options/, wire -Ddifficulty (an enum), -Dfunds (a u32) and -Dcheats (a bool) through addOptions into @import("build_options"). Try zig build run -Ddifficulty=hard -Dfunds=500000 -Dcheats.

build.zig

const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    const difficulty = b.option(enum { easy, normal, hard }, "difficulty", "Starting difficulty") orelse .normal;
    const start_funds = b.option(u32, "funds", "Starting C-bills") orelse 1_000_000;
    const cheats = b.option(bool, "cheats", "Enable cheat commands") orelse false;

    const opts = b.addOptions();
    opts.addOption([]const u8, "difficulty", @tagName(difficulty));
    opts.addOption(u32, "start_funds", start_funds);
    opts.addOption(bool, "cheats", cheats);

    const mod = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
    });
    mod.addOptions("build_options", opts);

    const exe = b.addExecutable(.{ .name = "options", .root_module = mod });
    b.installArtifact(exe);
    b.step("run", "Print the baked-in settings").dependOn(&b.addRunArtifact(exe).step);

    const tests = b.addTest(.{ .root_module = mod });
    b.step("test", "Run tests").dependOn(&b.addRunArtifact(tests).step);
}

$ zig build run -Ddifficulty=hard -Dfunds=500000 -Dcheats

An enum option lists its values in --help automatically. The enum is converted to its tag name before being stored, because a build option must be a type the generated file can spell. mod.addOptions("build_options", opts) is a shorthand for adding the options module as an import.

Exercise 31.3 · Custom steps practice

In exercises/31-build-system/ex3_steps/, add a demo step that runs the program with three fixed arguments, a fmt step using b.addFmt with .check = true, and make test depend on the format check. zig build -l should list all of them.

Solution

build.zig

const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});
    const mod = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
    });
    const exe = b.addExecutable(.{ .name = "steps", .root_module = mod });
    b.installArtifact(exe);

    // A "run" step that forwards `zig build run -- args`.
    const run_cmd = b.addRunArtifact(exe);
    run_cmd.step.dependOn(b.getInstallStep());
    if (b.args) |args| run_cmd.addArgs(args);
    b.step("run", "Run the program").dependOn(&run_cmd.step);

    // A "demo" step that always runs the program with fixed arguments.
    const demo_cmd = b.addRunArtifact(exe);
    demo_cmd.addArgs(&.{ "alpha", "beta", "gamma" });
    b.step("demo", "Run with three fixed arguments").dependOn(&demo_cmd.step);

    // A "fmt" step: zig fmt --check over src/.
    const fmt = b.addFmt(.{ .paths = &.{"src"}, .check = true });
    b.step("fmt", "Check formatting").dependOn(&fmt.step);

    // "test" depends on tests AND on the format check.
    const tests = b.addTest(.{ .root_module = mod });
    const test_step = b.step("test", "Run tests and the format check");
    test_step.dependOn(&b.addRunArtifact(tests).step);
    test_step.dependOn(&fmt.step);
}

Exercise 31.4 · Which mode am I in? warm-up

A single file that prints @import("builtin").mode, says whether safety checks are on, and uses std.math.add to detect overflow in a way that works in every mode. Run it with zig run and again with zig run -O ReleaseFast. File: exercises/31-build-system/ex4_mode.zig.

Solution 
//! Chapter 31, exercise 4: see the optimize mode from inside the program.
//! Run with:  zig run ex4_mode.zig
//! Then try:  zig run -O ReleaseFast ex4_mode.zig
//! Expected output (Debug):
//!   mode: Debug
//!   safety checks: on
//!   overflow check: caught error.Overflow
const std = @import("std");
const builtin = @import("builtin");

pub fn main() void {
    std.debug.print("mode: {s}\n", .{@tagName(builtin.mode)});
    const safe = switch (builtin.mode) {
        .Debug, .ReleaseSafe => true,
        .ReleaseFast, .ReleaseSmall => false,
    };
    std.debug.print("safety checks: {s}\n", .{if (safe) "on" else "off"});
    // Never rely on a panic to catch overflow: use the checked builtin.
    const big: u8 = 250;
    if (std.math.add(u8, big, 10)) |v| {
        std.debug.print("overflow check: {d}\n", .{v});
    } else |err| {
        std.debug.print("overflow check: caught {s}\n", .{@errorName(err)});
    }
}

mode: Debug
safety checks: on
overflow check: caught Overflow
$ zig run -O ReleaseFast ex4_mode.zig
mode: ReleaseFast

Check your understanding

  1. Does build() compile anything while it runs?
    AnswerNo. It adds steps and dependencies to a graph; the build runner executes the graph afterwards.
  2. What is the difference between b.addModule and b.createModule?
    AnswerBoth create a module; addModule also exposes it by name to packages that depend on yours, createModule keeps it private to this build.
  3. How does @import("money") in src/main.zig find lib/money.zig?
    AnswerThrough the executable's root module imports list, which maps the name "money" to the module whose root is lib/money.zig.
  4. Where do words after -- on the zig build run command line go?
    AnswerInto b.args, which the script forwards to the run step with addArgs; the program sees them as its arguments.
  5. What does b.option(bool, "verbose", "…") return when the user passes nothing?
    Answernull; the script supplies a default with orelse.
  6. Which optimisation modes keep safety checks on?
    AnswerDebug and ReleaseSafe. ReleaseFast and ReleaseSmall turn them off.
  7. Why does one project need two addTest calls?
    AnswerA test binary covers one module. A library module and an executable module each need their own.
  8. What does --prefix change, and what is its short form?
    AnswerThe install directory, zig-out by default; -p.
What you learned.
  • zig init writes build.zig, build.zig.zon, src/main.zig and src/root.zig.
  • build() describes a graph of steps; the runner executes it with caching and parallelism.
  • standardTargetOptions, standardOptimizeOption and b.option declare -D flags; zig build --help lists them.
  • addModule/createModule define modules; imports connects them by name; addExecutable takes a root_module.
  • installArtifact, addRunArtifact, b.args, b.step and dependOn build run steps; addTest per module builds test steps.
  • addOptions turns flags into @import("build_options") constants; addAnonymousImport binds data files; link_libc and linkSystemLibrary pull in C.
  • Debug and ReleaseSafe keep safety checks; ReleaseFast and ReleaseSmall drop them. --prefix moves the install; zig-out and .zig-cache are disposable.
  • IRON LEDGER's script is the template plus a data-file loop, build options, SQLite, packaging and a test step that also installs.
