43. The daily tick

In this chapter you read the function that makes a day happen. It is a fixed list of phases in a fixed order, and the order carries meaning: deliveries land before supplies are eaten, maintenance runs before battles, payroll runs last. You will learn how to read a phase, how the phases are tested in isolation, and how to add one of your own without disturbing the golden master.

What you need from earlier chapters. Chapter 6 (while with a continue expression, index loops that remove items, % for "every seventh day"), Chapter 16 (a function that returns !void and a chain of try calls), Chapter 22 (walking a map with an iterator and mutating through value_ptr), Chapter 12 (the Date struct from clock.zig, which you may remember from the original guide's section on methods) and Chapter 8.

43.1 Two clocks

Time in IRON LEDGER is two numbers that move together:

src/sim/clock.zig
pub const Clock = struct {
    date: Date = Date.campaign_default,
    day_index: u32 = 0, // days since campaign start; the canonical timestamp

    pub fn advance(self: *Clock) void {
        self.date = self.date.next();
        self.day_index += 1;
    }
};

day_index is the timestamp the whole simulation uses: a delivery has an eta_day, a wound has a wound_heal_day, an event has a deadline_day, all as plain u32 days since the campaign began. Comparing two of them is integer comparison. The Date beside it exists for two purposes only: to be printed, and to answer "is it the first of the month?" (isPayday). The house rule is that the calendar is rendered only at the edges. There is no std.Io.Clock.now anywhere in the core, because there is no io to call it with (Chapter 39).

Date.next is the by-value method you may have already read: copy self, bump the day, roll the month and year over, return the copy. Clock.advance takes a pointer and mutates. Both styles appear throughout the codebase and the choice is deliberate each time: a Date is a small value that is pleasant to treat as immutable; a Clock is a field of the state that moves in place.

43.2 The phase list

Here is the whole of a day, exactly as the source has it:

src/sim/tick.zig
pub fn advanceDay(gs: *GameState) !void {
    gs.clock.advance();
    gs.refreshHqStaffing(); // the back office is people (Stage 9C)

    // Phase order per clock.DayPhase — stubs marked with their stage.
    if (gs.clock.day_index % 7 == 0) network.resetWeeklyThroughput(gs); // links' week (Stage 9D)
    try runTravel(gs); // deliveries, couriers, transfers
    try runPolicies(gs); // standing cash top-ups and resupply (Stage 12: daily)
    try runStockPolicies(gs); // warehouse reorder points (Stage 12)
    try hq_ops.runDaily(gs); // bays, fabrication, construction (Stage 9C)
    try runSupplyConsumption(gs); // supply_consumption phase (Stage 9B)
    try medical.runDailyHealing(gs); // medical phase
    try runMarkets(gs); // acquisition_and_markets
    if (gs.clock.day_index % 7 == 0 and gs.clock.day_index > 0) {
        try maintenance.runWeeklyMaintenance(gs); // maintenance phase
        try maintenance.runWeeklyRepairs(gs);
    }
    try medical.runDailyTraining(gs); // training phase
    try runContracts(gs); // contract lifecycle
    try contract_control.runReturns(gs); // companies travelling home arrive
    if (gs.clock.date.day == 1) try contract_events.rollMonthly(gs); // event decks
    if (gs.clock.day_index % 7 == 3) try contract_events.rollWeekly(gs); // weekly happenings (Stage 12)
    try battle.runDaily(gs); // battle_resolution: due engagements resolve
    try contract_control.checkEffectiveness(gs); // the ineffectiveness clock (Stage 9E)
    if (gs.clock.day_index % 7 == 0 and gs.clock.day_index > 0) {
        try medical.runWeeklyRest(gs); // morale_fatigue phase
        runTrainingLances(gs); // lance roles (Stage 12)
    }
    try runFinances(gs);
    try contract_events.expireDue(gs); // decisions phase: deadlines pass
}

Read it as a sentence. The clock ticks. Anything in transit lands (runTravel). Standing orders top up cash and supplies. The HQ's bays and construction crews do a day's work. Deployed companies eat a day's supplies. The wounded heal a day. Markets refresh. Once a week, every hull gets its maintenance check and the repair queue moves. Training programs progress. Contracts start, end, and are scored; companies travelling home arrive. On the first of the month an event is drawn for each contract; on the third day of each week a smaller one. Battles that are due today are resolved. The ineffectiveness clock is checked. Once a week, everyone at home rests and training lances train. Finance runs. Decisions past their deadline default.

Now read it as code. Every phase is a function that takes *GameState and returns !void, called with try, so the first phase to fail stops the day and the error propagates up to advance and out of execute. Weekly phases are gated by day_index % 7 == 0 (with day_index > 0 so that day zero is not a maintenance day) and monthly ones by date.day == 1, which is the one place the calendar participates in a rule. Two phases are called without try because they cannot fail: network.resetWeeklyThroughput and runTrainingLances return void, and the compiler would reject a try on them.

The comments name the stage that introduced each phase. That is not decoration: the enum DayPhase in clock.zig was written at the start of the project as the intended order, and each stage filled in a stub. Reading the two side by side shows how a design sketch became code over time.

43.3 Why the order is the rule

The original guide put it in four sentences worth keeping: deliveries land before consumption so a convoy that arrives today feeds today. Maintenance runs before battles on the same day, so a hull that broke down this week does not fight. Finance runs last so the day's costs are on the books when payroll is counted. When you add a mechanic, the first question is which phase it belongs in and what must already have happened.

There is a fourth example hiding in the list: runReturns (companies arriving home) runs before the weekly runWeeklyRest, so a company that lands on a rest day rests. And a fifth: rollMonthly runs before battle.runDaily, because a monthly event may have spawned the very engagement that resolves today; the doc comment on DayPhase says so explicitly.

None of this is enforced by the compiler. It is enforced by tests that build a state where the order matters and check the outcome, which is the next section.

43.4 Reading a phase

Phases are small and shaped alike. Here is the start of runTravel, the first one:

pub fn runTravel(gs: *GameState) !void {
    // Failed sourcing attempts stay visible for two weeks, then clear.
    var fi: usize = 0;
    while (fi < gs.part_orders.items.len) {
        const o = gs.part_orders.items[fi];
        if (o.status == .failed and o.ordered_day + 14 <= gs.clock.day_index) _ = gs.part_orders.orderedRemove(fi) else fi += 1;
    }
    for (gs.part_orders.items) |*order| {
        if (order.status != .in_transit) continue;
        if (order.eta_day != null and gs.clock.day_index >= order.eta_day.?) {
            order.status = .delivered;
            // Land at the destination site; anything the warehouse or the
            // trucks can't hold is lost on the dock (Stage 9B).
            const dest: types.Site = if (order.dest == .outfit) gs.defaultSite() else order.dest;
            const room = gs.siteFreeTons(dest) / @max(1, part_mod.tons(order.part_key));
            const landed = @min(order.quantity, room);
            try gs.addStock(dest, order.part_key, landed);
            const tags = GameState.treasuryTags(GameState.siteTreasury(dest));
            try gs.log(.delivery, .{ .company = tags.company, .hq = tags.hq }, "[delivery] {s} x{d} received{s}", .{
                order.part_key, landed,
                if (landed < order.quantity) " — NO ROOM for the rest, written off" else "",
            });
        }
    }
    // … couriers, unit transfers …
}

Two loop forms from Chapter 6, chosen for a reason each. The first is an index loop because the body removes items: after orderedRemove(fi) the next item has slid into slot fi, so the index must not advance. The second is a for by pointer (|*order|) because the body mutates the item in place and removes nothing. The "is it due?" test is gs.clock.day_index >= order.eta_day.?, integer against integer, after an explicit null check; this is the pattern for every scheduled thing in the game.

And here is the phase that runs last, runFinances, abridged:

fn runFinances(gs: *GameState) !void {
    if (!gs.clock.date.isPayday()) return;

    var it = gs.people.iterator();
    while (it.next()) |entry| {
        const p = entry.value_ptr;
        if (p.status == .active) p.xp += monthly_service_xp;
    }
    // Seats and experience set ranks before pay is counted (12B.4); service
    // awards come due (12B.5).
    _ = try @import("personnel.zig").refreshRanks(gs);
    _ = @import("personnel.zig").refreshShares(gs);
    // New Year's Day (12C.8): the rating goes in the book.
    if (gs.clock.date.month == 1) {
        // … append a rating snapshot; log the designs entering service this year …
    }
    _ = try @import("personnel.zig").checkAllAwards(gs);
    // Notice is handed in on payday (Stage 12.20); grudges fade (12.21).
    _ = try @import("medical.zig").runMonthlyTurnover(gs);
    @import("contract_control.zig").driftStanding(gs);

    const payroll = gs.monthlyPayroll();
    if (payroll != 0) {
        try gs.postTransaction(.{
            .day = gs.clock.day_index,
            .amount = -payroll,
            .category = .payroll,
            .note = "monthly payroll",
        });
    }
    // … hull upkeep, HQ upkeep, loans, standing policies …
}

The first line is the whole monthly gate: not payday, nothing to do. Then a sequence of sub-phases whose order is again meaning (ranks are refreshed before payroll is summed, because rank scales pay). _ = try f(gs) discards a count the phase returns but a test wants; _ = f(gs) without try is a function that cannot fail. The map walk with entry.value_ptr is how every phase touches every person: a pointer, so the change sticks (Chapter 22).

43.5 Testing a phase on its own

Phases are called from advanceDay, but their tests do not go through it. medical.runMonthlyTurnover is called from runFinances on payday; its test calls it directly on a hand-built state:

src/sim/medical.zig
test "12.20/12.25: the restless hand in notice after a year (an inbox decision), the content stay" {
    var gs = GameState.init(std.testing.allocator, .{ .seed = 1220 });
    defer gs.deinit();
    _ = try gs.createCommander("T", .LC, .paymaster);
    _ = try @import("../gen/company_gen.zig").generateInto(&gs, "Alpha");
    // Content and fresh (and all thirty — age rolls are 12C.4's business):
    // nobody stirs however low the dice.
    gs.clock.day_index = 400;
    var ait = gs.people.iterator();
    while (ait.next()) |e| e.value_ptr.born_day = -30 * 365;
    try std.testing.expectEqual(@as(u32, 0), try runMonthlyTurnover(&gs));
    // Everyone miserable with a year in: notices land in the inbox, nobody has left yet.
    var pit = gs.people.iterator();
    while (pit.next()) |e| {
        e.value_ptr.morale = 5;
        e.value_ptr.fatigue = 90;
    }
    const notices = try runMonthlyTurnover(&gs);
    try std.testing.expect(notices > 0 and notices < gs.people.count());
    // Exhausted and unhappy is one in six a month (2d6 <= 4), not a stampede.
    const pct = notices * 100 / @as(u32, @intCast(gs.people.count()));
    try std.testing.expect(pct >= 6 and pct <= 30);
    try std.testing.expectEqual(@as(usize, notices), gs.event_queue.pending.items.len);
    // …
}

This is the general testing style of the simulation, and it is worth naming its parts. Build the smallest state that exercises the rule (a commander and one generated company). Set the clock and the fields directly, which tests may do. Call the phase. Assert on state, including a statistical bound (pct between 6 and 30) that is safe because the dice are seeded and the number is in fact fixed. The test also documents the rule in its name and comments better than any prose could.

The one test that does go through advanceDay is the payday test at the bottom of tick.zig:

test "payday fires on the 1st and only on the 1st" {
    var gs = GameState.init(std.testing.allocator, .{ .start_funds = 1_000_000 });
    defer gs.deinit();
    _ = try gs.hirePerson("Natasha", "Kerensky", .mekwarrior); // 1500/mo regular → Corporal ×1.1 on payday (12B.4)

    // Jan 1 (day 0) start → advancing 30 days lands on Jan 31: no payroll yet.
    for (0..30) |_| _ = try advanceDay(&gs);
    try std.testing.expectEqual(@as(i64, 1_000_000), gs.funds);

    // One more day → Feb 1: payroll posts, a month of service XP lands.
    _ = try advanceDay(&gs);
    try std.testing.expectEqual(@as(i64, 998_350), gs.funds);
    try std.testing.expectEqual(@as(usize, 1), gs.ledger.transactions.items.len);
    try std.testing.expectEqual(@as(u32, monthly_service_xp), gs.people.values()[0].xp);
}

Thirty-one days on a fresh state with one hire, and an exact number: 1,650 C-bills, which is 1,500 for a regular mekwarrior times 1.1 for the corporal's rank she is promoted to on the same payday, in that order, because refreshRanks runs before monthlyPayroll. If someone reorders those two lines, this number changes and the test says so.

Guided reading

  1. src/sim/clock.zig: Date, DayPhase (read its doc comment about order), Clock, and the leap-year test.
  2. src/sim/tick.zig: advanceDay, then in order runPolicies, runStockPolicies, runTravel, runSupplyConsumption, runMarkets, runContracts, runFinances. Each is under a hundred lines. For each, write down in one line what must already have happened today for it to be correct.
  3. One phase in another file, fully: medical.runDailyHealing in src/sim/medical.zig. Note the same map-walk-and-mutate shape.
  4. battle.runDaily in src/sim/battle.zig: fifteen lines that decide whether today is a battle day for each contract. Chapter 46 follows the call into resolveEngagement.
  5. The tests at the bottom of tick.zig and the turnover test in medical.zig.

Exercises

Exercise 43.1 · The two clocks stay in step warm-up

Write a test in tick.zig that advances a fresh default campaign 365 days and asserts both that day_index is 365 and that the date is 1 January 3026. Is 3025 a leap year? What would the date be if it were?

Solution 
test "the calendar and the day index move in lockstep" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    for (0..365) |_| try advanceDay(&gs);
    try std.testing.expectEqual(@as(u32, 365), gs.clock.day_index);
    const clock_mod = @import("clock.zig");
    try std.testing.expectEqual(clock_mod.Date{ .year = 3026, .month = 1, .day = 1 }, gs.clock.date);
}

3025 is not divisible by 4, so it has 365 days and the year rolls over exactly. In a leap year (3024 is one, as the clock test in clock.zig checks) 365 days from 1 January lands on 31 December. expectEqual compares the two Date structs field by field. Note that the full year of ticks, with all phases, runs in well under a second: the phases are cheap when there is nothing to do.

Exercise 43.2 · Add a phase challenge

Add a weekly phase runWeeklyPeace that increments a new counter gs.stats.weeks_at_peace whenever a week ends with no active contract. Decide where in advanceDay it belongs and say why. Write a test on a hand-built state. Then confirm the golden-master test still passes and explain why it was never at risk.

Solution
src/sim/state.zig, in Stats
    people_kia: u32 = 0,
    /// Weeks with no contract under way.
    weeks_at_peace: u32 = 0,
src/sim/tick.zig
    if (gs.clock.day_index % 7 == 0 and gs.clock.day_index > 0) {
        try medical.runWeeklyRest(gs); // morale_fatigue phase
        runTrainingLances(gs); // lance roles (Stage 12)
        runWeeklyPeace(gs);
    }

/// A week with no contract under way is a week of peace.
fn runWeeklyPeace(gs: *GameState) void {
    var it = gs.contracts.iterator();
    while (it.next()) |entry| if (entry.value_ptr.status == .active) return;
    gs.stats.weeks_at_peace += 1;
}

test "peace is counted weekly and only without an active contract" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    for (0..14) |_| try advanceDay(&gs);
    try std.testing.expectEqual(@as(u32, 2), gs.stats.weeks_at_peace);
}

It belongs in the existing weekly block after runContracts and runReturns have run, so that a contract that ended today counts as over, and after runWeeklyRest so it reads naturally with the other "end of week" bookkeeping. It returns void and is called without try. Days 7 and 14 are the two weekly ticks in fourteen days, hence 2. The golden master was never at risk because the new phase reads only state and a seeded clock: two campaigns with the same seed still do the same thing. It would have been at risk had the phase read anything outside the state, which is the subject of Chapter 49. (Stats is saved field by field in store.zig, so the new counter is not persisted until you add it there; Chapter 47 shows how.)

Exercise 43.3 · Find the phase practice

Without running anything, answer from the source: (a) which phase turns a wounded person's wound_heal_day into a healed status, and what must be true of medbay_admitted first? (b) Which phase moves money on a standing cash policy, and what stops it from sending twice? (c) If you moved runFinances to the top of advanceDay, name one test that would change its expected number.

Solution

(a) medical.runDailyHealing; a wound only starts healing once the player has admitted the person (medbay_admitted), which is the rule the Person field's comment states and the test "wounded only heal once admitted" in commands.zig checks. (b) runPolicies in tick.zig; it skips an entity whose balance is at or above the floor, whose monthly cap is spent, or that already has a courier in flight (in_flight). (c) Any test that pins a balance after a payday, because costs posted by the day's other phases would no longer be on the books when payroll is counted; the payday test's 998,350 is the obvious one, and the round-trip test in store.zig compares hashes that include funds.

Check your understanding

  1. What is the canonical timestamp, and what is the calendar for?
    Answerday_index: u32, days since campaign start, used for every deadline and comparison; the Date is for rendering and for detecting the first of the month.
  2. Why is there a day_index > 0 in the weekly gate?
    AnswerBecause 0 % 7 == 0: without it, the weekly phases would run on the campaign's first day.
  3. Why are resetWeeklyThroughput and runTrainingLances called without try?
    AnswerThey return void, not an error union; try on a non-error value is a compile error.
  4. Give two orderings in advanceDay that carry meaning.
    AnswerDeliveries (runTravel) before consumption; maintenance before battles; rollMonthly before battle.runDaily; runFinances last; refreshRanks before monthlyPayroll inside finance.
  5. How is a phase like runMonthlyTurnover tested?
    AnswerDirectly, on a hand-built state with fields set to force the situation, asserting on the resulting state (inbox length, statuses), not by advancing the calendar to a payday.
  6. Why does the index loop in runTravel not always increment?
    AnswerAfter orderedRemove(fi) the following item slides into slot fi, so incrementing would skip it.
What you learned.
  • A day is advanceDay: the clock ticks, then a fixed list of phases runs, each a function from *GameState to !void.
  • Weekly and monthly phases are gated by integer arithmetic on day_index and by date.day == 1; nothing reads a wall clock.
  • Order is meaning: what lands, heals, breaks or is paid depends on what ran before it, and tests pin those consequences with exact numbers.
  • Phases are tested in isolation on hand-built states; the whole pipeline is tested by a few end-to-end numbers like the payday test.
  • Adding a mechanic means choosing its phase, writing it as a function over the state, and testing it the same way.
