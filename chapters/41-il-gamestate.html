41. GameState: one arena, one dice bag

In this chapter you open the struct that holds an entire campaign. You will see why every allocation a campaign makes comes from one arena and is freed by one call, why the random number generator is a bag of named streams rather than a single generator, and how a 64-bit hash of the state turns "the simulation is deterministic" from a slogan into a test.

What you need from earlier chapters. Chapter 19 and Chapter 20 (the stack, the heap, and the ArenaAllocator in particular), Chapter 21 and Chapter 22 (unmanaged lists and hash maps: .empty, and an allocator passed to every growing call), Chapter 34 (std.Random.DefaultPrng and seeding), Chapter 18 (pointers into containers going stale), Chapter 13 (non-exhaustive enums as typed IDs) and Chapter 4 (wrapping multiplication, *%).

41.1 The struct

GameState lives in src/sim/state.zig, a file of about two thousand lines of which the struct definition is the first three hundred. Here it is with the fields grouped and most of the comments removed; read the types more than the names:

Several things you learned in Parts 1 and 2 are on display at once.

  • Four fields have no default (arena, rng, clock, funds) and init sets exactly those four. Everything else has a default, so init can be a four-line struct literal, and adding a defaulted field never touches init. Exercise 41.2 shows what happens when you add one without a default.
  • Every container is unmanaged and starts as .empty. None of them stores an allocator; the one allocator they all use is the arena, fetched with gs.allocator() at each call site. That is the 0.16 convention from Chapter 21 applied forty times.
  • The five entity maps are AutoArrayHashMapUnmanaged, the ordered kind (Chapter 22). Iterating an ordered map visits entries in insertion order on every machine and every run. An ordinary AutoHashMapUnmanaged would visit them in an order that depends on hash seeds and capacity, and the hash in 41.4 would differ between two identical campaigns. The choice of map type is a determinism decision.
  • Maps are keyed by typed IDs. people is keyed by PersonId, not u32. The non-exhaustive enum trick from Chapter 13 costs nothing at runtime and means gs.people.get(unit_id) is a compile error.
  • The ID counters are plain fields. next_person_id starts at 1 (0 is PersonId.none), and a fresh ID is @enumFromInt(self.next_person_id) followed by an increment. There is no global counter anywhere; it is part of the state and therefore saved, loaded and hashed with it.

What is not in the struct matters too. There is no io and no allocator other than the arena. There is no cache of derived numbers (a company's total battle value, say): those are recomputed by queries when asked. A cache is a second copy of the truth that can drift, and drift is the enemy of a state that must be reproducible.

41.2 The arena: one owner for everything

In Chapter 20 you chose allocators by lifetime. A campaign's lifetime is "from init to deinit", and every string, list, map and log line inside it lives exactly that long. That is the textbook case for an arena, and GameState uses one for everything:

pub fn deinit(self: *GameState) void {
    self.arena.deinit();
}

That one line frees every person, every hull, every ledger row, every formatted log line, and every hash map's backing store. No struct in src/domain needs a destructor that walks its children, and nothing in the simulation ever calls free. (A few domain structs, Person among them, do have a deinit method, but the game state never calls it; it exists for tests that build a Person with the testing allocator on its own.)

The trade, stated in the original guide and worth repeating: memory grows monotonically over a campaign. When a person is fired their record stays in the map with status .resigned; when a log line is written it is never freed; when a list shrinks its buffer is retained. A long campaign holds every log line it ever wrote. In exchange the simulation can never have a use-after-free, never leaks in the sense the testing allocator checks for, and never has to answer "who owns this string?". For a game whose whole state is a few megabytes, that is a good trade.

Look at how the arena shows up at a call site. This is the log method, which every subsystem uses to write a dated line:

src/sim/state.zig
/// Append a tagged, formatted entry (with the campaign date) to the log.
pub fn log(self: *GameState, category: LogCategory, ctx: LogCtx, comptime fmt: []const u8, args: anytype) !void {
    const d = self.clock.date;
    const line = try std.fmt.allocPrint(
        self.allocator(),
        "{d}-{d:0>2}-{d:0>2} " ++ fmt,
        .{ d.year, d.month, d.day } ++ args,
    );
    try self.event_log.append(self.allocator(), .{
        .day = self.clock.day_index,
        .category = category,
        .company = ctx.company,
        .hq = ctx.hq,
        .contract = ctx.contract,
        .text = line,
    });
}

Two compile-time tricks from Chapter 25 make this pleasant. "{d}-{d:0>2}-{d:0>2} " ++ fmt concatenates the caller's format string onto a date prefix at compile time, and .{ … } ++ args concatenates the two argument tuples, so every log line begins with a date and the caller never has to pass one. The formatted string comes from allocPrint on the arena and is stored by reference in the entry. Nobody will ever free it, and nobody needs to.

The LogCtx argument is a small struct of typed IDs with defaults, so a caller with nothing to tag passes .{} and a caller with a company passes .{ .company = id }. The log is queried later by those tags (Chapter 44), which is why the entry stores them as fields rather than baking "Alpha Company" into the text.

Pointers into the maps go stale. gs.people.getPtr(id) returns a *Person that points into the map's storage. If you then insert into gs.people and the map grows, the storage moves and your pointer is dangling. The arena does not save you from this; it is the same rule as Chapter 18's "a pointer into an ArrayList is invalid after append". The codebase's habit is to re-fetch after any insert: gs.force(id) is called again rather than a pointer kept across a createForce. When you write a command in Chapter 42, hire first and look up afterwards.

41.3 The dice bag

The second field of GameState is the random number generator, and it is not one generator:

src/sim/rng.zig (complete apart from the tests)
//! Deterministic RNG with named per-subsystem streams (ARCH §4).
//! Adding a roll in one system must never perturb another, so every
//! subsystem draws from its own stream. All combat/campaign dice are 2d6.

const std = @import("std");

pub const Stream = enum(u8) {
    generation, // company/person/name generation
    market, // contract/personnel/unit market rolls
    maintenance,
    acquisition,
    battle,
    events,
    medical,
    travel,

    const count = @typeInfo(Stream).@"enum".fields.len;
};

pub const Rng = struct {
    prngs: [Stream.count]std.Random.DefaultPrng,

    pub fn init(seed: u64) Rng {
        var self: Rng = undefined;
        for (&self.prngs, 0..) |*prng, i| {
            // Distinct, stable derivation per stream.
            prng.* = std.Random.DefaultPrng.init(seed ^ (0x9E3779B97F4A7C15 *% (i + 1)));
        }
        return self;
    }

    pub fn random(self: *Rng, stream: Stream) std.Random {
        return self.prngs[@intFromEnum(stream)].random();
    }

    /// The BattleTech die roll.
    pub fn roll2d6(self: *Rng, stream: Stream) u8 {
        const r = self.random(stream);
        return r.intRangeAtMost(u8, 1, 6) + r.intRangeAtMost(u8, 1, 6);
    }
};

Read init with Chapter 34 in mind. Eight DefaultPrng generators sit in an array sized by the number of enum variants, a trick from Chapter 27: add a stream to the enum and the array grows. Each is seeded from the campaign seed XORed with a large odd constant times the stream index, using wrapping multiplication *% because the product is meant to overflow; plain * would panic in a debug build. The for (&self.prngs, 0..) |*prng, i| form iterates the array by pointer so each element can be assigned through prng.*.

Why eight generators instead of one? The comment at the top says it in a line, and the original guide gave the concrete case: suppose you add a weather roll to battles. With one shared generator, every market roll that happens after the first battle now gets a different number than before, and a saved game replays differently after the update. With named streams, adding a draw to .battle leaves .market exactly where it was. The test below is the rule stated as code:

test "streams are independent and deterministic" {
    var a = Rng.init(42);
    var b = Rng.init(42);

    // Draw heavily from one stream in `a` only; another stream must still
    // match the untouched twin exactly.
    for (0..1000) |_| _ = a.roll2d6(.maintenance);
    for (0..10) |_| {
        try std.testing.expectEqual(b.roll2d6(.battle), a.roll2d6(.battle));
    }
}

Every call site names its stream, and the name is the subsystem: gs.rng.roll2d6(.battle) in the battle resolver, gs.rng.roll2d6(.events) when a monthly event is drawn, gs.rng.roll2d6(.medical) in turnover, &gs.rng with .generation passed to the person generator. The house rule in CLAUDE.md is that no PRNG is ever created anywhere else. If you grep the core for DefaultPrng.init you find exactly the one in rng.zig.

41.4 The hash

The last method to read is the one that makes determinism testable:

src/sim/state.zig
/// Deterministic digest of gameplay-relevant state. Two runs with the
/// same seed and command script must produce the same hash — the
/// regression harness every stage builds on (ARCH §13).
pub fn hash(self: *GameState) u64 {
    var h = std.hash.Wyhash.init(0x42544d43); // "BTMC"
    h.update(std.mem.asBytes(&self.clock.day_index));
    h.update(std.mem.asBytes(&self.funds));
    h.update(std.mem.asBytes(&self.reputation));
    h.update(std.mem.asBytes(&self.share_profit_bp));
    const txn_count: u64 = self.ledger.transactions.items.len;
    h.update(std.mem.asBytes(&txn_count));

    var it = self.people.iterator();
    while (it.next()) |entry| {
        const p = entry.value_ptr;
        h.update(std.mem.asBytes(&p.id));
        h.update(p.first_name);
        h.update(p.last_name);
        h.update(std.mem.asBytes(&p.role));
        h.update(std.mem.asBytes(&p.status));
        h.update(std.mem.asBytes(&p.xp));
        h.update(std.mem.asBytes(&p.fatigue));
        h.update(std.mem.asBytes(&p.morale));
        const injuries: u64 = p.injuries.items.len;
        h.update(std.mem.asBytes(&injuries));
    }
    var uit = self.units.iterator();
    while (uit.next()) |entry| {
        const u = entry.value_ptr;
        h.update(std.mem.asBytes(&u.id));
        h.update(u.chassis_key);
        h.update(std.mem.asBytes(&u.status));
        h.update(std.mem.asBytes(&u.quality));
        h.update(std.mem.asBytes(&u.armor_pct));
        h.update(std.mem.asBytes(&u.force));
        h.update(std.mem.asBytes(&u.pilot));
        h.update(std.mem.asBytes(&u.berth_hq));
    }
    // … forces, contracts, offers, HQs, the commander …
    return h.final();
}

std.hash.Wyhash is a fast non-cryptographic hash from the standard library; you feed it bytes with update and read a u64 with final. std.mem.asBytes(&x) views any value as a byte slice (Chapter 29), which is how integers and enums are fed in; strings are already slices. The function walks the ordered maps in insertion order, which is why the map type matters: an unordered map would feed the same entries in a different order on another run and the digest would differ.

Notice what is hashed and what is not. Names, roles, statuses, fatigue, morale, hull condition: gameplay facts. Not hashed: log text, market listings, the exact RNG state. The digest is meant to say "these two campaigns are the same game", and it is deliberately coarse so that harmless changes (a reworded log line) do not break the golden-master test. The exercises ask you to check that it is nevertheless sensitive to a single C-bill.

41.5 Reading a GameState method

The rest of state.zig is about a hundred methods. They fall into a few kinds, and knowing the kinds makes the file navigable:

  • Lookups that wrap a map's getPtr and return an optional pointer: person(id), unit(id), force(id). Callers write gs.person(id) orelse return Error.UnknownPerson.
  • Creation that mints an ID, builds a struct on the arena and inserts it: hirePerson, hireFromSpec, addUnit, createForce, foundHq, createCommander.
  • Money: postTreasury, treasuryBalance, transferFunds, monthlyPayroll. Chapter 45 is about these.
  • Derived facts that walk the maps and compute a number without caching it: companyOf, companiesAtHq, techHoursFor, siteFreeTons.
  • Stock (physical parts at a site): stockMap, addStock, takeStock, stockCount.

Here is one of the lookups and one of the creators, so you can see the shape:

pub fn person(self: *GameState, id: types.PersonId) ?*person_mod.Person {
    return self.people.getPtr(id);
}

/// Recruit a randomly generated person (AtB-style: experience on 2d6,
/// skills from the band, names from the tables).
pub fn recruitGenerated(self: *GameState, role: person_mod.Role) !types.PersonId {
    const spec = person_gen.generateWithBonus(&self.rng, role, self.recruitBonus());
    return self.hireFromSpec(spec);
}

The creator passes &self.rng to the generator in src/gen, which draws from the .generation stream. Even name generation goes through the dice bag; that is why two campaigns with the same seed hire the same people.

Guided reading

  1. src/sim/rng.zig, all of it. It is sixty lines and you have now seen most of them.
  2. src/sim/clock.zig: Date, Clock (two fields: a date and day_index), and the DayPhase enum that documents the tick order for Chapter 43.
  3. src/sim/state.zig, lines 1 to about 300: the small helper structs (Treasury, FundCourier, StandingPolicy, LogEntry, BayJob, Candidate), then the GameState fields. Every one of those helper structs is something you will meet again on a screen.
  4. Still in state.zig: init, deinit, allocator, postTreasury, treasuryBalance, person, hirePerson, log, stockMap, and finally hash. Use search; they are not adjacent.
  5. src/domain/person.zig: the Person struct fields (about sixty lines). Count how many are optionals with null defaults and note what each "not yet" means.

Exercises

Exercise 41.1 · Seeds diverge warm-up

The existing test shows that two Rng values with the same seed agree. Add a test to src/sim/rng.zig showing that two with different seeds do not: roll .battle fifty times on each and count how often the two rolls coincide. What threshold is safe, and why can you not demand zero coincidences?

Solution 
test "different seeds give different dice" {
    var a = Rng.init(1);
    var b = Rng.init(2);
    var same: u32 = 0;
    for (0..50) |_| {
        if (a.roll2d6(.battle) == b.roll2d6(.battle)) same += 1;
    }
    // Two 2d6 sequences agree by chance on roughly one roll in seven.
    try std.testing.expect(same < 25);
}

Two independent 2d6 rolls are equal with probability about 0.11 (sum over the eleven outcomes of the squared probabilities), so around five or six coincidences in fifty are expected and zero would itself be suspicious. The threshold 25 is far above any plausible run of luck while still catching the bug the test is for: an init that ignored its seed. Because the generator is deterministic, the count for seeds 1 and 2 is in fact a fixed number and the test will never flake; the loose bound just documents the intent.

Exercise 41.3 · Test the log practice

Write a test in src/sim/state.zig that creates a fresh state, calls gs.log(.decision, .{}, "hello {d}", .{7}), and asserts on the single entry: its text, its day and its category. What date prefix do you expect on day zero of a default campaign?

Solution 
test "log lines carry the campaign date and the tags" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    try gs.log(.decision, .{}, "hello {d}", .{7});
    try std.testing.expectEqual(@as(usize, 1), gs.event_log.items.len);
    const e = gs.event_log.items[0];
    try std.testing.expectEqualStrings("3025-01-01 hello 7", e.text);
    try std.testing.expectEqual(@as(u32, 0), e.day);
    try std.testing.expectEqual(LogCategory.decision, e.category);
}

The default Config starts on Date.campaign_default, 1 January 3025, and day_index is 0, so the prefix is 3025-01-01 with the month and day zero-padded by the {d:0>2} specifiers (Chapter 23). The defer gs.deinit() on the second line is not optional: std.testing.allocator reports the arena's memory as a leak without it.

Exercise 41.4 · The hash notices one C-bill practice

Write a test that takes gs.hash() of a fresh state, adds one to gs.funds, and asserts the hash changed; then subtracts one and asserts it is back to the original. Then answer: would the same test pass if you changed a log line's text instead of the funds?

Solution 
test "the hash notices a single c-bill" {
    var gs = GameState.init(std.testing.allocator, .{ .seed = 9 });
    defer gs.deinit();
    const before = gs.hash();
    gs.funds += 1;
    try std.testing.expect(gs.hash() != before);
    gs.funds -= 1;
    try std.testing.expectEqual(before, gs.hash());
}

It passes: funds is one of the first things fed to the hasher. A change to log text would not change the hash, because hash never reads event_log; it is a digest of gameplay-relevant state, and log wording is deliberately left out so that rewording a message does not break the golden-master test.

Check your understanding

  1. Which four fields must GameState.init set, and why those?
    Answerarena, rng, clock and funds: they are the fields without defaults, because each depends on something only the caller knows (the parent allocator, the seed, the start date, the starting money).
  2. What does gs.deinit() do, and what does it not need to do?
    AnswerIt calls arena.deinit(), which frees every allocation the campaign made. It does not need to walk any map or list, because nothing was allocated from anywhere else.
  3. Why are the entity maps AutoArrayHashMapUnmanaged rather than AutoHashMapUnmanaged?
    AnswerThe array variant iterates in insertion order, which is the same on every run and every machine; the hash order of the plain variant is not, and hash() walks the maps.
  4. Why does Rng.init use *%?
    AnswerThe seed derivation multiplies a large constant by the stream index and expects the product to wrap around 64 bits; plain * would be an overflow panic in Debug builds.
  5. What breaks if a new subsystem borrows the .battle stream instead of adding its own?
    AnswerNothing today, but every battle roll after the new subsystem's first draw shifts, so saved campaigns replay differently after the change; a new stream leaves existing streams untouched.
  6. Why is a pointer from gs.people.getPtr unsafe to keep across a hire?
    AnswerHiring inserts into the map; if the map grows it reallocates its storage and the pointer dangles. The arena does not prevent this; re-fetch after inserting.
  7. Name two things the hash includes and two it excludes.
    AnswerIncludes: day_index, funds, each person's fatigue and morale, each unit's status. Excludes: log text, market listings, the internal RNG state.
What you learned.
  • GameState is one struct holding ordered maps of entities keyed by typed IDs, lists of everything else, the clock, the money and two special members: an arena and a dice bag.
  • The arena owns every allocation of a campaign; deinit is one call and the domain has no destructors. Memory grows monotonically in exchange.
  • Rng is eight DefaultPrng generators, one per named stream, seeded from one campaign seed; every roll names its subsystem, so adding rolls to one subsystem never perturbs another.
  • hash() folds gameplay-relevant state into a u64 by walking the ordered maps; it is the instrument the golden-master test reads.
  • Pointers into the maps are invalidated by inserts; look up again after you create.
