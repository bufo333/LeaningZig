49. Determinism and the test suite

In this chapter you read the test that the whole architecture exists to make possible, then break it in the smallest way you can to see what it catches. You will also learn how the suite of 246 tests is organised, what each kind of test is for, and what "a change is done" means in this project.

What you need from earlier chapters. Chapter 8 (test blocks, expectEqual, the testing allocator and leak detection, refAllDecls), Chapter 9 (an array of struct values and iterating an array by pointer to fill it), Chapter 41 (what gs.hash() covers), Chapter 42 (a script of Command values), Chapter 34 (why a seed makes randomness repeatable) and Chapter 30 (why a file-level var is global mutable state).

49.1 The golden master

Here is the test, unabridged:

src/sim/commands.zig
test "golden master: same seed + same script = same state hash" {
    const script = [_]Command{
        .{ .hire = .{ .first = "Grayson", .last = "Carlyle", .role = .mekwarrior } },
        .{ .hire = .{ .first = "Lori", .last = "Kalmar", .role = .mekwarrior } },
        .{ .hire = .{ .first = "Clay", .last = "Cluny", .role = .tech_mek } },
        .{ .advance_days = 45 },
        .{ .fire = @enumFromInt(2) },
        .{ .advance_days = 45 },
    };

    var hashes: [2]u64 = undefined;
    for (&hashes) |*out| {
        var gs = GameState.init(std.testing.allocator, .{ .seed = 42 });
        defer gs.deinit();
        for (script) |cmd| _ = try execute(&gs, cmd);
        out.* = gs.hash();
    }
    try std.testing.expectEqual(hashes[0], hashes[1]);

    // A different seed must not accidentally replay the same campaign.
    var other = GameState.init(std.testing.allocator, .{ .seed = 43 });
    defer other.deinit();
    for (script) |cmd| _ = try execute(&other, cmd);
    // Note: with RNG unused in Stage 1 phases the state can legitimately
    // match across seeds; day/funds/roster still must match the script.
    try std.testing.expectEqual(@as(u32, 90), other.clock.day_index);
}

Two campaigns, same seed, same six commands, ninety days each, and their hashes must be equal. The script is an array of union values (Chapter 42) and the two runs are a for over an array of two u64 by pointer (Chapter 9), each run creating and destroying its own state inside the loop body so that the two never share anything. The test is cheap, a fraction of a second inside a suite that finishes in a few seconds, and it runs on every zig build test.

What can make it fail? Anything that lets the two runs diverge: a wall-clock read (impossible, no io), a global counter, a hash map iterated in hash order, a PRNG created outside the dice bag, a pointer left dangling by a reallocation and read as garbage. The property it guards, "the simulation is a pure function of seed and commands", is what makes every other test trustworthy: a test that pins 998_350 C-bills after a payday (Chapter 43) is only meaningful if the number cannot vary.

The second half of the test is a guard against a degenerate way of passing the first half: if init ignored its seed, two runs would trivially agree. The comment records an early limitation honestly (in Stage 1 few phases rolled dice, so different seeds could produce identical states) and settles for checking that the script ran to day 90.

49.2 Breaking it

Claims about what a test catches deserve the same treatment as claims about the compiler: try it. Add a file-level variable to tick.zig and use it in the finance phase:

var paydays_seen: u32 = 0;

fn runFinances(gs: *GameState) !void {
    if (!gs.clock.date.isPayday()) return;
    paydays_seen += 1;
    gs.funds -= paydays_seen;
    // …

This is the kind of thing a hurried programmer writes to count something. Run the suite:

error: 'sim.commands.test.golden master: same seed + same script = same state hash' failed:
       expected 2051892614612272315, found 12687838616412443031
error: 'persist.store.test.save → load → identical hash, and the loaded campaign keeps playing' failed:
       expected 7076991405417063463, found 807982363495903619
error: 'sim.tick.test.payday fires on the 1st and only on the 1st' failed:
       expected 998350, found 998349
error: 'sim.commands.test.payroll drains funds over three months, resignations stop costing' failed:
       expected 997910, found 997887

Four failures. The golden master fails because the counter persists across the two runs inside one test process: the first campaign sees paydays 1 to 3, the second sees 4 to 6, and their treasuries differ by a few C-bills. The round-trip test fails for the same reason (the loaded campaign continues counting where the original left off). And two payday tests fail because their pinned numbers are now off by the count. The message the suite sends is unambiguous: something outside GameState is influencing the state. Zig let you write the global (a file-level var is ordinary, Chapter 30); the rule against it is a house rule, and the golden master is its enforcement.

Contrast this with Exercise 43.2, where you added a phase that read only the state and a seeded clock: the golden master did not flinch. The test does not object to new behaviour; it objects to behaviour that is not a function of the inputs.

49.3 How the suite is organised

The 246 test blocks live next to the code they check, by house rule: every module carries its own. They fall into kinds, and each kind has a characteristic shape.

  • Domain tests check rule tables and formulas against known values from the sourcebooks: a 300-rated engine weighs 19 tons, a Shadow Hawk is a medium mek and an Atlas an assault one, a green pilot earns 0.6 of base pay. They are expectEqual on a function of constants, and they run in microseconds.
  • Data tests cross-check the ZON files: every loadout part exists, every RAT entry is a mek of the stated class, every world's faction is in the factions table (Chapter 40). They loop over constant slices and print the offending row.
  • Sim tests build a small state, run one command or one phase, and assert on state (Chapter 42, Chapter 43). Their names are sentences that state the rule. Dice-driven ones assert bounds over many seeded rolls (Chapter 46).
  • Persistence tests round-trip a campaign through an in-memory SQLite database and open a hand-written old-schema fixture (Chapter 47).
  • Client tests check the parts of src/tui that need no terminal: cell grids, size tiers, PNG decoding.
  • One reflective test in root.zig, std.testing.refAllDecls(@This()), forces every public declaration in the module tree to be compiled. Zig compiles lazily (Chapter 30), so an unreferenced function with a type error would otherwise stay invisible until someone called it. This test makes "it compiles" mean all of it.

Outside Zig are the two smoke scripts (Chapter 48): docs/tui_smoke.py drives the terminal client through every screen under a pseudo-terminal, and docs/repl_smoke.sh feeds a list of verbs to the REPL and greps for landmarks. They are slow (a couple of minutes) and they are the only tests that exercise the frontends as a user does.

CLAUDE.md states when a change is done: zig build test --summary all is green, and both smokes pass. The comment in build.zig above the test step records a day when that was not enough: the executable had a compile error that the tests did not see, because the tests compile the client as tests, not as the executable. The fix was to make the test step depend on the install step too, so a green run also means zig-out/bin/game is current. That is the kind of fact you only learn by reading the build script, which is why Chapter 39 sent you there first.

49.4 What a seeded test can and cannot pin

Because every roll is seeded, every test number is exact: the turnover test's "between 6 and 30 percent" is in fact one specific percentage for seed 1220. Why write a bound, then? Because the test is about the rule (exhausted and unhappy people leave at roughly one in six a month), not about that seed's particular dice, and a re-tuning of the table should not break it. The choice of exact number versus bound is a statement about what the test means. The payday test uses an exact number because payroll is arithmetic, not dice; the turnover test uses a bound because it is dice.

The same seed discipline is what makes a bug reproducible. When the game misbehaves, the seed and the command history (the REPL prints the verbs; the client's : line uses the same parser) are enough to replay it in a test. Several tests in commands.zig with names beginning "play feedback:" are exactly that: a session that went wrong, reduced to a script and a seed and pinned.

Exercises

Exercise 49.1 · Break the golden master practice

Do what 49.2 describes: add a file-level var to tick.zig, use it to change funds in runFinances, and run the suite. Record which tests fail. Then change the global so that it affects something the hash does not read (a log line's text, say) and run again. What do you conclude about the hash's coverage?

Solution

With gs.funds -= paydays_seen, four tests fail: the golden master, the store round trip, and the two payday tests, all with numbers off by a few C-bills. With the global only appended to a log line (try gs.log(.finance, .{}, "payday {d}", .{paydays_seen})), nothing fails, because hash() does not read log text and no test pins that line. Conclusion: the hash is a coarse instrument by design; it guards gameplay state, not every byte. A global that only affected presentation would slip past it, which is acceptable, and a global that affected the dice or the money would not, which is what matters. Remove the global when you are done.

Exercise 49.2 · A second golden master practice

The original test's script never creates a commander, so no HQ, no market and no contract is exercised. Write a second golden-master test whose script is create_commander, new_company and sixty days, and confirm it passes. Why is it worth having both?

Solution 
test "golden master with a commander and a company" {
    const script = [_]Command{
        .{ .create_commander = .{ .name = "Erik Kalmar", .origin = .CC, .profession = .quartermaster } },
        .{ .new_company = "Alpha" },
        .{ .advance_days = 60 },
    };
    var hashes: [2]u64 = undefined;
    for (&hashes) |*out| {
        var gs = GameState.init(std.testing.allocator, .{ .seed = 7 });
        defer gs.deinit();
        for (script) |cmd| _ = try execute(&gs, cmd);
        out.* = gs.hash();
    }
    try std.testing.expectEqual(hashes[0], hashes[1]);
}

It passes. The original script exercises hiring, the tick and firing; this one exercises company generation (hundreds of dice from the .generation stream), the starter HQ, market refreshes and two paydays with a real payroll. A global or an unordered iteration in any of those would show up here and not in the original. Golden masters are cheap; the more of the code a script reaches, the more the property is worth. (The store round-trip test, which plays forty days with a contract, is in effect a third one.)

Exercise 49.3 · Pin the dice warm-up

Write a test in rng.zig that pins the first two .battle rolls for seed 42 to their literal values. Find the values by printing them once. What would cause this test to fail, and would that be a bug?

Solution 
test "the first battle rolls for seed 42 are pinned" {
    var r = Rng.init(42);
    try std.testing.expectEqual(@as(u8, 4), r.roll2d6(.battle));
    try std.testing.expectEqual(@as(u8, 9), r.roll2d6(.battle));
}

It fails if the seed derivation in Rng.init changes, if the stream order in the Stream enum changes (the index feeds the seed), or if a future Zig release changes DefaultPrng's algorithm. None of those is a bug in the game's logic, but all of them silently change every campaign's dice and make old seeds unreplayable, which is worth knowing about the moment it happens. A pinned-dice test is the cheapest possible alarm for "the random stream moved".

Check your understanding

  1. What does the golden-master test assert, and how long does it take?
    AnswerTwo campaigns with seed 42 and the same six-command script produce equal hash() values after ninety days each; a fraction of a second.
  2. Name three faults it catches.
    AnswerA global mutable counter, a PRNG created outside the dice bag, iteration over an unordered hash map; also a wall-clock read (structurally impossible) and reads of stale memory.
  3. Why did adding a global counter also break the payday tests?
    AnswerThe counter changed the funds those tests pin to exact numbers; they fail on the arithmetic, not on determinism.
  4. What is refAllDecls for?
    AnswerZig compiles only what is referenced; the test references every public declaration so that dead or unreferenced code with a type error still fails the build.
  5. When does a test use an exact number and when a bound?
    AnswerExact for arithmetic (payroll), bounds for dice-driven behaviour (turnover, battles), even though the seed makes both deterministic; the choice states what the test means.
  6. What does "a change is done" mean in this project?
    Answerzig build test --summary all is green (which also builds the client), and both smoke scripts pass.
What you learned.
  • The golden-master test runs the same script twice from the same seed and compares hashes; it is the enforcement of the purity rule.
  • A file-level var that touches state breaks it and several pinned-number tests at once; a change that reads only state and seeded dice does not.
  • The 246 tests are grouped by kind (domain, data, sim, persistence, client, reflective) and live next to their code; two smoke scripts cover the frontends.
  • Seeded dice make every number exact; tests choose exact values for arithmetic and bounds for dice to say what they mean.
  • A bug is reproducible from a seed and a script, and several tests are exactly that.
