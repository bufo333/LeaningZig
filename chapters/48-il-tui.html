48. The terminal client

In this chapter you read the one part of the program that is not pure: the terminal client in src/tui/. It is layered so that the impure parts stay small, from raw bytes on a file descriptor up to a state machine whose main loop is five lines. You will see how a byte becomes a Key, how a grid of cells becomes ANSI, how the client is kept from touching the simulation directly, and how a program that reads a keyboard is tested without a human.

What you need from earlier chapters. Chapter 33 (std.Io, writers with buffers and flush), Chapter 32 (a program's main loop and its options), Chapter 14 (the Key union and switching on it), Chapter 6 (switch on integer ranges), Chapter 20 (an arena reset per frame), Chapter 17 (defer that restores the terminal however the program exits), Chapter 36 (an atomic flag set from a signal handler) and Chapter 35 (std.posix calls with C-shaped arguments).

48.1 The layers

The client is eight files, and each does one thing:

FileLinesJob
term.zig238Raw mode, the alternate screen, window size, reading bytes with a timeout, decoding them into Key, the resize signal.
screen.zig414A grid of cells with a style each; text, panes, borders, the {a}…{/} markup parser; flush to ANSI.
app.zig4,740The state machine: mode, tab, cursors, modals; draw per screen; handleKey per screen; the lobby and the new-campaign wizard.
png.zigAn 8-bit PNG decoder, inflate included, for emblems. No library.
emblem.zigThe kitty and iTerm2 image protocols, and half-block fallbacks.
music.zigRuns the system audio player as a child process and reaps it.
splash.zigThe title screen.
paths.zigWhere the save file, logos and music live for a source tree versus an installed copy.

The rule that governs all of them is in CLAUDE.md: the client may only call game.commands.execute, parse through game.cli, and read through game.queries. It never mutates GameState directly. A reviewer can grep for violations, and Exercise 48.2 has you do exactly that.

48.2 Bytes to keys

term.zig is the bottom. Its init puts the terminal into raw mode with tcsetattr and its deinit restores it:

src/tui/term.zig
pub const Term = struct {
    in_fd: posix.fd_t,
    orig: posix.termios,
    out: *std.Io.Writer,
    pending: [64]u8 = undefined,
    pending_len: usize = 0,

    /// Enter raw mode + alternate screen. `out` must outlive the Term.
    pub fn init(out: *std.Io.Writer) !Term {
        const fd = posix.STDIN_FILENO;
        const orig = try posix.tcgetattr(fd);
        var raw = orig;
        raw.lflag.ECHO = false;
        raw.lflag.ICANON = false;
        raw.lflag.ISIG = false;
        raw.lflag.IEXTEN = false;
        raw.iflag.IXON = false;
        raw.iflag.ICRNL = false;
        raw.iflag.BRKINT = false;
        raw.iflag.ISTRIP = false;
        raw.oflag.OPOST = false;
        raw.cc[@intFromEnum(posix.V.MIN)] = 0;
        raw.cc[@intFromEnum(posix.V.TIME)] = 0;
        try posix.tcsetattr(fd, .FLUSH, raw);

        var act: posix.Sigaction = .{
            .handler = .{ .handler = onWinch },
            .mask = posix.sigemptyset(),
            .flags = 0,
        };
        posix.sigaction(.WINCH, &act, null);

        // Alternate screen, hide cursor, clear.
        try out.writeAll("\x1b[?1049h\x1b[?25l\x1b[2J\x1b[H");
        try out.flush();
        return .{ .in_fd = fd, .orig = orig, .out = out };
    }

    pub fn deinit(self: *Term) void {
        self.out.writeAll("\x1b[0m\x1b[?25h\x1b[2J\x1b[H\x1b[?1049l") catch {};
        self.out.flush() catch {};
        posix.tcsetattr(self.in_fd, .FLUSH, self.orig) catch {};
    }

Zig's std.posix exposes termios as a struct with named flag fields, so raw mode is a list of assignments rather than the bit-masking you would do in C. The original settings are kept in orig and restored by deinit, which the caller pairs with defer term.deinit() so that a crash, an error or a normal quit all leave the terminal usable. Every call in deinit ends in catch {}, because there is nothing sensible to do if restoring the terminal fails on the way out.

The resize signal is handled with an atomic flag, the pattern from Chapter 36: a signal handler may not do much, so onWinch stores true and the main loop asks tookResize, which swaps it back to false.

Reading is a small buffer, a poll with a timeout, and a decoder:

    /// Decode one key, waiting up to `timeout_ms`.
    pub fn readKey(self: *Term, timeout_ms: i32) Key {
        if (!self.fill(timeout_ms)) return .none;
        const b = self.take() orelse return .none;
        return switch (b) {
            0x1b => self.readEscape(),
            '\r', '\n' => .enter,
            '\t' => .tab,
            0x7f, 0x08 => .backspace,
            1...7, 11, 12, 14...26 => .{ .ctrl = 'a' + b - 1 },
            else => self.readUtf8(b),
        };
    }

    fn readEscape(self: *Term) Key {
        // A lone ESC arrives with nothing behind it; sequences follow fast.
        if (!self.fill(25)) return .escape;
        const b = self.take() orelse return .escape;
        if (b == 'O') { /* SS3 sequences: F1..F4, arrows on some terminals */ }
        if (b != '[') return .escape;
        var num: u32 = 0;
        var have_num = false;
        while (true) {
            if (!self.fill(25)) return .escape;
            const c = self.take() orelse return .escape;
            switch (c) {
                '0'...'9' => {
                    num = num * 10 + (c - '0');
                    have_num = true;
                },
                ';' => { num = 0; have_num = false; },
                'A' => return .up,
                'B' => return .down,
                'C' => return .right,
                'D' => return .left,
                'Z' => return .backtab,
                '~' => return switch (num) {
                    1, 7 => .home,
                    3 => .delete,
                    5 => .pgup,
                    6 => .pgdn,
                    11 => .{ .f = 1 },
                    // … F2 to F12 …
                    else => .escape,
                },
                else => return .escape,
            }
        }
    }

readKey is the byte-to-key switch you saw in Chapter 14: ranges and lists of integers, and the control-key arm computes the letter with arithmetic on the byte. The interesting part is readEscape. An escape sequence for an arrow key is three bytes, ESC [ A, but the user pressing the Escape key alone sends one. The decoder cannot tell them apart from the first byte, so it waits 25 milliseconds for a second byte: nothing arrives, it was Escape; something arrives, it is a sequence. That is the classic terminal ambiguity, solved the classic way, in a function you can read in one sitting.

48.3 Cells to ANSI

screen.zig is a grid. Each cell is a character, a semantic style and, for pictures, two pixel colours:

src/tui/screen.zig
pub const Style = enum(u8) {
    normal,
    dim,
    amber,
    good,
    crit,
    sel, // cursor row / focused pane title
    tab, // active tab
    purple,
    box, // borders
    focus, // the focused pane's border line
    // Political colours for the star map (12B.9).
    blue, red, yellow, green, magenta, cyan, white, grey,

    fn sgr(self: Style) []const u8 {
        return switch (self) {
            .normal => "\x1b[0m",
            .dim => "\x1b[0;90m",
            .amber => "\x1b[0;33m",
            .good => "\x1b[0;32m",
            .crit => "\x1b[0;31m",
            .sel => "\x1b[0;30;46m",
            // …
        };
    }

    fn fromMarkup(c: u8) ?Style {
        return switch (c) {
            'a' => .amber,
            'g' => .good,
            'c' => .crit,
            's' => .sel,
            'd' => .dim,
            't' => .tab,
            'p' => .purple,
            '/' => .normal,
            else => null,
        };
    }
};

pub const Cell = struct {
    ch: u21 = ' ',
    style: Style = .normal,
    px: ?Pixels = null,
};

Styles are semantic (good, crit), not colours; the mapping to escape codes is one private function, and the eight markup letters from Chapter 44 map to styles in another. A query that writes {c}not admitted{/} never knows what red is. Drawing writes cells into the grid; text parses the markup as it goes; pane draws a titled box; lines fills a rectangle with rows and highlights the cursor row. Then one function emits the frame:

    pub fn flush(self: *Screen, out: *std.Io.Writer) !void {
        try out.writeAll("\x1b[H");
        var y: u16 = 0;
        while (y < self.rows) : (y += 1) {
            try out.print("\x1b[{d};1H", .{y + 1});
            var cur: ?Style = null;
            var x: u16 = 0;
            while (x < self.cols) : (x += 1) {
                const c = self.get(x, y);
                if (c.px) |p| { /* half-block pixel cell, true colour or 256-colour */ continue; }
                if (cur == null or cur.? != c.style) {
                    try out.writeAll(c.style.sgr());
                    cur = c.style;
                }
                var buf: [4]u8 = undefined;
                const n = std.unicode.utf8Encode(c.ch, &buf) catch 1;
                try out.writeAll(buf[0..n]);
            }
        }
        try out.writeAll("\x1b[0m");
        try out.flush();
    }

No diffing: every frame is the whole grid, cell by cell, with an escape code emitted only when the style changes from the previous cell. At terminal sizes (200 by 50 is ten thousand cells) that is a few tens of kilobytes twice a second, which is fast enough, and it makes the renderer trivially correct. The writer is the buffered stdout writer from main (a 64 KiB buffer, Chapter 33), so the frame goes out in one or two system calls at the final flush.

48.4 The loop

app.zig is the state machine. Its state is a struct with a mode (welcome, wizard, game), a tab, a modal, per-tab cursors and the campaign itself as an optional:

src/tui/app.zig (fields, abridged)
const Tab = enum(u8) { desk, map, forces, contracts, ledger, supply, hq, lab, people, market };
const Mode = enum { welcome, wizard, game };

pub const App = struct {
    gpa: std.mem.Allocator,
    io: std.Io,
    term: *Term,
    screen: Screen,
    store: game.store.Store,
    frame: std.heap.ArenaAllocator,
    lobby: std.heap.ArenaAllocator,
    gs: ?GameState = null,
    running: bool = true,
    music: ?music_mod.Player = null,
    // …
    mode: Mode = .welcome,
    tab: Tab = .desk,
    modal: Modal = .none,
    focus: u8 = 0,
    /// Cursor per tab per pane (welcome uses tab 0, wizard tab 1).
    cursor: [10][4]usize = [_][4]usize{[_]usize{0} ** 4} ** 10,
    msg: TextBuf = .{},
    msg_style: Style = .dim,
    // …
};

The client has grown since the original guide (ten tabs now, with People and Market added), but the loop is the same shape:

    pub fn run(self: *App) !void {
        // … defaults, terminal probe, music settings, splash …
        while (self.running) {
            if (self.term.tookResize()) {
                const size = self.term.size();
                try self.screen.resize(size.cols, size.rows);
            }
            try self.draw();
            const key = self.term.readKey(500);
            if (self.music) |*m| {
                m.poll();
                // … announce a new track in the status strip …
            }
            if (key == .none) continue;
            _ = self.frame.reset(.retain_capacity);
            self.handleKey(key) catch |err| self.say(.crit, "error: {s}", .{@errorName(err)});
        }
    }

    fn draw(self: *App) !void {
        _ = self.frame.reset(.retain_capacity);
        self.screen.clear();
        self.n_placements = 0;
        switch (self.mode) {
            .welcome => try self.drawWelcome(),
            .wizard => try self.drawWizard(),
            .game => try self.drawGame(),
        }
        // … modal over the top; emblem placement for kitty/iTerm2 …
        try self.screen.flush(self.term.out);
    }

    fn handleKey(self: *App, key: Key) !void {
        if (self.modal != .none) return self.handleModalKey(key);
        switch (self.mode) {
            .welcome => try self.handleWelcomeKey(key),
            .wizard => try self.handleWizardKey(key),
            .game => try self.handleGameKey(key),
        }
    }

    fn exec(self: *App, cmd: Command) !void {
        const g = &self.gs.?;
        _ = game.commands.execute(g, cmd) catch |err| {
            self.say(.crit, "refused: {s}", .{game.cli.errorText(err)});
            return;
        };
    }

Draw, wait up to half a second for a key, poll the music player, and if a key came, handle it. The half-second timeout is why the clock in the status strip ticks and a finished track is noticed without a keypress. draw resets the frame arena first, so every query result from the previous frame is gone before the new ones are made (Chapter 44); the loop resets it again before handleKey, because handlers call queries too. .retain_capacity keeps the arena's memory for reuse instead of returning it to the general-purpose allocator, so a steady state allocates nothing new per frame.

The error handling in the loop is the client's whole safety net: any error from a handler becomes a red line in the status strip, and the loop continues. exec is the narrower version for commands: a refusal from execute becomes a sentence via cli.errorText (Chapter 42). handleKey dispatches by modal, then mode, then (inside handleGameKey) by global keys, then tab, then a switch on the character. That is four levels of switch and no table of callbacks, which keeps every key's behaviour readable at its site.

48.5 What the loop looks like from the game's side

Here is a game-mode key handler, showing all three doors in a few lines. row is the highlighted ToeRow from the Forces query, q is game.queries and g is the campaign:

                    'A' => if (row) |r| {
                        const co = g.companyOf(r.force);

The client reads g.companyOf(…) and q.forceName(…) (queries and pure helpers), builds a command, calls execute, and formats the result. It never writes a field of g. Chapter 50 follows the c key all the way down.

48.6 Testing a program that reads a keyboard

The client is driven by bytes on a file descriptor, so it can be tested without a human. docs/tui_smoke.py forks the game under a pseudo-terminal, sends keystrokes, and asserts on the text that comes back:

assert "hired to fill the manning table" in plain()[-1200:], plain()[-1500:]
…
# ---- second pass: the minimum tier (80x24) and --ascii, every screen ----
os.execv(exe, [exe, "--tui", "--ascii", "--no-splash", "--no-music", "--store", db])
fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack("HHHH", 24, 80, 0, 0))
assert "F1 Desk" in p and "+-" in p, p[-2000:]          # ascii borders

Every screen and most modals are visited, twice: once at a large size and once at 80 by 24 with --ascii, which is why main has those flags. When the market pane was retitled, this script failed on the old title within seconds, which is the point of it. A sibling script, docs/repl_smoke.sh, pipes a list of verbs into --repl and greps for landmarks. Neither is a Zig test; both are part of "a change is done" in CLAUDE.md.

Inside Zig, the parts that do not need a terminal have ordinary tests: screen.zig tests that text clips to a width and honours markup, that pane borders land on the rectangle's edges, that a square image blits at a 2:1 cell aspect; app.zig tests the size-tier thresholds; png.zig decodes a tiny embedded image (@embedFile, Chapter 25). The test block at the top of main.zig is what pulls these files into the test build, since they are not part of the game module.

Guided reading

  1. src/tui/term.zig, all of it: Key, init, deinit, fill, take, readKey, readUtf8, readEscape.
  2. src/tui/screen.zig: Style, Cell, Screen.text (the markup parser), pane, lines, flush, and the tests.
  3. src/tui/app.zig: the Tab, Mode and Modal types, the App fields, then run, draw, handleKey, handleGameKey, exec, say. Then one screen pair: drawForces and the Forces arm of screenKey. Then pub fn run at the very bottom, which is where main hands over.
  4. docs/tui.md: the frame, the keyboard model and the screen table. It was written before the code and is still accurate about the boundary.
  5. docs/tui_smoke.py: skim for the shape (send, drain, assert).

Exercises

Exercise 48.1 · Markup becomes styles warm-up

Write a test in screen.zig that draws "{g}ok{/}!" into a ten-by-one screen and checks the cells: the first is styled .good, the second holds 'k', the third is back to .normal. Also check visibleLen of the same string.

Solution 
test "markup lands as styles in the cells" {
    var s = try Screen.init(std.testing.allocator, 10, 1);
    defer s.deinit();
    _ = s.text(0, 0, 10, "{g}ok{/}!", .normal);
    try std.testing.expectEqual(Style.good, s.get(0, 0).style);
    try std.testing.expectEqual(@as(u21, 'k'), s.get(1, 0).ch);
    try std.testing.expectEqual(Style.normal, s.get(2, 0).style);
    try std.testing.expectEqual(@as(usize, 3), visibleLen("{g}ok{/}!"));
}

Screen is one of the few structs in the program that takes an allocator it keeps (the grid must outlive many frames), so the test uses std.testing.allocator and pairs init with defer s.deinit(). text returns the number of cells used, discarded here with _ =. get takes u16 coordinates.

Exercise 48.2 · Grep the boundary practice

The rule says the client never mutates GameState. Write a grep that would find an assignment through the campaign pointer (g.funds = …, g.people…) in app.zig, run it, and report. Then count how many times the file calls execute or self.exec, and how many times it calls a query.

Solution 
$ grep -nE '\bg\.[a-z_]+(\.[a-z_]+)* (\+|-)?= ' src/tui/app.zig
(no output)

No direct writes; sixty-nine command sites; a hundred and seventy-five query calls. The ratio, roughly 2.5 reads per write, is what a view over a command/query boundary should look like.

Exercise 48.3 · The escape ambiguity practice

Without running anything, trace readKey for these byte sequences arriving together: (a) 1b 5b 41; (b) 1b alone; (c) 1b 5b 31 35 7e; (d) 03. Say what Key each yields and which branch decides it.

Solution

(a) ESC [ A: readEscape sees '[', then 'A', returns .up. (b) A lone ESC: fill(25) times out with nothing behind it, returns .escape. (c) ESC [ 1 5 ~: the digits accumulate num = 15, then '~' switches on num and returns .{ .f = 5 }. (d) Byte 3 is in the range 1...7, so the control arm returns .{ .ctrl = 'a' + 3 - 1 }, which is .{ .ctrl = 'c' }; Ctrl-C reaches the program as a key because raw mode cleared ISIG, and the app decides what to do with it rather than the kernel.

Check your understanding

  1. Why does Term.deinit swallow every error with catch {}?
    AnswerIt runs on the way out, often from a defer during an error; there is no useful recovery from failing to restore the terminal, and returning an error from a deinit would complicate every caller.
  2. How does the client tell Escape from an arrow key?
    AnswerAfter an ESC byte, readEscape waits 25 milliseconds for a following byte; none means the Escape key, a '[' or 'O' means a sequence to decode.
  3. What does Screen.flush not do, and why is that acceptable?
    AnswerIt does not diff against the previous frame; it emits every cell. At terminal sizes that is tens of kilobytes per frame, which a buffered writer handles easily, and it makes the renderer trivially correct.
  4. Where is the frame arena reset, and why twice?
    AnswerAt the top of draw and just before handleKey in the loop; both draw functions and key handlers call queries that allocate into it, and neither should see the other's leftovers.
  5. Why is the timeout in readKey(500) half a second rather than blocking?
    AnswerSo the loop redraws periodically without input: the music player is polled, a resize is noticed, the status strip updates.
  6. What are the client's three permitted calls into the simulation?
    Answergame.commands.execute (through exec or directly), game.cli.parseCommand for the : line, and the functions of game.queries.
  7. How is a screen tested without a terminal?
    Answerscreen.zig's grid is a plain struct with tests on cell contents; the whole client is driven under a pseudo-terminal by docs/tui_smoke.py, which sends keys and asserts on the text that comes back.
What you learned.
  • The client is layered: term.zig turns bytes into a Key union, screen.zig turns cells into ANSI, app.zig is a state machine over mode, tab, modal and cursors.
  • Raw mode is entered with tcsetattr and restored by a deinit that never fails; a resize is an atomic flag set by a signal handler.
  • The main loop is draw, wait half a second for a key, poll, handle; every handler error becomes a status-line sentence.
  • A frame arena is reset before drawing and before handling, so queries allocate freely and nothing accumulates.
  • The client only ever calls execute, parseCommand and queries; a grep confirms it, and a pseudo-terminal script tests every screen.
