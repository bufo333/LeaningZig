10. Slices

In this chapter you will learn the type you will use more than any other in Zig: the slice. A slice is a pointer plus a length, a window onto some array that lives elsewhere. You will make slices from arrays, read and write through them, learn why []const T and []T differ, see the bounds check that protects you, meet the sentinel-terminated and many-item cousins briefly, and understand why nearly every function you write from now on takes a slice instead of an array.

10.1 A window onto an array

The previous chapter ended on a wall: a function taking [4]u8 cannot accept a [3]u8. Slices are how Zig climbs that wall without losing safety. A slice does not own any elements. It says "start here, and there are this many". Make one by writing a range in square brackets after an array:

basics.zig

const std = @import("std");

pub fn main() void {
    const roster = [_]u8{ 10, 20, 30, 40, 50 };
    const middle = roster[1..4]; // elements 1, 2, 3 (4 is excluded)
    std.debug.print("{any}\n", .{middle});
    std.debug.print("len {d}, first {d}\n", .{ middle.len, middle[0] });
    std.debug.print("type: {any}\n", .{@TypeOf(middle)});
}
{ 20, 30, 40 }
len 3, first 20
type: *const [3]u8

roster[1..4] means "from index 1 up to but not including index 4": elements 1, 2 and 3. The end is exclusive, exactly like Python's roster[1:4], so end - start is the length. The result knows its length, 3, and you index it from zero: middle[0] is roster[1].

Look at the printed type, though: *const [3]u8, a pointer to a three-element array, not a slice. That is a small 0.16 detail worth knowing. When both bounds are compile-time constants, Zig can work out the length and gives you the more precise pointer-to-array type. It coerces to a slice the moment you need one, so in practice you treat it as a slice. Use runtime bounds, or write the slice type explicitly, and you get a real slice:

forms.zig

const std = @import("std");

pub fn main() void {
    var roster = [_]u8{ 10, 20, 30, 40, 50 };
    const tail = roster[2..]; // from index 2 to the end
    const head = roster[0..2]; // first two
    const all: []u8 = &roster; // &array coerces to a slice of the whole thing
    var n: usize = 1;
    n += 2;
    const runtime = roster[n..]; // the bounds can be runtime values
    std.debug.print("tail {any}\n", .{tail});
    std.debug.print("head {any}\n", .{head});
    std.debug.print("all  {any} (type {any})\n", .{ all, @TypeOf(all) });
    std.debug.print("runtime {any} (type {any})\n", .{ runtime, @TypeOf(runtime) });
}
tail { 30, 40, 50 }
head { 10, 20 }
all  { 10, 20, 30, 40, 50 } (type []u8)
runtime { 40, 50 } (type []u8)

Three forms to memorise:

  • arr[a..b]: from a to b exclusive.
  • arr[a..]: from a to the end.
  • &arr: the whole array. A pointer to an array coerces to a slice whenever a slice is expected, which is why you passed &a to std.mem.eql in the last chapter.

The type []u8 reads "slice of u8". No number in the brackets, because the length is not part of the type any more; it is a field of the value.

10.2 A slice is a view, not a copy

This is the fact that separates slices from arrays. Assigning an array copies it; making a slice copies nothing. The slice points into the original memory, and writing through it changes the original.

view.zig

const std = @import("std");

pub fn main() void {
    var roster = [_]u8{ 10, 20, 30, 40, 50 };
    const window = roster[1..3];
    window[0] = 99; // writes through to roster[1]
    std.debug.print("roster: {any}\n", .{roster});
    std.debug.print("window: {any}\n", .{window});
    std.debug.print("same memory: {}\n", .{&window[0] == &roster[1]});
}
roster: { 10, 99, 30, 40, 50 }
window: { 99, 30 }
same memory: true

window[0] = 99 wrote into roster[1], because that is where the window starts. The last line proves it: the address of window[0] is the address of roster[1]. There are two names for one byte.

In memory a slice is two machine words: a pointer to the first element and a usize length. You can look at them as .ptr and .len. Copying a slice copies those two words, not the elements. That makes slices cheap to pass around and dangerous in exactly one way: the array they point at must outlive them. Zig catches the most common version of that mistake at compile time:

dangling.zig

const std = @import("std");

fn makeSlice() []const u8 {
    var local = [_]u8{ 1, 2, 3 };
    local[0] = 9;
    return &local; // points at a variable that is about to disappear
}

pub fn main() void {
    std.debug.print("{any}\n", .{makeSlice()});
}

            ^~~~~
dangling.zig:4:9: note: declared runtime-known here

local lives on the stack frame of makeSlice, which is torn down when the function returns. A slice pointing into it would point at garbage. The compiler refuses. When you want a function to hand back text or data, either the caller provides the buffer (the pattern in 10.6 and in every bufPrint call) or the function allocates (Chapter 19).

10.3 []const T and []T

A slice type says whether you may write through it. []u8 allows writes; []const u8 does not. The rule for coercion is one-way: a mutable slice can become a const slice for free, never the reverse.

constness.zig

const std = @import("std");

fn sum(xs: []const u8) u32 {
    var t: u32 = 0;
    for (xs) |x| t += x;
    return t;
}

fn zero(xs: []u8) void {
    for (xs) |*x| x.* = 0;
}

pub fn main() void {
    var a = [_]u8{ 1, 2, 3 };
    const b = [_]u8{ 4, 5, 6 };
    std.debug.print("{d} {d}\n", .{ sum(&a), sum(&b) }); // []u8 coerces to []const u8
    zero(&a);
    std.debug.print("{any}\n", .{a});
}
6 15
{ 0, 0, 0 }

10.4 Bounds are checked here too

A slice knows its length, so indexing and re-slicing are checked just as with arrays. Because the bounds are usually runtime values, the check is usually at runtime:

bounds.zig

const std = @import("std");

fn firstN(xs: []const u8, n: usize) []const u8 {
    return xs[0..n];
}

pub fn main() void {
    const roster = [_]u8{ 10, 20, 30 };
    std.debug.print("{any}\n", .{firstN(&roster, 2)});
    std.debug.print("{any}\n", .{firstN(&roster, 5)});
}

Note also what the check is guarding. Slicing does not copy, so the check is the only thing standing between your program and reading memory it has no business with. In C the equivalent call quietly returns a pointer past the end of the buffer.

10.5 Why functions take slices

The payoff comes now. Rewrite the average with a slice parameter and it works for four elements, twelve, a window of four in the middle of twelve, or none at all:

why.zig

const std = @import("std");

fn average(xs: []const u32) u32 {
    if (xs.len == 0) return 0;
    var t: u32 = 0;
    for (xs) |x| t += x;
    return t / @as(u32, @intCast(xs.len));
}

pub fn main() void {
    const lance = [_]u32{ 55, 65, 70, 50 };
    const company = [_]u32{ 55, 65, 70, 50, 80, 85, 75, 60, 35, 40, 30, 45 };
    std.debug.print("lance avg {d}\n", .{average(&lance)});
    std.debug.print("company avg {d}\n", .{average(&company)});
    std.debug.print("heavy lance avg {d}\n", .{average(company[4..8])});
    std.debug.print("nothing avg {d}\n", .{average(&[_]u32{})});
}
lance avg 60
company avg 57
heavy lance avg 75
nothing avg 0

One function, any length. company[4..8] hands it the middle of an array without copying anything. &[_]u32{} is an empty array's address, which coerces to an empty slice; the len == 0 guard handles it.

The @intCast is because xs.len is a usize and the arithmetic is in u32; Zig will not silently narrow a 64-bit value to 32 bits. You will write this cast often when mixing lengths with other integers.

This is why the standard library is written in terms of slices. std.mem.eql, std.mem.indexOf, std.fmt.bufPrint, the writer print methods: all of them take and return slices, so they compose with arrays of any size, with pieces of arrays, and, once you have an allocator, with memory from the heap.

10.6 Loops and mutation through a slice

Slices loop exactly like arrays. The pointer-capture form is how you modify elements in place, and it needs no & in front, because a slice is already a kind of pointer:

iter.zig

const std = @import("std");

pub fn main() void {
    var hp = [_]u8{ 12, 7, 0, 3 };
    const wounded: []u8 = &hp;

    for (wounded, 0..) |h, i| {
        std.debug.print("pilot {d}: {d} hp\n", .{ i, h });
    }
    for (wounded) |*h| { // capture a pointer to mutate in place
        if (h.* > 0) h.* += 1;
    }
    std.debug.print("{any}\n", .{hp});

    // Two slices of equal length walked together.
    const names = [_][]const u8{ "Kai", "Nat", "Bo", "Ivy" };
    for (names, wounded) |n, h| {
        std.debug.print("{s}={d} ", .{ n, h });
    }
    std.debug.print("\n", .{});
}
pilot 0: 12 hp
pilot 1: 7 hp
pilot 2: 0 hp
pilot 3: 3 hp
{ 13, 8, 0, 4 }
Kai=13 Nat=8 Bo=0 Ivy=4

Three loops: (slice, 0..) |v, i| gives value and index; (slice) |*v| gives a pointer for writing; (a, b) |x, y| walks two slices in step. That last form requires equal lengths and panics otherwise, which is a feature: it turns a silent mismatch into a loud one.

For bulk copies and fills there are two builtins and two helpers:

copies.zig

const std = @import("std");

pub fn main() void {
    var buf: [8]u8 = undefined;
    @memset(&buf, '.'); // fill every byte
    std.debug.print("{s}\n", .{&buf});

    const src = "mek";
    @memcpy(buf[0..src.len], src); // lengths must match exactly
    std.debug.print("{s}\n", .{&buf});

    // Overlapping copy: shift "mek" two places right.
    std.mem.copyForwards(u8, buf[2..5], buf[0..3]);
    std.debug.print("{s}\n", .{&buf});
    std.mem.copyBackwards(u8, buf[3..6], buf[1..4]);
    std.debug.print("{s}\n", .{&buf});
}

10.7 Sentinel-terminated slices

A string literal is not quite a plain array. Its type carries an extra promise: there is a zero byte just past the end.

sentinel.zig

const std = @import("std");

pub fn main() void {
    const lit = "Alpha"; // *const [5:0]u8: five bytes plus a hidden 0
    const s: [:0]const u8 = lit; // sentinel-terminated slice
    const plain: []const u8 = lit; // ordinary slice, sentinel forgotten
    std.debug.print("{any}\n", .{@TypeOf(lit)});
    std.debug.print("{any} len {d}, byte after end: {d}\n", .{ @TypeOf(s), s.len, s[s.len] });
    std.debug.print("{any} len {d}\n", .{ @TypeOf(plain), plain.len });
}
*const [5:0]u8
[:0]const u8 len 5, byte after end: 0
[]const u8 len 5

*const [5:0]u8 reads "pointer to a constant array of 5 bytes, terminated by 0". The :0 is the sentinel. A slice can carry the same promise, [:0]const u8, and it is allowed to read the element at len, which a plain slice may not. The promise is what C needs (C strings find their end by looking for the zero), so you meet this type mostly at the edge where Zig calls C (Chapter 35) and in std.process arguments. The rest of the time you drop the sentinel by coercing to []const u8, as the third line shows, and nothing is lost: the length is still there.

10.8 Many-item pointers, briefly

The .ptr field of a slice has type [*]T, a many-item pointer. It is a pointer to some number of elements, with no idea how many. You can index it and it will not check anything.

many.zig

const std = @import("std");

pub fn main() void {
    const roster = [_]u8{ 10, 20, 30, 40, 50 };
    const slice: []const u8 = &roster;
    const p: [*]const u8 = slice.ptr; // many-item pointer: no length
    std.debug.print("{d} {d}\n", .{ p[0], p[4] });
    // p[5] would compile and read garbage: nothing knows where the end is.
    const back: []const u8 = p[0..3]; // give it a length again
    std.debug.print("{any}\n", .{back});
}
10 50
{ 10, 20, 30 }

This is the C pointer, and Zig keeps it for talking to C and for the rare data structure that tracks its own lengths. In ordinary code you should almost never write [*]T; if you find yourself reaching for it, a slice is what you want. Knowing it exists helps you read error messages like expected '[]u8', found '[*]u8': something lost its length, and p[0..n] gives it back.

10.9 Slices of slices

The element type of a slice can be a slice. A list of names is the everyday example: []const []const u8, a slice of strings.

nested.zig

const std = @import("std");

pub fn main() void {
    const names = [_][]const u8{ "1st Lance", "2nd Lance", "3rd Lance" };
    const some: []const []const u8 = names[1..];
    for (some, 0..) |name, i| {
        std.debug.print("{d}: {s} ({d} bytes)\n", .{ i, name, name.len });
    }
    const one = names[0];
    std.debug.print("{s}\n", .{one[0..3]}); // slicing a slice
}
0: 2nd Lance (9 bytes)
1: 3rd Lance (9 bytes)
1st

Read it inside out: []const u8 is one string; []const ([]const u8) is a slice of them. names[1..] takes the last two strings without copying any characters, and one[0..3] slices a string, which is what the next chapter is all about.

In IRON LEDGER. The command parser is built entirely on slices. Every function in src/sim/cli.zig takes a []const u8 and returns a slice or a parsed value, so the same code handles a keystroke buffer in the terminal and a line from a script file: 
// src/sim/cli.zig
pub fn parseSite(tok: []const u8) ParseError!types.Site { ... }
pub fn parseTreasury(tok: []const u8) ParseError!Treasury { ... }
pub fn need(tok: ?[]const u8) ParseError![]const u8 { ... }
pub fn usage(verb: []const u8) ?[]const u8 { ... }

Notice ?[]const u8: an optional slice, meaning "maybe a token, maybe nothing" (Chapter 15). The terminal reads keys into a fixed byte array and hands slices of it to the decoder, so no memory is allocated per keypress. And the guide's one-liner for a file's base name is pure slicing: if (std.mem.lastIndexOfScalar(u8, path, '/')) |k| path[k + 1 ..] else path.

Exercise 10.1 · Slice basics warm-up

Write lastN, inner and halves, each returning slices of the input without copying. Name the file: exercises/10-slices/ex1_slice_basics.zig.

Solution 
//! Chapter 10, exercise 1: slice basics.
//! Run with:  zig test ex1_slice_basics.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// The last `n` elements of `xs`. If n is larger than xs.len, return all of xs.
fn lastN(xs: []const u8, n: usize) []const u8 {
    if (n >= xs.len) return xs;
    return xs[xs.len - n ..];
}

/// Everything except the first and last element. Empty if xs has fewer than 3.
fn inner(xs: []const u8) []const u8 {
    if (xs.len < 3) return xs[0..0];
    return xs[1 .. xs.len - 1];
}

/// Split `xs` in half. The first half gets the extra element when odd.
fn halves(xs: []const u8) [2][]const u8 {
    const mid = (xs.len + 1) / 2;
    return .{ xs[0..mid], xs[mid..] };
}

test "lastN" {
    const d = [_]u8{ 1, 2, 3, 4, 5 };
    try std.testing.expectEqualSlices(u8, &[_]u8{ 4, 5 }, lastN(&d, 2));
    try std.testing.expectEqualSlices(u8, &d, lastN(&d, 9));
    try std.testing.expectEqual(@as(usize, 0), lastN(&d, 0).len);
}

test "inner" {
    const d = [_]u8{ 1, 2, 3, 4, 5 };
    try std.testing.expectEqualSlices(u8, &[_]u8{ 2, 3, 4 }, inner(&d));
    try std.testing.expectEqual(@as(usize, 0), inner(d[0..2]).len);
}

test "halves" {
    const d = [_]u8{ 1, 2, 3, 4, 5 };
    const h = halves(&d);
    try std.testing.expectEqualSlices(u8, &[_]u8{ 1, 2, 3 }, h[0]);
    try std.testing.expectEqualSlices(u8, &[_]u8{ 4, 5 }, h[1]);
    const e = halves(d[0..0]);
    try std.testing.expectEqual(@as(usize, 0), e[0].len + e[1].len);
}

The empty slice xs[0..0] is a legitimate value: pointer to the start, length zero. halves returns an array of two slices; the array is copied out (two pointer-length pairs), the data is not.

Exercise 10.2 · Mutating through slices practice

Write heal (saturating add on every element), raiseFloor, and padCopy using @memcpy and @memset. Note that the tests pass sub-slices like xs[2..] and buf[4..]. Name the file: exercises/10-slices/ex2_mutate.zig.

Solution 
//! Chapter 10, exercise 2: mutating through slices.
//! Run with:  zig test ex2_mutate.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Add `delta` to every element, saturating at 255.
fn heal(hp: []u8, delta: u8) void {
    for (hp) |*h| h.* +|= delta;
}

/// Set every element that is below `floor` to `floor`.
fn raiseFloor(xs: []i32, floor: i32) void {
    for (xs) |*x| {
        if (x.* < floor) x.* = floor;
    }
}

/// Copy `src` into the front of `dst` and fill the rest with `pad`.
/// Returns dst.len. Panics if src is longer than dst (that is a caller bug).
fn padCopy(dst: []u8, src: []const u8, pad: u8) usize {
    @memcpy(dst[0..src.len], src);
    @memset(dst[src.len..], pad);
    return dst.len;
}

test "heal saturates" {
    var hp = [_]u8{ 250, 10, 0 };
    heal(&hp, 10);
    try std.testing.expectEqual([3]u8{ 255, 20, 10 }, hp);
}

test "raiseFloor" {
    var xs = [_]i32{ -5, 0, 5 };
    raiseFloor(&xs, 0);
    try std.testing.expectEqual([3]i32{ 0, 0, 5 }, xs);
    raiseFloor(xs[2..], 100); // only the tail
    try std.testing.expectEqual([3]i32{ 0, 0, 100 }, xs);
}

test "padCopy" {
    var buf: [8]u8 = undefined;
    const n = padCopy(&buf, "mek", ' ');
    try std.testing.expectEqual(@as(usize, 8), n);
    try std.testing.expectEqualStrings("mek     ", &buf);
    _ = padCopy(buf[4..], "ab", '-');
    try std.testing.expectEqualStrings("mek ab--", &buf);
}

+|= is saturating addition (Chapter 4). padCopy works on any buffer size because dst is a slice; the second call in the test fills only the last four bytes.

Exercise 10.3 · Searching and windows practice

Write argMax (returning an optional index), from (a suffix slice starting at the first element over a threshold), and bestWindow (the largest sum of w consecutive elements). Name the file: exercises/10-slices/ex3_search.zig.

Solution 
//! Chapter 10, exercise 3: searching and windows.
//! Run with:  zig test ex3_search.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Index of the largest element, or null when the slice is empty.
fn argMax(xs: []const i32) ?usize {
    if (xs.len == 0) return null;
    var best: usize = 0;
    for (xs, 0..) |x, i| {
        if (x > xs[best]) best = i;
    }
    return best;
}

/// The slice of `xs` that starts at the first element >= `threshold`.
/// Empty slice at the end if nothing qualifies.
fn from(xs: []const i32, threshold: i32) []const i32 {
    for (xs, 0..) |x, i| {
        if (x >= threshold) return xs[i..];
    }
    return xs[xs.len..];
}

/// The largest sum of any `w` consecutive elements. Requires w <= xs.len and w > 0.
fn bestWindow(xs: []const i32, w: usize) i32 {
    var best: i32 = std.math.minInt(i32);
    var start: usize = 0;
    while (start + w <= xs.len) : (start += 1) {
        var s: i32 = 0;
        for (xs[start .. start + w]) |x| s += x;
        if (s > best) best = s;
    }
    return best;
}

test "argMax" {
    try std.testing.expectEqual(@as(?usize, 2), argMax(&[_]i32{ 1, 5, 9, 3 }));
    try std.testing.expectEqual(@as(?usize, 0), argMax(&[_]i32{ 9, 9, 9 }));
    try std.testing.expectEqual(@as(?usize, null), argMax(&[_]i32{}));
}

test "from" {
    const d = [_]i32{ 1, 4, 2, 8, 3 };
    try std.testing.expectEqualSlices(i32, &[_]i32{ 4, 2, 8, 3 }, from(&d, 4));
    try std.testing.expectEqualSlices(i32, &[_]i32{ 8, 3 }, from(&d, 5));
    try std.testing.expectEqual(@as(usize, 0), from(&d, 100).len);
}

test "bestWindow" {
    const d = [_]i32{ 1, 4, 2, 8, 3 };
    try std.testing.expectEqual(@as(i32, 8), bestWindow(&d, 1));
    try std.testing.expectEqual(@as(i32, 11), bestWindow(&d, 2));
    try std.testing.expectEqual(@as(i32, 18), bestWindow(&d, 5));
}

bestWindow slides a sub-slice xs[start .. start + w] along the input; each window is a view, so the loop allocates nothing. xs[xs.len..] is the empty slice at the very end, a legal way to say "no elements qualified".

Exercise 10.4 · A fixed-size log challenge

A struct keeps the last four values pushed into a ring. Implement push, ordered (oldest first, written into a caller's buffer) and raw (a slice of the valid part of the internal array). This previews structs from Chapter 12; the method syntax is explained there. Name the file: exercises/10-slices/ex4_ring.zig.

Solution 
//! Chapter 10, exercise 4: a fixed-size log with a slice view (challenge).
//! Run with:  zig test ex4_ring.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Keeps the last `cap` values pushed. Older values are overwritten.
const Log = struct {
    buf: [4]u32 = undefined,
    len: usize = 0, // how many slots are valid (0..4)
    next: usize = 0, // where the next push goes

    fn push(self: *Log, v: u32) void {
        self.buf[self.next] = v;
        self.next = (self.next + 1) % self.buf.len;
        if (self.len < self.buf.len) self.len += 1;
    }

    /// Copy the valid values, oldest first, into `out` and return the filled part.
    fn ordered(self: Log, out: []u32) []u32 {
        const start = if (self.len < self.buf.len) 0 else self.next;
        var i: usize = 0;
        while (i < self.len) : (i += 1) {
            out[i] = self.buf[(start + i) % self.buf.len];
        }
        return out[0..self.len];
    }

    /// The valid part of the raw buffer (no reordering).
    fn raw(self: *const Log) []const u32 {
        return self.buf[0..self.len];
    }
};

test "fills up then wraps" {
    var log = Log{};
    var out: [4]u32 = undefined;
    try std.testing.expectEqual(@as(usize, 0), log.ordered(&out).len);
    log.push(1);
    log.push(2);
    try std.testing.expectEqualSlices(u32, &[_]u32{ 1, 2 }, log.ordered(&out));
    log.push(3);
    log.push(4);
    log.push(5); // overwrites 1
    try std.testing.expectEqualSlices(u32, &[_]u32{ 2, 3, 4, 5 }, log.ordered(&out));
    try std.testing.expectEqualSlices(u32, &[_]u32{ 5, 2, 3, 4 }, log.raw());
}

raw returns a slice into the struct's own array, so it takes self by pointer: a by-value self would be a copy that dies when the function returns, and the compiler would reject the slice, as in 10.2. ordered writes into the caller's buffer instead, so it can take self by value.

Check your understanding

  1. What two pieces of information make up a slice?
    AnswerA pointer to the first element (.ptr) and a length (.len).
  2. How many elements does arr[2..5] have, and which ones?
    AnswerThree: indexes 2, 3 and 4. The end bound is exclusive.
  3. Does writing through a slice change the original array?
    AnswerYes. A slice is a view; it does not copy the elements.
  4. Can you pass a []u8 where []const u8 is expected? The reverse?
    AnswerYes to the first, no to the second. Mutable coerces to const; going the other way is a compile error ("cast discards const qualifier").
  5. Why does return &local; fail to compile when local is an array inside the function?
    AnswerThe array lives in the function's stack frame and is gone after the return; a slice into it would be dangling. Have the caller supply a buffer instead.
  6. What does [:0]const u8 promise that []const u8 does not?
    AnswerThat the element just past len is a zero byte. C APIs rely on it.
  7. What is wrong with @memcpy(&buf, "mek") when buf is [8]u8?
    AnswerThe lengths differ (8 versus 3) and @memcpy requires them to match. Slice the destination: @memcpy(buf[0..3], "mek").
What you learned.
  • A slice []T is a pointer and a length: a window onto an array, not a copy.
  • Make one with arr[a..b], arr[a..], or &arr. Compile-time bounds give *const [N]T, which coerces to a slice.
  • []const T for reading, []T for writing; mutable coerces to const, never the reverse.
  • Indexing and slicing are bounds-checked; a slice must not outlive its array, and the compiler catches returning a local's address.
  • Functions take slices so one signature serves any length or sub-range.
  • for (s) |*v| mutates in place; @memset, @memcpy (equal lengths, no overlap) and std.mem.copyForwards/copyBackwards do bulk work.
  • [:0]T adds a sentinel for C; [*]T is a length-less many-item pointer you rarely need.
