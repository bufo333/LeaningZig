50. One keypress, end to end

In this chapter you follow a single keypress through every layer you have read: from a byte on a file descriptor, through the client's dispatch, into a command, through validation and mutation, back out as a result, onto the screen through a query, and (not yet) into the save file. Nothing new is introduced; the point is to see the parts you know as one motion, and then to test each layer alone.

What you need from earlier chapters. This chapter is a synthesis of Chapter 42 (the crew_company arm), Chapter 44 (the manning query), Chapter 45 (a signing bonus through postTreasury) and Chapter 48 (readKey, handleKey, draw). If any of those is hazy, this chapter will show you which.

50.1 The setup

Start the client (zig build run -- --tui), load or create a campaign, press F3 for the Forces screen, and put the cursor on a company row. The manning pane on the right (cycle to it with r if it shows damage) lists fourteen roles with have, need and open columns. Some lines are red: the company is short of astechs, or medics, or a mechanic. Press c.

Here is everything that happens, layer by layer, with the source for each.

50.2 Bytes

The loop in App.run is waiting in self.term.readKey(500). The terminal is in raw mode, so the byte 0x63 arrives immediately rather than after Enter. fill polls the file descriptor, reads into the 64-byte pending buffer, and take hands over the first byte:

        return switch (b) {
            0x1b => self.readEscape(),
            '\r', '\n' => .enter,
            '\t' => .tab,
            0x7f, 0x08 => .backspace,
            1...7, 11, 12, 14...26 => .{ .ctrl = 'a' + b - 1 },
            else => self.readUtf8(b),
        };

0x63 is not an escape, not a control byte; readUtf8 sees a one-byte sequence and returns .{ .char = 'c' }. The Key union value goes back to the loop, which resets the frame arena and calls self.handleKey(key).

50.3 Dispatch

Four switches deep. handleKey: no modal is open, so it switches on mode and finds .game. handleGameKey: the key is .char, and 'c' is not one of the global keys (:, n, q, ?, digits), so it falls to screenKey(ch). screenKey switches on self.tab and finds .forces. The Forces arm has already fetched the screen's rows for this frame and computed row, the ToeRow under the cursor, with its force ID:

                    'c' => if (row) |r| {
                        const co = g.companyOf(r.force);
                        if (co != .none) {
                            const res = game.commands.execute(g, .{ .crew_company = co }) catch |err| {
                                self.say(.crit, "{s}", .{game.cli.errorText(err)});
                                return;
                            };
                            self.say(if (res.still_open == 0) .good else .amber, "{s}: {d} hired to fill the manning table · {d} lines still open (no candidates on the boards yet)", .{ q.forceName(g, co), res.hired_count, res.still_open });
                        }
                    },

g.companyOf(r.force) resolves whatever the cursor is on (a lance, a hull inside a lance, the company itself) to its company; a row outside any company yields .none and the key does nothing. Then the client builds the command value .{ .crew_company = co } and calls execute. This arm calls execute directly rather than through self.exec because it wants the Result; the shape of the error handling is the same.

50.4 Validate

Inside execute, the .crew_company arm (Chapter 42) checks three things before touching anything:

            const f = gs.force(company) orelse return Error.UnknownForce;
            if (f.echelon != .company) return Error.NotACompany;
            if (gs.deploymentContract(company) != null) return Error.CompanyDeployed;

The force must exist, must be a company (not a lance or a battalion), and must not be deployed on a contract, because hiring happens at an HQ's hall and a company in the field is light-years away. Any refusal returns a named error, and the client's catch turns it into a red sentence from cli.errorText: "that company is deployed — hire at an HQ hall and xfer person <id> co:N to send people out to it".

50.5 Mutate

With the checks passed, the arm asks personnel.manningNeeds(gs, company) for the fourteen-row table: a role, a need and a reason for each, derived from the company's hulls (a mek wants a mekwarrior and a share of a tech and astechs; a MASH truck wants a doctor and medics). For each row it compares need against manningHave and fills the gap:

            for (personnel.manningNeeds(gs, company)) |n| {
                var have = personnel.manningHave(gs, company, n.role);
                while (have < n.need) : (have += 1) {
                    if (personnel.isPooledRole(n.role)) {
                        // MekHQ hires astechs and medics to complement on
                        // demand: no market, no signing bonus, salary only.
                        const spec = person_gen.generateWithBonus(&gs.rng, n.role, gs.recruitBonus());
                        const id = try gs.hireFromSpec(spec);
                        gs.person(id).?.assigned_force = company;
                        hired += 1;
                    } else if (try hireRoleFromHall(gs, n.role, company)) {
                        hired += 1;
                    } else {
                        still_open += n.need - have;
                        break;
                    }
                }
            }
            _ = try gs.autoAssign(company);
            try gs.log(.decision, .{ .company = company }, "[raise] {s}: {d} hired to fill the manning table ({d} still open — the halls had nobody)", .{ f.name, hired, still_open });

Two paths. Astechs and medics are pooled roles: generated on the spot from the .generation stream (so the same seed produces the same people) and hired by hireFromSpec, which mints a PersonId, builds the Person on the arena and inserts it into the ordered map. Every other role comes from the hiring hall's candidates via hireRoleFromHall, which finds the first candidate of that role and runs the .hire_candidate command, and that arm debits the signing bonus through postTreasury (Chapter 45), one ledger entry and one balance change. When the hall has nobody of a role, the gap is counted in still_open and the loop moves to the next row. Finally autoAssign seats pilots and techs on the company's hulls, and a log line is written with the company tag so the Desk's log can filter it.

Notice what the arm never does: it never allocates from anything but the campaign arena, never reads the clock except through gs.clock, never rolls a die except through gs.rng, and never touches the terminal. It is a pure function of the state and the command, which is the property Chapter 49 tests.

50.6 Report

            return .{ .hired_count = hired, .still_open = still_open };

Two numbers in a Result whose other fields keep their defaults. Back in the client, self.say formats them into one sentence with a style chosen by whether anything is still open: green for "5 hired to fill the manning table · 0 lines still open", amber if the hall could not supply everyone. say writes into a fixed 128-byte buffer with bufPrint (Chapter 23) and stores the style; the status strip draws it on the next frame.

50.7 Redraw

The loop comes round. draw resets the frame arena, clears the grid, and drawForces calls queries.toeFiltered for the tree and queries.manning for the pane:

    for (needs) |n| {
        const have = personnel.manningHave(gs, company, n.role);
        const open = n.need -| have;
        // …
        try out.append(alloc, .{ .role = n.role, .have = have, .need = n.need, .text = try std.fmt.allocPrint(alloc,
            "{s: <16} {d: >5} {d: >5} {s}{d: >5}{{/}}   {{d}}{s}{{/}}",
            .{ @tagName(n.role), have, n.need, if (open > 0) "{c}" else "{g}", open, why }) });
    }

The rows that were red are green, because manningHave recomputed from the people map that now has new entries in it. Nothing was cached and nothing was told to update: the query reads state, the screen draws the query. The tech-hours line above the table changed too, because the new astechs add hours. screen.flush emits the frame, and the terminal shows it.

50.8 Persist

Nothing yet. Saving is its own action (:save, or the save-and-return choice on q), and when it runs, the new people are rows in the person table like any other: one bindAll each, in map order, with ord recording their place (Chapter 47). If the player quits without saving, the arena is freed by gs.deinit() and the hires never happened.

50.9 Every layer alone

The reason to trace a keypress is to see that each layer can be exercised without the others, and the project does:

  • The command has a test with a seeded hall ("12: a raised company is an empty skeleton; hulls bought for it land in a lance …; halls crew it" in commands.zig), which runs .crew_company and asserts on the roster.
  • The query has a test on a generated company ("manning matches the starter generator's ratios" in queries.zig), which checks the fourteen rows against the generator's own numbers.
  • The parser has a test that crew co:1 becomes .{ .crew_company = 1 }, since the same command is reachable by typing.
  • The client is covered by docs/tui_smoke.py, which presses c on the Forces screen and looks for "hired to fill the manning table" in the output.
  • The persistence of the result is covered by the round-trip test, which hires people and compares hashes across a save.

Every layer is visible in the text, and none of them needs the others to be tested. That is what the architecture buys, and it is why the whole program can be read the way you have just read it.

Guided reading

  3. src/sim/commands.zig: the .crew_company arm, hireRoleFromHall, and the .hire_candidate arm it calls.

Exercises

Exercise 50.1 · The command alone practice

Write a test in commands.zig that creates a commander and a company, runs crew_company twice, and asserts that the second run hires nobody and reports the same number of open lines as the first. Then assert that crewing ForceId.none is refused, and say which error.

Solution 
test "crewing a company twice hires nobody the second time" {
    var gs = GameState.init(std.testing.allocator, .{ .seed = 11 });
    defer gs.deinit();
    _ = try execute(&gs, .{ .create_commander = .{ .name = "T", .origin = .LC, .profession = .paymaster } });
    const co = (try execute(&gs, .{ .new_company = "Alpha" })).created_force;
    const first = try execute(&gs, .{ .crew_company = co });
    const second = try execute(&gs, .{ .crew_company = co });
    try std.testing.expectEqual(@as(u32, 0), second.hired_count);
    try std.testing.expectEqual(first.still_open, second.still_open);
    try std.testing.expectError(Error.UnknownForce, execute(&gs, .{ .crew_company = .none }));
}

The second run finds have >= need on every row the first run filled, and the same halls empty for the rows it could not, so the counts match. .none fails the first check, gs.force(company) orelse return Error.UnknownForce, before the echelon check can say NotACompany; the order of validations decides which error a caller sees, which is worth knowing when you write errorText entries.

Exercise 50.2 · The parser alone warm-up

Write a test in cli.zig that parses crew co:1 and checks the resulting command's payload is force 1. (If you did Exercise 42.1, add a line for your morale verb.)

Solution 
test "crew parses to the company it names" {
    var it = std.mem.tokenizeScalar(u8, "co:1", ' ');
    const cmd = (try parseCommand("crew", &it)).?;
    try std.testing.expectEqual(@as(u32, 1), @intFromEnum(cmd.crew_company));
}

parseSite turns co:1 into a Site union and the crew branch takes its company. The .? unwraps the optional (a known verb never returns null) and cmd.crew_company reads the payload, which is a compile error if the tag were something else, since the tag is only checked at runtime; in a test that is fine because a wrong tag panics and fails the test.

Exercise 50.3 · Trace a different key practice

Repeat the seven steps for the A key on the same screen (auto-assign). Which steps are identical, which differ, and which query redraws differently afterwards?

Solution

Bytes (0x41 becomes .{ .char = 'A' }) and dispatch are identical down to the Forces arm. The command is .{ .auto_assign = co }, sent through self.exec because the handler does not need the result. Validation is the arm's own (the force must exist and be a company). Mutation is gs.autoAssign(company) alone: no hiring, no money, so nothing goes through postTreasury. Report is a plain "auto-assigned Alpha" in green. Redraw: the TO&E tree (toeFiltered) changes, because seats now show pilots and techs, while the manning pane's have counts do not change, since assignment moves people between seats rather than onto the payroll. Persist: nothing, as before.

Check your understanding

  1. Why does the byte 0x63 become a key immediately, without Enter?
    AnswerThe terminal is in raw mode (ICANON off), so bytes are delivered as typed rather than line by line.
  2. Where does the client learn which company the cursor is on?
    AnswerFrom the ToeRow the Forces query returned for this frame; its force field is resolved to a company with companyOf. It never counts rows.
  3. Which of the three validations would a deployed company fail, and what does the user see?
    Answergs.deploymentContract(company) != null, returning Error.CompanyDeployed; the status line shows the sentence errorText maps it to.
  4. Where does the signing bonus for a hall hire get debited?
    AnswerNot in the crew_company arm: hireRoleFromHall runs the .hire_candidate command, whose arm posts the bonus through postTreasury.
  5. Why do the manning rows turn green on the next frame?
    AnswerBecause queries.manning recomputes have from the people map every frame; there is no cache to invalidate.
  6. Is anything written to disk by this keypress?
    AnswerNo. Saving is a separate action; until then the hires exist only in the campaign arena.
What you learned.
  • A keypress is: a byte decoded to a Key, four switches of dispatch, a Command value, validate-mutate-report inside execute, a sentence in the status line, and a redraw that recomputes everything from state.
  • Pooled roles are generated from the seeded stream; other roles come from the hall via the hire_candidate command, which is where money moves.
  • Nothing is cached and nothing is written to disk until the player saves.
  • Each layer has its own test: the command, the query, the parser, the client under a pseudo-terminal, and the round trip.
