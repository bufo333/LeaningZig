0. How to use this book

In this chapter you will learn how the book is laid out, how to run the examples and exercises with the zig command, how to check your answers, and what IRON LEDGER is and why every chapter keeps pointing at it.

0.1 What this book is

This is a slow book. It teaches the Zig programming language, version 0.16, from the very first line you type to the point where you can open a real 31,000-line program and read it with understanding. It assumes you have written a little code in some language, enough to know what a loop and a function are, and nothing else. If you have never used C, never thought about where a variable lives in memory, and never seen a compiler refuse to build your program because of an unused variable, you are exactly the reader it was written for.

Zig is a small language with strong opinions. It has no hidden memory allocation, no hidden control flow, no exceptions, and no garbage collector. Every one of those absences is a design choice, and the book explains the reason each time one of them shows up. Learning Zig is largely learning to like those reasons.

Every chapter from 1 onward follows the same shape. It opens with a short statement of goals, works through its topic in numbered subsections, and ends with three fixed pieces: a blue In IRON LEDGER box that shows where the chapter's idea appears in the game's source, a set of exercises with hidden solutions, and a short quiz with hidden answers. A summary box closes the chapter.

Inside a chapter you will see callouts. An amber note adds context. A green Try it box asks you to change something and run it again. A red warning marks a trap that catches beginners. Read the warnings twice.

The book is meant to be read in order through Part 2 at least. Later parts lean on earlier ones, and the exercises assume you did the previous chapter's exercises. Part 5 can be read on its own by someone who already knows Zig.

0.3 Running the examples

You need a terminal and the Zig compiler. Chapter 1 walks through installing it. Once zig version prints 0.16.0, you can run any single-file example in this book with one command:

$ zig run hello.zig
Hello, world!

zig run compiles the file to a temporary executable and runs it. There is no project to set up and no build file to write. Every example in Parts 0 to 3 is a complete file you can copy into an editor, save, and run this way. Programs whose output goes to the terminal print it through std.debug.print, which writes to the standard error stream; you will see the output either way, and Chapter 2 explains the difference.

Examples that contain tests are run with a different command:

$ zig test ex2_overflow.zig
All 4 tests passed.

zig test compiles the file, runs every test "..." { } block in it, and reports how many passed. A test that fails prints where and why. This is the main way you will check your own work.

All output shown in the book in a dark terminal block was produced by actually running the code with Zig 0.16.0. Where a program is meant to fail, the book shows the real compiler error or the real panic message, trimmed of a few lines of internal stack trace, so you learn what those messages look like before you meet them alone.

0.4 Doing the exercises

Each chapter has three to six exercises, marked warm-up, practice, or challenge. They live in the exercises/ folder next to the chapters, one folder per chapter, and every exercise is a single .zig file with a header comment that tells you three things: what to do, which command runs it, and how you will know you are done.

//! Chapter 04, exercise 2: overflow arithmetic.
//! Run with:  zig test ex2_overflow.zig
//! Goal: make every test pass without changing the tests.

There are two kinds. A zig test exercise has tests at the bottom of the file; you fill in the function bodies marked // TODO until every test passes. A zig run exercise asks you to make the program print exactly the output listed in the header. Some starters do not compile until you finish them, and the header says so when that is the case.

Every exercise has a complete solution in a solutions/ subfolder and, in the book, behind a Solution disclosure under the exercise text. Try before you look. When you do look, read the explanation under the code, because the point of most exercises is a rule, not a program.

Try it. Before going on, make a folder for your work, such as ~/zig-book. You will keep every program you write in it, and by the end of Part 0 it will hold a few dozen small files you can look back on.

0.5 What IRON LEDGER is, and why it anchors the book

IRON LEDGER is a mercenary-company simulator set in the BattleTech universe. You command a small band of BattleMech pilots in the year 3025, take contracts, fight battles, repair machines, pay salaries, and try to end each month with more C-bills than you started with. It runs in a terminal, saves to a SQLite database, and is written entirely in Zig with no third-party libraries. Its source lives in the game/ folder next to this course and is about 31,000 lines long.

It is here for a reason that has nothing to do with giant robots. A book that teaches a language with toy examples leaves you unable to read a real program, because real programs are where the toy pieces meet: a struct holds a list that was made by an allocator that belongs to a game state that a command mutates that a query reads that a screen draws. IRON LEDGER is big enough to have all of that, small enough to read in full, and, because it was written in Zig 0.16 with no libraries, every idiom it uses is one this book can teach you.

So each chapter ends by pointing at the game. In Chapter 4 you learn integer arithmetic, then see that the game stores money as a 64-bit integer and never uses a float for it. In Chapter 6 you learn switch, then see the calendar's days-in-month function. By the time you reach Part 5, the tour of the game's architecture, you have already met most of its code in small pieces. The last chapters put the pieces together and follow one keypress from the terminal all the way through the simulation and back.

You do not need to know BattleTech. A BattleMech is a walking tank measured in tons; a lance is four of them; a C-bill is money; a contract is a job. That is the whole glossary you need, and the appendix has the rest.

0.6 A word about compile errors

Zig's compiler is strict in ways that surprise people who come from Python or JavaScript. An unused variable is an error. A variable declared changeable but never changed is an error. Reusing a name from an outer scope is an error. None of these stop a Python program. In Zig they stop the build, and the book shows you each one deliberately, with the exact text the compiler prints, so that the first time it happens on your own code you recognise it and know the one-line fix.

Treat the compiler as a patient reviewer rather than an obstacle. Almost every message it prints names the file, the line, the column, and often what to do about it. Learning to read those messages is a skill this book teaches on purpose, and Appendix A4 collects the common ones in one place.
