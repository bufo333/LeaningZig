13. Enums

In this chapter you will define closed sets of named values, switch over them with the compiler checking that you forgot nothing, give them methods and explicit integer representations, convert between enums and integers and strings, and learn the trick IRON LEDGER uses for every entity ID: the non-exhaustive enum. By the end you should reach for an enum whenever you catch yourself about to use a string or a magic number to mean "which kind".

13.1 A closed set of names

A person in the company has a role: pilot, technician, doctor, administrator. You could store that as a string, but then "Tech", "tech" and "tehc" are all valid and only one is what you meant. An enum lists the allowed values once and makes anything else a compile error.

basics.zig

const std = @import("std");

const Role = enum {
    mekwarrior,
    tech,
    doctor,
    admin,
};

pub fn main() void {
    const r = Role.mekwarrior;
    const t: Role = .tech; // shorthand when the type is known
    std.debug.print("{any} {any}\n", .{ r, t });
    std.debug.print("{s}\n", .{@tagName(t)});
    std.debug.print("{}\n", .{r == .mekwarrior});
    std.debug.print("{}\n", .{r == t});
}
.mekwarrior .tech
tech
true
false

Role.mekwarrior is the full spelling. When the type is already known, from a declared variable type, a parameter, or a comparison against an existing enum value, you write just the dot and the name: .tech. That shorthand is used far more than the full form; the guide calls it the leading-dot style and you will see it in every switch and every function call that takes an enum.

Enums compare with == and !=; that is one of the reasons to prefer them over strings. @tagName gives you the name as a string, which is how {s} printed tech. {any} prints the leading-dot form.

13.2 Methods and switch

Like a struct, an enum can contain functions, and a function taking the enum as its first parameter is a method. Inside them, switch is the natural tool:

switch.zig

const std = @import("std");

const Role = enum {
    mekwarrior,
    tech,
    doctor,
    admin,

    /// Monthly salary in C-bills.
    pub fn baseSalary(self: Role) i64 {
        return switch (self) {
            .mekwarrior => 1_500,
            .tech => 800,
            .doctor => 1_500,
            .admin => 500,
        };
    }

    pub fn isCombat(self: Role) bool {
        return self == .mekwarrior;
    }
};

pub fn main() void {
    const roster = [_]Role{ .mekwarrior, .mekwarrior, .tech, .doctor, .admin };
    var payroll: i64 = 0;
    for (roster) |r| {
        payroll += r.baseSalary();
        std.debug.print("{s:<10} {d} combat={}\n", .{ @tagName(r), r.baseSalary(), r.isCombat() });
    }
    std.debug.print("payroll {d}\n", .{payroll});
}
mekwarrior 1500 combat=true
mekwarrior 1500 combat=true
tech       800 combat=false
doctor     1500 combat=false
admin      500 combat=false
payroll 5800

switch is an expression here: each arm produces a value and the whole thing is returned. The arms name enum values with the leading dot. And every value is named, which brings us to the property that makes enums worth using.

        .mekwarrior, .aero_pilot => 1_500,

else switches off the safety net. The moment a switch has an else arm, adding a new enum value no longer produces an error there; it silently falls into else. Use else when "everything else" genuinely means the same thing, as a default salary might. When each value deserves its own thought, name them all and let the compiler nag you.

13.4 Explicit tag types and integer conversion

Every enum is stored as an integer. By default Zig picks the smallest that fits; you can choose it yourself with enum(u8), and you can assign the values:

tagtype.zig

const std = @import("std");

const Quality = enum(u8) {
    f = 0,
    d = 1,
    c = 2,
    b = 3,
    a = 4,
};

const Phase = enum(u8) { travel, supply, events, battle, finances }; // 0, 1, 2, ...

pub fn main() void {
    std.debug.print("{d} bytes\n", .{@sizeOf(Quality)});
    std.debug.print("{d}\n", .{@intFromEnum(Quality.b)});
    const q: Quality = @enumFromInt(4);
    std.debug.print("{s}\n", .{@tagName(q)});
    std.debug.print("{d} {d}\n", .{ @intFromEnum(Phase.travel), @intFromEnum(Phase.finances) });
    std.debug.print("{}\n", .{@intFromEnum(Phase.travel) < @intFromEnum(Phase.battle)});

    var counts = [_]u32{0} ** 5;
    for ([_]Quality{ .a, .c, .a, .f }) |x| counts[@intFromEnum(x)] += 1;
    std.debug.print("{any}\n", .{counts});
}

3
a
0 4
true
{ 1, 0, 1, 0, 2 }

@intFromEnum goes from enum to integer; @enumFromInt goes back, taking its target type from context. With no explicit values, they count up from zero in declaration order, which makes @intFromEnum(a) < @intFromEnum(b) a test of declaration order; IRON LEDGER's clock.zig has a test that checks its day phases are in the right order exactly this way. The last lines show the most common use of the integer: indexing an array of counters by enum value.

13.5 Non-exhaustive enums and typed IDs

An enum whose last member is _ is non-exhaustive: it declares that any value of the tag type is valid, not only the named ones. It must have an explicit tag type. IRON LEDGER uses this for every entity ID:

nonexh.zig

const std = @import("std");

pub const PersonId = enum(u32) { none = 0, _ };
pub const UnitId = enum(u32) { none = 0, _ };

fn describe(id: PersonId) void {
    switch (id) {
        .none => std.debug.print("nobody\n", .{}),
        _ => std.debug.print("person #{d}\n", .{@intFromEnum(id)}),
    }
}

pub fn main() void {
    const kai: PersonId = @enumFromInt(7);
    describe(kai);
    describe(.none);
    std.debug.print("{}\n", .{kai == .none});
    std.debug.print("{d} bytes, same as u32\n", .{@sizeOf(PersonId)});
}
person #7
nobody
false
4 bytes, same as u32

Read enum(u32) { none = 0, _ } as "a u32 with one named value, none, and every other number allowed". At runtime a PersonId is four bytes, exactly a u32; it costs nothing. But it is a distinct type. Its purpose is the error below:

A function that wants a person's ID will not accept a unit's ID, even though both are 32-bit numbers underneath. With plain u32 IDs this bug compiles and corrupts a save file; with typed IDs it does not compile. And .none gives a spelled-out "no one" value instead of a magic zero.

A switch on a non-exhaustive enum uses _ as its catch-all arm for the unnamed values, as describe shows. It is different from else: else would also cover any named values you left out, while _ covers only the unnamed ones, so the exhaustiveness check still protects the names.

The whole pattern, as the game writes it. 
// src/domain/types.zig
pub const PersonId = enum(u32) { none = 0, _ };
pub const UnitId = enum(u32) { none = 0, _ };
pub const ForceId = enum(u32) { none = 0, _ };
pub const ContractId = enum(u32) { none = 0, _ };
Converting is explicit and rare: @enumFromInt(n) where a user typed a number, @intFromEnum(id) where the ID is written to a file or printed. Everywhere in between, the ID is opaque.

13.6 From strings to enums

User input arrives as text. std.meta.stringToEnum looks a name up and returns an optional:

stringto.zig

const std = @import("std");

const Role = enum { mekwarrior, tech, doctor, admin };

pub fn main() void {
    const inputs = [_][]const u8{ "tech", "doctor", "pilot", "Tech" };
    for (inputs) |s| {
        if (std.meta.stringToEnum(Role, s)) |r| {
            std.debug.print("{s} -> {any}\n", .{ s, r });
        } else {
            std.debug.print("{s} -> not a role\n", .{s});
        }
    }
}
tech -> .tech
doctor -> .doctor
pilot -> not a role
Tech -> not a role

The match is exact and case-sensitive, so "Tech" is rejected; lower-case the input first if you want to be lenient. Together with @tagName this gives you a free, always-in-sync parser and printer for any enum: the names in the source are the names in the file format.

To iterate over every value, std.enums.values returns them in declaration order, and @typeInfo can count them:

fields.zig

const std = @import("std");

const Role = enum { mekwarrior, tech, doctor, admin };

pub fn main() void {
    // Walk every value of an enum.
    for (std.enums.values(Role)) |r| {
        std.debug.print("{d}: {s}\n", .{ @intFromEnum(r), @tagName(r) });
    }
    std.debug.print("{d} roles\n", .{@typeInfo(Role).@"enum".fields.len});
}
0: mekwarrior
1: tech
2: doctor
3: admin
4 roles

13.7 Enum literals

What is .tech on its own, before it meets a type? Zig calls it an enum literal. It is a compile-time value that becomes whichever enum the context asks for:

literal.zig

const std = @import("std");

const Role = enum { mekwarrior, tech };
const Status = enum { active, tech };

fn roleName(r: Role) []const u8 {
    return @tagName(r);
}

pub fn main() void {
    std.debug.print("{s}\n", .{roleName(.tech)}); // .tech becomes Role.tech
    const s: Status = .tech; // the same literal, a different enum
    std.debug.print("{s}\n", .{@tagName(s)});
    const lit = .tech; // no context: an enum literal, not yet any enum
    std.debug.print("{any}\n", .{@TypeOf(lit)});
}
tech
tech
@EnumLiteral()

The same literal .tech became a Role in the call and a Status in the declaration, because both enums have a member with that name. Assigned to a plain const with no type, it stays an enum literal (@EnumLiteral()) and can be used later wherever an enum with that member is expected. You will see enum literals as lightweight options in the standard library, for example the .real in std.Io.Clock.now(.real, io) and the .scalar in std.mem.TokenIterator(u8, .scalar).

13.8 When to reach for an enum

A few habits will serve you well. If a value can only ever be one of a fixed list of things, it is an enum, even when there are only two of them: enum { attacker, defender } reads better than a bool called is_attacker, and it can grow to three sides without a rewrite. If you find a u8 whose comment says "0 = green, 1 = regular, 2 = veteran", it is an enum with an explicit tag type, and the comment becomes the member names. If a function takes a string and immediately compares it against a handful of known words, parse it once with stringToEnum at the edge and pass the enum inward, so the rest of the program never sees the text.

The one thing an enum cannot do is carry data with each alternative. A key press is enter or escape or a character, and which character; a command is advance_day or hire, and whom. For that you need the enum's bigger sibling, the tagged union, which is the subject of Chapter 14. Everything you learned here, the leading-dot literals, exhaustive switch, @tagName, carries over unchanged.

In IRON LEDGER. The roles enum is the largest in the domain layer, and its salary method is the canonical exhaustive switch:

Elsewhere the same ideas recur: src/main.zig prints @tagName(c.status) and @intFromEnum(c.id) in its reports; src/sim/clock.zig tests that @intFromEnum(DayPhase.travel) < @intFromEnum(DayPhase.supply_consumption); and the typed IDs in src/domain/types.zig keep a PersonId from ever being handed to a function that wanted a UnitId.

Exercise 13.1 · An enum with methods warm-up

Give Role three methods: an exhaustive baseSalary with grouped arms, isCombat, and supervisor, which returns an optional Role. The last test walks every value with std.enums.values. Name the file: exercises/13-enums/ex1_roles.zig.

Solution 
//! Chapter 13, exercise 1: an enum with methods.
//! Run with:  zig test ex1_roles.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Role = enum {
    mekwarrior,
    aero_pilot,
    tech,
    astech,
    doctor,
    medic,
    admin,

    pub fn baseSalary(self: Role) i64 {
        return switch (self) {
            .mekwarrior, .aero_pilot, .doctor => 1_500,
            .tech => 800,
            .astech, .medic => 400,
            .admin => 500,
        };
    }

    pub fn isCombat(self: Role) bool {
        return switch (self) {
            .mekwarrior, .aero_pilot => true,
            else => false,
        };
    }

    /// The role that supervises this one, or null at the top.
    pub fn supervisor(self: Role) ?Role {
        return switch (self) {
            .astech => .tech,
            .medic => .doctor,
            .mekwarrior, .aero_pilot, .tech, .doctor => .admin,
            .admin => null,
        };
    }
};

test "salaries" {
    try std.testing.expectEqual(@as(i64, 1_500), Role.mekwarrior.baseSalary());
    try std.testing.expectEqual(@as(i64, 400), Role.medic.baseSalary());
    try std.testing.expectEqual(@as(i64, 500), Role.admin.baseSalary());
}

test "combat" {
    try std.testing.expect(Role.aero_pilot.isCombat());
    try std.testing.expect(!Role.tech.isCombat());
}

test "supervisor chain" {
    try std.testing.expectEqual(@as(?Role, .tech), Role.astech.supervisor());
    try std.testing.expectEqual(@as(?Role, .admin), Role.tech.supervisor());
    try std.testing.expectEqual(@as(?Role, null), Role.admin.supervisor());
}

test "payroll over every role" {
    var total: i64 = 0;
    for (std.enums.values(Role)) |r| total += r.baseSalary();
    try std.testing.expectEqual(@as(i64, 6_600), total);
}

baseSalary and supervisor name every value so that adding a role forces a decision in both. isCombat uses else deliberately: a new role is non-combat until someone says otherwise, and that default is safe.

Exercise 13.2 · Explicit tags and conversions practice

Quality is an enum(u8) with values 0 to 4. Implement improve and degrade (stepping through the integer, clamped at the ends), parse from a letter, and letter for display. Name the file: exercises/13-enums/ex2_quality.zig.

Solution 
//! Chapter 13, exercise 2: explicit tag types and conversions.
//! Run with:  zig test ex2_quality.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Unit quality grades, worst to best. The integer is the index into tables.
const Quality = enum(u8) {
    f = 0,
    d = 1,
    c = 2,
    b = 3,
    a = 4,

    /// One grade better, capped at a.
    pub fn improve(self: Quality) Quality {
        if (self == .a) return .a;
        return @enumFromInt(@intFromEnum(self) + 1);
    }

    /// One grade worse, capped at f.
    pub fn degrade(self: Quality) Quality {
        if (self == .f) return .f;
        return @enumFromInt(@intFromEnum(self) - 1);
    }

    /// Parse a single letter, either case. Anything else is null.
    pub fn parse(c: u8) ?Quality {
        return switch (std.ascii.toLower(c)) {
            'f' => .f,
            'd' => .d,
            'c' => .c,
            'b' => .b,
            'a' => .a,
            else => null,
        };
    }

    /// Upper-case letter for display.
    pub fn letter(self: Quality) u8 {
        return std.ascii.toUpper(@tagName(self)[0]);
    }
};

test "size and values" {
    try std.testing.expectEqual(@as(usize, 1), @sizeOf(Quality));
    try std.testing.expectEqual(@as(u8, 3), @intFromEnum(Quality.b));
}

test "improve and degrade clamp" {
    try std.testing.expectEqual(Quality.d, Quality.f.improve());
    try std.testing.expectEqual(Quality.a, Quality.a.improve());
    try std.testing.expectEqual(Quality.f, Quality.f.degrade());
    try std.testing.expectEqual(Quality.c, Quality.b.degrade());
}

test "parse and letter" {
    try std.testing.expectEqual(@as(?Quality, .b), Quality.parse('b'));
    try std.testing.expectEqual(@as(?Quality, .b), Quality.parse('B'));
    try std.testing.expectEqual(@as(?Quality, null), Quality.parse('x'));
    try std.testing.expectEqual(@as(u8, 'A'), Quality.a.letter());
}

test "histogram indexed by the tag" {
    var counts = [_]u32{0} ** 5;
    for ([_]Quality{ .a, .c, .a, .f }) |q| counts[@intFromEnum(q)] += 1;
    try std.testing.expectEqual([5]u32{ 1, 0, 1, 0, 2 }, counts);
}

The clamp checks come first so that @enumFromInt is only ever given 0 to 4; without them, .a.improve() would build the value 5 and panic. letter leans on @tagName so the display letter can never disagree with the source.

Exercise 13.3 · Typed IDs practice

Declare PersonId and UnitId exactly as IRON LEDGER does, then write a generator that hands out fresh IDs, a Pilot whose unit defaults to .none, and a parser from text. Name the file: exercises/13-enums/ex3_ids.zig.

Solution 
//! Chapter 13, exercise 3: typed IDs with non-exhaustive enums.
//! Run with:  zig test ex3_ids.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

pub const PersonId = enum(u32) { none = 0, _ };
pub const UnitId = enum(u32) { none = 0, _ };

/// Hands out fresh PersonIds, starting at 1.
const IdGen = struct {
    next: u32 = 1,

    pub fn newPerson(self: *IdGen) PersonId {
        const id: PersonId = @enumFromInt(self.next);
        self.next += 1;
        return id;
    }
};

/// A pilot may or may not be assigned to a unit.
const Pilot = struct {
    id: PersonId,
    unit: UnitId = .none,

    pub fn isAssigned(self: Pilot) bool {
        return self.unit != .none;
    }
};

/// Parse text like "7" into a PersonId. "0" or garbage is null.
fn parsePersonId(s: []const u8) ?PersonId {
    const n = std.fmt.parseInt(u32, s, 10) catch return null;
    if (n == 0) return null;
    return @enumFromInt(n);
}

test "ids are distinct values" {
    var gen = IdGen{};
    const a = gen.newPerson();
    const b = gen.newPerson();
    try std.testing.expect(a != b);
    try std.testing.expect(a != .none);
    try std.testing.expectEqual(@as(u32, 1), @intFromEnum(a));
    try std.testing.expectEqual(@as(u32, 2), @intFromEnum(b));
}

test "assignment uses .none as absent" {
    var gen = IdGen{};
    var p = Pilot{ .id = gen.newPerson() };
    try std.testing.expect(!p.isAssigned());
    p.unit = @enumFromInt(42);
    try std.testing.expect(p.isAssigned());
}

test "parsing" {
    try std.testing.expectEqual(@as(?PersonId, @enumFromInt(7)), parsePersonId("7"));
    try std.testing.expectEqual(@as(?PersonId, null), parsePersonId("0"));
    try std.testing.expectEqual(@as(?PersonId, null), parsePersonId("seven"));
}

test "ids cost nothing" {
    try std.testing.expectEqual(@sizeOf(u32), @sizeOf(PersonId));
}

The last test is the point of the exercise: @sizeOf(PersonId) == @sizeOf(u32). Type safety here is free at runtime. The parser refuses zero so that .none can only be produced on purpose, never by a user typing 0.

Exercise 13.4 · A day-phase state machine challenge

The phases of a campaign day are an ordered enum. Implement next (using std.enums.values), before, a label that capitalises the tag name into a buffer, and runDay, which steps from a starting phase to the end. Name the file: exercises/13-enums/ex4_phases.zig.

Solution 
//! Chapter 13, exercise 4: a day-phase state machine (challenge).
//! Run with:  zig test ex4_phases.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// The phases of one campaign day, in order.
const Phase = enum(u8) {
    travel,
    supply,
    events,
    battle,
    finances,
    decisions,

    /// The next phase, or null after the last one.
    pub fn next(self: Phase) ?Phase {
        const all = std.enums.values(Phase);
        const i = @intFromEnum(self);
        if (i + 1 >= all.len) return null;
        return all[i + 1];
    }

    /// True when `self` happens before `other`.
    pub fn before(self: Phase, other: Phase) bool {
        return @intFromEnum(self) < @intFromEnum(other);
    }

    /// Human label: the tag name with the first letter upper-cased, into buf.
    pub fn label(self: Phase, buf: []u8) []const u8 {
        const name = @tagName(self);
        @memcpy(buf[0..name.len], name);
        buf[0] = std.ascii.toUpper(buf[0]);
        return buf[0..name.len];
    }
};

/// Run every phase from `start` to the end, writing the names visited into `out`.
/// Returns how many phases ran.
fn runDay(start: Phase, out: []Phase) usize {
    var n: usize = 0;
    var p: ?Phase = start;
    while (p) |cur| : (p = cur.next()) {
        out[n] = cur;
        n += 1;
    }
    return n;
}

runDay uses while (p) |cur| : (p = cur.next()): loop while the optional holds a value, and after each pass replace it with the next phase, which becomes null after the last one. That loop shape returns in Chapter 15. IRON LEDGER's daily tick (Chapter 43) walks its DayPhase enum in the same spirit.

Check your understanding

  1. When can you write .tech instead of Role.tech?
    AnswerWhenever the expected type is known from context: a typed declaration, a parameter, a switch arm, a comparison with an existing Role.
  2. What happens when a switch over an enum leaves a value out?
    AnswerA compile error, switch must handle all possibilities, naming the unhandled value. Unless the switch has an else arm, which absorbs it silently.
  3. What do @intFromEnum and @enumFromInt do, and which one can panic?
    AnswerThey convert between an enum and its integer tag. @enumFromInt panics in safe builds if the integer matches no named value of an exhaustive enum.
  4. What does the _ at the end of enum(u32) { none = 0, _ } mean?
    AnswerThe enum is non-exhaustive: every u32 is a valid value, not only the named ones. It needs an explicit tag type.
  5. Why does IRON LEDGER use PersonId instead of u32?
    AnswerSame size, same cost, but a distinct type: passing a UnitId where a PersonId is expected is a compile error rather than a silent bug, and .none is a named absent value.
  6. How do you turn the string "doctor" into Role.doctor?
    Answerstd.meta.stringToEnum(Role, "doctor"), which returns ?Role: null if the name does not match exactly.
  7. What is the difference between else and _ as a switch arm?
    Answerelse matches every value not listed, named or not, and disables the exhaustiveness check. _ matches only the unnamed values of a non-exhaustive enum; named values must still all be handled.
What you learned.
  • const E = enum { a, b, c }; declares a closed set; write values as E.a or, with context, .a. Enums compare with ==.
  • Enums hold methods and constants like structs. switch over an enum must be exhaustive unless it has else; grouped arms use commas.
  • enum(u8) fixes the tag type; values may be assigned explicitly. @intFromEnum and @enumFromInt convert; the latter is checked.
  • enum(u32) { none = 0, _ } is a non-exhaustive enum: a typed integer with a named "none". IRON LEDGER uses it for every ID. Switch on it with _.
  • @tagName gives the name; std.meta.stringToEnum parses one; std.enums.values lists them all.
  • A bare .name is an enum literal that becomes whatever enum the context needs.
