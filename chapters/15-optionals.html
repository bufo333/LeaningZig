15. Optionals

In this chapter you will learn how Zig represents "a value that might not be there". You will write the optional type ?T, unwrap it with orelse, if, while and .?, and see why an optional pointer costs nothing. By the end you will read a chain like if (gs.person(id)) |p| if (p.born_day) |born| without slowing down.

15.1 The problem with "nothing"

Every program has values that are sometimes missing. A pilot may have no birthday on record. A lookup by name may find nobody. A parser may reach the end of the input. Most languages you have used answer this with a special value: None in Python, null or undefined in JavaScript, NULL in C. The trouble is that in those languages any variable can hold the special value, so any line of code might be the one that trips over it. "Cannot read property of undefined" is the most common runtime error in JavaScript for exactly this reason.

Zig takes a different position. A plain u32 is always a number. A plain *Pilot always points at a pilot. If a value may be absent, its type says so, and the compiler refuses to let you use it as if it were present until you have checked. The type is written with a question mark in front: ?u32 is "maybe a u32", ?*Pilot is "maybe a pointer to a Pilot", ?[]const u8 is "maybe a string".

The absent value is spelled null. It is only ever a valid value for an optional type. You cannot put null into a u32, and the compiler will tell you so.

15.2 Declaring and printing an optional

Here is the smallest program that uses one.

opt1.zig

const std = @import("std");

pub fn main() void {
    var maybe_age: ?u32 = null;
    std.debug.print("start: {?}\n", .{maybe_age});

    maybe_age = 27;
    std.debug.print("later: {?}\n", .{maybe_age});

    const shown: u32 = maybe_age orelse 0;
    std.debug.print("shown: {d}\n", .{shown});

    const nothing: ?u32 = null;
    std.debug.print("fallback: {d}\n", .{nothing orelse 0});
}
start: null
later: 27
shown: 27
fallback: 0

Four things to notice. First, the variable is declared as ?u32 and starts out as null. Second, assigning a plain 27 to it works without ceremony: a u32 coerces into a ?u32 automatically, because "definitely 27" is a fine answer to "maybe a number". The coercion never goes the other way. Third, the format specifier {?} prints an optional, showing either the value or the word null. Fourth, orelse turns the optional back into a plain value by supplying what to use when it is null.

What happens if you try to use a ?u32 where a u32 is required, without unwrapping it?

const std = @import("std");

pub fn main() void {
    const age: ?u32 = 27;
    const n: u32 = age; // error: cannot assign ?u32 to u32
    std.debug.print("{d}\n", .{n});
}
opt2.zig:5:20: error: expected type 'u32', found '?u32'
    const n: u32 = age; // error: cannot assign ?u32 to u32
                   ^~~
opt2.zig:5:20: note: cannot convert optional to payload type
opt2.zig:5:20: note: consider using '.?', 'orelse', or 'if'

Read that error message slowly, because you will see it often in your first weeks: "cannot convert optional to payload type", followed by a helpful list of the three ways to fix it. The payload is the value inside the optional. The rest of this chapter is those three ways.

15.3 Functions that return optionals

The most common place an optional appears is as the return type of a search. Here is a roster and a function that finds a name's position in it.

opt3.zig

const std = @import("std");

const pilots = [_][]const u8{ "Kerensky", "Steiner", "Liao" };

/// Position of a pilot in the roster, or null if not there.
fn indexOfPilot(name: []const u8) ?usize {
    for (pilots, 0..) |p, i| {
        if (std.mem.eql(u8, p, name)) return i;
    }
    return null;
}

pub fn main() void {
    std.debug.print("Steiner -> {?}\n", .{indexOfPilot("Steiner")});
    std.debug.print("Davion  -> {?}\n", .{indexOfPilot("Davion")});
}
Steiner -> 1
Davion  -> null

The function's return type is ?usize. Inside it, return i returns a plain usize, which coerces to the optional. return null is the "not found" answer. In Python you might return -1 or raise an exception; in C you would return -1 or SIZE_MAX and hope every caller remembers to check. Here, every caller must deal with the possibility of null, because a ?usize cannot be used as an index until it is unwrapped.

15.4 orelse: a fallback, or an early exit

You have already seen x orelse 0: if x is present, use its value; otherwise use 0. The right-hand side of orelse can be any expression of the payload type. But it can also be something that does not produce a value at all: a return, a break, a continue, or unreachable. This is the form you will see the most in real code.

opt4.zig

const std = @import("std");

const pilots = [_][]const u8{ "Kerensky", "Steiner", "Liao" };

fn indexOfPilot(name: []const u8) ?usize {
    for (pilots, 0..) |p, i| {
        if (std.mem.eql(u8, p, name)) return i;
    }
    return null;
}

/// The pilot after `name` in the roster, or null if `name` is unknown
/// or is the last one. `orelse return null` ends the function early.
fn nextPilot(name: []const u8) ?[]const u8 {
    const i = indexOfPilot(name) orelse return null;
    if (i + 1 >= pilots.len) return null;
    return pilots[i + 1];
}

pub fn main() void {
    std.debug.print("after Kerensky: {?s}\n", .{nextPilot("Kerensky")});
    std.debug.print("after Liao:     {?s}\n", .{nextPilot("Liao")});
    std.debug.print("after Davion:   {?s}\n", .{nextPilot("Davion")});

    // We *know* Steiner is in the roster, so null is impossible here.
    const i = indexOfPilot("Steiner") orelse unreachable;
    std.debug.print("Steiner sits at {d}\n", .{i});
}
after Kerensky: Steiner
after Liao:     null
after Davion:   null
Steiner sits at 1

Look at the first line of nextPilot: const i = indexOfPilot(name) orelse return null;. If the lookup finds nothing, the function returns right there and the rest of the body never runs. If it finds something, i is a plain usize, not an optional, and the code after it is free to use it as an index. This one line replaces a whole if (x == null) return null; block, and it is why Zig functions that do several lookups in a row stay flat instead of nesting.

The last form, orelse unreachable, says "I know this is never null". In a Debug build, if you are wrong, the program panics with a clear message. In a release build with safety off, it is undefined behaviour. Use it only when the surrounding code has already guaranteed the value is there, as in the example: we looked up a name that is literally in the array.

The format specifier {?s} is worth remembering: it prints an optional string, showing null when absent. In general, ? followed by the specifier you would use for the payload works for any optional.

15.5 if (x) |v|: run code only when present

When you want to do something with the value if it is there and something else if it is not, use if with a capture. The bars around v introduce a new constant holding the unwrapped payload, visible only inside the following block.

opt5.zig

const std = @import("std");

fn describe(slot: ?u8) void {
    if (slot) |n| {
        std.debug.print("slot holds {d}\n", .{n});
    } else {
        std.debug.print("slot is empty\n", .{});
    }
}

pub fn main() void {
    describe(4);
    describe(null);

    // if/else as an expression, choosing a value
    const a: ?u8 = 4;
    const b: ?u8 = null;
    const tonnage_a: u8 = if (a) |v| v * 10 else 50;
    const tonnage_b: u8 = if (b) |v| v * 10 else 50;
    std.debug.print("{d} {d}\n", .{ tonnage_a, tonnage_b });

    // comparing with null directly, no unwrap needed
    std.debug.print("a == null? {}\n", .{a == null});
    std.debug.print("b == null? {}\n", .{b == null});
    std.debug.print("a == 4?    {}\n", .{a == 4});
}
slot holds 4
slot is empty
40 50
a == null? false
b == null? true
a == 4?    true

Three forms in one file. The statement form, if (slot) |n| { … } else { … }, is what you reach for most of the time. The expression form, if (a) |v| v * 10 else 50, produces a value and is handy for computing a field from an optional lookup. IRON LEDGER uses exactly this shape to get a unit's tonnage from a catalogue entry that might be missing: const tonnage: u8 = if (chassis_mod.find(u.chassis_key)) |d| d.tonnage else 50;.

The third form is comparison. You may compare an optional to null directly with == and !=, and you may even compare it to a plain value: a == 4 is true when a holds 4 and false when it is null or holds something else. This is a common way to write a guard clause: if (p.leave_until_day != null) ….

Reading the bars. Once you have seen |v| after an if, a while, a for or a catch, you have seen the whole idea: the thing between the bars is the unwrapped value for the block that follows. It is always a fresh constant. If you need to modify the payload in place, capture a pointer to it with |*v|, which works when the optional itself is a variable you can address, as in if (self.gs) |*g| g.deinit(); from the game's terminal client.

15.6 .?: assert it is present

The third unwrapping form is the shortest. Putting .? after an optional gives you the payload, and if the optional is null the program panics.

opt6.zig

const std = @import("std");

pub fn main() void {
    const present: ?u32 = 42;
    const absent: ?u32 = null;

    std.debug.print("present.? = {d}\n", .{present.?});
    std.debug.print("about to unwrap absent...\n", .{});
    std.debug.print("absent.? = {d}\n", .{absent.?});
}
present.? = 42
about to unwrap absent...
thread 12345 panic: attempt to use null value
ch15/opt6.zig:9:49: 0x… in main (opt6)
    std.debug.print("absent.? = {d}\n", .{absent.?});
                                                ^
<zig>/lib/std/start.zig:698:59: 0x… in callMain (opt6)
    if (fn_info.params.len == 0) return wrapMain(root.main());
…

That is a real panic with a real stack trace pointing at the exact expression that failed. .? is the same as orelse unreachable, spelled more briefly. Use it when nullness would be a bug in your program, not a normal outcome. A lookup by a key you just inserted, a value you checked two lines earlier, an ID handed to you by code that only produces valid IDs: those are .? situations. User input is never a .? situation.

Trap. Beginners sprinkle .? everywhere to make the compiler stop complaining. That converts a compile-time check into a run-time crash, which is exactly what optionals exist to prevent. If you find yourself typing .?, ask "what should happen if this is null?" If the honest answer is "that would be a bug", keep it. If the answer is "then skip it" or "then use a default", you want if or orelse instead.

15.7 while (it.next()) |v|: iterators

Combine an optional-returning function with a while capture and you have Zig's iterator protocol. There is no interface to implement and no special syntax to learn: any function that returns ?T can drive a loop, and the loop stops the first time it returns null.

opt7.zig

const std = @import("std");

/// Counts down from `n` to 1, then is exhausted.
const Countdown = struct {
    n: u32,

    fn next(self: *Countdown) ?u32 {
        if (self.n == 0) return null;
        const v = self.n;
        self.n -= 1;
        return v;
    }
};

pub fn main() void {
    var cd = Countdown{ .n = 3 };
    while (cd.next()) |v| {
        std.debug.print("t-minus {d}\n", .{v});
    }

    var words = std.mem.tokenizeScalar(u8, "hire  pilot  Steiner", ' ');
    while (words.next()) |w| {
        std.debug.print("word: {s}\n", .{w});
    }
}
t-minus 3
t-minus 2
t-minus 1
word: hire
word: pilot
word: Steiner

The standard library's tokenizers, splitters, directory walkers and hash-map iterators all work this way. You saw std.mem.tokenizeScalar in Chapter 11; the while (words.next()) |w| line here is why its next returns ?[]const u8. Writing your own iterator, as Countdown does, is a matter of keeping some state in a struct and writing one next method that returns null when done.

15.8 What an optional costs

An optional needs somewhere to record "present or not". For most types that means an extra byte, padded up to the type's alignment. For pointers it costs nothing at all, because a pointer is never allowed to be zero in Zig, so the value zero is free to mean null. This is called the null pointer optimisation, and it means ?*T is exactly as cheap as the raw nullable pointer a C programmer would use, with the compiler doing the checking the C programmer had to do by hand.

opt8.zig

const std = @import("std");

pub fn main() void {
    std.debug.print("u32:    {d} bytes\n", .{@sizeOf(u32)});
    std.debug.print("?u32:   {d} bytes\n", .{@sizeOf(?u32)});
    std.debug.print("*u32:   {d} bytes\n", .{@sizeOf(*u32)});
    std.debug.print("?*u32:  {d} bytes\n", .{@sizeOf(?*u32)});
    std.debug.print("[]u8:   {d} bytes\n", .{@sizeOf([]u8)});
    std.debug.print("?[]u8:  {d} bytes\n", .{@sizeOf(?[]u8)});
}
u32:    4 bytes
?u32:   8 bytes
*u32:   8 bytes
?*u32:  8 bytes
[]u8:   16 bytes
?[]u8:  16 bytes

?u32 doubles in size because of alignment. ?*u32 and ?[]u8 do not grow at all: a slice is a pointer plus a length, and the pointer part carries the null. So when you design a function that "finds a thing or not", returning an optional pointer, ?*const Chassis, is not a compromise. It is the natural shape.

15.9 Optional fields and chains

Optionals are how a struct expresses "not yet" or "not applicable". A person hired by a test might have no birthday. A pilot on leave has a day the leave ends; a pilot not on leave has none. Rather than a magic number like 0 or -1, the field is an optional with a default of null.

opt9.zig

const std = @import("std");

const Person = struct {
    name: []const u8,
    born_day: ?i32 = null,
    leave_until_day: ?u32 = null,

    fn isAvailable(self: Person, day: u32) bool {
        if (self.leave_until_day) |until| return day > until;
        return true;
    }
};

const Unit = struct {
    name: []const u8,
    pilot: ?*const Person = null,
};

pub fn main() void {
    const ada = Person{ .name = "Ada", .born_day = 5 };
    const bo = Person{ .name = "Bo", .leave_until_day = 30 };
    const day: u32 = 20;

    const units = [_]Unit{
        .{ .name = "Locust", .pilot = &ada },
        .{ .name = "Marauder", .pilot = &bo },
        .{ .name = "Atlas" },
    };

    for (units) |u| {
        if (u.pilot) |p| {
            if (p.born_day) |born| {
                const age_days = @as(i64, day) - @as(i64, born);
                std.debug.print("{s}: pilot {s}, age {d} days\n", .{ u.name, p.name, age_days });
            } else {
                std.debug.print("{s}: pilot {s}, birthday unknown\n", .{ u.name, p.name });
            }
            if (!p.isAvailable(day)) std.debug.print("  ({s} is on leave)\n", .{p.name});
        } else {
            std.debug.print("{s}: no pilot assigned\n", .{u.name});
        }
    }

    // A chain: only runs when every link is present.
    for (units) |u| if (u.pilot) |p| if (p.isAvailable(day)) {
        std.debug.print("ready: {s} in the {s}\n", .{ p.name, u.name });
    };
}
Locust: pilot Ada, age 15 days
Marauder: pilot Bo, birthday unknown
  (Bo is on leave)
Atlas: no pilot assigned
ready: Ada in the Locust

Two optionals are nested here: a unit may have no pilot, and a pilot may have no birthday. Each if … |x| peels one layer. The last loop shows the compact chain form, if (u.pilot) |p| if (p.isAvailable(day)) { … }: an if whose body is another if, with no braces between them. It reads as "if there is a pilot, and the pilot is available". You will see this idiom throughout IRON LEDGER, and once you have written it a few times it stops looking odd. Note the semicolon after the closing brace: because the whole thing is the body of a brace-less for, it is a single statement and needs one.

Inside isAvailable, the pattern if (self.leave_until_day) |until| return day > until; followed by return true; is the optional version of a guard clause. It is often clearer than one long boolean expression.

15.10 An optional of an optional

Because ?T is a type like any other, ??T is legal, and it is not the same as ?T. "Present, but holding null" and "absent" are different values. You will rarely want this, but it comes up when a generic container stores optionals, and it explains why orelse only removes one layer at a time.

opt10.zig

const std = @import("std");

pub fn main() void {
    const inner: ?u8 = null;
    const outer: ??u8 = inner;
    std.debug.print("outer == null? {}\n", .{outer == null});
    if (outer) |i| {
        std.debug.print("outer present, inner == null? {}\n", .{i == null});
    }
}
outer == null? false
outer present, inner == null? true

15.11 Why no null by default

Step back and look at what the type system has bought you. Every place a value might be missing is marked in the type. Every place that marking is removed is visible in the code: an orelse, an if capture, a .?. The compiler will not let you forget a check, and when you deliberately assert with .?, a Debug build tells you the exact line if you were wrong. Compare this to hunting for the origin of a null that surfaced three modules away from where it was created.

The price is a little typing. In practice, most Zig programs have far fewer optionals than JavaScript programs have undefined checks, because most values simply are never absent, and their types say so.

In IRON LEDGER. The simulation looks things up by typed ID constantly, and every lookup returns an optional pointer. GameState.person in game/src/sim/state.zig is one line, return self.people.getPtr(id);, with return type ?*person_mod.Person. Callers pick the unwrapping form that fits: a command handler writes const p = gs.person(id) orelse return Error.UnknownPerson; because an unknown ID is a user mistake to report; a query writes if (gs.person(u.pilot)) |pilot| if (pilot.isAvailable(day)) … because a unit with no pilot is simply skipped; and code that has just created a unit writes gs.unit(seat).? because failure there would be a bug. Optional fields carry "not yet" state on the domain structs: leave_until_day: ?u32 = null, wound_heal_day: ?u32 = null, born_day: ?i32 = null. And the catalogue lookup in game/src/domain/chassis.zig is the shape from section 15.8: 
pub fn find(key: []const u8) ?*const Chassis {
    for (catalog) |*c| {
        if (std.mem.eql(u8, c.key, key)) return c;
    }
    return null;
}

Exercise 15.1 · A lookup that may find nothing warm-up

Implement find, which returns the index of a name in a fixed roster or null, and after, which returns the following name using orelse return null. File: exercises/15-optionals/ex1_lookup.zig.

Solution 
//! Chapter 15, exercise 1: a lookup that may find nothing.
//! Run with:  zig test ex1_lookup.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const roster = [_][]const u8{ "Kerensky", "Steiner", "Liao", "Davion" };

/// Return the index of `name` in the roster, or null when it is not there.
fn find(name: []const u8) ?usize {
    for (roster, 0..) |entry, i| {
        if (std.mem.eql(u8, entry, name)) return i;
    }
    return null;
}

/// Return the name that follows `name`, or null when `name` is unknown
/// or already the last one. Use `orelse return null`.
fn after(name: []const u8) ?[]const u8 {
    const i = find(name) orelse return null;
    if (i + 1 >= roster.len) return null;
    return roster[i + 1];
}

test "find present and absent" {
    try std.testing.expectEqual(@as(?usize, 1), find("Steiner"));
    try std.testing.expectEqual(@as(?usize, 3), find("Davion"));
    try std.testing.expectEqual(@as(?usize, null), find("Marik"));
}

test "after" {
    try std.testing.expectEqualStrings("Liao", after("Steiner").?);
    try std.testing.expect(after("Davion") == null);
    try std.testing.expect(after("Marik") == null);
}

find returns a plain usize from inside the loop and null after it; both coerce to ?usize. In after, the orelse return null makes i a plain index for the rest of the function.

Exercise 15.2 · Defaults and first-present practice

Write four small functions: a default with orelse, a chain of orelse that picks the first present of three, a sum over a slice of ?u32 using if captures, and a count of the null entries using == null. File: exercises/15-optionals/ex2_orelse.zig.

Solution 
//! Chapter 15, exercise 2: defaults and first-present.
//! Run with:  zig test ex2_orelse.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// The tonnage of a unit, or 50 when the catalogue had no entry.
fn tonnageOr50(found: ?u8) u8 {
    return found orelse 50;
}

/// The first of three optionals that is present, or null if none is.
fn firstPresent(a: ?u32, b: ?u32, c: ?u32) ?u32 {
    return a orelse b orelse c;
}

/// Sum of the present values only. Use `if (x) |v|`.
fn sumPresent(values: []const ?u32) u32 {
    var total: u32 = 0;
    for (values) |maybe| {
        if (maybe) |v| total += v;
    }
    return total;
}

/// How many are null? Use `== null`.
fn countMissing(values: []const ?u32) usize {
    var n: usize = 0;
    for (values) |maybe| {
        if (maybe == null) n += 1;
    }
    return n;
}

test "tonnageOr50" {
    try std.testing.expectEqual(@as(u8, 75), tonnageOr50(75));
    try std.testing.expectEqual(@as(u8, 50), tonnageOr50(null));
}

test "firstPresent" {
    try std.testing.expectEqual(@as(?u32, 2), firstPresent(null, 2, 3));
    try std.testing.expectEqual(@as(?u32, 3), firstPresent(null, null, 3));
    try std.testing.expectEqual(@as(?u32, null), firstPresent(null, null, null));
}

test "sumPresent and countMissing" {
    const vals = [_]?u32{ 1, null, 4, null, 10 };
    try std.testing.expectEqual(@as(u32, 15), sumPresent(&vals));
    try std.testing.expectEqual(@as(usize, 2), countMissing(&vals));
}

a orelse b orelse c works because orelse is right-associative: a orelse (b orelse c). Its right-hand side is a ?u32, so the whole expression is still an optional, which is what the test expects.

Exercise 15.3 · Write your own iterator practice

Give Range a next method that returns ?u32, then write sum as a while (it.next()) |v| loop. File: exercises/15-optionals/ex3_iterator.zig.

Solution 
//! Chapter 15, exercise 3: write your own iterator.
//! Run with:  zig test ex3_iterator.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Yields `start`, `start + step`, ... while the value is below `end`.
const Range = struct {
    next_value: u32,
    end: u32,
    step: u32,

    fn init(start: u32, end: u32, step: u32) Range {
        return .{ .next_value = start, .end = end, .step = step };
    }

    /// Return the next value, or null once the range is exhausted.
    fn next(self: *Range) ?u32 {
        if (self.next_value >= self.end) return null;
        const v = self.next_value;
        self.next_value += self.step;
        return v;
    }
};

/// Drain an iterator with `while (it.next()) |v|` and add up the values.
fn sum(it: *Range) u32 {
    var total: u32 = 0;
    while (it.next()) |v| total += v;
    return total;
}

test "range yields then stops" {
    var r = Range.init(0, 10, 3);
    try std.testing.expectEqual(@as(?u32, 0), r.next());
    try std.testing.expectEqual(@as(?u32, 3), r.next());
    try std.testing.expectEqual(@as(?u32, 6), r.next());
    try std.testing.expectEqual(@as(?u32, 9), r.next());
    try std.testing.expectEqual(@as(?u32, null), r.next());
    try std.testing.expectEqual(@as(?u32, null), r.next());
}

test "sum drains it" {
    var r = Range.init(1, 5, 1);
    try std.testing.expectEqual(@as(u32, 10), sum(&r));
    var empty = Range.init(5, 5, 1);
    try std.testing.expectEqual(@as(u32, 0), sum(&empty));
}

next takes *Range because it must change the stored counter. Once exhausted it keeps returning null, which is the polite behaviour for an iterator and is what the last two assertions check.

Exercise 15.4 · Optional fields and optional pointers challenge

Complete isAvailable (a guard on an optional field), oldest (returns ?*const Person, skipping people with no birthday) and firstAvailable. File: exercises/15-optionals/ex4_fields.zig.

Solution 
//! Chapter 15, exercise 4: optional fields and optional pointers.
//! Run with:  zig test ex4_fields.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Person = struct {
    name: []const u8,
    born_day: ?i32 = null,
    leave_until_day: ?u32 = null,

    /// Available unless on leave that has not yet ended.
    fn isAvailable(self: Person, day: u32) bool {
        if (self.leave_until_day) |until| return day > until;
        return true;
    }
};

/// Pointer to the person with the smallest known birthday, or null if
/// nobody has a birthday on record.
fn oldest(people: []const Person) ?*const Person {
    var best: ?*const Person = null;
    for (people) |*p| {
        const born = p.born_day orelse continue;
        if (best) |b| {
            if (born < b.born_day.?) best = p;
        } else {
            best = p;
        }
    }
    return best;
}

/// Pointer to the first available person, or null.
fn firstAvailable(people: []const Person, day: u32) ?*const Person {
    for (people) |*p| if (p.isAvailable(day)) return p;
    return null;
}

const crew = [_]Person{
    .{ .name = "Ada", .born_day = 200, .leave_until_day = 40 },
    .{ .name = "Bo" },
    .{ .name = "Cy", .born_day = 120 },
};

test "isAvailable" {
    try std.testing.expect(!crew[0].isAvailable(30));
    try std.testing.expect(crew[0].isAvailable(41));
    try std.testing.expect(crew[1].isAvailable(0));
}

test "oldest skips unknown birthdays" {
    const o = oldest(&crew) orelse return error.TestUnexpectedResult;
    try std.testing.expectEqualStrings("Cy", o.name);
    const nobody = [_]Person{ .{ .name = "X" }, .{ .name = "Y" } };
    try std.testing.expect(oldest(&nobody) == null);
}

test "firstAvailable" {
    try std.testing.expectEqualStrings("Bo", firstAvailable(&crew, 10).?.name);
    try std.testing.expectEqualStrings("Ada", firstAvailable(&crew, 50).?.name);
    const all_away = [_]Person{.{ .name = "Z", .leave_until_day = 99 }};
    try std.testing.expect(firstAvailable(&all_away, 10) == null);
}

In oldest, orelse continue skips a person with no birthday in one line. The running best is itself an optional pointer, so the body uses an if … |b| … else to distinguish "no candidate yet" from "compare with the candidate". The b.born_day.? is safe because we only ever store people whose birthday is present.

Check your understanding

  1. What does the compiler say if you assign a ?u32 to a u32?
    Answer"expected type 'u32', found '?u32'", with a note that you cannot convert an optional to its payload type, and a hint to use .?, orelse or if.
  2. What is the difference between x orelse 0 and x orelse return?
    AnswerThe first substitutes 0 when x is null and continues. The second leaves the function when x is null; the variable being assigned only exists on the present path.
  3. When is .? appropriate?
    AnswerWhen null would be a bug, not a normal outcome: the value was produced or checked by code you control. It panics in Debug if it is wrong. Never use it on user input.
  4. How many bytes does ?*u32 take on a 64-bit machine, and why?
    Answer8, the same as *u32. Pointers cannot be zero, so the zero bit pattern represents null with no extra storage.
  5. How does a while loop know when an iterator is finished?
    Answerwhile (it.next()) |v| stops the first time next returns null. Any function returning ?T can be an iterator.
  6. Is if (a) |v| if (v.b) |w| … legal, and what does it mean?
    AnswerYes. The body of the outer if is another if. It runs the innermost block only when both a and a.b are present.
  7. Can an optional be compared with ==?
    AnswerYes, both to null and to a plain value of the payload type. a == 4 is false when a is null.
What you learned.
  • ?T is a type that holds either a T or null; a T coerces into it, never the other way.
  • Unwrap with orelse (a fallback value, or return/break/continue/unreachable), with if (x) |v| … else …, or with .?, which panics on null.
  • while (it.next()) |v| is the iterator protocol; any ?T-returning function drives it.
  • ?*T and ?[]T cost nothing extra; ?u32 costs padding.
  • Optional fields with = null defaults express "not yet"; chains of captures peel one layer each.
  • The point is that every possible absence is in the type, and every place you remove it is visible in the code.
