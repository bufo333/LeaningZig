46. Battles and events

In this chapter you read the two places where dice decide things: the battle resolver, which collapses an engagement into one opposed roll and then does a great deal of bookkeeping, and the event decks, which turn a monthly roll into either an automatic consequence or a decision waiting in the inbox. Both are built from tagged unions and a seeded stream, and both are tested by asserting on outcomes across many rolls rather than on any single roll.

What you need from earlier chapters. Chapter 14 (tagged unions with many payload types, and an exhaustive switch that lists every tag), Chapter 6 (labeled blocks that yield a value with break :blk, and an if … else if chain as an expression), Chapter 34 (seeded random draws), Chapter 4 (widening with @as(i32, …) before adding signed and unsigned quantities), Chapter 15 (optional fields as "not yet") and Chapter 41 (the named RNG streams).

46.1 When a battle happens

A battle is not a screen and not a turn. It is a phase of the daily tick (Chapter 43) that asks each active contract whether an engagement is due:

src/sim/battle.zig
pub fn runDaily(gs: *GameState) !void {
    var it = gs.contracts.iterator();
    while (it.next()) |entry| {
        const c = entry.value_ptr;
        if (c.status != .active or c.kind.isGarrisonClass()) continue;
        if (c.next_battle_day == null) {
            c.next_battle_day = gs.clock.day_index + nextBattleGap(gs, c);
            continue;
        }
        if (gs.clock.day_index >= c.next_battle_day.?) {
            try resolveEngagement(gs, c);
            c.next_battle_day = gs.clock.day_index + nextBattleGap(gs, c);
        }
    }
}

The optional field next_battle_day: ?u32 is the "not yet" pattern from Chapter 15: null means no battle has been scheduled, so schedule one; otherwise compare the integer day and resolve when it arrives. nextBattleGap rolls the gap from the .battle stream, so the rhythm of a contract is itself seeded.

46.2 One roll decides the engagement

resolveEngagement is three hundred lines and there is no map and no turns. The player's side is built by walking the company's lances, summing each hull's battle value adjusted for damage, ammunition on hand and the pilot's skill with fatigue and injury penalties, then scaling by campaign modifiers (supplies, morale, recon, air cover, support lances). The enemy is a fraction of that, set by contract kind, scenario and a variance roll. Then one roll:

pub fn resolveEngagement(gs: *GameState, c: *contract_mod.Contract) !void {
    // Where and in what (12C.10): the world's ground, the day's weather.
    const env: terrain_mod.Environment = blk: {
        const world = planet_mod.find(c.planet_key) orelse break :blk .{};
        const t = terrain_mod.terrainOf(world);
        break :blk .{ .terrain = t, .weather = terrain_mod.rollWeather(&gs.rng, .battle, t) };
    };
    var player = try playerSideIn(gs, c, env);
    defer player.engaged.deinit(gs.allocator());
    if (player.engaged.items.len == 0) {
        c.score -= 2;
        try gs.log(.battle, .{ .company = c.assigned_company, .contract = c.id }, "[AAR] {s}: no combat-effective units — objective conceded", .{@tagName(c.kind)});
        return;
    }

    // What kind of fight this is (12C.9, AtB scenario table): it scales
    // the enemy, tilts the roll, weights the score and decides what a
    // held field is worth.
    const scenario = @import("../domain/scenario.zig").roll(&gs.rng, .battle, c.kind);

    // Enemy: strength relative to the player's committed BV, pirate rabble
    // to house regulars by employer's foe.
    const variance: types.Bp = (@as(types.Bp, gs.rng.roll2d6(.battle)) - 7) * 500;
    var enemy_bv = types.applyBp(types.applyBp(types.applyBp(player.bv, contract_mod.enemyStrengthBp(c.kind) + variance), scenario.enemy_bp), gs.diff().enemy_bp);
    // …
    const enemy_power = enemy_elem.effectivePower(.{});

    // One opposed roll decides the engagement (rounds within are abstracted;
    // ARCH §7 steps 3–4 collapse into the margin).
    const scenario_mod: i32 = @as(i32, scenario.roll_mod) + (if (player.mods.recon_quality > 0) @as(i32, scenario.scout_bonus) else 0) + env.rollMod();
    // Close terrain evens the odds: numbers count for less in the woods and the streets.
    const ratio_bonus: i32 = if (env.close()) @min(ratioBonus(player.power, enemy_power), 2) else ratioBonus(player.power, enemy_power);
    var roll = @as(i32, gs.rng.roll2d6(.battle)) + ratio_bonus + scenario_mod;
    // Edge (12B.6): a pilot with Edge to spend re-rolls a lost engagement once per contract.
    var edge_used_by: ?*person_mod.Person = null;
    if (roll < 6) {
        for (player.engaged.items) |uid| {
            const u = gs.unit(uid) orelse continue;
            const p = gs.person(u.pilot) orelse continue;
            if (p.has("edge") and !p.edge_spent) {
                p.edge_spent = true;
                edge_used_by = p;
                roll = @as(i32, gs.rng.roll2d6(.battle)) + ratio_bonus + scenario_mod;
                break;
            }
        }
    }
    const outcome: autoresolve.Outcome = if (roll >= 11) .decisive_victory //
        else if (roll >= 8) .victory //
        else if (roll >= 6) .draw //
        else if (roll >= 4) .defeat //
        else .rout;

    // Player losses scale with how badly it went. // TUNE
    const hit_pct: u32 = switch (outcome) {
        .decisive_victory => 8,
        .victory => 15,
        .draw => 25,
        .defeat => 40,
        .rout => 55,
    };
    // … three hundred lines of consequences …
}

Several idioms you know are working together. The environment is computed in a labeled block (Chapter 6) that can bail out early with break :blk .{} when the planet is unknown. Every dice call names .battle, so the market is untouched by a fight. The variance is basis points around zero: 2d6 minus 7 gives a symmetric spread, times 500, added to a base strength multiplier, then applied with applyBp three times in a chain (contract kind, scenario, difficulty). The roll modifiers are widened to i32 with @as before being added, because roll2d6 returns u8 and a modifier can be negative; Chapter 4 warned that mixing signed and unsigned needs an explicit widening. The outcome is an if chain as an expression, producing a five-variant enum from autoresolve.zig, and the loss percentages are an exhaustive switch over it.

Everything after the outcome is bookkeeping: which hulls are hit and where, who is wounded or killed, what ammunition was spent, what salvage the trucks can haul, what the contract's score and the pilots' records gain, and a multi-line after-action report written to the log with gs.log(.battle, …). The function is long because the report is detailed, but it is straight-line code with no state of its own: every fact it needs is in gs, every change it makes is to gs.

46.3 Testing dice

You cannot assert that a particular battle is won; you can assert that stronger sides win more. The tests at the bottom of battle.zig have names like "battles resolve with consequences and stronger forces win more", "hard hits wound pilots: a season of fighting sends someone to the medbay", and "9B: dry mounts are silenced — ammo is combat power". Each builds a company, runs many engagements with a fixed seed, and asserts on aggregates (wins over a season, at least one wound, a power number that drops when the ammunition is gone). Because the seed is fixed the aggregates are in fact exact numbers, but the assertions are written as bounds so that a re-tuning of the loss table does not break them for no reason. That is the same discipline as the turnover test in Chapter 43.

46.4 Events: a union of effects

Contract events use the same tagged-union idea as commands, at a smaller scale. An event's consequence is a list of effects:

src/sim/events.zig
/// One consequence of an event option. Relative where it must scale
/// (contract pay), absolute where flat money reads better.
pub const Effect = union(enum) {
    cash: types.CBills,
    cash_monthly_pct: i16, // % of the contract's monthly_net
    reputation: i16,
    morale: i8, // applied to everyone in the company
    fatigue: u8,
    xp_all: u16,
    score: i16, // contract success score (drives Stage 7 outcomes)
    damage_random_units: u8, // N line-lance hulls take abstract battle wear
    damage_convoy_units: u8, // N support-echelon vehicles (trucks, ambulances) take wear
    parts_windfall: u8, // salvaged spares into the pool
    supply_loss: types.CBills, // posted as a supplies expense
    /// Standing with the contract's employer (Stage 12.22).
    employer_standing: i16,
    /// Stock landed in the company's field stores (munitions off the books).
    field_stock: struct { key: []const u8, qty: u16 },
    // Personnel effects (Stage 12.25) act on the event's `person`.
    raise_pct: u8,
    retention_bonus_months: u8,
    let_go,
    replace_from_hall,
    // Prisoner effects (12B.7) act on the event's `person`, a POW.
    ransom_prisoner,
    release_prisoner,
    recruit_prisoner,
};

pub const Option = struct {
    label: []const u8,
    effects: []const Effect = &.{},
};

pub const Event = struct {
    day: u32,
    kind: EventKind,
    contract: types.ContractId = .none,
    company: types.ForceId = .none,
    person: types.PersonId = .none,
    /// Empty = auto event (applied at roll time, never queued).
    options: []const Option = &.{},
    /// Applied automatically at the deadline if the player never answers.
    default_choice: usize = 0,
    deadline_day: u32 = 0,
    chosen: ?usize = null,

    pub fn needsDecision(self: *const Event) bool {
        return self.options.len > 0 and self.chosen == null;
    }
};

An Effect carries a small signed or unsigned integer sized to what it means: morale is i8 because it can go down, fatigue is u8 because an event only ever adds it. A few carry nothing, like let_go. The Option is a label and a slice of effects, and an Event is a slice of options with a default and a deadline. options.len == 0 means the event is automatic and was applied when rolled; otherwise it waits.

The decks themselves are functions from a 2d6 roll to an Entry, in contract_events.zig. They are ordinary Zig, not data files, because each entry's log text and effects are hand-written prose and the tables are short. Here is what happens on the first of the month:

src/sim/contract_events.zig
pub fn rollMonthly(gs: *GameState) !void {
    var it = gs.contracts.iterator();
    while (it.next()) |entry| {
        const c = entry.value_ptr;
        if (c.status != .active) continue;

        const roll = gs.rng.roll2d6(.events);
        const deck = if (c.kind.isGarrisonClass()) garrisonDeck(roll) else combatDeck(roll);

        const ctx: @import("state.zig").LogCtx = .{ .company = c.assigned_company, .contract = c.id };
        if (deck.options.len == 0) {
            try applyEffects(gs, deck.auto_effects, c);
            try gs.log(.contract, ctx, "[{s}] (2d6 = {d}) {s}{s}", .{ @tagName(c.kind), roll, deck.log, try effectsPlain(gs, deck.auto_effects) });
        } else try queueDecision(gs, deck, c, roll);
    }
}

Roll from the .events stream, pick a deck by contract class, and either apply and log or queue. Note the two arguments the log line gets from ctx: the company and the contract, so the Desk's log pane can later filter "everything that happened to Alpha on this contract" (Chapter 41).

46.5 Decision or dice: the inbox rule

The rule that decides whether an event goes to the inbox is stated in the original guide: if none of its effects touch money, stock or damage, the sim rolls the default and logs it; otherwise it waits for the player with a deadline. In the current source that rule is not a function; it is a property of how the decks are written, and a test asserts it for every deck and every roll:

test "12.24: automatic events never move money, stock or hulls — those are decisions" {
    var roll: u8 = 2;
    while (roll <= 12) : (roll += 1) {
        const decks = [_]Entry{ garrisonDeck(roll), combatDeck(roll), weeklyDeck(true, roll), weeklyDeck(false, roll) };
        for (decks) |e| {
            if (e.options.len > 0) continue;
            for (e.auto_effects) |fx| switch (fx) {
                .fatigue, .morale, .xp_all, .score, .reputation, .employer_standing => {},
                .cash, .cash_monthly_pct, .supply_loss, .parts_windfall, .field_stock, .damage_random_units, .damage_convoy_units, .raise_pct, .retention_bonus_months, .let_go, .replace_from_hall, .ransom_prisoner, .release_prisoner, .recruit_prisoner => {
                    std.debug.print("auto event {s} carries a player-facing effect\n", .{@tagName(e.kind)});
                    return error.TestUnexpectedResult;
                },
            };
        }
    }
}

Read the switch. It has no else, so it lists every Effect tag and sorts each into "harmless in an automatic event" or "must be a decision". Add an effect to the union and this test fails to compile until someone decides which side of the line it is on. That is a deliberate use of exhaustiveness as a design checklist, and Exercise 46.1 walks you through it. The loop over rolls 2 to 12 and all four decks means the property is checked for every entry that can ever be drawn.

Queued decisions carry one more mechanism. If the player has answered the same kind of event the same way three times running, the game stops asking:

fn queueDecision(gs: *GameState, deck: Entry, c: *contract_mod.Contract, roll: u8) !void {
    const ctx: @import("state.zig").LogCtx = .{ .company = c.assigned_company, .contract = c.id };
    const mem = try gs.event_memory.getOrPut(gs.allocator(), deck.kind);
    if (!mem.found_existing) mem.value_ptr.* = .{};
    mem.value_ptr.last_day = gs.clock.day_index;
    if (mem.value_ptr.streak >= tuning.contract.standing_order_after and mem.value_ptr.last_choice < deck.options.len) {
        const opt = deck.options[mem.value_ptr.last_choice];
        try applyEffects(gs, opt.effects, c);
        try gs.log(.contract, ctx, "[{s}] (2d6 = {d}) {s} — standing order: \"{s}\"{s} (`sop clear {s}` to be asked again)", .{ @tagName(c.kind), roll, deck.log, opt.label, try effectsPlain(gs, opt.effects), @tagName(deck.kind) });
        return;
    }
    try gs.event_queue.push(gs.allocator(), .{
        .day = gs.clock.day_index,
        .kind = deck.kind,
        .contract = c.id,
        .company = c.assigned_company,
        .options = deck.options,
        .default_choice = deck.default_choice,
        .deadline_day = gs.clock.day_index + decision_window_days,
    });
    try gs.log(.decision, ctx, "[{s}] DECISION: {s} (inbox, {d} days to answer)", .{ @tagName(c.kind), deck.log, decision_window_days });
}

getOrPut (Chapter 22) fetches or creates the memory for this event kind in one call; the found_existing flag tells you which happened, and a new entry is initialised with .{}. The standing-order threshold comes from the tuning table (Chapter 40). The deadline is a day index; when it passes, expireDue in the tick applies default_choice and logs that the player let it default. Time never stops for an event, which is the design sentence at the top of events.zig.

Guided reading

  1. src/sim/autoresolve.zig: Element, effectivePower, CampaignMods and Outcome. This is the arithmetic of a side's strength, all integers and basis points, and it has its own tests.
  2. src/sim/battle.zig: runDaily, then resolveEngagement from the top to the hit_pct table, then skim the rest for the shape (hits, wounds, ammo, salvage, score, report). Read one test at the bottom fully.
  3. src/sim/events.zig, all of it (149 lines).
  4. src/sim/contract_events.zig: Entry, one deck function (garrisonDeck), rollMonthly, queueDecision, resolveChoice, expireDue, and applyEffectsFor, which is the exhaustive switch that turns each Effect into a state change.
  5. The tests "auto events apply, decisions queue with deadlines, defaults fire" and "12.24: automatic events never move money, stock or hulls".

Exercise 46.1 · Add an effect and let the compiler list the switches practice

Add a variant xp_pilot: u16 to Effect and build. Write down every file and line the compiler names, then remove the variant. You do not have to implement the effect; the point is to see the checklist.

Solution 
src/sim/queries.zig:286:23: error: switch must handle all possibilities
src/sim/events.zig:89:5: note: unhandled enumeration value: 'xp_pilot'
src/sim/contract_events.zig:352:9: error: switch must handle all possibilities
src/sim/contract_events.zig:731:39: error: switch must handle all possibilities

Three switches: queries.effectsText (how the inbox describes an option to the player), contract_events.applyEffectsFor (what the effect does to the state), and the 12.24 test (which side of the decision line it is on). Those are precisely the three questions a new effect must answer: how is it shown, what does it do, and may it happen without asking. The compiler reports them across two compilations because the test binary and the executable are built separately; you may see the queries.zig error twice.

Exercise 46.2 · Every roll has a line warm-up

Write a test in contract_events.zig that, for every roll from 2 to 12, checks the garrison and combat decks return an entry with non-empty log text, and that any entry with options has a default_choice inside the option list (so that expireDue can never index out of bounds).

Solution 
test "every monthly roll has a line for the log and a default" {
    var roll: u8 = 2;
    while (roll <= 12) : (roll += 1) {
        try std.testing.expect(garrisonDeck(roll).log.len > 0);
        const e = combatDeck(roll);
        try std.testing.expect(e.log.len > 0);
        // A decision always has a default the deadline can apply.
        if (e.options.len > 0) try std.testing.expect(e.default_choice < e.options.len);
    }
}

The deck functions are private (fn, not pub fn) but a test in the same file can call them. The property about default_choice is the kind of thing that is obviously true today and quietly stops being true when someone reorders the options of one entry; a loop over all eleven rolls costs nothing.

Exercise 46.3 · needsDecision warm-up

Write a test in events.zig showing that an event with options needs a decision, stops needing one once chosen is set, and that an event with no options never needed one.

Solution 
test "an answered decision stops needing one" {
    var ev: Event = .{ .day = 1, .kind = .betrayal, .options = &.{.{ .label = "Fight" }} };
    try std.testing.expect(ev.needsDecision());
    ev.chosen = 0;
    try std.testing.expect(!ev.needsDecision());
    const auto: Event = .{ .day = 1, .kind = .quiet_month };
    try std.testing.expect(!auto.needsDecision());
}

&.{.{ .label = "Fight" }} is the address of an anonymous array literal with one Option in it, coerced to []const Option; the effects field takes its default of an empty slice. ev must be var because chosen is assigned; auto can be const.

Check your understanding

  1. How does the game decide that today is a battle day for a contract?
    Answerbattle.runDaily compares day_index with the contract's next_battle_day; if that field is null it schedules one with a seeded gap instead.
  2. Why is the outcome an if … else if expression rather than a lookup table?
    AnswerThe thresholds are on a signed roll with modifiers that can push it far outside 2 to 12, so range comparisons are the natural form; the result is an enum so the loss tables can switch on it exhaustively.
  3. Why widen roll2d6's result with @as(i32, …)?
    AnswerIt returns u8, and the modifiers being added are signed i32; Zig requires an explicit widening before mixing them.
  4. What makes an event automatic rather than a decision?
    AnswerAn Entry with no options is applied at roll time; one with options is queued with a deadline. A test asserts that automatic entries carry only effects that do not touch money, stock, hulls or people.
  5. What happens to a decision the player never answers?
    AnswerWhen day_index passes its deadline_day, expireDue applies default_choice and logs it; time never waits.
  6. What is a standing order?
    AnswerAfter the player has chosen the same option for the same event kind enough times in a row (a tuning knob), queueDecision applies that choice automatically and logs it, until sop clear resets the memory.
  7. Which three places must change when an Effect variant is added?
    AnswerThe display switch in queries.effectsText, the application switch in contract_events.applyEffectsFor, and the classification switch in the 12.24 test.
What you learned.
  • A battle is a phase of the tick that resolves when an integer day arrives, and the engagement itself is one seeded 2d6 roll plus modifiers mapped to a five-variant outcome.
  • Strength, variance and difficulty are all basis-point arithmetic on integers; dice come only from the .battle stream.
  • Dice are tested by aggregates over many seeded rolls, with bounds rather than exact values.
  • Events are a tagged union of effects grouped into options; no options means automatic, otherwise the inbox with a deadline and a default.
  • An exhaustive switch in a test is a design checklist: every new effect must be classified before the code compiles.
