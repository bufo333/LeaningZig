21. Growable lists: ArrayList

In this chapter you will meet std.ArrayList, the standard library's growable array, and learn its 0.16 shape: an unmanaged struct that starts as .empty and takes an allocator on every call that might grow it. You will append, insert, remove, iterate by pointer, build strings with it, hand its buffer to a caller with toOwnedSlice, and learn the one trap that bites everyone: a pointer into the list that goes stale when the list regrows.

21.1 Why arrays are not enough

An array in Zig has a length that is part of its type. [4]u32 is four integers, always, forever. A slice is a view of memory somebody else owns. Neither can grow. But most real programs collect things whose count they do not know in advance: lines of a file, units in a hangar, people who answered a recruiting ad. For that you need a buffer on the heap that can be replaced with a bigger one when it fills up. That is exactly what std.ArrayList(T) is: a slice called items, a capacity that says how big the underlying buffer really is, and a handful of methods that keep the two in step.

If you come from Python this is a list; from JavaScript, an array; from C++, a std::vector. The difference is that Zig's version will not allocate behind your back. Every method that might need more room takes the allocator as its first argument, so the call site shows you where memory can be requested and where it can fail.

21.2 The smallest list

a_basic.zig

const std = @import("std");

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var list: std.ArrayList(u32) = .empty;
    defer list.deinit(gpa);

    try list.append(gpa, 10);
    try list.append(gpa, 20);
    try list.append(gpa, 30);

    std.debug.print("items: {any}\n", .{list.items});
    std.debug.print("len: {d}, capacity: {d}\n", .{ list.items.len, list.capacity });
    std.debug.print("second: {d}\n", .{list.items[1]});
}
items: { 10, 20, 30 }
len: 3, capacity: 33
second: 20

Four things to notice. First, the type is std.ArrayList(u32): a function that takes a type and returns a struct type, which is how all generic containers work in Zig (you will write your own in Chapter 26). Second, the starting value is .empty, a constant on the type meaning "no buffer, length zero, capacity zero". No allocator is stored in the list. Third, append takes gpa because it might need to grow, and it returns an error union because growing can fail, hence try. Fourth, deinit takes the allocator too, since it has to know whom to give the buffer back to, and we put it in a defer right after the declaration so it cannot be forgotten.

list.items is an ordinary slice, []u32. Anything you learned about slices in Chapter 10 works on it: index it, take its .len, loop over it, pass it to a function that wants a slice. The capacity (33 here, on this platform and this element size) is larger than the length because the list grows in jumps so that appending is cheap on average. The exact number is an implementation detail and you should never rely on it.

In Zig 0.16 there is only one ArrayList and it is unmanaged. Older tutorials show std.ArrayList(u32).init(allocator) and calls like list.append(5) with no allocator. Those forms no longer exist. The name std.ArrayListUnmanaged still works as an alias and IRON LEDGER uses it throughout, but it means exactly the same type as std.ArrayList.

21.3 Watching it grow

Let's print the capacity every time it changes while we append two hundred bytes.

b_growth.zig

const std = @import("std");

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var list: std.ArrayList(u8) = .empty;
    defer list.deinit(gpa);

    var last_cap: usize = 0;
    for (0..200) |i| {
        try list.append(gpa, @intCast(i));
        if (list.capacity != last_cap) {
            std.debug.print("len {d: >3} -> capacity {d}\n", .{ list.items.len, list.capacity });
            last_cap = list.capacity;
        }
    }
}
len   1 -> capacity 129
len 130 -> capacity 323

Two hundred appends, two allocations. When the buffer is full, the list asks the allocator for a bigger one (here about two and a half times the size), copies the old contents across, frees the old buffer and carries on. Most appends therefore touch no allocator at all; they just write one element and bump items.len. This is why append is described as "amortised constant time": expensive once in a while, free the rest of the time.

If you already know how many elements you will add, say so with ensureTotalCapacity and then use appendAssumeCapacity, which cannot fail and takes no allocator. You will see that in 21.8.

21.4 Adding and removing

Here is the full toolkit for changing a list, on a list of strings so the effect is easy to see. The show helper exists because {s} prints one string, not a slice of strings.

c_remove.zig

const std = @import("std");

fn show(label: []const u8, items: []const []const u8) void {
    std.debug.print("{s: <22}", .{label});
    for (items) |s| std.debug.print("{s} ", .{s});
    std.debug.print("\n", .{});
}

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var list: std.ArrayList([]const u8) = .empty;
    defer list.deinit(gpa);
    try list.appendSlice(gpa, &.{ "alpha", "bravo", "charlie", "delta", "echo" });
    show("start:", list.items);

    try list.insert(gpa, 1, "NEW");
    show("insert(1, NEW):", list.items);

    const gone = list.orderedRemove(1);
    show("orderedRemove(1):", list.items);
    std.debug.print("  (removed {s})\n", .{gone});

    const swapped = list.swapRemove(0);
    show("swapRemove(0):", list.items);
    std.debug.print("  (removed {s})\n", .{swapped});

    const top = list.pop();
    show("pop():", list.items);
    std.debug.print("  (popped {?s})\n", .{top});

    list.clearRetainingCapacity();
    std.debug.print("cleared: len {d}, capacity {d}\n", .{ list.items.len, list.capacity });
    std.debug.print("pop on empty: {?s}\n", .{list.pop()});
}
start:                alpha bravo charlie delta echo 
insert(1, NEW):       alpha NEW bravo charlie delta echo 
orderedRemove(1):     alpha bravo charlie delta echo 
  (removed NEW)
swapRemove(0):        echo bravo charlie delta 
  (removed alpha)
pop():                echo bravo charlie 
  (popped delta)
cleared: len 0, capacity 15
pop on empty: null

Read the transcript against the calls:

  • appendSlice(gpa, slice) appends many at once. The argument &.{ ... } is a pointer to an anonymous array, which coerces to a slice.
  • insert(gpa, i, item) shifts everything from i onward one place right. It takes the allocator because it may grow.
  • orderedRemove(i) removes element i and shifts the rest left, preserving order. It returns the removed element. No allocator: removing never allocates.
  • swapRemove(i) removes element i by moving the last element into its slot. It is constant time, but the order changes: echo jumped to the front.
  • pop() removes and returns the last element as an optional. On an empty list it returns null instead of crashing, which is why the last line prints null.
  • clearRetainingCapacity() sets the length to zero but keeps the buffer, so refilling the list will not allocate again. Its sibling clearAndFree(gpa) gives the buffer back too.

Choose swapRemove when you do not care about order and the list is long; choose orderedRemove when order matters. Removing from the front of a long list with orderedRemove in a loop is quadratic, so if you find yourself doing that, ask whether you want a different data structure.

21.5 Iterating: by value or by pointer

A for loop over list.items gives you each element by value, which means a copy. If the element is a struct and you want to change it in place, you need a pointer, and the syntax is the same one you met for arrays and slices in Chapter 18: put a * in front of the capture name.

d_pointers.zig

const std = @import("std");

const Merc = struct { name: []const u8, wounds: u8 };

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var roster: std.ArrayList(Merc) = .empty;
    defer roster.deinit(gpa);
    try roster.append(gpa, .{ .name = "Kell", .wounds = 0 });
    try roster.append(gpa, .{ .name = "Natasha", .wounds = 1 });

    // By value: `m` is a copy. Changing it changes nothing in the list.
    for (roster.items) |m| {
        var copy = m;
        copy.wounds += 10;
    }
    std.debug.print("after by-value loop: {d} {d}\n", .{ roster.items[0].wounds, roster.items[1].wounds });

    // By pointer: `m` points into the list's buffer.
    for (roster.items) |*m| m.wounds += 1;
    std.debug.print("after by-pointer loop: {d} {d}\n", .{ roster.items[0].wounds, roster.items[1].wounds });

    // Or index straight in.
    roster.items[0].name = "Morgan Kell";
    std.debug.print("{s}\n", .{roster.items[0].name});
}
after by-value loop: 0 1
after by-pointer loop: 1 2
Morgan Kell

The first loop copies each Merc into m, then into copy, and adds ten to the copy. The list is untouched. (The extra copy variable is there because the compiler rejects assigning to a by-value capture; it knows that would be a silent no-op.) The second loop captures *m, a *Merc pointing into the list's buffer, and m.wounds += 1 writes through it. Zig auto-dereferences field access on pointers, so you write m.wounds, not m.*.wounds.

21.6 The stale-pointer trap

Now the trap. Because the list's buffer can move when it grows, a pointer into items is only valid until the next call that might grow the list.

e_stale.zig

const std = @import("std");

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var list: std.ArrayList(u32) = .empty;
    defer list.deinit(gpa);
    try list.append(gpa, 10);

    const first = &list.items[0]; // a pointer into the buffer
    std.debug.print("capacity {d}, first lives at {*}\n", .{ list.capacity, first });

    for (0..100) |i| try list.append(gpa, @intCast(i)); // forces a regrow
    std.debug.print("capacity {d}, first now at {*}\n", .{ list.capacity, &list.items[0] });

    std.debug.print("through the old pointer: {d}\n", .{first.*}); // BUG
}
capacity 33, first lives at u32@1074a0000
capacity 158, first now at u32@1074e0000
Segmentation fault at address 0x1074a0000
e_stale.zig:18:20: 0x102a19bd0 in main (e_stale)
    std.debug.print("through the old pointer: {d}\n", .{first.*}); // BUG

The list started with room for 33 elements. The 101 appends forced a regrow, the buffer moved to a new address, and the old one was returned to the allocator. first still points at the old address. In Debug mode the DebugAllocator unmaps freed pages, so reading through first crashes immediately with a stack trace. That is the good outcome. In ReleaseFast, the same read might silently return stale data, or whatever the allocator has since put there.

Rule. Never keep a pointer (or a slice) into list.items across a call to append, appendSlice, insert, ensureTotalCapacity, or anything else that takes the allocator. Keep the index instead and re-derive the pointer when you need it: &list.items[i]. The same rule applies to every growable container in this Part, including the hash maps of Chapter 22.

This is also why for (list.items) |*m| is safe: the loop does not append. If you ever need to append while iterating, iterate by index and expect the loop bound to change.

21.7 A string builder

A string is bytes, so std.ArrayList(u8) is a growable string. It even has a print method that formats straight into the buffer, so you do not need allocPrint and a temporary.

f_builder.zig

const std = @import("std");

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var sb: std.ArrayList(u8) = .empty;
    defer sb.deinit(gpa);

    try sb.appendSlice(gpa, "Lance: ");
    const pilots = [_][]const u8{ "Kell", "Natasha", "Grayson" };
    for (pilots, 0..) |p, i| {
        if (i > 0) try sb.appendSlice(gpa, ", ");
        try sb.appendSlice(gpa, p);
    }
    try sb.append(gpa, '\n');
    try sb.print(gpa, "{d} pilots, {d} bytes so far", .{ pilots.len, sb.items.len });

    std.debug.print("{s}\n", .{sb.items});

    const owned = try sb.toOwnedSlice(gpa); // sb is now empty; we own `owned`
    defer gpa.free(owned);
    std.debug.print("owned len {d}, list len {d}\n", .{ owned.len, sb.items.len });
}
Lance: Kell, Natasha, Grayson
3 pilots, 30 bytes so far
owned len 55, list len 0

toOwnedSlice(gpa) is the handshake at the end. It shrinks the buffer to exactly the length used, returns it as a plain []u8, and resets the list to .empty. The caller now owns that slice and must free it with the same allocator; the list owns nothing, so its deinit in the defer is harmless. This is how functions return "a list of things" in Zig: build with an ArrayList, return a slice.

Sometimes you want a real *std.Io.Writer (the thing print and writeAll live on, which you met when printing to stdout in Chapter 2) that grows a heap buffer. That is std.Io.Writer.Allocating. It is the right choice when you want to pass "somewhere to write" to a function that should not know or care whether it is writing to a file, a fixed buffer or memory.

g_allocating.zig

const std = @import("std");

fn describe(w: *std.Io.Writer, name: []const u8, tons: u32) !void {
    try w.print("{s} ({d} tons)", .{ name, tons });
}

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    var aw: std.Io.Writer.Allocating = .init(gpa);
    defer aw.deinit();

    try describe(&aw.writer, "Atlas", 100);
    try aw.writer.writeAll(" / ");
    try describe(&aw.writer, "Locust", 20);

    std.debug.print("{s}\n", .{aw.written()});

    const text = try aw.toOwnedSlice();
    defer gpa.free(text);
    std.debug.print("{d} bytes\n", .{text.len});
}
Atlas (100 tons) / Locust (20 tons)
35 bytes

aw.writer is the generic writer, aw.written() is the bytes so far, and aw.toOwnedSlice() hands you the buffer exactly like the list did. Under the hood it is an ArrayList(u8) with a writer interface on top.

21.8 A list of structs, returned as a slice

The pattern IRON LEDGER uses in every query: build a list of small structs inside a function, hand the buffer to the caller.

h_structs.zig

const std = @import("std");

const Unit = struct { name: []const u8, tons: u32, bv: u32 };

fn heaviest(units: []const Unit) ?Unit {
    if (units.len == 0) return null;
    var best = units[0];
    for (units[1..]) |u| if (u.tons > best.tons) {
        best = u;
    };
    return best;
}

fn buildLance(gpa: std.mem.Allocator) ![]Unit {
    var list: std.ArrayList(Unit) = .empty;
    errdefer list.deinit(gpa);
    try list.ensureTotalCapacity(gpa, 4); // one allocation, not four
    list.appendAssumeCapacity(.{ .name = "Atlas", .tons = 100, .bv = 1897 });
    list.appendAssumeCapacity(.{ .name = "Marauder", .tons = 75, .bv = 1363 });
    list.appendAssumeCapacity(.{ .name = "Locust", .tons = 20, .bv = 432 });
    return list.toOwnedSlice(gpa);
}

pub fn main() !void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa_state.deinit();
    const gpa = gpa_state.allocator();

    const lance = try buildLance(gpa);
    defer gpa.free(lance);

    var total: u32 = 0;
    for (lance) |u| total += u.tons;
    std.debug.print("{d} units, {d} tons\n", .{ lance.len, total });
    if (heaviest(lance)) |h| std.debug.print("heaviest: {s}\n", .{h.name});
}
3 units, 195 tons
heaviest: Atlas

Three details worth copying. errdefer list.deinit(gpa) rather than defer: if toOwnedSlice succeeds, the list is empty and the caller owns the buffer, so we only want to clean up on the error path. ensureTotalCapacity followed by appendAssumeCapacity turns three possible allocations into one. And heaviest takes a plain []const Unit, not the list: functions that only read should accept slices, so they work on arrays, lists and anything else.

Exercise 21.1 · Squares warm-up

Write fn squaresUpTo(gpa: std.mem.Allocator, n: u32) ![]u32 that returns the squares of 0 to n-1 as a slice the caller owns. Reserve the capacity up front so there is exactly one allocation. Name the file: exercises/21-arraylist/ex1_squares.zig.

Solution 
//! Chapter 21, exercise 1: build a list, hand it back as a slice.
//! Run with:  zig test ex1_squares.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Return the squares 0*0, 1*1, ... (n-1)*(n-1) as a slice the caller owns.
fn squaresUpTo(gpa: std.mem.Allocator, n: u32) ![]u32 {
    var list: std.ArrayList(u32) = .empty;
    errdefer list.deinit(gpa);
    try list.ensureTotalCapacity(gpa, n);
    for (0..n) |i| {
        const v: u32 = @intCast(i);
        list.appendAssumeCapacity(v * v);
    }
    return list.toOwnedSlice(gpa);
}

test "five squares" {
    const s = try squaresUpTo(std.testing.allocator, 5);
    defer std.testing.allocator.free(s);
    try std.testing.expectEqualSlices(u32, &.{ 0, 1, 4, 9, 16 }, s);
}

test "zero squares is an empty slice, not an error" {
    const s = try squaresUpTo(std.testing.allocator, 0);
    defer std.testing.allocator.free(s);
    try std.testing.expectEqual(@as(usize, 0), s.len);
}

errdefer list.deinit(gpa) covers the case where ensureTotalCapacity succeeds and toOwnedSlice fails; on success the list is already empty. For n = 0 the result is an empty slice and free on it is fine.

Exercise 21.2 · Remove all, two ways practice

Write removeAllOrdered, which removes every element equal to a value and keeps order, and removeAllFast, which may reorder. Both return the count removed. Think carefully about what happens to your loop index after each removal. Name the file: exercises/21-arraylist/ex2_remove_all.zig.

Solution 
//! Chapter 21, exercise 2: remove every matching element, two ways.
//! Run with:  zig test ex2_remove_all.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Remove every element equal to `value`, keeping the order of the rest.
/// Returns how many were removed.
fn removeAllOrdered(list: *std.ArrayList(i32), value: i32) usize {
    var removed: usize = 0;
    var i: usize = 0;
    while (i < list.items.len) {
        if (list.items[i] == value) {
            _ = list.orderedRemove(i);
            removed += 1;
        } else {
            i += 1;
        }
    }
    return removed;
}

/// Same, but order does not matter, so use the cheaper swapRemove.
/// Walking backwards means a swap never moves an element we still need to look at.
fn removeAllFast(list: *std.ArrayList(i32), value: i32) usize {
    var removed: usize = 0;
    var i = list.items.len;
    while (i > 0) {
        i -= 1;
        if (list.items[i] == value) {
            _ = list.swapRemove(i);
            removed += 1;
        }
    }
    return removed;
}

test "ordered removal keeps order" {
    const a = std.testing.allocator;
    var list: std.ArrayList(i32) = .empty;
    defer list.deinit(a);
    try list.appendSlice(a, &.{ 7, 1, 7, 2, 7, 3, 7 });
    try std.testing.expectEqual(@as(usize, 4), removeAllOrdered(&list, 7));
    try std.testing.expectEqualSlices(i32, &.{ 1, 2, 3 }, list.items);
}

test "fast removal keeps the right elements" {
    const a = std.testing.allocator;
    var list: std.ArrayList(i32) = .empty;
    defer list.deinit(a);
    try list.appendSlice(a, &.{ 7, 1, 7, 2, 7, 3, 7 });
    try std.testing.expectEqual(@as(usize, 4), removeAllFast(&list, 7));
    std.mem.sort(i32, list.items, {}, std.sort.asc(i32));
    try std.testing.expectEqualSlices(i32, &.{ 1, 2, 3 }, list.items);
}

test "nothing to remove" {
    const a = std.testing.allocator;
    var list: std.ArrayList(i32) = .empty;
    defer list.deinit(a);
    try list.appendSlice(a, &.{ 1, 2 });
    try std.testing.expectEqual(@as(usize, 0), removeAllFast(&list, 9));
    try std.testing.expectEqual(@as(usize, 2), list.items.len);
}

In the ordered version, after removing at i the next element has slid into slot i, so do not increment. The fast version walks backwards: swapRemove(i) moves the last element into i, and since everything after i has already been examined, nothing is skipped.

Exercise 21.3 · Join practice

Write joinWith(gpa, parts, sep) using an ArrayList(u8) as a string builder, then describeLance which produces "2 units: Atlas, Locust" (and "1 unit: Atlas" for one). Use the list's print method for the count. Name the file: exercises/21-arraylist/ex3_join.zig.

Solution 
//! Chapter 21, exercise 3: a string builder.
//! Run with:  zig test ex3_join.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Join `parts` with `sep` between them. The caller owns the result.
fn joinWith(gpa: std.mem.Allocator, parts: []const []const u8, sep: []const u8) ![]u8 {
    var sb: std.ArrayList(u8) = .empty;
    errdefer sb.deinit(gpa);
    for (parts, 0..) |p, i| {
        if (i > 0) try sb.appendSlice(gpa, sep);
        try sb.appendSlice(gpa, p);
    }
    return sb.toOwnedSlice(gpa);
}

/// "3 units: Atlas, Locust, Marauder"
fn describeLance(gpa: std.mem.Allocator, names: []const []const u8) ![]u8 {
    var sb: std.ArrayList(u8) = .empty;
    errdefer sb.deinit(gpa);
    try sb.print(gpa, "{d} unit{s}: ", .{ names.len, if (names.len == 1) "" else "s" });
    const joined = try joinWith(gpa, names, ", ");
    defer gpa.free(joined);
    try sb.appendSlice(gpa, joined);
    return sb.toOwnedSlice(gpa);
}

test "join three" {
    const s = try joinWith(std.testing.allocator, &.{ "a", "b", "c" }, ", ");
    defer std.testing.allocator.free(s);
    try std.testing.expectEqualStrings("a, b, c", s);
}

test "join one and none" {
    const one = try joinWith(std.testing.allocator, &.{"solo"}, "-");
    defer std.testing.allocator.free(one);
    try std.testing.expectEqualStrings("solo", one);
    const none = try joinWith(std.testing.allocator, &.{}, "-");
    defer std.testing.allocator.free(none);
    try std.testing.expectEqualStrings("", none);
}

test "describe" {
    const s = try describeLance(std.testing.allocator, &.{ "Atlas", "Locust" });
    defer std.testing.allocator.free(s);
    try std.testing.expectEqualStrings("2 units: Atlas, Locust", s);
    const t = try describeLance(std.testing.allocator, &.{"Atlas"});
    defer std.testing.allocator.free(t);
    try std.testing.expectEqualStrings("1 unit: Atlas", t);
}

The standard library has std.mem.join that does the first function for you; writing it once by hand is the point. Notice the defer gpa.free(joined) for the temporary: describeLance owns it until it has been copied into the builder.

Exercise 21.4 · Roster challenge

Build a Roster struct wrapping an ArrayList(Merc) with hire, battle (every merc takes one wound, in place), releaseWorseThan(limit) (ordered removal, returns count) and best() which returns a pointer to the merc with the lowest gunnery, or null. The tests write through that pointer. Name the file: exercises/21-arraylist/ex4_roster.zig.

Solution 
//! Chapter 21, exercise 4: a roster of structs.
//! Run with:  zig test ex4_roster.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Merc = struct { name: []const u8, gunnery: u8, wounds: u8 };

const Roster = struct {
    mercs: std.ArrayList(Merc) = .empty,

    fn deinit(self: *Roster, gpa: std.mem.Allocator) void {
        self.mercs.deinit(gpa);
    }

    fn hire(self: *Roster, gpa: std.mem.Allocator, name: []const u8, gunnery: u8) !void {
        try self.mercs.append(gpa, .{ .name = name, .gunnery = gunnery, .wounds = 0 });
    }

    /// Every merc takes one wound. Must mutate in place.
    fn battle(self: *Roster) void {
        for (self.mercs.items) |*m| m.wounds += 1;
    }

    /// Release every merc whose gunnery is worse (higher) than `limit`, keeping order.
    fn releaseWorseThan(self: *Roster, limit: u8) usize {
        var released: usize = 0;
        var i: usize = 0;
        while (i < self.mercs.items.len) {
            if (self.mercs.items[i].gunnery > limit) {
                _ = self.mercs.orderedRemove(i);
                released += 1;
            } else i += 1;
        }
        return released;
    }

    /// Pointer to the best shot (lowest gunnery), or null if empty.
    fn best(self: *Roster) ?*Merc {
        if (self.mercs.items.len == 0) return null;
        var b = &self.mercs.items[0];
        for (self.mercs.items[1..]) |*m| if (m.gunnery < b.gunnery) {
            b = m;
        };
        return b;
    }
};

test "hire, fight, release" {
    const a = std.testing.allocator;
    var r: Roster = .{};
    defer r.deinit(a);
    try r.hire(a, "Kell", 2);
    try r.hire(a, "Rookie", 6);
    try r.hire(a, "Natasha", 1);
    r.battle();
    try std.testing.expectEqual(@as(u8, 1), r.mercs.items[1].wounds);
    try std.testing.expectEqual(@as(usize, 1), r.releaseWorseThan(4));
    try std.testing.expectEqualStrings("Kell", r.mercs.items[0].name);
    try std.testing.expectEqualStrings("Natasha", r.mercs.items[1].name);
}

test "best is a live pointer" {
    const a = std.testing.allocator;
    var r: Roster = .{};
    defer r.deinit(a);
    try std.testing.expect(r.best() == null);
    try r.hire(a, "Kell", 2);
    try r.hire(a, "Natasha", 1);
    r.best().?.wounds = 9; // writes through to the list
    try std.testing.expectEqual(@as(u8, 9), r.mercs.items[1].wounds);
}

best returns a pointer into the list, which is fine as long as the caller uses it before the next hire. The test does exactly that. If you wanted a safer API you would return the index instead.

Exercise 21.5 · Run-length encoding challenge

Write encode(gpa, bytes) ![]Run where Run is struct { byte: u8, count: u32 }, and decode(gpa, runs) ![]u8 that reverses it (look at appendNTimes). Name the file: exercises/21-arraylist/ex5_rle.zig.

Solution 
//! Chapter 21, exercise 5: run-length encoding into a list of structs.
//! Run with:  zig test ex5_rle.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Run = struct { byte: u8, count: u32 };

fn encode(gpa: std.mem.Allocator, input: []const u8) ![]Run {
    var runs: std.ArrayList(Run) = .empty;
    errdefer runs.deinit(gpa);
    for (input) |c| {
        if (runs.items.len > 0 and runs.items[runs.items.len - 1].byte == c) {
            runs.items[runs.items.len - 1].count += 1;
        } else {
            try runs.append(gpa, .{ .byte = c, .count = 1 });
        }
    }
    return runs.toOwnedSlice(gpa);
}

fn decode(gpa: std.mem.Allocator, runs: []const Run) ![]u8 {
    var out: std.ArrayList(u8) = .empty;
    errdefer out.deinit(gpa);
    for (runs) |r| try out.appendNTimes(gpa, r.byte, r.count);
    return out.toOwnedSlice(gpa);
}

test "encode" {
    const runs = try encode(std.testing.allocator, "aaabccdddd");
    defer std.testing.allocator.free(runs);
    try std.testing.expectEqual(@as(usize, 4), runs.len);
    try std.testing.expectEqual(Run{ .byte = 'a', .count = 3 }, runs[0]);
    try std.testing.expectEqual(Run{ .byte = 'd', .count = 4 }, runs[3]);
}

test "round trip" {
    const text = "mmmmeeeeccchhh warrior";
    const runs = try encode(std.testing.allocator, text);
    defer std.testing.allocator.free(runs);
    const back = try decode(std.testing.allocator, runs);
    defer std.testing.allocator.free(back);
    try std.testing.expectEqualStrings(text, back);
}

test "empty" {
    const runs = try encode(std.testing.allocator, "");
    defer std.testing.allocator.free(runs);
    try std.testing.expectEqual(@as(usize, 0), runs.len);
}

The encoder peeks at the last run through runs.items[runs.items.len - 1] and mutates it in place; that expression is re-evaluated each time, so it is never stale even though append happens between iterations.

Check your understanding

  1. Why does append take an allocator but pop does not?
    Answerappend may need to grow the buffer, which means asking an allocator for memory (and possibly failing). pop only decrements the length; it never allocates, so it needs neither the allocator nor an error return.
  2. What is the difference between items.len and capacity?
    Answeritems.len is how many elements are in use; capacity is how many the underlying buffer could hold before the next regrow. Capacity is always at least the length.
  3. After const p = &list.items[2]; try list.append(gpa, x);, is p safe to use?
    AnswerNo. The append may have moved the buffer, leaving p pointing at freed memory. Keep the index and take the pointer again afterwards.
  4. What does swapRemove(0) do to a list [a, b, c, d]?
    AnswerIt returns a and moves the last element into slot 0: the list becomes [d, b, c]. Order is not preserved.
  5. After const s = try list.toOwnedSlice(gpa);, who must free what?
    AnswerThe caller must gpa.free(s). The list is now .empty, so its deinit frees nothing (but is still harmless to call).
  6. How do you change a struct element inside a list during a for loop?
    AnswerCapture by pointer: for (list.items) |*item| item.field = ...;. A plain capture gives you a copy.
  7. You want to build a string by calling a function that takes a *std.Io.Writer. Which type do you use?
    Answerstd.Io.Writer.Allocating, initialised with .init(gpa); pass &aw.writer and read back aw.written() or toOwnedSlice().
What you learned.
  • std.ArrayList(T) is unmanaged in 0.16: start it as .empty, pass the allocator to every growing call, and deinit(gpa) it.
  • items is a normal slice; capacity is the buffer size; growth happens in jumps so appends are cheap on average.
  • append, appendSlice, insert grow; pop (optional), orderedRemove, swapRemove, clearRetainingCapacity do not.
  • Iterate with |*item| to mutate in place; never hold a pointer into the list across a growing call.
  • ArrayList(u8) plus print is a string builder; std.Io.Writer.Allocating is the same idea behind a writer interface.
  • Build inside a function, return toOwnedSlice(gpa), use errdefer for cleanup on the failure path.
