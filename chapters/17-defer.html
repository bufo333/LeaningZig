17. defer, errdefer and cleanup

In this chapter you will learn Zig's answer to "make sure this gets cleaned up": the defer statement, which runs when the enclosing block ends, and its sibling errdefer, which runs only when the block ends with an error. You will see the exact order they run in, the classic resource pairs they protect, and the two things a defer is not allowed to do.

17.1 The cleanup problem

Almost every resource comes in a pair. You open a file and must close it. You allocate memory and must free it. You lock a mutex and must unlock it. You begin a database transaction and must commit or roll it back. The first half is easy: it happens where you need the resource. The second half is where bugs live, because a function can leave in more ways than one. An early return, a try that fails, a break out of a loop: each is a path that has to remember the cleanup.

Languages solve this differently. Python has with, Java has try-with-resources, C++ runs destructors when a variable goes out of scope, Go has defer. Zig has defer too, but scoped to the block rather than the function, and it comes with a variant that only fires on failure. Together they let you write the cleanup on the line right after the setup, where you cannot forget it, and then stop thinking about it.

17.2 defer runs at the end of the block

def1.zig

const std = @import("std");

pub fn main() void {
    std.debug.print("open the hangar\n", .{});
    defer std.debug.print("close the hangar\n", .{});

    std.debug.print("power up the mech\n", .{});
    defer std.debug.print("power down the mech\n", .{});

    std.debug.print("run the mission\n", .{});
}
open the hangar
power up the mech
run the mission
power down the mech
close the hangar

defer statement; means "do not run this now; run it when the surrounding block is about to end". The block here is main's body, so both deferred prints run after "run the mission". Notice the order: the mech powers down before the hangar closes. Deferred statements run in reverse order of registration, last in, first out. That is not an accident. If setup happens in the order A then B, cleanup should happen B then A, because B may depend on A still being there. The mech needs the hangar around it to power down inside; the file needs the directory open to be closed. You get the right order for free by writing each cleanup directly after its setup.

def2.zig

const std = @import("std");

pub fn main() void {
    defer std.debug.print("1st defer registered, runs last\n", .{});
    defer std.debug.print("2nd defer registered, runs second\n", .{});
    defer std.debug.print("3rd defer registered, runs first\n", .{});
    std.debug.print("body done\n", .{});
}
body done
3rd defer registered, runs first
2nd defer registered, runs second
1st defer registered, runs last

One more detail worth seeing once: a deferred statement is evaluated when it runs, not when it is registered. If it mentions a variable, it sees the variable's final value.

const std = @import("std");

pub fn main() void {
    var x: u32 = 1;
    defer std.debug.print("defer sees x = {d}\n", .{x});
    x = 2;
    std.debug.print("body sets x = {d}\n", .{x});
}
body sets x = 2
defer sees x = 2

17.3 The scope is the block, not the function

This is the point where Zig differs from Go, and the one to get right early. A defer belongs to the innermost block it appears in: a function body, but also a bare { … } block, an if body, or a loop body. It runs when that block exits.

def3.zig

const std = @import("std");

pub fn main() void {
    std.debug.print("start of main\n", .{});
    {
        defer std.debug.print("  leaving the inner block\n", .{});
        std.debug.print("  inside the inner block\n", .{});
    }
    std.debug.print("back in main, block already cleaned up\n", .{});

    var i: u32 = 0;
    while (i < 3) : (i += 1) {
        defer std.debug.print("  end of iteration {d}\n", .{i});
        std.debug.print("  iteration {d}\n", .{i});
    }
    std.debug.print("end of main\n", .{});
}
start of main
  inside the inner block
  leaving the inner block
back in main, block already cleaned up
  iteration 0
  end of iteration 0
  iteration 1
  end of iteration 1
  iteration 2
  end of iteration 2
end of main

The defer inside the bare block ran before "back in main". The defer inside the loop body ran at the end of every iteration, not once at the end of main. This is nearly always what you want: if you open a file per iteration, you want it closed per iteration. It is also the source of the one real trap with defer, in section 17.7.

17.4 errdefer: only on the failure path

Sometimes cleanup should happen only if things went wrong. You began a transaction: on success you commit and keep the changes; on failure you roll back. You allocated a struct and are filling it in: on success you hand it to the caller, who now owns it; on failure you must free it yourself, because the caller will never see it. errdefer registers a statement that runs only when the block exits by returning an error.

def4.zig

const std = @import("std");

fn work(fail: bool) !void {
    std.debug.print("  BEGIN\n", .{});
    errdefer std.debug.print("  ROLLBACK (errdefer)\n", .{});
    defer std.debug.print("  cleanup (defer, always)\n", .{});

    if (fail) return error.Boom;
    std.debug.print("  COMMIT\n", .{});
}

pub fn main() void {
    std.debug.print("success path:\n", .{});
    work(false) catch {};
    std.debug.print("failure path:\n", .{});
    work(true) catch |err| std.debug.print("  caller saw {s}\n", .{@errorName(err)});
}
success path:
  BEGIN
  COMMIT
  cleanup (defer, always)
failure path:
  BEGIN
  cleanup (defer, always)
  ROLLBACK (errdefer)
  caller saw Boom

Read the failure path carefully. Both deferred statements were registered, errdefer first and defer second. On the way out they run in reverse: the defer cleanup, then the errdefer rollback. On the success path the errdefer is silently skipped. "Exits with an error" means specifically that the block's function returns an error value: a return error.X, or a try that fails. A normal return, even of a value the caller might consider bad, does not trigger it.

You can capture the error that is escaping, which is useful for logging:

def5.zig

const std = @import("std");

fn load(name: []const u8) !u32 {
    errdefer |err| std.debug.print("load('{s}') failed: {s}\n", .{ name, @errorName(err) });
    if (name.len == 0) return error.EmptyName;
    if (name[0] == '#') return error.BadName;
    return @intCast(name.len);
}

pub fn main() void {
    _ = load("alpha") catch {};
    _ = load("") catch {};
    _ = load("#x") catch {};
}
load('') failed: EmptyName
load('#x') failed: BadName

The successful call to load("alpha") printed nothing, because its errdefer never ran.

17.5 The constructor pattern

The most important use of errdefer is in functions that build something out of several allocations. Suppose the first allocation succeeds and the second fails. The function returns an error; the caller receives nothing and so cannot free anything. Unless the function itself frees the first allocation on the way out, it leaks. The rule is: after each step that acquires something, add an errdefer that releases it. Then any later failure unwinds everything acquired so far, in reverse order, and the success path hands the whole thing to the caller intact.

def6.zig

const std = @import("std");

const Pilot = struct { name: []const u8, skill: u8 };

/// Builds a pilot on the heap. If anything after the allocation fails,
/// the errdefer gives the memory back so the caller has nothing to clean.
fn makePilot(a: std.mem.Allocator, name: []const u8, skill: u8) !*Pilot {
    const p = try a.create(Pilot);
    errdefer a.destroy(p);

    if (skill > 8) return error.SkillOutOfRange;
    p.* = .{ .name = name, .skill = skill };
    return p;
}

test "makePilot cleans up after itself on failure" {
    const a = std.testing.allocator;

    const ok = try makePilot(a, "Ada", 4);
    defer a.destroy(ok);
    try std.testing.expectEqualStrings("Ada", ok.name);

    // No leak here: errdefer destroyed the half-built pilot.
    try std.testing.expectError(error.SkillOutOfRange, makePilot(a, "Bo", 9));
}
1/1 def6.test.makePilot cleans up after itself on failure...OK
All 1 tests passed.

The test uses std.testing.allocator, which fails the test if any allocation is not freed by the end. Remove the errdefer line and run it again: the second call leaks the half-built pilot and the test reports it. (Chapter 19 shows that report in full.) Here is a slightly harder version, where a loop acquires several things and the errdefer has to release however many were done:

def7.zig

const std = @import("std");

fn buildRoster(a: std.mem.Allocator, count: usize) ![][]u8 {
    const roster = try a.alloc([]u8, count);
    errdefer a.free(roster);

    var built: usize = 0;
    errdefer for (roster[0..built]) |name| a.free(name);

    for (roster, 0..) |*slot, i| {
        if (i == 3) return error.Simulated; // fail part way through
        slot.* = try std.fmt.allocPrint(a, "pilot-{d}", .{i});
        built += 1;
    }
    return roster;
}

test "partial failure frees everything built so far" {
    const a = std.testing.allocator;
    try std.testing.expectError(error.Simulated, buildRoster(a, 5));

    const r = try buildRoster(a, 2);
    defer {
        for (r) |name| a.free(name);
        a.free(r);
    }
    try std.testing.expectEqualStrings("pilot-1", r[1]);
}
1/1 def7.test.partial failure frees everything built so far...OK
All 1 tests passed.

The counter built is read by the errdefer at the moment it runs, not when it was registered, so it sees how far the loop got. This is the same "evaluated late" behaviour from section 17.2, doing useful work. Also notice the order: the errdefer that frees the names was registered second, so it runs first, before the one that frees the outer slice it reads from.

17.6 The classic pairs

Once you see resources as pairs, defer becomes a habit: write the acquire, immediately write defer release, and move on. Here are three real pairs in one program, using the 0.16 standard library.

def10.zig

const std = @import("std");

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const a = init.gpa;

    // Pair 1: alloc / free
    const buf = try a.alloc(u8, 16);
    defer a.free(buf);

    // Pair 2: lock / unlock
    var mutex: std.Io.Mutex = .init;
    try mutex.lock(io);
    defer mutex.unlock(io);

    // Pair 3: open / close, on a real file
    var dir = std.Io.Dir.cwd();
    var file = try dir.createFile(io, "def10_out.txt", .{});
    defer file.close(io);

    @memset(buf, '=');
    var wb: [64]u8 = undefined;
    var w = file.writer(io, &wb);
    try w.interface.print("{s}\n", .{buf});
    try w.interface.flush();
    std.debug.print("wrote {d} bytes, all three pairs unwind now\n", .{buf.len + 1});
}
wrote 17 bytes, all three pairs unwind now

Three pairs, three defers, each on the line after its acquire, and the function body below them never mentions cleanup again. When main ends they run in reverse: the file closes, the mutex unlocks, the buffer is freed. The fourth classic pair, begin and rollback or commit, is a job for errdefer, and you will see the game's real one in the IRON LEDGER box below.

AcquireReleaseUsual form

A note on the mutex: in Zig 0.16 the general mutex is std.Io.Mutex, its lock takes an io and can return an error (cancellation), and unlock also takes io. Older tutorials show std.Thread.Mutex, which no longer exists. Chapter 36 covers threads properly.

17.7 Traps

Trap: defer in a loop. Because a loop body is a block, a defer inside it runs every iteration. That is right for per-iteration resources. It is wrong if you meant "clean up once, after the loop". If you write defer list.deinit(a) inside a loop that appends to list, the list is destroyed at the end of the first iteration and you are using freed memory on the second. Put the defer where the resource was created: if the list was created before the loop, the defer goes before the loop. Exercise 17.4 makes you do this right.
Trap: a defer cannot return or try. A deferred statement runs while the block is already leaving; there is no function left to return from, and no way to route an error. Both are compile errors: 
const std = @import("std");

fn f() !void {
    defer return error.Nope;
}

pub fn main() !void {
    try f();
}
def8.zig:4:11: error: cannot return from defer expression
    defer return error.Nope;
          ^~~~~~~~~~~~~~~~~
def8.zig:4:5: note: defer expression here
    defer return error.Nope;
    ^~~~~~~~~~~~~~~~~~~~~~~
const std = @import("std");

fn f() !void {
    defer {
        try std.fmt.parseInt(u8, "x", 10);
    }
}

pub fn main() !void {
    try f();
}
def9.zig:5:9: error: 'try' not allowed inside defer expression
        try std.fmt.parseInt(u8, "x", 10);
        ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
def9.zig:4:5: note: defer expression here
    defer {
    ^~~~~
If a cleanup can fail, decide what to do with the failure right there: defer file.close(io); is fine because close cannot fail; errdefer db.exec("ROLLBACK") catch {}; is how the game says "if the rollback itself fails, there is nothing more we can do". The catch {} is deliberate and commented.
Not a trap, but a surprise: no destructors. Zig will not run cleanup for you when a variable goes out of scope. A struct with a deinit method does nothing when it dies; you must write defer thing.deinit() yourself. This is on purpose. Nothing in Zig happens that you did not write, so there is never a hidden call at the end of a block. The trade is one line of defer per resource, which the compiler helps you remember for memory (the testing allocator) and which review makes easy to check, since setup and cleanup are adjacent.
In IRON LEDGER. The save store's opener in game/src/persist/store.zig has every idea from this chapter in twelve lines: a transaction begun, an errdefer that rolls it back with its own failure swallowed, a series of trys that each might trigger it, and a COMMIT that stands only if all of them passed. 
pub fn fromDb(db: sqlite.Db) !Store {
    try db.exec(ddl);
    const store: Store = .{ .db = db };
    const stored: u32 = @intCast(@max(1, store.getSetting("schema_version", 1)));
    if (stored > schema_version) return error.StoreNewerThanGame;
    try db.exec("BEGIN");
    errdefer db.exec("ROLLBACK") catch {};
    for (migrations) |m| {
        if (m.version <= stored) continue;
        if (!try hasColumnRt(db, m.table, m.column)) try db.exec(m.sql);
    }
    try store.setSetting("schema_version", schema_version);
    try db.exec("COMMIT");
    return store;
}
The constructor pattern appears in game/src/tui/emblem.zig, where Emblem.load decodes a PNG, registers errdefer { var i = img; i.deinit(gpa); }, and only then duplicates the bytes; if the dupe fails, the decoded image is released. And the wizard's generateCampaign in game/src/tui/app.zig builds a GameState, writes errdefer gs.deinit();, then runs three commands through try: any failure tears down the half-made campaign instead of leaking it into the app.

Exercise 17.2 · errdefer keeps a failing constructor leak-free practice

Implement Squad.create, which makes two allocations and validates in between. A bad size must return error.BadSize without leaking. The testing allocator will tell you if you got it wrong. File: exercises/17-defer/ex2_errdefer.zig.

Solution 
//! Chapter 17, exercise 2: errdefer keeps a failing constructor leak-free.
//! Run with:  zig test ex2_errdefer.zig
//! Goal: make every test pass without changing the tests. The testing
//! allocator fails the test if anything leaks.
const std = @import("std");

const Squad = struct {
    name: []u8,
    skills: []u8,

    /// Allocates a copy of `name` and a skills array. If `size` is 0 or
    /// more than 12, fails with error.BadSize, leaking nothing.
    fn create(a: std.mem.Allocator, name: []const u8, size: usize) !Squad {
        const name_copy = try a.dupe(u8, name);
        errdefer a.free(name_copy);

        if (size == 0 or size > 12) return error.BadSize;

        const skills = try a.alloc(u8, size);
        errdefer a.free(skills);
        @memset(skills, 4);

        return .{ .name = name_copy, .skills = skills };
    }

    fn deinit(self: *Squad, a: std.mem.Allocator) void {
        a.free(self.skills);
        a.free(self.name);
    }
};

test "good squad" {
    var s = try Squad.create(std.testing.allocator, "Alpha", 4);
    defer s.deinit(std.testing.allocator);
    try std.testing.expectEqualStrings("Alpha", s.name);
    try std.testing.expectEqual(@as(usize, 4), s.skills.len);
    try std.testing.expectEqual(@as(u8, 4), s.skills[3]);
}

test "bad size leaks nothing" {
    try std.testing.expectError(error.BadSize, Squad.create(std.testing.allocator, "Beta", 0));
    try std.testing.expectError(error.BadSize, Squad.create(std.testing.allocator, "Gamma", 13));
}

Each allocation is followed by its own errdefer. The second one is technically unnecessary as written, since nothing after it can fail, but adding it costs nothing and protects you when someone later adds a step. Try removing the first errdefer and read the leak report.

Exercise 17.3 · begin / commit / rollback practice

Implement Ledger.payAll so that a list of bills is paid atomically: begin a transaction, roll back with errdefer if any debit fails, commit at the end. File: exercises/17-defer/ex3_transaction.zig.

Solution 
//! Chapter 17, exercise 3: begin / commit / rollback with errdefer.
//! Run with:  zig test ex3_transaction.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Ledger = struct {
    funds: i64,
    snapshot: i64 = 0,
    in_transaction: bool = false,
    rollbacks: u32 = 0,

    fn begin(self: *Ledger) void {
        self.snapshot = self.funds;
        self.in_transaction = true;
    }
    fn commit(self: *Ledger) void {
        self.in_transaction = false;
    }
    fn rollback(self: *Ledger) void {
        self.funds = self.snapshot;
        self.in_transaction = false;
        self.rollbacks += 1;
    }

    fn debit(self: *Ledger, amount: i64) !void {
        if (amount > self.funds) return error.InsufficientTreasury;
        self.funds -= amount;
    }

    /// Pay every bill in `bills` as one transaction: either all of them
    /// are paid, or none are. Use begin, errdefer rollback, commit.
    fn payAll(self: *Ledger, bills: []const i64) !void {
        self.begin();
        errdefer self.rollback();
        for (bills) |b| try self.debit(b);
        self.commit();
    }
};

test "all bills paid" {
    var l = Ledger{ .funds = 100 };
    try l.payAll(&.{ 10, 20, 30 });
    try std.testing.expectEqual(@as(i64, 40), l.funds);
    try std.testing.expect(!l.in_transaction);
    try std.testing.expectEqual(@as(u32, 0), l.rollbacks);
}

test "one bad bill rolls back the rest" {
    var l = Ledger{ .funds = 100 };
    try std.testing.expectError(error.InsufficientTreasury, l.payAll(&.{ 10, 20, 500, 5 }));
    try std.testing.expectEqual(@as(i64, 100), l.funds);
    try std.testing.expect(!l.in_transaction);
    try std.testing.expectEqual(@as(u32, 1), l.rollbacks);
}

Four lines, and the same shape as the game's fromDb. The second test checks that after the failure the funds are back to 100, the transaction flag is clear, and exactly one rollback happened.

Exercise 17.4 · defer inside a loop challenge

Implement processAll, which opens and closes one fake file per iteration. The tests require that at most one file is open at a time, that every open is matched by a close, and that an error part way through still closes the current file. File: exercises/17-defer/ex4_loop.zig.

Solution 
//! Chapter 17, exercise 4: defer inside a loop runs every iteration.
//! Run with:  zig test ex4_loop.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// A fake file handle that counts opens and closes on a shared tally.
const Tally = struct { opens: u32 = 0, closes: u32 = 0, max_open: u32 = 0, open_now: u32 = 0 };

fn open(t: *Tally) void {
    t.opens += 1;
    t.open_now += 1;
    if (t.open_now > t.max_open) t.max_open = t.open_now;
}
fn close(t: *Tally) void {
    t.closes += 1;
    t.open_now -= 1;
}

/// Process `n` files one after another. Each must be closed before the
/// next is opened, and every file must be closed even when `fail_at`
/// makes the function return early with an error.
fn processAll(t: *Tally, n: u32, fail_at: ?u32) !void {
    var i: u32 = 0;
    while (i < n) : (i += 1) {
        open(t);
        defer close(t);
        if (fail_at) |f| if (i == f) return error.Corrupt;
    }
}

test "every open is matched by a close, one at a time" {
    var t = Tally{};
    try processAll(&t, 5, null);
    try std.testing.expectEqual(@as(u32, 5), t.opens);
    try std.testing.expectEqual(@as(u32, 5), t.closes);
    try std.testing.expectEqual(@as(u32, 1), t.max_open);
}

test "an early error still closes the current file" {
    var t = Tally{};
    try std.testing.expectError(error.Corrupt, processAll(&t, 5, 2));
    try std.testing.expectEqual(@as(u32, 3), t.opens);
    try std.testing.expectEqual(@as(u32, 3), t.closes);
    try std.testing.expectEqual(@as(u32, 0), t.open_now);
}

Because the defer close(t) is inside the loop body, it runs at the end of every iteration, which keeps max_open at 1. When the return error.Corrupt fires on iteration 2, the block still unwinds, so the third open gets its close.

Check your understanding

  1. In what order do three defers in the same block run?
    AnswerReverse order of registration: the last one written runs first.
  2. When does a defer inside a while body run?
    AnswerAt the end of every iteration, because the loop body is a block.
  3. What triggers an errdefer?
    AnswerThe block's function returning an error: a return error.X or a failing try. A normal return, even of an unhappy value, does not.
  4. Why does a constructor need errdefer after each allocation?
    AnswerIf a later step fails, the caller receives an error and no object, so it cannot free the earlier allocations. Only the constructor can, and errdefer does it on the error path alone.
  5. Can you try inside a defer?
    AnswerNo. The block is already leaving; there is nowhere for the error to go. Handle it there, for example with catch {}.
  6. Does a deferred expression see the value of a variable at registration time or at run time?
    AnswerAt run time. It is evaluated when it runs, which is how a loop counter can tell the errdefer how much to undo.
  7. Why does Zig not run deinit automatically when a struct goes out of scope?
    AnswerNo hidden control flow: nothing runs that you did not write. You add defer x.deinit() yourself, right after creating x.
What you learned.
  • defer stmt; runs stmt when the enclosing block ends, however it ends, in reverse order of registration.
  • The scope is the block: a bare {}, an if body or a loop body, not just the function.
  • errdefer runs only when the block exits with an error; errdefer |err| captures which one.
  • After each acquire in a constructor, write an errdefer release; the success path hands everything to the caller.
  • Write the release on the line after the acquire: alloc/free, open/close, lock/unlock, begin/rollback.
  • A deferred statement cannot return or try; handle cleanup failures in place.
