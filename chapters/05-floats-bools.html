5. Floats, booleans and comparisons

In this chapter you will learn Zig's two floating-point types and why 0.1 + 0.2 is not 0.3, how to convert between integers and floats deliberately, how to print floats, what NaN and infinity are, and how comparisons and the boolean operators and, or and ! work. You will also see that Zig has no notion of a "truthy" value.

5.1 f32 and f64

A floating-point number stores a sign, a fraction, and an exponent, so it can hold 0.001 and 6.02e23 in the same type. Zig's two everyday float types are f32 (about 7 significant digits) and f64 (about 16). There are also f16, f80 and f128 for special purposes. Use f64 unless you have a reason not to; it is the natural type of most maths libraries and of the constants in std.math.

floats.zig
const std = @import("std");

pub fn main() void {
    const a: f32 = 0.1;
    const b: f64 = 0.1;
    std.debug.print("f32: {d}\n", .{a});
    std.debug.print("f64: {d}\n", .{b});
    const widened: f64 = a; // f32 widens to f64 for free
    std.debug.print("the f32 0.1, seen as f64: {d}\n", .{widened});
    var sum: f64 = 0.0;
    sum += 0.1;
    sum += 0.1;
    sum += 0.1;
    std.debug.print("0.1 + 0.1 + 0.1 = {d}\n", .{sum});
    std.debug.print("equal to 0.3? {}\n", .{sum == 0.3});
}
$ zig run floats.zig
f32: 0.1
f64: 0.1
the f32 0.1, seen as f64: 0.10000000149011612
0.1 + 0.1 + 0.1 = 0.30000000000000004
equal to 0.3? false

The first two lines look identical because Zig prints the shortest decimal that reads back as the same float. The third line tells the truth: the f32 nearest to 0.1 is actually 0.100000001490116…, and widening it to f64 exposes the digits. The last two lines are the famous one. Three tenths added together is not three tenths, because none of them was exactly a tenth to begin with. Floats are binary fractions; 0.1 in binary repeats forever, the way 1/3 does in decimal, and gets cut off.

The rule that follows is: never compare floats for equality when they came from arithmetic, and never use floats for money. Section 5.5 shows the comparison technique; IRON LEDGER's answer to money is Chapter 4's integers.

5.2 Float literals

A literal with a decimal point or an exponent is a comptime_float, the float twin of comptime_int from Chapter 3. It becomes an f32 or f64 when it meets one.

float_literal.zig
const std = @import("std");

pub fn main() void {
    const x = 2.5;
    std.debug.print("{s}\n", .{@typeName(@TypeOf(x))});
    const y: f64 = x;
    const z: f32 = 1.0e3;
    const w: f64 = 6.02e23;
    std.debug.print("{d} {d} {d} {e}\n", .{ y, z, w, w });
}
$ zig run float_literal.zig
comptime_float
2.5 1000 602000000000000000000000 6.02e23

1.0e3 is scientific notation for 1000; 6.02e23 is 6.02 times ten to the 23rd. A float literal must have a digit on both sides of the point: 1.0, not 1. and not .5. As with integers, a var initialised from a bare float literal needs a type annotation.

5.3 Converting between integers and floats

Integers and floats are different kinds of value, and Zig makes you say when you move between them.

float_conv.zig
const std = @import("std");

pub fn main() void {
    const tons: u32 = 55;
    const as_float: f64 = @floatFromInt(tons);
    const half = as_float / 2.0;
    std.debug.print("half of {d} tons is {d}\n", .{ tons, half });

    const price: f64 = 4_701_000.75;
    const whole: i64 = @intFromFloat(price); // truncates toward zero
    std.debug.print("truncated: {d}\n", .{whole});

    const rounded: i64 = @intFromFloat(@round(price));
    const floored: i64 = @intFromFloat(@floor(-2.5));
    const ceiled: i64 = @intFromFloat(@ceil(-2.5));
    std.debug.print("round {d}, floor(-2.5) {d}, ceil(-2.5) {d}\n", .{ rounded, floored, ceiled });

    const narrow: f32 = @floatCast(price); // f64 -> f32 loses precision
    std.debug.print("as f32: {d}\n", .{narrow});
}
$ zig run float_conv.zig
half of 55 tons is 27.5
truncated: 4701000
round 4701001, floor(-2.5) -3, ceil(-2.5) -2
as f32: 4701001
  • @floatFromInt(x) makes a float from an integer. The target type comes from context, as with the casts in Chapter 4, so you write it on a line with a type annotation or wrap it in @as(f64, …).
  • @intFromFloat(x) makes an integer from a float, dropping the fraction (rounding toward zero). Combine it with @round, @floor, or @ceil to choose a different rounding first.
  • @floatCast(x) changes float width. Going from f64 to f32 rounds to fewer digits, as the last line shows.

Two shortcuts exist, and you should know them so you are not surprised, but you should not lean on them. First, an integer type coerces to a float type without a builtin when every value of the integer type is exactly representable in the float: a u32 becomes an f64 silently, because f64 has 53 bits of fraction and can hold any 32-bit integer. The same applies inside arithmetic, so tons * ratio with a u32 and an f64 compiles and gives an f64:

mix_bad2.zig
const std = @import("std");

fn scale(tons: u32, ratio: f64) f64 {
    return tons * ratio;
}

pub fn main() void {
    std.debug.print("{d}\n", .{scale(55, 0.5)});
}
$ zig run mix_bad2.zig
27.5

But a u64 does not fit exactly in an f64, nor an i32 in an f32, and those are refused:

coerce7.zig
const std = @import("std");
fn a(x: u64) f64 {
    return x; // u64 -> f64 is lossy above 2^53
}
pub fn main() void {
    std.debug.print("{d}\n", .{a(55)});
}
$ zig run coerce7.zig
coerce7.zig:3:12: error: expected type 'f64', found 'u64'
    return x; // u64 -> f64 is lossy above 2^53
           ^
coerce7.zig:2:14: note: function return type declared here
fn a(x: u64) f64 {
             ^~~

Second, a runtime integer and a float literal do not mix at all, because the literal has no concrete type to resolve against:

coerce2.zig
const std = @import("std");
fn f(tons: u32) f64 {
    return tons + 0.5; // int + float literal
}
pub fn main() void {
    std.debug.print("{d}\n", .{f(55)});
}
$ zig run coerce2.zig
coerce2.zig:3:17: error: incompatible types: 'u32' and 'comptime_float'
    return tons + 0.5; // int + float literal
           ~~~~~^~~~~
coerce2.zig:3:12: note: type 'u32' here
    return tons + 0.5; // int + float literal
           ^~~~
coerce2.zig:3:19: note: type 'comptime_float' here
    return tons + 0.5; // int + float literal
                  ^~~

And a float never becomes an integer by itself, whatever its value:

$ zig run coerce3.zig
coerce3.zig:3:12: error: expected type 'u32', found 'f64'
    return x; // float -> int should never coerce
           ^
coerce3.zig:2:14: note: function return type declared here
fn f(x: f64) u32 {
             ^~~

The habit that avoids all of this is to write @floatFromInt whenever an integer enters a float calculation. It always works, it is explicit about where precision might be lost, and a reader does not have to remember the exact-representability table.

Trap: integer division happens first. const half: f64 = tons / 2; with tons: u32 = 55 gives 27, not 27.5. The division is done between integers, truncating, and the result is only then widened to a float. Convert before dividing: @as(f64, @floatFromInt(tons)) / 2.0.

Converting the other way is also checked. @intFromFloat panics in Debug builds if the float's integer part does not fit the target type:

intfromfloat_fail.zig
const std = @import("std");

pub fn main() void {
    var big: f64 = 300.0;
    big += 1.0;
    const small: u8 = @intFromFloat(big);
    std.debug.print("{d}\n", .{small});
}
$ zig run intfromfloat_fail.zig
thread 12345 panic: integer part of floating point value out of bounds
intfromfloat_fail.zig:6:23: 0x10000abcd in main (intfromfloat_fail)
    const small: u8 = @intFromFloat(big);
                      ^

5.4 Printing floats

The {d} placeholder prints a float in plain decimal, and the precision option controls how many digits follow the point:

fmt_floats.zig
const std = @import("std");

pub fn main() void {
    const x: f64 = 1234.5678;
    std.debug.print("{d}\n", .{x});
    std.debug.print("{d:.1}\n", .{x});
    std.debug.print("{d:.0}\n", .{x});
    std.debug.print("{d:12.2}|\n", .{x});
    std.debug.print("{d:<12.2}|\n", .{x});
    std.debug.print("{e}\n", .{x});
    std.debug.print("{e:.3}\n", .{x});
    std.debug.print("{any}\n", .{x});
    std.debug.print("{}\n", .{x});
}
$ zig run fmt_floats.zig
1234.5678
1234.6
1235
     1234.57|
1234.57     |
1.2345678e3
1.235e3
1234.5678
1234.5678

{d} alone prints the shortest exact representation; {d:.1} rounds to one decimal and {d:.0} to none. Width and alignment work as for integers. {e} prints scientific notation, with its own precision. {any} and the bare {} both give the same shortest form as {d}. For a table of prices, {d:.2} is almost always what you want.

5.5 Arithmetic, NaN and infinity

The four operators work on floats as you would expect, and the remainder builtins from Chapter 4 apply to floats as well: % on a float is an error, @rem and @mod are not. std.math has the usual functions and constants.

float_ops.zig
const std = @import("std");

pub fn main() void {
    const a: f64 = 7.0;
    const b: f64 = 2.0;
    std.debug.print("{d} {d} {d} {d}\n", .{ a + b, a - b, a * b, a / b });
    std.debug.print("rem {d}, mod {d}\n", .{ @rem(a, b), @mod(-a, b) });
    std.debug.print("sqrt {d}, pow {d}, pi {d:.4}\n", .{ @sqrt(a), std.math.pow(f64, a, b), std.math.pi });
    std.debug.print("{d}\n", .{1.0 / 3.0});
}
$ zig run float_ops.zig
9 5 14 3.5
rem 1, mod 1
sqrt 2.6457513110645907, pow 49, pi 3.1416
0.3333333333333333333333333333333333

Notice the last line: 1.0 / 3.0 printed with far more digits than an f64 has. Both operands were literals, so the division happened at compile time in comptime_float, which is exact, and only the printing rounded it. Give either side a runtime type and you get the sixteen-digit f64 answer.

Unlike integer division, float division by zero does not panic. It produces one of the special values that every float type carries:

naninf.zig
const std = @import("std");

pub fn main() void {
    var zero: f64 = 0.0;
    zero += 0.0;
    const one: f64 = 1.0;
    const inf = one / zero;
    const neg_inf = -one / zero;
    const nan = zero / zero;
    std.debug.print("{d} {d} {d}\n", .{ inf, neg_inf, nan });
    std.debug.print("nan == nan? {}\n", .{nan == nan});
    std.debug.print("isNan {}, isInf {}\n", .{ std.math.isNan(nan), std.math.isInf(inf) });
    std.debug.print("constants: {d} {d}\n", .{ std.math.inf(f64), std.math.nan(f64) });
    std.debug.print("f64 max {e}, f32 max {e}\n", .{ std.math.floatMax(f64), std.math.floatMax(f32) });
}
$ zig run naninf.zig
inf -inf nan
nan == nan? false
isNan true, isInf true
constants: inf nan
f64 max 1.7976931348623157e308, f32 max 3.4028235e38

Dividing a nonzero number by zero gives infinity with the appropriate sign. Dividing zero by zero, or taking the square root of a negative, gives NaN, "not a number". NaN has one property that catches everyone: it is not equal to anything, including itself. nan == nan is false. To test for it, use std.math.isNan; for infinity, std.math.isInf. std.math.inf(T) and std.math.nan(T) construct them, and std.math.floatMax(T) is the largest finite value of the type.

A NaN spreads: any arithmetic with a NaN gives a NaN, so one bad division early in a calculation poisons everything after it. If a float result looks wrong, print it; nan in the output points straight at the problem.

5.6 Comparisons

Six operators compare two values of the same type and produce a bool:

compare.zig
const std = @import("std");

pub fn main() void {
    const a: i32 = 5;
    const b: i32 = 7;
    std.debug.print("{} {} {} {} {} {}\n", .{ a == b, a != b, a < b, a <= b, a > b, a >= b });

    var x: f64 = 0.1;
    x += 0.2;
    std.debug.print("0.1 + 0.2 = {d}\n", .{x});
    std.debug.print("0.1 + 0.2 == 0.3 ? {}\n", .{x == 0.3});
    const close = std.math.approxEqAbs(f64, x, 0.3, 1e-9);
    std.debug.print("close enough? {}\n", .{close});

    const result = a < b;
    std.debug.print("{s}\n", .{@typeName(@TypeOf(result))});
}
$ zig run compare.zig
false true true true false false
0.1 + 0.2 = 0.30000000000000004
0.1 + 0.2 == 0.3 ? false
close enough? true
bool

==, !=, <, <=, >, >=. They work on integers, floats, booleans (only == and !=), enums, and a few other types; they do not work on strings, which need std.mem.eql (Chapter 11). Comparison between different integer types follows peer type resolution; comparing an integer to a float needs a conversion.

The float lines demonstrate the fix for section 5.1's problem. Instead of asking whether two computed floats are equal, ask whether they are within a tolerance: std.math.approxEqAbs(f64, a, b, 1e-9) is true when the absolute difference is below the fourth argument. There is also approxEqRel for a relative tolerance, which suits very large or very small values. In tests, std.testing.expectApproxEqAbs does the same job.

One thing Zig does not allow that Python does: chaining. 1 < x < 10 is a compile error, "comparison operators cannot be chained". Write 1 < x and x < 10.

5.7 Booleans

bool has two values, true and false, and three operators, which are words rather than symbols:

bools.zig
const std = @import("std");

pub fn main() void {
    const has_pilot = true;
    const has_mech = false;
    std.debug.print("and: {}\n", .{has_pilot and has_mech});
    std.debug.print("or:  {}\n", .{has_pilot or has_mech});
    std.debug.print("not: {}\n", .{!has_mech});
    std.debug.print("as int: {d}\n", .{@intFromBool(has_pilot)});
    const morale: u8 = 60;
    const fatigue: u8 = 30;
    const ready = has_pilot and morale >= 50 and fatigue < 40;
    std.debug.print("ready to deploy: {}\n", .{ready});
}
$ zig run bools.zig
and: false
or:  true
not: true
as int: 1
ready to deploy: true

and, or, and !. There is no && or ||; type a && b and the compiler says "ambiguous use of '&&'; use 'and' for logical AND". @intFromBool converts to 1 or 0 when you need to add a flag to a number. Comparisons bind tighter than and, and and binds tighter than or, so a and b >= 50 or c means (a and (b >= 50)) or c. When in doubt, add parentheses; zig fmt will not remove them.

and and or short-circuit: the right side is only evaluated when the left side has not already decided the answer.

shortcircuit.zig
const std = @import("std");

fn loud(name: []const u8, value: bool) bool {
    std.debug.print("  evaluating {s}\n", .{name});
    return value;
}

pub fn main() void {
    std.debug.print("false and ...:\n", .{});
    _ = loud("left", false) and loud("right", true);
    std.debug.print("true or ...:\n", .{});
    _ = loud("left", true) or loud("right", false);
}
$ zig run shortcircuit.zig
false and ...:
  evaluating left
true or ...:
  evaluating left

This matters when the right side is expensive or would fail: i < items.len and items[i] == x is safe because the index is only read when it is in range. Chapter 15 leans on this with optionals.

5.8 No truthiness

In Python, JavaScript and C, a number can stand in for a boolean: zero is false, anything else is true. Zig does not do this. The condition of an if or a while must be a bool, and a number is not one:

truthy.zig
const std = @import("std");

pub fn main() void {
    const count: u32 = 3;
    if (count) {
        std.debug.print("nonzero\n", .{});
    }
}
$ zig run truthy.zig
truthy.zig:5:9: error: expected type 'bool', found 'u32'
    if (count) {
        ^~~~~

Write the comparison out: if (count != 0) or if (count > 0). The same applies to pointers and everything else. It costs a few characters and removes a whole class of "is an empty list false?" questions. The only values that can appear in a condition besides bool are optionals and error unions, which have their own special if syntax that captures the inner value; those are Chapters 15 and 16.

In IRON LEDGER. Floats appear in exactly two places in the whole game, and both are geometry rather than accounting: the distance between two worlds in game/src/domain/planet.zig (const dx: f64 = @floatFromInt(a.x - b.x); and then @sqrt(dx * dx + dy * dy)), and the star map, where light-year coordinates are scaled to terminal columns (game/src/tui/app.zig): 
const usable_w: f64 = @floatFromInt(@max(20, @as(i32, inner.w) - 16));
const usable_h: f64 = @floatFromInt(@max(6, @as(i32, inner.h) - 2));
var sx: f64 = @as(f64, @floatFromInt(max_x - min_x)) / usable_w;
var sy: f64 = @as(f64, @floatFromInt(max_y - min_y)) / usable_h;
// …
return .{ @intFromFloat(@floor(cx)), @intFromFloat(@floor(cy)) };
Every integer that enters the calculation goes through @floatFromInt, every result that becomes a screen position goes through @floor and then @intFromFloat, and there is no float anywhere in src/sim/ or src/econ/. Booleans, on the other hand, are everywhere; the calendar's leap-year test in game/src/sim/clock.zig is a one-line boolean expression: return (year % 4 == 0 and year % 100 != 0) or year % 400 == 0;. You will write it yourself in Chapter 7.

Exercise 5.1 · Integer in, float out warm-up

Write average3, which returns the mean of three u32 values as an f64, and percent, which returns part as a percentage of whole rounded to the nearest whole number. You will need @floatFromInt, @intFromFloat and @round. Name the file: exercises/05-floats-bools/ex1_average.zig.

Solution 
//! Chapter 05, exercise 1: integer in, float out.
//! Run with:  zig test ex1_average.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Average of three tonnages as an f64 (so 20, 55, 100 gives 58.333...).
fn average3(a: u32, b: u32, c: u32) f64 {
    const sum: f64 = @floatFromInt(a + b + c);
    return sum / 3.0;
}

/// Percentage of `part` out of `whole`, rounded to the nearest whole number.
/// 1 out of 3 is 33, 2 out of 3 is 67.
fn percent(part: u32, whole: u32) u32 {
    const p: f64 = @floatFromInt(part);
    const w: f64 = @floatFromInt(whole);
    return @intFromFloat(@round(p / w * 100.0));
}

test "average3" {
    try std.testing.expectApproxEqAbs(@as(f64, 58.3333), average3(20, 55, 100), 0.001);
    try std.testing.expectEqual(@as(f64, 50), average3(50, 50, 50));
}

test "percent rounds" {
    try std.testing.expectEqual(@as(u32, 33), percent(1, 3));
    try std.testing.expectEqual(@as(u32, 67), percent(2, 3));
    try std.testing.expectEqual(@as(u32, 100), percent(7, 7));
    try std.testing.expectEqual(@as(u32, 0), percent(0, 7));
}

The sum is computed in u32 and converted once, which is fine here; converting each value first would also work. In percent, the conversions happen before the division, avoiding the integer-division trap, and @round runs before @intFromFloat so that 66.67 becomes 67 rather than 66.

Exercise 5.2 · Comparing honestly practice

Write nearlyEqual(a, b, tolerance) without using std.math.approxEqAbs, and isUsable(x), which is true only for finite numbers. The first test adds 0.1 ten times and checks that the sum is not 1.0 but is nearly 1.0. Name the file: exercises/05-floats-bools/ex2_approx.zig.

Solution 
//! Chapter 05, exercise 2: comparing floats honestly.
//! Run with:  zig test ex2_approx.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// True when a and b are within `tolerance` of each other.
fn nearlyEqual(a: f64, b: f64, tolerance: f64) bool {
    return @abs(a - b) <= tolerance;
}

/// True when x is a finite number (not NaN, not +/- infinity).
fn isUsable(x: f64) bool {
    return !std.math.isNan(x) and !std.math.isInf(x);
}

test "nearlyEqual" {
    var sum: f64 = 0.0;
    for (0..10) |_| sum += 0.1;
    try std.testing.expect(sum != 1.0); // the classic surprise
    try std.testing.expect(nearlyEqual(sum, 1.0, 1e-9));
    try std.testing.expect(!nearlyEqual(1.0, 1.1, 0.01));
}

test "isUsable" {
    try std.testing.expect(isUsable(3.5));
    try std.testing.expect(isUsable(0.0));
    try std.testing.expect(!isUsable(std.math.nan(f64)));
    try std.testing.expect(!isUsable(std.math.inf(f64)));
    try std.testing.expect(!isUsable(-std.math.inf(f64)));
}

@abs works on floats as well as integers. isUsable must reject NaN explicitly, because x == x is the only comparison that catches it and that reads as a trick; std.math.isNan says what it means.

Exercise 5.3 · Ready to deploy practice

Write canDeploy as a single boolean expression from four inputs, following the rule in its doc comment, and moraleLabel as an if expression with three outcomes. Name the file: exercises/05-floats-bools/ex3_ready.zig.

Solution 
//! Chapter 05, exercise 3: a readiness check with and/or/not.
//! Run with:  zig test ex3_ready.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// A unit may deploy when it has a pilot, is not destroyed, and either has
/// at least 30 armor or is being sent on a milk run.
fn canDeploy(has_pilot: bool, destroyed: bool, armor: u8, milk_run: bool) bool {
    return has_pilot and !destroyed and (armor >= 30 or milk_run);
}

/// Morale label: "high" at 70 or more, "low" below 30, otherwise "steady".
fn moraleLabel(morale: u8) []const u8 {
    return if (morale >= 70) "high" else if (morale < 30) "low" else "steady";
}

test "canDeploy" {
    try std.testing.expect(canDeploy(true, false, 50, false));
    try std.testing.expect(canDeploy(true, false, 10, true));
    try std.testing.expect(!canDeploy(true, false, 10, false));
    try std.testing.expect(!canDeploy(false, false, 100, true));
    try std.testing.expect(!canDeploy(true, true, 100, true));
}

test "moraleLabel" {
    try std.testing.expectEqualStrings("high", moraleLabel(70));
    try std.testing.expectEqualStrings("steady", moraleLabel(69));
    try std.testing.expectEqualStrings("steady", moraleLabel(30));
    try std.testing.expectEqualStrings("low", moraleLabel(29));
}

The parentheses around the or are required: without them, and would bind first and a milk run would let a pilotless, destroyed unit deploy. if … else if … else as an expression is previewed here and covered in Chapter 6.

Exercise 5.4 · Price per ton challenge

Write perTon and then print the three-row report in the starter's header: name 12 wide, tons 3 wide, price 9 wide, and price per ton 10 wide with two decimals, followed by the average per-ton price. The starter already loops over three arrays at once with for (names, tons, prices) |name, t, price|, a form Chapter 6 explains. Name the file: exercises/05-floats-bools/ex4_report.zig.

Solution 
//! Chapter 05, exercise 4: a formatted float report.
//! Run with:  zig run ex4_report.zig
//! Expected output (on stderr):
//!   Locust        20 t   1512000 C-bills   75600.00 per ton
//!   Shadow Hawk   55 t   4701000 C-bills   85472.73 per ton
//!   Atlas        100 t   9626000 C-bills   96260.00 per ton
//!   average price per ton: 85777.58
const std = @import("std");

fn perTon(price: u32, tons: u32) f64 {
    const p: f64 = @floatFromInt(price);
    const t: f64 = @floatFromInt(tons);
    return p / t;
}

pub fn main() void {
    const names = [_][]const u8{ "Locust", "Shadow Hawk", "Atlas" };
    const tons = [_]u32{ 20, 55, 100 };
    const prices = [_]u32{ 1_512_000, 4_701_000, 9_626_000 };
    var total: f64 = 0.0;
    for (names, tons, prices) |name, t, price| {
        const ratio = perTon(price, t);
        total += ratio;
        std.debug.print("{s:<12} {d:>3} t {d:>9} C-bills {d:>10.2} per ton\n", .{
            name, t, price, ratio,
        });
    }
    std.debug.print("average price per ton: {d:.2}\n", .{total / 3.0});
}

{d:>10.2} combines width, alignment and precision. The running total is an f64 so that the average keeps its fraction; dividing by 3.0 rather than 3 keeps the literal a float, although a comptime_int would also coerce here.

Check your understanding

  1. Why is 0.1 + 0.2 == 0.3 false for f64 values?
    AnswerNone of 0.1, 0.2 and 0.3 is exactly representable in binary, and the rounding errors of the two operands do not cancel. Compare with a tolerance instead.
  2. How do you turn a u32 into an f64, and the reverse?
    Answer@floatFromInt(x) and @intFromFloat(x), with the target type given by context. The reverse drops the fraction and panics if the integer part does not fit.
  3. What does const h: f64 = n / 2; give when n: u32 = 7?
    Answer3, not 3.5. The integer division runs first, then the result is widened.
  4. What is nan == nan?
    Answerfalse. NaN is unequal to everything, itself included. Use std.math.isNan.
  5. Does 1.0 / 0.0 panic?
    AnswerNo. Float division by zero gives infinity (or NaN for 0/0); only integer division by zero panics.
  6. Why does if (count) fail when count is a u32?
    AnswerZig has no truthiness; a condition must be a bool. Write if (count != 0).
  7. What is wrong with a && b?
    AnswerZig's logical operators are the words and and or; && is a compile error that tells you so.
What you learned.
  • f64 is the default float; floats are approximate, so never test computed floats for equality and never use them for money.
  • @floatFromInt, @intFromFloat and @floatCast convert explicitly; some lossless int-to-float coercions are allowed, but write the builtin anyway, and convert before dividing.
  • {d:.2} prints a float with two decimals; {e} is scientific notation.
  • Float division by zero gives inf or NaN rather than panicking; NaN is never equal to anything; test with std.math.isNan.
  • Comparisons give bool, cannot be chained, and need std.math.approxEqAbs for floats.
  • Boolean operators are and, or, !; they short-circuit; there is no truthiness.
