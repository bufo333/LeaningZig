3. Variables, constants and types

In this chapter you will learn how Zig names values with const and var, when you must write a type and when the compiler works it out, and what undefined means. You will meet four compile errors that every Zig beginner hits in their first hour, with the exact text the compiler prints, and learn the one-line fix for each.

3.1 const and var

A name is introduced with one of two keywords. const binds a name to a value that will never change. var declares a variable that can be assigned again later.

constvar.zig
const std = @import("std");

pub fn main() void {
    const company_name = "Grey Death Legion";
    var funds: i64 = 1_000_000;
    funds -= 250_000;
    std.debug.print("{s} has {d} C-bills\n", .{ company_name, funds });
}
$ zig run constvar.zig
Grey Death Legion has 750000 C-bills

The company name never changes, so it is a const. The funds go down, so they are a var. funds -= 250_000 is short for funds = funds - 250_000, and the same shorthand exists for +=, *=, and the other operators.

Try to change a const and the compiler refuses:

assign_const.zig
const std = @import("std");

pub fn main() void {
    const funds: i64 = 1_000_000;
    funds -= 250_000;
    std.debug.print("{d}\n", .{funds});
}
$ zig run assign_const.zig
assign_const.zig:5:5: error: cannot assign to constant
    funds -= 250_000;
    ^~~~~

The habit to build is the reverse of what most languages teach: start with const, and only write var when you have a line that assigns to the name a second time. This is not just style. The compiler enforces it, as you will see in section 3.5, and it makes code easier to read, because every var is a promise that the value changes somewhere below.

3.2 Type annotations and inference

Every value in Zig has a type, and the type is fixed for the life of the name. You can write the type after a colon, or you can leave it out and let the compiler infer it from the value.

annot.zig
const std = @import("std");

pub fn main() void {
    const a: u8 = 200; // annotated
    const b = a; // inferred: b is also u8
    const c: i64 = a; // u8 fits inside i64, so this is allowed
    const d: f64 = 2.5; // a float literal needs a home too
    std.debug.print("{d} {d} {d} {d}\n", .{ a, b, c, d });
    std.debug.print("{s} {s} {s} {s}\n", .{
        @typeName(@TypeOf(a)), @typeName(@TypeOf(b)),
        @typeName(@TypeOf(c)), @typeName(@TypeOf(d)),
    });
}
$ zig run annot.zig
200 200 200 2.5
u8 u8 i64 f64

@TypeOf(x) is a builtin that gives the type of an expression, and @typeName turns a type into a printable string; together they let a program report what the compiler decided. Here b was declared with no annotation and got u8 because it was initialised from a u8. c was annotated i64 and the u8 value was coerced to the wider type, which is allowed because every u8 value fits in an i64. The reverse, putting an i64 into a u8, is refused, and Chapter 4 covers the rules.

So when do you need the annotation? Inference works whenever the right-hand side already has a concrete type: another variable, a function's return value, an expression of typed values. It does not work, or works differently from what you meant, in two common cases.

3.3 Number literals are comptime_int

Write const x = 42; and ask for its type.

comptime_int.zig
const std = @import("std");

pub fn main() void {
    const x = 42;
    std.debug.print("{s}\n", .{@typeName(@TypeOf(x))});
    const big = 1_000_000_000_000_000_000_000; // does not fit in u64
    std.debug.print("{d}\n", .{big});
    const y: u8 = x; // fine: 42 fits in a u8
    std.debug.print("{d}\n", .{y});
}
$ zig run comptime_int.zig
comptime_int
1000000000000000000000
42

The type is comptime_int: an integer known at compile time, with no fixed width. It can be as large as you like, which is why the thousand-billion-billion literal printed without complaint, and it silently becomes whatever concrete type it is used as, which is why const y: u8 = x worked. A comptime_int is more like a number written on paper than a number stored in memory. Float literals are the same: 2.5 has type comptime_float.

This is convenient right up until you try to change one at runtime:

var_needs_type.zig
const std = @import("std");

pub fn main() void {
    var count = 0;
    count += 1;
    std.debug.print("{d}\n", .{count});
}
$ zig run var_needs_type.zig
var_needs_type.zig:4:9: error: variable of type 'comptime_int' must be const or comptime
    var count = 0;
        ^~~~~
var_needs_type.zig:4:9: note: to modify this variable at runtime, it must be given an explicit fixed-size number type

The note tells you the fix. A var lives in memory and memory has a fixed size, so the compiler needs to know how many bytes to set aside. Write var count: u32 = 0; and the program builds. Rule: a var initialised from a bare number literal always needs a type annotation. A const initialised from a literal does not, and stays a comptime_int until it is used somewhere with a concrete type.

Why not just default to i32 or i64? C does, and the result is that 1 << 40 is silently zero on many compilers because the literal was an int. Zig's literal type is exact and unbounded; only when it meets a concrete type does it get a width, and if it does not fit you get an error at that spot rather than wrong bits.

3.4 Four errors you will hit today

Zig refuses to build code that contains things which are almost always mistakes. Other languages emit warnings for these; Zig emits errors, on the grounds that a warning everyone ignores is worth nothing. Here are the four you will meet first, each with its real message and its fix.

Unused local. Declare something and never use it:

unused.zig
const std = @import("std");

pub fn main() void {
    const tonnage: u32 = 100;
    std.debug.print("ready\n", .{});
}
$ zig run unused.zig
unused.zig:4:11: error: unused local constant
    const tonnage: u32 = 100;
          ^~~~~~~

Usually the fix is to delete the declaration or to use it. Sometimes you genuinely want a name you do not use yet, for example while writing a function one piece at a time; then you discard it by assigning it to the underscore:

discard.zig
const std = @import("std");

pub fn main() void {
    const tonnage: u32 = 100;
    _ = tonnage;
    std.debug.print("ready\n", .{});
}
$ zig run discard.zig
ready

_ = tonnage; tells the compiler "I know, and I mean it." The same applies to function parameters (Chapter 7) and to return values you choose to ignore. The exercise starters in this book use it constantly, so that a half-finished function still compiles. Using a name after discarding it is itself an error ("pointless discard"), so remove the underscore line when you fill the function in.

Never-mutated var. Declare a var and never assign to it again:

never_mutated.zig
const std = @import("std");

pub fn main() void {
    var tonnage: u32 = 100;
    std.debug.print("{d}\n", .{tonnage});
}
$ zig run never_mutated.zig
never_mutated.zig:4:9: error: local variable is never mutated
    var tonnage: u32 = 100;
        ^~~~~~~
never_mutated.zig:4:9: note: consider using 'const'

The fix is in the note: change var to const. This is the rule that makes the "start with const" habit mandatory rather than optional.

Shadowing. Reuse a name that is already visible:

shadow.zig
const std = @import("std");

pub fn main() void {
    const count: u32 = 1;
    {
        const count: u32 = 2;
        std.debug.print("{d}\n", .{count});
    }
    std.debug.print("{d}\n", .{count});
}
$ zig run shadow.zig
shadow.zig:6:15: error: local constant 'count' shadows local constant from outer scope
        const count: u32 = 2;
              ^~~~~
shadow.zig:4:11: note: previous declaration here
    const count: u32 = 1;
          ^~~~~

In most languages the inner count would quietly hide the outer one inside the braces. Zig forbids it, because a reader scanning the function sees one name and expects one meaning. The fix is a different name. The rule applies to every kind of declaration, including the standard-library import at the top of the file:

shadow_std.zig
const std = @import("std");

pub fn main() void {
    const std = 5;
    _ = std;
}
$ zig run shadow_std.zig
shadow_std.zig:4:11: error: local constant shadows declaration of 'std'
    const std = 5;
          ^~~
shadow_std.zig:1:1: note: declared here
const std = @import("std");
^~~~~~~~~~~~~~~~~~~~~~~~~~

Assigning to a const you met in section 3.1: error: cannot assign to constant. The fix is var, if the value really changes.

Trap: the errors come one at a time. When a file has several problems the compiler often reports only the first, because it stops analysing a function at its first error. Fix it, run again, and the next one appears. This is normal and not a sign that you have made things worse.

3.5 undefined

Every declaration needs an initial value. When you have nothing meaningful to put there yet, because the value will be filled in before it is read, you write undefined:

undef.zig
const std = @import("std");

pub fn main() void {
    var total: u32 = undefined;
    total = 10;
    total += 5;
    std.debug.print("{d}\n", .{total});
}
$ zig run undef.zig
15

undefined is a promise: "I will assign this before I read it." The compiler reserves the memory and does not initialise it. You saw var buf: [1024]u8 = undefined; in Chapter 2, where a 1024-byte buffer was declared for a writer to fill; zeroing it first would be wasted work.

Break the promise and you get garbage, not an error:

undef_read.zig
const std = @import("std");

pub fn main() void {
    var total: u32 = undefined;
    total += 5;
    std.debug.print("{d}\n", .{total});
}
$ zig run undef_read.zig
2863311535

In a debug build Zig fills undefined memory with the byte 0xAA, which is why the number is 2863311535 (0xAAAAAAAA) plus five. That pattern is a deliberate tell: if you ever see 43690, 2863311535, or a string of AA bytes in a value, you read something you never set. In a release build the memory holds whatever was there before, and the bug is silent. Use undefined only when the assignment is a line or two away, and prefer a real initial value whenever one makes sense.

3.6 Block scope

A pair of braces is a block, and a name declared inside a block exists only until the closing brace.

block.zig
const std = @import("std");

pub fn main() void {
    const outer: u32 = 1;
    {
        const inner: u32 = 2;
        std.debug.print("inside: {d} {d}\n", .{ outer, inner });
    }
    std.debug.print("outside: {d}\n", .{outer});
    std.debug.print("outside: {d}\n", .{inner});
}
$ zig run block.zig
block.zig:10:41: error: use of undeclared identifier 'inner'
    std.debug.print("outside: {d}\n", .{inner});
                                        ^~~~~

The outer name is visible inside the block; the inner name is gone after it. Function bodies, loop bodies, and the branches of an if are all blocks. You can also open a bare block anywhere just to limit how long a name lives, which the first example did.

A block can also produce a value. Give it a label, and break :label value leaves the block with that value as its result:

block_value.zig
const std = @import("std");

pub fn main() void {
    const tonnage: u32 = 55;
    const weight_class = blk: {
        if (tonnage <= 35) break :blk "light";
        if (tonnage <= 55) break :blk "medium";
        if (tonnage <= 75) break :blk "heavy";
        break :blk "assault";
    };
    std.debug.print("{d} tons is {s}\n", .{ tonnage, weight_class });
}
$ zig run block_value.zig
55 tons is medium

The label blk: goes before the opening brace; the name is yours to choose. Each break :blk ends the block and supplies the value for weight_class. This is how Zig writes "compute a value in several steps, right here" without a helper function or a mutable temporary, and IRON LEDGER uses it often. Chapter 6 shows that if and loops can produce values in the same spirit.

3.7 Top-level declarations

So far every name was declared inside main. Names can also be declared at the top of the file, outside any function, where they are visible to every function in the file.

globals.zig
const std = @import("std");

const max_lance_size = 4;
var battles_fought: u32 = 0;

pub fn main() void {
    battles_fought += 1;
    battles_fought += 1;
    std.debug.print("lance size {d}, battles {d}\n", .{ max_lance_size, battles_fought });
}
$ zig run globals.zig
lance size 4, battles 2

Top-level const is common and good: it is how a file names its constants, imports, and types. Top-level var is a global variable, which every function can change from anywhere; it is legal, occasionally useful, and generally avoided for the same reasons as in any language. IRON LEDGER's simulation core has no global variables at all, by design, and Chapter 41 explains why that matters for a game that must replay identically from a seed.

One difference from local declarations: the order of top-level declarations does not matter. main can use max_lance_size even if it were declared below it, and a function can call another declared further down the file.

3.8 Naming

zig fmt does not police names, but the standard library and nearly all Zig code follow one convention, and this book does too:

  • snake_case for variables, constants, and struct fields: company_name, max_lance_size.
  • camelCase for functions: applyBp, daysInMonth.
  • TitleCase for types: GameState, Date. A function that returns a type is also TitleCase (Chapter 26).

Constants are not shouted in capitals; max_lance_size, not MAX_LANCE_SIZE. Names can contain digits and underscores but not start with a digit. If you truly need a name that is a keyword or contains odd characters, @"…" quoting exists, and you will see it in Chapter 27.

In IRON LEDGER. The game's main opens with a run of var declarations for its command-line flags, each with an explicit initial value, followed by a loop that sets them (game/src/main.zig): 
var repl = false;
var tui = false;
var ascii = false;
var no_splash = false;
var no_music = false;
var data_dir: ?[]const u8 = null;
The first five need no annotation because false has a concrete type, bool. The last one must be annotated because null alone does not say what kind of thing might be there; ?[]const u8 means "either a string or nothing" (Chapter 15). Each of these is a var because the loop below assigns to it; if the loop stopped assigning to one, the build would fail with "local variable is never mutated". And further down game/src/main.zig you will find var stdin_buf: [4096]u8 = undefined;, a buffer declared exactly the way Chapter 2's output buffer was.

Exercises

Exercise 3.1 · Make the compiler happy warm-up

The starter contains four compile errors of the kinds shown in this chapter: an unused local, a never-mutated var, a shadowed name, and an assignment to a const. Fix each in the smallest way that keeps the program's meaning, running zig run after each fix to see the next error. Do not delete the print at the bottom. Name the file: exercises/03-variables/ex1_fix_errors.zig.

Solution 
//! Chapter 03, exercise 1: make the compiler happy.
//! Run with:  zig run ex1_fix_errors.zig
//! Expected output (on stderr):
//!   4 units, 250 tons, avg 62
const std = @import("std");

pub fn main() void {
    const units: u32 = 4;
    const total: u32 = 250; // was var, never mutated
    const commander = "Carlyle";
    _ = commander; // was unused
    const average = total / units;
    {
        const inner_average = 0; // was shadowing `average`
        _ = inner_average;
    }
    // `units = 4;` removed: you cannot assign to a const
    std.debug.print("{d} units, {d} tons, avg {d}\n", .{ units, total, average });
}

The compiler reports the shadowing first and the others one at a time as you fix them. Notice that the unused name is fixed with a discard rather than a deletion, which is what you do when the name is part of a design you have not finished.

Exercise 3.2 · Name the types warm-up

Four top-level constants are declared without types. The tests below them check the type of each with @TypeOf. Add the annotation each test asks for, and nothing else. Run with zig test. Name the file: exercises/03-variables/ex2_types.zig.

Solution 
//! Chapter 03, exercise 2: give each value the type the tests expect.
//! Run with:  zig test ex2_types.zig
//! Goal: make every test pass by changing only the declarations marked TODO.
const std = @import("std");

const seats: u8 = 4;
const tonnage: u32 = 55;
const ratio: f64 = 0.5;
const funds: i64 = 1_000_000;

test "seats is a u8" {
    try std.testing.expectEqual(u8, @TypeOf(seats));
}

test "tonnage is a u32" {
    try std.testing.expectEqual(u32, @TypeOf(tonnage));
}

test "ratio is an f64" {
    try std.testing.expectEqual(f64, @TypeOf(ratio));
}

test "funds is an i64 and can go negative" {
    try std.testing.expectEqual(i64, @TypeOf(funds));
    const after: i64 = funds - 2_000_000;
    try std.testing.expect(after < 0);
}

Without annotations the four constants are comptime_int and comptime_float, and expectEqual(u8, @TypeOf(seats)) fails because the types differ. Types are values in Zig, so a test can compare them like numbers; Chapter 26 makes much of this.

Exercise 3.3 · A value from a block practice

Write weightClass so that it computes its result with a labeled block and break :blk, without early returns, then returns that value. The tests define the boundaries. Name the file: exercises/03-variables/ex3_block_value.zig.

Solution 
//! Chapter 03, exercise 3: compute a value with a labeled block.
//! Run with:  zig test ex3_block_value.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Return the weight class name for a BattleMech tonnage:
/// up to 35 "light", up to 55 "medium", up to 75 "heavy", otherwise "assault".
fn weightClass(tonnage: u32) []const u8 {
    const class = blk: {
        if (tonnage <= 35) break :blk "light";
        if (tonnage <= 55) break :blk "medium";
        if (tonnage <= 75) break :blk "heavy";
        break :blk "assault";
    };
    return class;
}

test "light" {
    try std.testing.expectEqualStrings("light", weightClass(20));
    try std.testing.expectEqualStrings("light", weightClass(35));
}

test "medium" {
    try std.testing.expectEqualStrings("medium", weightClass(36));
    try std.testing.expectEqualStrings("medium", weightClass(55));
}

test "heavy and assault" {
    try std.testing.expectEqualStrings("heavy", weightClass(75));
    try std.testing.expectEqualStrings("assault", weightClass(100));
}

Every path through the block must reach a break :blk; the final one has no condition so that the block always produces something. If you forget it the compiler complains that the block's value is void where a string was expected.

Exercise 3.4 · Swap practice

The starter declares a, b and swaps as constants and then tries to swap the first two and count the swap. Change the declarations that must change, and only those, then write the swap with a single temporary. Name the file: exercises/03-variables/ex4_swap.zig.

Solution 
//! Chapter 03, exercise 4: swap two variables and count mutations.
//! Run with:  zig run ex4_swap.zig
//! Expected output (on stderr):
//!   before: a=3 b=7
//!   after:  a=7 b=3
//!   swaps: 1
const std = @import("std");

pub fn main() void {
    var a: u32 = 3;
    var b: u32 = 7;
    var swaps: u32 = 0;
    std.debug.print("before: a={d} b={d}\n", .{ a, b });
    const tmp = a;
    a = b;
    b = tmp;
    swaps += 1;
    std.debug.print("after:  a={d} b={d}\n", .{ a, b });
    std.debug.print("swaps: {d}\n", .{swaps});
}

All three become var because all three are assigned again. The temporary is a const because it is set once. If you had made tmp a var, the compiler would have told you it is never mutated.

Check your understanding

  1. What is the type of x in const x = 42;?
    Answercomptime_int: an exact compile-time integer with no fixed width. It becomes a concrete type when used as one.
  2. Why does var count = 0; fail to compile?
    AnswerA runtime variable needs a fixed size, and a comptime_int has none. Write var count: u32 = 0; (or another concrete type).
  3. You declared var total: u32 = 5; and the compiler says "local variable is never mutated". What is the fix?
    AnswerChange var to const. Nothing assigns to total after its declaration.
  4. How do you keep an unused variable without deleting it?
    AnswerDiscard it: _ = name;. Remove the discard once you start using the name, or you get a "pointless discard" error.
  5. Is it legal to declare const i inside a loop body when a const i exists outside the loop?
    AnswerNo. Shadowing is a compile error in Zig; pick a different name.
  6. What value does a var x: u32 = undefined; hold if you read it before assigning?
    AnswerIn a debug build, the byte pattern 0xAA repeated (2863311535 for a u32); in a release build, whatever was in that memory. Either way it is a bug.
  7. How does a block produce a value?
    AnswerLabel it, blk: { … }, and leave it with break :blk value;. The block expression evaluates to that value.
What you learned.
  • const never changes; var can be reassigned. Start with const; the compiler rejects a var that is never mutated.
  • Types come after a colon and are usually inferred, but a var initialised from a bare literal must be annotated because literals are comptime_int / comptime_float.
  • Unused locals, never-mutated vars, shadowing, and assigning to a const are compile errors; the fixes are delete or _ =, const, rename, and var.
  • undefined reserves memory without initialising it; read it only after assigning.
  • Braces make a scope; a labeled block can yield a value with break :label value.
  • Top-level declarations are visible file-wide in any order; names are snake_case, camelCase for functions, TitleCase for types.
