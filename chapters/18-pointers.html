18. Pointers

In this chapter you will learn what a pointer is, how to take one with & and follow it with .*, and why a function that needs to change its argument takes a pointer. You will meet the four pointer shapes Zig distinguishes, the difference between a constant pointer and a pointer to a constant, function pointers, and the two classic pointer bugs, one of which the 0.16 compiler now catches for you.

18.1 A pointer is an address

Every variable lives somewhere in memory, at a numbered location called its address. A pointer is a value that holds such an address. Instead of holding a morale score, it holds "where the morale score is". Through the pointer you can read the score, and, if the pointer allows it, change it. That indirection is the whole idea; everything else in this chapter is about the rules Zig puts around it so that it stays safe.

If you come from Python or JavaScript you have used pointers without the name: when you pass a list to a function and the function appends to it, the caller sees the change, because the "list" you passed was really a reference to the list. Zig makes that reference explicit and gives it a type. If you come from C, Zig's pointers are C's pointers with the dangerous operations removed: no arithmetic on single-item pointers, no implicit null, no silent casts.

ptr1.zig

const std = @import("std");

pub fn main() void {
    var morale: u8 = 50;
    const p: *u8 = &morale; // p holds the address of morale

    std.debug.print("morale = {d}\n", .{morale});
    std.debug.print("p.*    = {d}\n", .{p.*});

    p.* += 10; // write through the pointer
    std.debug.print("after p.* += 10, morale = {d}\n", .{morale});

    morale = 5; // write to the variable directly
    std.debug.print("after morale = 5, p.* = {d}\n", .{p.*});

    std.debug.print("type of p: {s}\n", .{@typeName(@TypeOf(p))});
}
morale = 50
p.*    = 50
after p.* += 10, morale = 60
after morale = 5, p.* = 5
type of p: *u8

Three pieces of syntax. *u8 is the type "pointer to a u8". &morale takes the address of morale, producing a value of that type. p.* follows the pointer, and can appear on either side of an assignment: p.* += 10 writes through it, p.* in a print reads through it. Because p and morale name the same byte of memory, changing one changes what you see through the other.

Note that p itself is declared const. That is because the pointer value never changes: it always points at morale. What it points at changes freely, because the type is *u8, a pointer to a mutable byte. Section 18.6 comes back to this distinction.

18.2 *const T: look but do not touch

A pointer type can promise not to write. *const u8 is a pointer through which you may only read. Trying to assign through it is a compile error.

const std = @import("std");

pub fn main() void {
    var morale: u8 = 50;
    const view: *const u8 = &morale; // may read, may not write
    std.debug.print("{d}\n", .{view.*});
    view.* = 60;
}
ptr2.zig:7:9: error: cannot assign to constant
    view.* = 60;
    ~~~~^~
referenced by:
…

A *T coerces to a *const T automatically (giving up the right to write is always safe), never the reverse. This is why so many function parameters in Zig are *const Something: the function is saying "I need to see the whole thing without copying it, and I promise not to change it". Taking the address of a const variable gives you a *const pointer; you cannot get a mutable pointer to something that was declared constant.

18.3 Passing a pointer to mutate

Function arguments in Zig are passed by value: the function gets its own copy and changes to the copy are invisible to the caller. To let a function change the caller's variable, pass a pointer to it. This is the same rule you saw for self in Chapter 12: methods that mutate take self: *T, methods that only read take self: T or self: *const T.

ptr3.zig

const std = @import("std");

const Pilot = struct { name: []const u8, morale: u8, missions: u32 };

// Takes a copy. Changes stay inside this function.
fn cheerCopy(p: Pilot) void {
    var local = p;
    local.morale += 10;
}

// Takes a pointer. Changes reach the caller's variable.
fn cheer(p: *Pilot) void {
    p.morale += 10; // no arrow, no (*p).morale: field access auto-derefs
    p.missions += 1;
}

fn describe(p: *const Pilot) void {
    std.debug.print("{s}: morale {d}, {d} missions\n", .{ p.name, p.morale, p.missions });
}

pub fn main() void {
    var ada = Pilot{ .name = "Ada", .morale = 50, .missions = 0 };
    cheerCopy(ada);
    describe(&ada);
    cheer(&ada);
    describe(&ada);
    cheer(&ada);
    describe(&ada);
}
Ada: morale 50, 0 missions
Ada: morale 60, 1 missions
Ada: morale 70, 2 missions

cheerCopy did nothing visible: it cheered a copy and the copy was thrown away. cheer took *Pilot and its changes stuck. Two conveniences make pointer code read cleanly. First, field access through a pointer needs no arrow: p.morale works whether p is a Pilot or a *Pilot; the compiler inserts the dereference. Second, when you call a method on a variable, Zig takes the address for you: ada.cheer() would work as well as cheer(&ada). You only write & explicitly when passing the pointer as an ordinary argument, as here.

When to take a pointer, and when not to. Take *T when you must mutate. Take *const T when the struct is large and you only read it. Take a plain T for small structs you only read; the compiler is free to pass them however is cheapest. Do not take a pointer "for speed" on a two-field struct; it makes the call site noisier for nothing.

18.4 Pointers to elements, to whole arrays, and to many items

Zig has four pointer shapes, and the type spells out which one you have.

TypePoints atCan index?Knows its length?
*Texactly one Tnon/a
*[N]Tan array of N itemsyesyes, at compile time
[]T (slice)len itemsyesyes, at run time
[*]Tsome unknown number of itemsyesno

ptr4.zig

const std = @import("std");

pub fn main() void {
    var hp = [_]u8{ 10, 20, 30, 40 };

    // pointer to one element
    const second: *u8 = &hp[1];
    second.* = 25;

    // iterate by pointer to modify in place
    for (&hp) |*h| h.* += 1;

    // pointer to the whole array, and coercion to a slice
    const whole: *[4]u8 = &hp;
    const sl: []u8 = whole; // *[N]T coerces to []T
    std.debug.print("{any} len {d}\n", .{ sl, sl.len });
    std.debug.print("{s}\n", .{@typeName(@TypeOf(&hp))});

    // many-item pointer: no length, indexable, used at C boundaries
    const many: [*]u8 = &hp;
    std.debug.print("many[0] = {d}, many[3] = {d}\n", .{ many[0], many[3] });
    std.debug.print("back to a slice: {any}\n", .{many[0..4]});
}
{ 11, 26, 31, 41 } len 4
*[4]u8
many[0] = 11, many[3] = 41
back to a slice: { 11, 26, 31, 41 }

&hp[1] is a single-item pointer to the second element. for (&hp) |*h| iterates the array by pointer, so h.* += 1 changes each element in place; you met this in Chapter 9. &hp on the whole array is a *[4]u8, a pointer to an array, and it coerces to a slice []u8 whenever a slice is wanted, which is why you can pass &array to any function that takes a slice. This coercion is the most common way slices come into existence.

The many-item pointer [*]T is the odd one out: it can be indexed, but carries no length, so nothing stops you indexing past the end. Zig keeps it for one reason: it is what a C pointer is. You will see [*]u8 and its zero-terminated cousin [*:0]const u8 at the boundary with C libraries and almost nowhere else. Whenever you get one, turn it back into a slice as soon as you know the length, as the last line does with many[0..4].

18.5 Alignment, *anyopaque and @ptrCast

Every type has an alignment: an address it may live at must be a multiple of that number. A u32 lives at a multiple of 4, a u64 at a multiple of 8. Structs take the largest alignment of their fields. You rarely think about this, because the compiler and allocators handle it, but the numbers are visible and pointer types carry them.

ptr5.zig

const std = @import("std");

const Unit = struct { tonnage: u8, armour: u16 };

pub fn main() void {
    std.debug.print("u8   size {d} align {d}\n", .{ @sizeOf(u8), @alignOf(u8) });
    std.debug.print("u16  size {d} align {d}\n", .{ @sizeOf(u16), @alignOf(u16) });
    std.debug.print("u32  size {d} align {d}\n", .{ @sizeOf(u32), @alignOf(u32) });
    std.debug.print("u64  size {d} align {d}\n", .{ @sizeOf(u64), @alignOf(u64) });
    std.debug.print("Unit size {d} align {d}\n", .{ @sizeOf(Unit), @alignOf(Unit) });

    var u = Unit{ .tonnage = 55, .armour = 120 };

    // Erase the type: any pointer can become *anyopaque.
    const opaque_ptr: *anyopaque = &u;

    // Recover it: @ptrCast changes the pointee type, @alignCast asserts alignment.
    const back: *Unit = @ptrCast(@alignCast(opaque_ptr));
    back.armour += 1;
    std.debug.print("armour via round trip: {d}\n", .{u.armour});
}
u8   size 1 align 1
u16  size 2 align 2
u32  size 4 align 4
u64  size 8 align 8
Unit size 4 align 2
armour via round trip: 121

*anyopaque is the pointer that has forgotten its type: "an address, of something". It is Zig's spelling of C's void*. Any single-item pointer coerces to it. To get the type back you use @ptrCast, and because *anyopaque has an alignment of 1 while *Unit requires 2, you also need @alignCast, which asserts (checked in Debug) that the address really is suitably aligned. The pair @ptrCast(@alignCast(p)) is the standard incantation, and the destination type is taken from the declared type of the variable you assign to. This is exactly how the allocator interface works: std.mem.Allocator stores a *anyopaque to "whatever the concrete allocator is" and each implementation casts it back to itself. You will write that cast yourself in Chapter 20.

18.6 Constant pointer versus pointer to constant

Two different things can be constant: the pointer, or what it points at. They are independent.

ptr7.zig

const std = @import("std");

pub fn main() void {
    var a: u8 = 1;
    var b: u8 = 2;

    // A pointer to a mutable value; the variable p itself can be re-pointed.
    var p: *u8 = &a;
    p.* = 10;
    p = &b;
    p.* = 20;

    // A constant pointer to a mutable value: q always points at a,
    // but a may still be changed through it.
    const q: *u8 = &a;
    q.* += 1;

    // A pointer to a constant: r may be re-pointed, but never written through.
    var r: *const u8 = &a;
    r = &b;

    std.debug.print("a={d} b={d} r.*={d}\n", .{ a, b, r.* });
}
a=11 b=20 r.*=20
  • var p: *u8: both may change. You can re-point p and write through it.
  • const q: *u8: the pointer is fixed, the target is writable. This is the common case for a local you take once.
  • var r: *const u8: the pointer may be re-pointed, but never written through.
  • const s: *const u8: neither, the fully read-only view.

Read the type from right to left: *const u8 is "pointer to (const u8)". The const or var at the front of the declaration is about the variable holding the pointer, as for any other variable.

18.7 Optional pointers

Chapter 15 promised that ?*T is free, and it is the shape every "find or fail" function returns. Combine it with a capture and you can mutate what you found.

ptr8.zig

const std = @import("std");

const Pilot = struct { name: []const u8, skill: u8 };

var roster = [_]Pilot{
    .{ .name = "Ada", .skill = 4 },
    .{ .name = "Bo", .skill = 6 },
};

fn find(name: []const u8) ?*Pilot {
    for (&roster) |*p| {
        if (std.mem.eql(u8, p.name, name)) return p;
    }
    return null;
}

pub fn main() void {
    if (find("Bo")) |p| {
        p.skill -= 1; // train: lower is better in this ruleset
        std.debug.print("{s} now skill {d}\n", .{ p.name, p.skill });
    }
    const missing = find("Cy");
    std.debug.print("Cy found? {}\n", .{missing != null});
    std.debug.print("?*Pilot is {d} bytes, same as *Pilot ({d})\n", .{ @sizeOf(?*Pilot), @sizeOf(*Pilot) });
}
Bo now skill 5
Cy found? false
?*Pilot is 8 bytes, same as *Pilot (8)

A plain pointer in Zig can never be null; that is what allows the optimisation and what makes p.* always safe on a *T. The compiler is strict about it even at the lowest level:

}

18.8 Function pointers

Functions have addresses too, so you can store one in a variable and call it later. The type is *const fn (Args) Ret, and a plain function name coerces to it. A table of function pointers is how you build a dispatcher, a pipeline, or a callback.

ptr6.zig

const std = @import("std");

fn double(x: i32) i32 {
    return x * 2;
}
fn negate(x: i32) i32 {
    return -x;
}

const Op = *const fn (i32) i32;

fn applyAll(ops: []const Op, start: i32) i32 {
    var v = start;
    for (ops) |op| v = op(v);
    return v;
}

pub fn main() void {
    const f: Op = double;
    std.debug.print("double(21) = {d}\n", .{f(21)});

    const pipeline = [_]Op{ double, negate, double };
    std.debug.print("pipeline(3) = {d}\n", .{applyAll(&pipeline, 3)});
    std.debug.print("{s}\n", .{@typeName(Op)});
}
double(21) = 42
pipeline(3) = -12
*const fn (i32) i32

The const in *const fn is required: you cannot write through a pointer into code. Calling through a function pointer looks exactly like calling a function, op(v). In the standard library, this is how sorting takes its comparison function and how the allocator's vtable holds its four operations.

18.9 The two classic pointer bugs

A pointer is only as good as the memory behind it. Two mistakes produce a pointer to memory that is no longer what you think it is. Both are called dangling pointers, and using one is undefined behaviour: the program might crash, might print garbage, or might appear to work until the day it does not.

Bug 1: a pointer to a local that has ended. Local variables live in the function's stack frame, which is discarded when the function returns. A pointer to one of them is meaningless afterwards. In C this compiles silently. In Zig 0.16, the simple case is a compile error:

const std = @import("std");

// DO NOT DO THIS. `n` lives in makeCounter's stack frame, which is gone
// the moment the function returns. The pointer now points at garbage.
fn makeCounter() *u32 {
    var n: u32 = 0;
    return &n;
}

pub fn main() void {
    const c = makeCounter();
    c.* += 1;
    std.debug.print("{d}\n", .{c.*});
}
ptr9.zig:7:13: error: returning address of expired local variable 'n'
    return &n;
            ^
ptr9.zig:6:9: note: declared runtime-known here
    var n: u32 = 0;
…

The compiler cannot catch every variation, for instance storing &local into a struct that outlives the function, so keep the rule in your head: never let a pointer to a local escape the block the local was declared in. If a value must outlive the function that made it, put it on the heap (Chapter 19) or return it by value and let the caller store it.

Bug 2: a pointer into a container that grew. A growable list keeps its items in one buffer. When it runs out of room, it allocates a bigger buffer, copies the items across, and frees the old one. Any pointer you took into the old buffer now points at freed memory. This one the compiler cannot see, because whether the buffer moves depends on run-time sizes.

ptr10.zig

const std = @import("std");

pub fn main(init: std.process.Init) !void {
    const a = init.gpa;
    var list: std.ArrayList(u32) = .empty;
    defer list.deinit(a);

    try list.append(a, 7);
    const first: *u32 = &list.items[0]; // pointer into the list's buffer
    std.debug.print("before growth, first -> {d}\n", .{first.*});

    // Grow the list a lot. Sooner or later it must move its buffer.
    var i: u32 = 0;
    while (i < 10_000) : (i += 1) try list.append(a, i);

    const still_same = (first == &list.items[0]);
    std.debug.print("buffer still at the old address? {}\n", .{still_same});
    std.debug.print("safe way: re-fetch, items[0] = {d}\n", .{list.items[0]});
    // Reading first.* here would be use-after-free. We do not.
}
before growth, first -> 7
buffer still at the old address? false
safe way: re-fetch, items[0] = 7

The program compares addresses rather than reading through the stale pointer, because reading it would be undefined behaviour and no output from it could be trusted. The comparison shows the buffer moved. The rule that follows: do not hold a pointer into a list or map across an operation that can grow it. Hold an index or a key instead, and re-fetch the pointer after the insert. The IRON LEDGER box has the game's own version of this lesson.

Trap. The dangerous thing about dangling pointers is that they often work. The old buffer's bytes may still be there for a while, so a test passes, and the bug appears weeks later when an allocator reuses that memory. In Debug builds the DebugAllocator helps, because it never hands freed memory back out and unmaps it where it can, so a stale read usually crashes immediately with a trace. Run your tests in Debug.
In IRON LEDGER. Every command handler is a function on gs: *GameState, and every lookup returns an optional pointer into the state's maps: gs.person(id), gs.unit(id), gs.force(id) are all ?*T. The RNG bag in game/src/sim/rng.zig seeds its array of generators by iterating with pointers so it can assign through them: 
for (&self.prngs, 0..) |*prng, i| {
    prng.* = std.Random.DefaultPrng.init(seed ^ (0x9E3779B97F4A7C15 *% (i + 1)));
}
The stale-pointer bug from section 18.9 is one the project hit for real. From the original guide: "If you hold *Force from a hash map and then insert into that map, the map may reallocate and your pointer now points at freed memory. The fix is to re-fetch after any insert." That is why you will see gs.force(id) called again a few lines after a createForce, rather than a pointer kept across it, and why the domain code passes typed IDs around instead of pointers wherever a value must survive a tick.

Exercise 18.1 · Swap through pointers warm-up

Write swap(a: *i32, b: *i32), bump(p: *u32, by: u32) and twice(p: *const u32) u32. File: exercises/18-pointers/ex1_swap.zig.

Solution 
//! Chapter 18, exercise 1: swap through pointers.
//! Run with:  zig test ex1_swap.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Exchange the values behind the two pointers.
fn swap(a: *i32, b: *i32) void {
    const tmp = a.*;
    a.* = b.*;
    b.* = tmp;
}

/// Add `by` to the value behind `p`.
fn bump(p: *u32, by: u32) void {
    p.* += by;
}

/// Read-only: a pointer to const may be read but never written through.
fn twice(p: *const u32) u32 {
    return p.* * 2;
}

test "swap" {
    var x: i32 = 1;
    var y: i32 = 2;
    swap(&x, &y);
    try std.testing.expectEqual(@as(i32, 2), x);
    try std.testing.expectEqual(@as(i32, 1), y);
}

test "bump and twice" {
    var n: u32 = 5;
    bump(&n, 3);
    try std.testing.expectEqual(@as(u32, 8), n);
    try std.testing.expectEqual(@as(u32, 16), twice(&n));
    const frozen: u32 = 21;
    try std.testing.expectEqual(@as(u32, 42), twice(&frozen));
}

twice takes *const u32, which is why the test can pass &frozen, the address of a constant. Try changing its parameter to *u32 and see the compile error.

Exercise 18.2 · Mutate a struct through a pointer practice

Implement survive(p: *Pilot), which updates fields in place, rating(p: *const Pilot), and surviveAll(pilots: []Pilot), which iterates by pointer. File: exercises/18-pointers/ex2_mutate.zig.

Solution 
//! Chapter 18, exercise 2: mutate a struct through a pointer.
//! Run with:  zig test ex2_mutate.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Pilot = struct {
    name: []const u8,
    gunnery: u8,
    piloting: u8,
    missions: u32 = 0,
};

/// One mission survived: missions + 1; every 3rd mission improves
/// gunnery by one (lower is better, minimum 0).
fn survive(p: *Pilot) void {
    p.missions += 1;
    if (p.missions % 3 == 0 and p.gunnery > 0) p.gunnery -= 1;
}

/// Sum of both skills. Takes a pointer to const: it only reads.
fn rating(p: *const Pilot) u8 {
    return p.gunnery + p.piloting;
}

/// Apply `survive` to every pilot in the slice, in place.
fn surviveAll(pilots: []Pilot) void {
    for (pilots) |*p| survive(p);
}

test "survive mutates the caller's pilot" {
    var ada = Pilot{ .name = "Ada", .gunnery = 4, .piloting = 5 };
    survive(&ada);
    survive(&ada);
    try std.testing.expectEqual(@as(u32, 2), ada.missions);
    try std.testing.expectEqual(@as(u8, 4), ada.gunnery);
    survive(&ada);
    try std.testing.expectEqual(@as(u8, 3), ada.gunnery);
    try std.testing.expectEqual(@as(u8, 8), rating(&ada));
}

test "surviveAll" {
    var lance = [_]Pilot{
        .{ .name = "A", .gunnery = 4, .piloting = 5, .missions = 2 },
        .{ .name = "B", .gunnery = 0, .piloting = 5, .missions = 2 },
    };
    surviveAll(&lance);
    try std.testing.expectEqual(@as(u8, 3), lance[0].gunnery);
    try std.testing.expectEqual(@as(u8, 0), lance[1].gunnery);
    try std.testing.expectEqual(@as(u32, 3), lance[1].missions);
}

Inside surviveAll, for (pilots) |*p| gives a *Pilot for each element, which is exactly what survive wants. Without the star you would get copies and the array would not change.

Exercise 18.3 · Arrays, elements and many items practice

Four functions, one per pointer shape: a slice to double in place, a *[4]u8 to fill, a ?*u32 pointing at the largest element, and a [*]const u32 summed with an explicit length. File: exercises/18-pointers/ex3_arrays.zig.

Solution 
//! Chapter 18, exercise 3: pointers to arrays, elements and many items.
//! Run with:  zig test ex3_arrays.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Double every element in place.
fn doubleAll(items: []u32) void {
    for (items) |*x| x.* *= 2;
}

/// Pointer to a fixed-size array: set every element to `v`.
fn fill4(arr: *[4]u8, v: u8) void {
    for (arr) |*x| x.* = v;
}

/// Pointer to the largest element, or null for an empty slice.
fn largest(items: []u32) ?*u32 {
    if (items.len == 0) return null;
    var best: *u32 = &items[0];
    for (items[1..]) |*x| if (x.* > best.*) {
        best = x;
    };
    return best;
}

/// A many-item pointer has no length, so the caller passes one.
fn sumMany(p: [*]const u32, n: usize) u32 {
    var total: u32 = 0;
    var i: usize = 0;
    while (i < n) : (i += 1) total += p[i];
    return total;
}

test "doubleAll" {
    var hp = [_]u32{ 1, 2, 3 };
    doubleAll(&hp); // *[3]u32 coerces to []u32
    try std.testing.expectEqualSlices(u32, &.{ 2, 4, 6 }, &hp);
}

test "fill4" {
    var buf: [4]u8 = undefined;
    fill4(&buf, 'x');
    try std.testing.expectEqualStrings("xxxx", &buf);
}

test "largest points into the slice" {
    var hp = [_]u32{ 5, 9, 2 };
    const p = largest(&hp).?;
    p.* = 0; // writing through the pointer changes the array
    try std.testing.expectEqualSlices(u32, &.{ 5, 0, 2 }, &hp);
    var none = [_]u32{};
    try std.testing.expect(largest(&none) == null);
}

test "sumMany" {
    const hp = [_]u32{ 1, 2, 3, 4 };
    const many: [*]const u32 = &hp;
    try std.testing.expectEqual(@as(u32, 10), sumMany(many, 4));
    try std.testing.expectEqual(@as(u32, 3), sumMany(many, 2));
}

largest returns a pointer into the caller's slice, and the test proves it by writing zero through the pointer and checking the array. sumMany has to be told the length; that is the price of a many-item pointer, and why you convert to a slice as soon as you can.

Exercise 18.4 · A dispatch table of function pointers challenge

Build a table mapping names to *const fn (i32) i32, a lookup returning ?Op, an apply that combines lookup and call, and a pipeline. File: exercises/18-pointers/ex4_fnptr.zig.

Solution 
//! Chapter 18, exercise 4: a dispatch table of function pointers.
//! Run with:  zig test ex4_fnptr.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Op = *const fn (i32) i32;

fn double(x: i32) i32 {
    return x * 2;
}
fn negate(x: i32) i32 {
    return -x;
}
fn square(x: i32) i32 {
    return x * x;
}

const Entry = struct { name: []const u8, op: Op };

const table = [_]Entry{
    .{ .name = "double", .op = double },
    .{ .name = "negate", .op = negate },
    .{ .name = "square", .op = square },
};

/// Look up the operation by name, or null if unknown.
fn lookup(name: []const u8) ?Op {
    for (table) |e| if (std.mem.eql(u8, e.name, name)) return e.op;
    return null;
}

/// Apply the named operation, or return null if the name is unknown.
fn apply(name: []const u8, x: i32) ?i32 {
    const op = lookup(name) orelse return null;
    return op(x);
}

/// Run every op in `ops` left to right, starting from `start`.
fn pipeline(ops: []const Op, start: i32) i32 {
    var v = start;
    for (ops) |op| v = op(v);
    return v;
}

test "apply by name" {
    try std.testing.expectEqual(@as(?i32, 10), apply("double", 5));
    try std.testing.expectEqual(@as(?i32, -5), apply("negate", 5));
    try std.testing.expectEqual(@as(?i32, 25), apply("square", 5));
    try std.testing.expectEqual(@as(?i32, null), apply("cube", 5));
}

test "pipeline" {
    const ops = [_]Op{ double, square, negate };
    try std.testing.expectEqual(@as(i32, -36), pipeline(&ops, 3));
    try std.testing.expectEqual(@as(i32, 7), pipeline(&.{}, 7));
}

Function names coerce to the pointer type when placed in the table. apply uses orelse return null so that an unknown name becomes a null result rather than a crash.

Exercise 18.5 · Do not keep a pointer across a growth challenge

Implement recruit, which appends a pilot to an ArrayList and then links the new pilot and the previous one as wingmen. The list grows five thousand times in the test, so any pointer taken before the append is unsafe afterwards. Use indices. File: exercises/18-pointers/ex5_stale.zig.

Solution 
//! Chapter 18, exercise 5: do not keep a pointer across a growth.
//! Run with:  zig test ex5_stale.zig
//! Goal: make every test pass without changing the tests. `recruit`
//! must never read through a pointer that may have gone stale.
const std = @import("std");

const Pilot = struct { name: []const u8, wingman: ?usize = null };

/// Add `name`, then pair the new pilot with the previous one as wingmen.
/// Returns the index of the new pilot. Hold INDICES, not pointers,
/// across the append: appending may move the whole buffer.
fn recruit(a: std.mem.Allocator, list: *std.ArrayList(Pilot), name: []const u8) !usize {
    const new_index = list.items.len;
    try list.append(a, .{ .name = name });
    if (new_index > 0) {
        const prev = new_index - 1;
        list.items[new_index].wingman = prev;
        list.items[prev].wingman = new_index;
    }
    return new_index;
}

test "pairing survives many reallocations" {
    const a = std.testing.allocator;
    var list: std.ArrayList(Pilot) = .empty;
    defer list.deinit(a);

    var i: usize = 0;
    while (i < 5000) : (i += 1) {
        const idx = try recruit(a, &list, "pilot");
        try std.testing.expectEqual(i, idx);
    }
    try std.testing.expectEqual(@as(?usize, 1), list.items[0].wingman);
    try std.testing.expectEqual(@as(?usize, 2), list.items[1].wingman);
    try std.testing.expectEqual(@as(?usize, 4999), list.items[4998].wingman);
    try std.testing.expectEqual(@as(?usize, 4998), list.items[4999].wingman);
}

The tempting wrong version takes const prev = &list.items[len - 1]; before the append and writes prev.wingman after it. It may even pass a small test. Indices survive reallocation because they are re-resolved against list.items every time.

Check your understanding

  1. What do &x and p.* do?
    Answer&x produces a pointer to x; p.* follows a pointer to read or write the value it points at.
  2. Why must a function that changes its argument take a pointer?
    AnswerArguments are passed by value, so the function gets a copy. A pointer lets it reach the caller's original.
  3. What is the difference between *[4]u8, []u8 and [*]u8?
    AnswerPointer to an array of exactly 4 (length known at compile time); slice (pointer plus run-time length); many-item pointer (no length at all, for C boundaries).
  4. Is const p: *u8 = &x; a pointer you can write through?
    AnswerYes. const fixes the pointer variable; the type *u8 allows writing through it. *const u8 would not.
  5. What does @ptrCast(@alignCast(p)) do to a *anyopaque?
    Answer@alignCast asserts the address has the alignment the target type needs; @ptrCast changes the pointee type to the one being assigned to.
  6. Why is returning &local from a function wrong, and what does Zig 0.16 do about it?
    AnswerThe local's stack frame is gone after return, so the pointer dangles. The compiler rejects the direct case with "returning address of expired local variable".
  7. You take a pointer to an element of an ArrayList, then append. What should you assume?
    AnswerThat the pointer is invalid. The buffer may have moved. Keep an index and re-fetch after the append.
What you learned.
  • *T holds an address; &x makes one; p.* follows it; field access through a pointer needs no arrow.
  • *const T may only be read through; *T coerces to it, not the reverse.
  • Pass *T to mutate, *const T to read a large struct, plain T for small read-only values.
  • Four shapes: *T, *[N]T (coerces to a slice), []T, [*]T (C boundary only).
  • *anyopaque is the untyped pointer; recover the type with @ptrCast(@alignCast(p)).
  • Pointers can be null only as ?*T; function pointers are *const fn (…) R.
  • Never let a pointer to a local escape, and never hold a pointer into a container across a growth.
