16. Errors

In this chapter you will learn how Zig functions report failure: not by throwing, not by returning -1, but by returning a value from an error set. You will write error sets, error unions and the four verbs try, catch, switch and errdefer (the last one gets its own chapter next). You will read a real error return trace and learn what an error escaping from main does to your program's exit code.

16.1 Errors are values

If you come from Python or JavaScript, failure means an exception: control jumps out of the current function, and out of its caller, and its caller's caller, until something catches it. Nothing in the source text of the intermediate functions shows that this can happen. If you come from C, failure means a return code that every caller must remember to check, and many do not.

Zig sits between the two. A function that can fail says so in its return type, and callers must do something with the failure: pass it up, handle it, or explicitly assert it cannot happen. But there is no jumping. An error is an ordinary value, returned with an ordinary return, and the code that passes it up is visible in the text as a try.

The values come from an error set, which looks like an enum of failure names:

const HireError = error{
    InsufficientTreasury,
    NoBerth,
    UnknownPerson,
};

A single error value is written error.NoBerth. A function that either succeeds with a u32 or fails with a HireError has the return type HireError!u32, read as "HireError or u32". This is an error union. Here is a complete program.

err1.zig

const std = @import("std");

const HireError = error{
    InsufficientTreasury,
    NoBerth,
    UnknownPerson,
};

fn hire(treasury: u32, cost: u32, free_berths: u32) HireError!u32 {
    if (free_berths == 0) return error.NoBerth;
    if (cost > treasury) return error.InsufficientTreasury;
    return treasury - cost;
}

pub fn main() !void {
    const left = try hire(10_000, 2_500, 3);
    std.debug.print("hired, {d} c-bills left\n", .{left});

    const left2 = try hire(1_000, 2_500, 3);
    std.debug.print("hired again, {d} c-bills left\n", .{left2});
}

There is a lot in that transcript. The first hire succeeds and prints. The second fails: hire returns error.InsufficientTreasury, the try in main sees an error and returns it from main, and because main is declared as !void, the runtime prints the error's name, prints an error return trace, and exits with status 1. The trace is not a stack trace of where the program was; it is a list of every return error… and every try the error passed through on its way out, innermost first. In Debug builds this is free and always on, and it is the single most useful thing Zig gives you for debugging failures.

The exit code matters when your program is run from a script. echo $? after a successful run prints 0. After an error escapes main, it prints 1. You do not have to write any of this yourself.

16.2 try: pass it up

try expr means: evaluate expr; if it is an error, return that error from the current function right now; otherwise unwrap the success value. It is exactly this expansion:

const left = hire(10_000, 2_500, 3) catch |err| return err;

Nine out of ten error sites in real Zig code are a try. The failure path exists, is handled, and takes one syllable. Because try returns from the current function, the current function must itself be able to return errors. If it is not, you get a compile error, and it is one of the first you will meet:

    if (n == 0) return error.Zero;
    return n * 2;
}

pub fn main() void {
    const v = try mightFail(3);
    std.debug.print("{d}\n", .{v});
}

16.3 Inferred error sets: !T

Writing error{…}!u32 on every function gets old. If you write just !u32, the compiler infers the error set from the body: every return error.X and every try contributes its errors. step1, step2 and step3 above all use this. Most functions you write should too. Name the set explicitly when it is part of an interface other people will program against (IRON LEDGER names commands.Error because the UI switches on it), or when you want the compiler to reject an error that should not be possible.

16.4 catch: handle it here

When you do not want to pass an error up, catch handles it in place. It has four shapes, and you will use all of them.

err2.zig

const std = @import("std");

fn parseTonnage(text: []const u8) !u8 {
    return std.fmt.parseInt(u8, text, 10);
}

pub fn main() void {
    // 1. catch with a fallback value
    const a = parseTonnage("55") catch 50;
    const b = parseTonnage("heavy") catch 50;
    std.debug.print("a={d} b={d}\n", .{ a, b });

    // 2. catch and look at the error
    const c = parseTonnage("999") catch |err| blk: {
        std.debug.print("could not parse: {s}\n", .{@errorName(err)});
        break :blk 0;
    };
    std.debug.print("c={d}\n", .{c});

    // 3. catch {} : swallow it (rare, do it on purpose)
    _ = parseTonnage("x") catch {};

    // 4. catch unreachable: "this cannot fail", checked in Debug
    const d = parseTonnage("75") catch unreachable;
    std.debug.print("d={d}\n", .{d});
}
a=55 b=50
could not parse: Overflow
c=0
d=75
  • expr catch value: if it fails, use value instead. The most common shape after try.
  • expr catch |err| { … }: capture the error and run a block. If the block must produce a value for the surrounding expression, use a labelled block with break :blk value, as in the third example. If the block returns or continues, no value is needed.
  • expr catch {}: swallow it. Legal, occasionally right, and always worth a comment. The game uses it for "if even the rollback fails there is nothing more to do".
  • expr catch unreachable: assert it cannot fail. Debug builds panic if you are wrong. Reach for it when the input is a compile-time constant you can see is valid, like divCeil(u32, n, 30) catch unreachable where the divisor is literally 30.

Note that "999" failed with Overflow, not with some generic "bad input": parseInt into a u8 reports a number that is too large separately from a string that is not a number. Its error set has several members, and @errorName turns any of them into its name as a string.

16.5 Switching on an error

Inside a catch |err| block, err is a value of the function's error set, and you can switch on it like an enum. The switch must be exhaustive: name every member of the set, or add an else.

err3.zig

const std = @import("std");

const ParseError = error{ Empty, NotANumber, TooBig };

fn parsePercent(text: []const u8) ParseError!u8 {
    if (text.len == 0) return error.Empty;
    const n = std.fmt.parseInt(u32, text, 10) catch return error.NotANumber;
    if (n > 100) return error.TooBig;
    return @intCast(n);
}

fn describe(text: []const u8) void {
    const pct = parsePercent(text) catch |err| {
        const msg = switch (err) {
            error.Empty => "you gave me nothing",
            error.NotANumber => "that is not a number",
            error.TooBig => "a percentage between 0 and 100",
        };
        std.debug.print("'{s}': {s}\n", .{ text, msg });
        return;
    };
    std.debug.print("'{s}': {d}%\n", .{ text, pct });
}

pub fn main() void {
    describe("40");
    describe("");
    describe("forty");
    describe("140");
}
'40': 40%
'': you gave me nothing
'forty': that is not a number
'140': a percentage between 0 and 100

This is the pattern for turning errors into sentences at the edge of a program. Note how parsePercent itself converts the standard library's parse error into its own vocabulary with catch return error.NotANumber. The caller never sees Overflow or InvalidCharacter; it sees the three cases the function promised. Because the set is explicit, forgetting one is a compile error:

const std = @import("std");

const ParseError = error{ Empty, NotANumber };

fn parsePercent(text: []const u8) ParseError!u8 {
    if (text.len == 0) return error.Empty;
    return std.fmt.parseInt(u8, text, 10) catch error.NotANumber;
}

pub fn main() void {
    _ = parsePercent("5") catch |err| switch (err) {
        error.Empty => std.debug.print("empty\n", .{}),
        // forgot NotANumber
    };
}

16.6 Merging sets, anyerror and @errorName

Error sets combine with ||. If load can fail in the file layer or the format layer, its set is the union of both, and any function that calls it with try inherits the union.

err5.zig

const std = @import("std");

const FileError = error{ NotFound, PermissionDenied };
const ParseError = error{ BadSyntax, TooLong };
const LoadError = FileError || ParseError;

fn load(name: []const u8) LoadError!u32 {
    if (name.len == 0) return error.NotFound;
    if (name.len > 8) return error.TooLong;
    if (name[0] == '!') return error.BadSyntax;
    return @intCast(name.len);
}

fn report(err: anyerror) void {
    std.debug.print("failed with {s}\n", .{@errorName(err)});
}

pub fn main() void {
    const names = [_][]const u8{ "save1", "", "!bad", "far_too_long" };
    for (names) |n| {
        const v = load(n) catch |err| {
            report(err);
            continue;
        };
        std.debug.print("loaded {s}: {d}\n", .{ n, v });
    }

    // an error set is a type; its members are values you can compare
    const e: LoadError = error.TooLong;
    std.debug.print("e == error.TooLong? {}\n", .{e == error.TooLong});
    std.debug.print("the whole union: {}\n", .{LoadError});
}
loaded save1: 5
failed with NotFound
failed with BadSyntax
failed with TooLong
e == error.TooLong? true
the whole union: error{BadSyntax,NotFound,PermissionDenied,TooLong}

anyerror is the set of every error in the whole program. A function taking anyerror accepts any error value at all, which is what you want for a generic "print this failure" helper like report. Any specific set coerces to anyerror; the reverse needs an explicit check. Printing an error set type with {} shows its members, sorted, as the last line demonstrates.

Two more shapes you will meet in signatures. std.mem.Allocator.Error!T says "this can only fail with OutOfMemory". And error{}!T uses the empty set: the function cannot fail, but has the error-union shape so that try on it compiles. It appears in generic code that wants one calling convention whether or not the underlying operation can fail.

const std = @import("std");

/// `error{}` is the empty set: this function promises it cannot fail,
/// but still has the error-union shape so `try` works on it.
fn cannotFail(x: u32) error{}!u32 {
    return x + 1;
}

fn onlyOom(a: std.mem.Allocator) std.mem.Allocator.Error![]u8 {
    return a.alloc(u8, 4);
}

pub fn main() !void {
    const v = try cannotFail(1);
    std.debug.print("{d}\n", .{v});
    const buf = try onlyOom(std.heap.page_allocator);
    defer std.heap.page_allocator.free(buf);
    std.debug.print("{d} bytes\n", .{buf.len});
}
2
4 bytes

16.7 An error union around an optional

Because ?T is a type, E!?T is a type: "either an error, or maybe a T". The two mean different things and both are useful. A command parser is the classic case: a malformed line is an error, an unrecognised verb is simply no command.

err7.zig

const std = @import("std");

const Command = union(enum) {
    hire: []const u8,
    fire: []const u8,
    quit,
};

const ParseError = error{ MissingName, EmptyLine };

/// Can fail (bad syntax), and on success may still be "not a command".
fn parseCommand(line: []const u8) ParseError!?Command {
    var it = std.mem.tokenizeScalar(u8, line, ' ');
    const verb = it.next() orelse return error.EmptyLine;
    if (std.mem.eql(u8, verb, "quit")) return .quit;
    if (std.mem.eql(u8, verb, "hire")) return .{ .hire = it.next() orelse return error.MissingName };
    if (std.mem.eql(u8, verb, "fire")) return .{ .fire = it.next() orelse return error.MissingName };
    return null; // not a verb we know
}

pub fn main() void {
    const lines = [_][]const u8{ "hire Steiner", "dance", "hire", "", "quit" };
    for (lines) |line| {
        const maybe = parseCommand(line) catch |err| {
            std.debug.print("'{s}': error {s}\n", .{ line, @errorName(err) });
            continue;
        };
        if (maybe) |cmd| {
            std.debug.print("'{s}': {s}\n", .{ line, @tagName(cmd) });
        } else {
            std.debug.print("'{s}': unknown verb, ignored\n", .{line});
        }
    }
}
'hire Steiner': hire
'dance': unknown verb, ignored
'hire': error MissingName
'': error EmptyLine
'quit': quit

Read the type inside-out: an optional Command, wrapped in a possible ParseError. Unwrap it in the same order: catch or try first to remove the error, then if … |cmd| or orelse to remove the optional. Inside the parser, it.next() orelse return error.MissingName converts a missing token (an optional) into an error in one expression. Keep the two ideas distinct in your own designs: an optional is for "absent, and that is normal"; an error is for "something went wrong and the caller should know why".

16.8 Testing errors

std.testing.expectError asserts that an expression fails with a specific error. Combined with try on the success path, it lets a test cover both outcomes without any if.

err8.zig

const std = @import("std");

const Bank = struct {
    funds: u32,

    const WithdrawError = error{Insufficient};

    fn withdraw(self: *Bank, amount: u32) WithdrawError!void {
        if (amount > self.funds) return error.Insufficient;
        self.funds -= amount;
    }
};

test "withdraw succeeds when funds allow" {
    var b = Bank{ .funds = 100 };
    try b.withdraw(40);
    try std.testing.expectEqual(@as(u32, 60), b.funds);
}

test "withdraw fails when short" {
    var b = Bank{ .funds = 10 };
    try std.testing.expectError(error.Insufficient, b.withdraw(40));
    try std.testing.expectEqual(@as(u32, 10), b.funds);
}
1/2 err8.test.withdraw succeeds when funds allow...OK
2/2 err8.test.withdraw fails when short...OK
All 2 tests passed.

Note that test blocks themselves return !void, which is why try works inside them. A test that returns an error fails.

16.9 Why this design

Exceptions hide control flow: any call might not return. Return codes hide failures: any caller might not check. Zig's error unions make the failure part of the type and the propagation part of the text, so both are visible, and the compiler enforces that neither is forgotten. The cost is a try on most lines that call something fallible. In exchange you get exhaustive handling at the edges, a return trace that names every hop, and functions whose signatures tell you everything that can go wrong.

One thing errors deliberately cannot do is carry data. error.UnknownPerson has no field for which person. If the caller needs details, put them somewhere the caller can read (a field on the struct, an out-parameter, a log), or return a tagged union instead. This keeps errors as cheap as an integer, which is what makes returning them on every hop free.

In IRON LEDGER. The command layer names its error set explicitly in game/src/sim/commands.zig, about sixty members merged with the allocator's, and every command goes through one function with that set in its signature: 
pub const Error = error{
    UnknownPerson,
    UnknownForce,
    UnknownUnit,
    InsufficientTreasury,
    CompanyDeployed,
    NoBerth,
    BadPercent,
    BadYear,
    // … about sixty
} || std.mem.Allocator.Error;   // merged with OutOfMemory

pub fn execute(gs: *GameState, cmd: Command) Error!Result { // … }
The errors travel up unchanged until the user interface, where errorText in game/src/sim/cli.zig takes an anyerror and switches it into sentences, with else => @errorName(err) as the fallback so an unexpected error still shows its name. The terminal client's key loop is a single catch: self.handleKey(key) catch |err| self.say(.crit, "error: {s}", .{@errorName(err)});, so no keypress can crash the game, and the REPL parser returns ParseError!?Command, exactly the nesting from section 16.7.

Exercise 16.1 · An error set and a function that uses it warm-up

Implement parsePercent returning ParseError!u8, converting the standard library's parse failure into error.NotANumber, and sumPercent which propagates with try. File: exercises/16-errors/ex1_parse.zig.

Solution 
//! Chapter 16, exercise 1: an error set and a function that uses it.
//! Run with:  zig test ex1_parse.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const ParseError = error{ Empty, NotANumber, TooBig };

/// "40" -> 40. "" -> Empty. "forty" -> NotANumber. "140" -> TooBig.
fn parsePercent(text: []const u8) ParseError!u8 {
    if (text.len == 0) return error.Empty;
    const n = std.fmt.parseInt(u32, text, 10) catch return error.NotANumber;
    if (n > 100) return error.TooBig;
    return @intCast(n);
}

/// Parse two percentages and add them; propagate any error with `try`.
fn sumPercent(a: []const u8, b: []const u8) ParseError!u32 {
    const x = try parsePercent(a);
    const y = try parsePercent(b);
    return @as(u32, x) + y;
}

test "good input" {
    try std.testing.expectEqual(@as(u8, 40), try parsePercent("40"));
    try std.testing.expectEqual(@as(u8, 100), try parsePercent("100"));
}

test "bad input" {
    try std.testing.expectError(error.Empty, parsePercent(""));
    try std.testing.expectError(error.NotANumber, parsePercent("forty"));
    try std.testing.expectError(error.TooBig, parsePercent("140"));
}

test "try propagates" {
    try std.testing.expectEqual(@as(u32, 70), try sumPercent("30", "40"));
    try std.testing.expectError(error.TooBig, sumPercent("30", "400"));
    try std.testing.expectError(error.Empty, sumPercent("", "400"));
}

The catch return error.NotANumber is the translation step: callers only ever see the three errors in ParseError. Parsing into a u32 first and checking > 100 afterwards keeps "140" a TooBig rather than an overflow.

Exercise 16.2 · catch, and switching on an error practice

Write parseOr with a one-line catch, an exhaustive errorText switch, and describe, which returns a tagged union of value or message. File: exercises/16-errors/ex2_catch.zig.

Solution 
//! Chapter 16, exercise 2: catch, and switching on an error.
//! Run with:  zig test ex2_catch.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const ParseError = error{ Empty, NotANumber, TooBig };

fn parsePercent(text: []const u8) ParseError!u8 {
    if (text.len == 0) return error.Empty;
    const n = std.fmt.parseInt(u32, text, 10) catch return error.NotANumber;
    if (n > 100) return error.TooBig;
    return @intCast(n);
}

/// Parse, or fall back to `default`. One line with `catch`.
fn parseOr(text: []const u8, default: u8) u8 {
    return parsePercent(text) catch default;
}

/// A sentence for each error. The switch must be exhaustive.
fn errorText(err: ParseError) []const u8 {
    return switch (err) {
        error.Empty => "you gave me nothing",
        error.NotANumber => "that is not a number",
        error.TooBig => "a percentage between 0 and 100",
    };
}

/// Parse and, on failure, return the sentence instead of the number.
/// Return type: a tagged union so the caller can tell which happened.
const Outcome = union(enum) { value: u8, message: []const u8 };

fn describe(text: []const u8) Outcome {
    const v = parsePercent(text) catch |err| return .{ .message = errorText(err) };
    return .{ .value = v };
}

test "parseOr" {
    try std.testing.expectEqual(@as(u8, 40), parseOr("40", 5));
    try std.testing.expectEqual(@as(u8, 5), parseOr("", 5));
    try std.testing.expectEqual(@as(u8, 5), parseOr("x", 5));
}

test "errorText" {
    try std.testing.expectEqualStrings("you gave me nothing", errorText(error.Empty));
    try std.testing.expectEqualStrings("a percentage between 0 and 100", errorText(error.TooBig));
}

test "describe" {
    try std.testing.expectEqual(@as(u8, 12), describe("12").value);
    try std.testing.expectEqualStrings("that is not a number", describe("twelve").message);
}

describe shows catch |err| return …: the catch block leaves the function, so no value is needed for v on that path. Try deleting one arm of errorText's switch to see the exhaustiveness error.

Exercise 16.3 · Merging sets, anyerror and @errorName practice

Define LoadError as the merge of two sets and Allocator.Error, implement load, and write an errorText(anyerror) with an else that falls back to @errorName. File: exercises/16-errors/ex3_merge.zig.

Solution 
//! Chapter 16, exercise 3: merging error sets, anyerror and @errorName.
//! Run with:  zig test ex3_merge.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const FileError = error{ NotFound, PermissionDenied };
const FormatError = error{ BadSyntax, TooLong };

/// Everything `load` can fail with: both sets merged, plus OutOfMemory.
const LoadError = FileError || FormatError || std.mem.Allocator.Error;

/// Pretend loader. Returns a copy of `name` (caller frees) or an error:
///   ""        -> NotFound
///   "locked"  -> PermissionDenied
///   starts '!' -> BadSyntax
///   > 8 chars -> TooLong
fn load(a: std.mem.Allocator, name: []const u8) LoadError![]u8 {
    if (name.len == 0) return error.NotFound;
    if (std.mem.eql(u8, name, "locked")) return error.PermissionDenied;
    if (name[0] == '!') return error.BadSyntax;
    if (name.len > 8) return error.TooLong;
    return a.dupe(u8, name);
}

/// A message for any error at all. Unknown ones fall back to @errorName.
fn errorText(err: anyerror) []const u8 {
    return switch (err) {
        error.NotFound => "no such save",
        error.PermissionDenied => "that save is locked",
        error.OutOfMemory => "out of memory",
        else => @errorName(err),
    };
}

test "load ok" {
    const s = try load(std.testing.allocator, "save1");
    defer std.testing.allocator.free(s);
    try std.testing.expectEqualStrings("save1", s);
}

test "load errors" {
    const a = std.testing.allocator;
    try std.testing.expectError(error.NotFound, load(a, ""));
    try std.testing.expectError(error.PermissionDenied, load(a, "locked"));
    try std.testing.expectError(error.BadSyntax, load(a, "!x"));
    try std.testing.expectError(error.TooLong, load(a, "far_too_long"));
}

test "errorText" {
    try std.testing.expectEqualStrings("no such save", errorText(error.NotFound));
    try std.testing.expectEqualStrings("TooLong", errorText(error.TooLong));
    try std.testing.expectEqualStrings("Whatever", errorText(error.Whatever));
}

The last assertion passes error.Whatever, an error that appears nowhere else in the program. It is still a valid anyerror, and the else arm prints its name. Also note the first test frees what load returned: an error union around an owned slice is the usual shape for "allocate or fail".

//! Chapter 16, exercise 4: an error union around an optional (E!?T).
//! Run with:  zig test ex4_nested.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Command = union(enum) {
    hire: []const u8,
    fire: []const u8,
    advance: u32,

const ParseError = error{ EmptyLine, MissingArgument, BadNumber };

/// Parse one line of the REPL.
///   error  -> the line was malformed
///   null   -> well-formed but not a verb we know
///   value  -> a command
fn parseCommand(line: []const u8) ParseError!?Command {
    var it = std.mem.tokenizeScalar(u8, line, ' ');
    const verb = it.next() orelse return error.EmptyLine;
    if (std.mem.eql(u8, verb, "quit")) return .quit;
    if (std.mem.eql(u8, verb, "hire")) return .{ .hire = it.next() orelse return error.MissingArgument };
    if (std.mem.eql(u8, verb, "fire")) return .{ .fire = it.next() orelse return error.MissingArgument };
    if (std.mem.eql(u8, verb, "advance")) {
        const arg = it.next() orelse return error.MissingArgument;
        const n = std.fmt.parseInt(u32, arg, 10) catch return error.BadNumber;
        return .{ .advance = n };
    }
    return null;
}

test "commands" {
    const h = (try parseCommand("hire Steiner")).?;
    try std.testing.expectEqualStrings("Steiner", h.hire);
    const adv = (try parseCommand("advance 7")).?;
    try std.testing.expectEqual(@as(u32, 7), adv.advance);
    try std.testing.expect((try parseCommand("quit")).? == .quit);
}

test "unknown verb is null, not an error" {
    try std.testing.expect((try parseCommand("dance wildly")) == null);
}

test "malformed lines are errors" {
    try std.testing.expectError(error.EmptyLine, parseCommand("   "));
    try std.testing.expectError(error.MissingArgument, parseCommand("hire"));
    try std.testing.expectError(error.BadNumber, parseCommand("advance soon"));
}

Every missing token becomes an error through orelse return error.…, and the number parse becomes BadNumber through catch return. The tests unwrap in the right order: (try parseCommand(…)).? removes the error first, then the optional.

Check your understanding

  1. What does try f() expand to?
    Answerf() catch |err| return err: on failure, return the error from the current function; on success, the unwrapped value.
  2. Why does try inside a function returning void fail to compile?
    AnswerBecause try may return an error, and the function's return type says it returns none. Make it !void or handle the error with catch.
  3. What happens when an error escapes main?
    AnswerThe runtime prints error: Name, an error return trace in Debug builds, and the process exits with status 1.
  4. What is the difference between an error return trace and a stack trace?
    AnswerA stack trace shows where the program is now. An error return trace lists every return error and try the error passed through on its way up, innermost first.
  5. When would you use catch unreachable?
    AnswerWhen you can see from the inputs that failure is impossible, such as dividing by a literal constant. Debug builds panic if you are wrong.
  6. What does A || B mean for error sets?
    AnswerThe merged set containing every member of both. A function that trys calls from both layers has the merged set as its inferred error set.
  7. What is the difference between returning null and returning an error from a parser?
    Answernull means "nothing here, and that is normal" (unknown verb). An error means "something went wrong and the caller should know why" (missing argument).
  8. Can an error carry a payload, like a message or an ID?
    AnswerNo. Errors are bare names, as cheap as an integer. Put the details somewhere else, or return a tagged union.
What you learned.
  • An error set is a list of names; error.Name is a value; E!T is "error or value"; !T lets the compiler infer E.
  • try passes an error up and is only legal in a function that can return errors.
  • catch value, catch |err| {…}, catch {} and catch unreachable handle errors in place.
  • A switch on an error must be exhaustive; explicit sets make forgotten cases compile errors.
  • A || B merges sets; anyerror accepts all; @errorName gives the name as text.
  • An error escaping main prints a return trace and exits with status 1.
  • E!?T nests an optional inside an error union; unwrap the error first, then the optional.
