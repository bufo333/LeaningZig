20. Choosing an allocator

In this chapter you will meet the allocators the standard library ships, learn what each one is for, and see the one pattern that does most of the work in real Zig programs: an arena per lifetime. You will run out of memory on purpose, watch a use-after-free crash cleanly, write an allocator of your own that counts what passes through it, and finish with a table to choose from.

20.1 The allocator is a decision

Chapter 19 showed that a std.mem.Allocator is a small value that any function can take. Because it is a value, the caller decides which one to pass, and different choices have very different behaviour. One allocator checks every free and reports leaks. One never frees anything individually and releases everything at once. One hands out memory from a fixed array and refuses when it is full. They all present the same interface, so the code that uses them does not change; only the line that creates the allocator does.

This is the part of Zig that newcomers find strangest, and the part that experienced Zig programmers like most. Instead of one heap with one policy for the whole program, you match the allocator to the lifetime of the data. Memory that lives for one frame gets a frame allocator. Memory that lives for one campaign gets a campaign allocator. The program becomes easier to reason about because the question "when is this freed?" has a structural answer.

20.2 DebugAllocator: the one for development

You met it in Chapter 19. std.heap.DebugAllocator(.{}) is a general-purpose allocator that tracks every block, detects leaks, double frees and, where the operating system allows, use-after-free. It is slower than a production allocator, which is fine, because its job is to be in your Debug builds and tests. Here is what a use-after-free looks like under it.

al8.zig

const std = @import("std");

pub fn main() void {
    var gpa: std.heap.DebugAllocator(.{}) = .init;
    defer _ = gpa.deinit();
    const a = gpa.allocator();

    const buf = a.alloc(u8, 4) catch return;
    a.free(buf);
    buf[0] = 1; // use after free
    std.debug.print("{d}\n", .{buf[0]});
}
Segmentation fault at address 0x…
ch20/al8.zig:10:8: 0x… in main (al8)
    buf[0] = 1; // use after free
       ^
…

The crash is immediate and points at the offending line, because the DebugAllocator unmaps freed pages rather than reusing them. The same bug under a production allocator would silently write into memory that something else may now own. This is why you run tests in Debug.

init.gpa in main is a DebugAllocator in Debug builds. In release builds the runtime swaps it for std.heap.c_allocator if you linked libc and std.heap.smp_allocator otherwise, both fast and unchecked. Your code does not change.

20.3 page_allocator: straight from the operating system

std.heap.page_allocator asks the operating system for memory directly, one page at a time. It needs no setup and no deinit, and it is thread-safe. It is also the most expensive way to get a small block, because a page is the smallest thing the OS will give you, and a system call is the slowest thing your program does.

al4.zig

const std = @import("std");

pub fn main() !void {
    const a = std.heap.page_allocator;
    const small = try a.alloc(u8, 1);
    defer a.free(small);
    const big = try a.alloc(u8, 10_000);
    defer a.free(big);
    std.debug.print("page size on this machine: {d}\n", .{std.heap.pageSize()});
    std.debug.print("1-byte alloc at {*}\n", .{small.ptr});
    std.debug.print("10000-byte alloc at {*}\n", .{big.ptr});
}
page size on this machine: 16384
1-byte alloc at u8@100d8c000
10000-byte alloc at u8@100d90000

Asking for one byte cost a whole 16-kilobyte page. Use the page allocator as the backing for other allocators (it is what DebugAllocator and ArenaAllocator get their big chunks from) and for a few large, long-lived buffers. Do not use it for thousands of small strings.

20.4 ArenaAllocator: free everything at once

An arena takes a backing allocator, grabs chunks from it, and hands out pieces of those chunks by bumping a pointer. Allocation is nearly free. Individual free calls do nothing. When you are done with everything the arena gave out, you call arena.deinit() and all of it goes back at once.

al1.zig

const std = @import("std");

pub fn main(init: std.process.Init) !void {
    var arena = std.heap.ArenaAllocator.init(init.gpa);
    defer arena.deinit(); // one call frees every allocation below
    const a = arena.allocator();

    var total: usize = 0;
    var i: u32 = 0;
    while (i < 1000) : (i += 1) {
        const line = try std.fmt.allocPrint(a, "log line {d}: contract signed", .{i});
        total += line.len;
        // no free. Ever. The arena remembers.
    }
    std.debug.print("built 1000 strings, {d} bytes, zero frees written\n", .{total});
    std.debug.print("arena holds about {d} bytes\n", .{arena.queryCapacity()});
}
built 1000 strings, 28890 bytes, zero frees written
arena holds about 56886 bytes

A thousand strings, no frees, no leak report: the single defer arena.deinit() covers them all. The arena is the right tool whenever a group of allocations share one lifetime: everything built while answering one request, drawing one frame, running one test, or loading one file. The code that does the work can allocate freely and never think about cleanup, because the boundary of the lifetime is where the arena is destroyed.

The cost is that memory only grows until the arena is reset. If one thing inside the group needs to be freed early, an arena will not do it. And you must not hand an arena's memory to something that outlives the arena. If a value must escape, dupe it into a longer-lived allocator first.

Arenas can also be reset instead of destroyed. arena.reset(.retain_capacity) forgets every allocation but keeps the chunks, so the next round of allocations reuses them without touching the backing allocator. This is the frame pattern:

al2.zig

const std = @import("std");

fn drawFrame(a: std.mem.Allocator, frame_no: u32) !void {
    // Every frame formats a handful of strings and forgets them.
    var rows: std.ArrayList([]const u8) = .empty;
    var i: u32 = 0;
    while (i < 3) : (i += 1) {
        try rows.append(a, try std.fmt.allocPrint(a, "frame {d} row {d}", .{ frame_no, i }));
    }
    std.debug.print("{s} ... {d} rows\n", .{ rows.items[0], rows.items.len });
}

pub fn main(init: std.process.Init) !void {
    var frame = std.heap.ArenaAllocator.init(init.gpa);
    defer frame.deinit();

    var frame_no: u32 = 0;
    while (frame_no < 3) : (frame_no += 1) {
        _ = frame.reset(.retain_capacity); // wipe last frame, keep the pages
        try drawFrame(frame.allocator(), frame_no);
        std.debug.print("  capacity after frame {d}: {d}\n", .{ frame_no, frame.queryCapacity() });
    }
}
frame 0 row 0 ... 3 rows
  capacity after frame 0: 424
frame 1 row 0 ... 3 rows
  capacity after frame 1: 424
frame 2 row 0 ... 3 rows
  capacity after frame 2: 424

After the first frame, capacity stops changing: the arena has learned how much a frame needs and simply reuses it. Three reset modes exist: .free_all releases the chunks too, .retain_capacity keeps them all, and .retain_with_limit = n keeps up to n bytes, a good choice when one unusual frame might otherwise pin a large buffer forever. reset returns a bool saying whether it could satisfy the request, which is why the examples write _ = arena.reset(…).

20.5 FixedBufferAllocator: a heap inside an array

Sometimes you want allocation without a heap at all: in a tiny embedded program, in a hot loop where a system call is unacceptable, or just because you know an upper bound and want to be told if you were wrong. FixedBufferAllocator hands out slices of an array you give it, and returns OutOfMemory when the array is full.

al3.zig

const std = @import("std");

pub fn main() !void {
    var buffer: [64]u8 = undefined; // the whole heap, on the stack
    var fba = std.heap.FixedBufferAllocator.init(&buffer);
    const a = fba.allocator();

    const first = try a.alloc(u8, 40);
    std.debug.print("got {d} bytes, used {d} of {d}\n", .{ first.len, fba.end_index, buffer.len });

    const second = a.alloc(u8, 40) catch |err| {
        std.debug.print("second alloc failed: {s}\n", .{@errorName(err)});
        return;
    };
    _ = second;
}
got 40 bytes, used 40 of 64
second alloc failed: OutOfMemory

The buffer here is a local array, so the "heap" lives on the stack and vanishes with the function. There is no deinit. free only reclaims the most recent allocation (it is a bump allocator, like the arena), so treat it as an arena with a hard limit. The end_index field tells you how much is used, which is handy in tests.

20.6 stackFallback: small on the stack, big on the heap

A common shape is "this is usually small, but occasionally huge". std.heap.stackFallback(N, fallback) gives you an allocator that serves requests from an N-byte buffer on the stack until it runs out, then transparently switches to the fallback allocator. Small cases never touch the heap; large cases still work.

al6.zig

const std = @import("std");

fn join(a: std.mem.Allocator, parts: []const []const u8) ![]u8 {
    return std.mem.join(a, ", ", parts);
}

pub fn main(init: std.process.Init) !void {
    // Up to 256 bytes come from the stack; anything bigger goes to init.gpa.
    var sfa = std.heap.stackFallback(256, init.gpa);
    const a = sfa.get();

    const short = try join(a, &.{ "Ada", "Bo" });
    defer a.free(short);
    std.debug.print("{s}\n", .{short});

    const parts = [_][]const u8{"a-fairly-long-name"} ** 30;
    const long = try join(a, &parts);
    defer a.free(long);
    std.debug.print("{d} bytes, spilled to the fallback\n", .{long.len});
}
Ada, Bo
598 bytes, spilled to the fallback

Note the sfa.get() rather than .allocator(): the stack-fallback allocator must be a var and get takes its address, because the buffer lives inside it. Free through the same allocator as always; it knows which memory came from where.

20.7 c_allocator: libc's malloc

If your program links the C library, std.heap.c_allocator wraps malloc and free. It is fast, thread-safe and the natural choice when you are also handing memory to C code that will free it. It needs libc, so build with -lc (on macOS libc is always present, so it works either way; on Linux without -lc the link fails).

al5.zig

const std = @import("std");

pub fn main() !void {
    const a = std.heap.c_allocator; // needs: zig run -lc al5.zig
    const s = try a.dupe(u8, "malloc says hi");
    defer a.free(s);
    std.debug.print("{s}\n", .{s});
}
malloc says hi

For pure-Zig programs that need a fast general-purpose allocator in release builds, std.heap.smp_allocator does the same job with no libc dependency. As noted above, init.gpa already makes this choice for you.

20.8 The pattern: one arena per lifetime

Put the pieces together and you get the structure IRON LEDGER uses, and that most substantial Zig programs converge on. There are three lifetimes, and each gets an allocator that matches it.

LifetimeAllocatorWhat lives thereFreed when
The processinit.gpa (DebugAllocator in Debug)The app struct, the terminal, the save store, the backing for every arenamain returns; leaks reported
The campaignAn ArenaAllocator owned by GameStateEvery person, unit, log line and ledger rowgs.deinit(): one call
One frame, one request, one testA per-frame arena, reset each frame; a per-test arenaQuery results: rows of formatted text drawn onceframe.reset(.retain_capacity) before the next frame

The arena is why the simulation core can be relaxed about strings. A query builds hundreds of small strings with allocPrint and never frees one; the caller resets the arena after drawing. The game state does the same at campaign scale: there is no per-object destructor anywhere in the domain, because gs.deinit() is the destructor for everything. The trade is stated plainly in the source: memory grows monotonically over a campaign (a long game holds every log line it ever wrote), in exchange for never having a use-after-free and never forgetting a free.

The habit to take from this: when you write a function that allocates, do not decide the lifetime inside it. Take an allocator, use it, and let the caller decide by choosing what to pass. The same summary(a, &gs) function serves a test with a throwaway arena, a TUI with a frame arena, and a CLI with init.gpa and explicit frees, and it does not know which.

20.9 Writing an allocator: a counting wrapper

An allocator is a struct pointer plus a vtable of four functions, so writing one is not magic. The most useful custom allocator is a wrapper that forwards to another allocator and measures. Here is one that counts.

al7.zig

const std = @import("std");

/// An allocator that wraps another and counts what passes through.
const Counting = struct {
    child: std.mem.Allocator,
    allocs: usize = 0,
    frees: usize = 0,
    bytes: usize = 0,

    fn allocator(self: *Counting) std.mem.Allocator {
        return .{ .ptr = self, .vtable = &vtable };
    }

    const vtable: std.mem.Allocator.VTable = .{
        .alloc = alloc,
        .resize = resize,
        .remap = remap,
        .free = free,
    };

    fn alloc(ctx: *anyopaque, len: usize, alignment: std.mem.Alignment, ret_addr: usize) ?[*]u8 {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        const result = self.child.rawAlloc(len, alignment, ret_addr);
        if (result != null) {
            self.allocs += 1;
            self.bytes += len;
        }
        return result;
    }

    fn resize(ctx: *anyopaque, memory: []u8, alignment: std.mem.Alignment, new_len: usize, ret_addr: usize) bool {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        return self.child.rawResize(memory, alignment, new_len, ret_addr);
    }

    fn remap(ctx: *anyopaque, memory: []u8, alignment: std.mem.Alignment, new_len: usize, ret_addr: usize) ?[*]u8 {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        return self.child.rawRemap(memory, alignment, new_len, ret_addr);
    }

    fn free(ctx: *anyopaque, memory: []u8, alignment: std.mem.Alignment, ret_addr: usize) void {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        self.frees += 1;
        self.child.rawFree(memory, alignment, ret_addr);
    }
};

pub fn main(init: std.process.Init) !void {
    var counting = Counting{ .child = init.gpa };
    const a = counting.allocator();

    var list: std.ArrayList(u32) = .empty;
    defer list.deinit(a);
    var i: u32 = 0;
    while (i < 1000) : (i += 1) try list.append(a, i);

    const s = try std.fmt.allocPrint(a, "{d} items", .{list.items.len});
    defer a.free(s);
    std.debug.print("{s}\n", .{s});
    std.debug.print("allocs={d} frees={d} bytes requested={d}\n", .{ counting.allocs, counting.frees, counting.bytes });
}
1000 items
allocs=9 frees=7 bytes requested=9380

The four vtable functions take the state as *anyopaque and cast it back with @ptrCast(@alignCast(ctx)), exactly as Chapter 18 described. Each forwards to the child's raw method and updates a tally. The alignment parameter's type is std.mem.Alignment and the ret_addr is for debug traces; you pass both straight through. With the wrapper in place you can see that appending a thousand items to an ArrayList took nine allocations (the buffer doubles as it grows) and that the seven frees plus the two defers still pending at print time will balance. Exercise 20.4 has you write this yourself and assert the balance in a test.

Exercise 20.1 · An arena for a pile of short-lived strings warm-up

Write report(a, n), which builds n formatted lines into an owned slice. The first test runs it through an arena and frees with one deinit; the second runs it through the testing allocator and frees piece by piece. Same function, both must pass. File: exercises/20-allocators/ex1_arena.zig.

Solution 
//! Chapter 20, exercise 1: an arena for a pile of short-lived strings.
//! Run with:  zig test ex1_arena.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Build a report of `n` lines using `a` and return the lines. The
/// caller decides how to free (with an arena: one deinit).
fn report(a: std.mem.Allocator, n: u32) ![][]const u8 {
    var out: std.ArrayList([]const u8) = .empty;
    var i: u32 = 0;
    while (i < n) : (i += 1) {
        try out.append(a, try std.fmt.allocPrint(a, "day {d}: nothing to report", .{i + 1}));
    }
    return out.toOwnedSlice(a);
}

test "arena frees everything at once" {
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit(); // this is the ONLY free in the test
    const a = arena.allocator();

    const lines = try report(a, 50);
    try std.testing.expectEqual(@as(usize, 50), lines.len);
    try std.testing.expectEqualStrings("day 50: nothing to report", lines[49]);
}

test "the same function works with a plain allocator, if you free" {
    const a = std.testing.allocator;
    const lines = try report(a, 3);
    defer {
        for (lines) |l| a.free(l);
        a.free(lines);
    }
    try std.testing.expectEqualStrings("day 2: nothing to report", lines[1]);
}

The function does not know or care which allocator it was given. That is the whole point of taking it as a parameter: the caller chooses the lifetime.

Exercise 20.2 · A fixed buffer runs out practice

Implement countUntilFull, which allocates labels from a FixedBufferAllocator over a size-byte array until it fails, and returns how many fit. File: exercises/20-allocators/ex2_fba.zig.

Solution 
//! Chapter 20, exercise 2: a fixed buffer runs out.
//! Run with:  zig test ex2_fba.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Format `n` into memory taken from `a`. Caller frees.
fn label(a: std.mem.Allocator, n: u32) ![]u8 {
    return std.fmt.allocPrint(a, "unit-{d}", .{n});
}

/// How many labels fit in a buffer of `size` bytes before OutOfMemory?
fn countUntilFull(comptime size: usize) usize {
    var buffer: [size]u8 = undefined;
    var fba = std.heap.FixedBufferAllocator.init(&buffer);
    const a = fba.allocator();
    var n: usize = 0;
    while (true) : (n += 1) {
        _ = label(a, 100) catch break;
    }
    return n;
}

test "labels come out of the buffer" {
    var buffer: [32]u8 = undefined;
    var fba = std.heap.FixedBufferAllocator.init(&buffer);
    const a = fba.allocator();
    const l = try label(a, 7);
    try std.testing.expectEqualStrings("unit-7", l);
    try std.testing.expect(fba.end_index >= 6);
}

test "a full buffer fails cleanly with OutOfMemory" {
    var buffer: [16]u8 = undefined;
    var fba = std.heap.FixedBufferAllocator.init(&buffer);
    const a = fba.allocator();
    _ = try label(a, 1);
    _ = try label(a, 2);
    try std.testing.expectError(error.OutOfMemory, label(a, 3));
}

test "bigger buffer, more labels" {
    try std.testing.expect(countUntilFull(64) < countUntilFull(256));
    try std.testing.expectEqual(@as(usize, 0), countUntilFull(4));
}

size is comptime because it is the length of an array type. The loop stops on the first OutOfMemory, which the catch break turns into ordinary control flow. There is no cleanup: the buffer is a local.

Exercise 20.3 · One arena per frame practice

Implement runFrames, which draws frames frames through one arena, resetting with .retain_capacity between them, and returns the final capacity. The test asserts that 200 frames use no more capacity than one. File: exercises/20-allocators/ex3_frame.zig.

Solution 
//! Chapter 20, exercise 3: one arena per frame, reset between frames.
//! Run with:  zig test ex3_frame.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// One frame's worth of work: a few formatted rows, never freed one by one.
fn drawFrame(a: std.mem.Allocator, frame_no: u32) !usize {
    var bytes: usize = 0;
    var i: u32 = 0;
    while (i < 20) : (i += 1) {
        const row = try std.fmt.allocPrint(a, "frame {d} row {d}", .{ frame_no, i });
        bytes += row.len;
    }
    return bytes;
}

/// Run `frames` frames through one arena, resetting it between frames
/// so that its capacity stops growing after the first frame.
/// Returns the arena's capacity after the last frame.
fn runFrames(gpa: std.mem.Allocator, frames: u32) !usize {
    var arena = std.heap.ArenaAllocator.init(gpa);
    defer arena.deinit();
    var f: u32 = 0;
    while (f < frames) : (f += 1) {
        _ = arena.reset(.retain_capacity);
        _ = try drawFrame(arena.allocator(), f);
    }
    return arena.queryCapacity();
}

test "capacity does not grow with the number of frames" {
    const one = try runFrames(std.testing.allocator, 1);
    const many = try runFrames(std.testing.allocator, 200);
    try std.testing.expect(one > 0);
    try std.testing.expectEqual(one, many);
}

Change the reset mode to .free_all and the test still passes (capacity after the last frame is the same), but the arena now goes back to the backing allocator every frame. Remove the reset entirely and the assertion fails, because the arena keeps growing.

Exercise 20.4 · An allocator that counts challenge

Fill in the four vtable functions of Counting so that it forwards to its child and tallies allocations, frees and bytes requested. The second test checks that an ArrayList frees exactly as many times as it allocates. File: exercises/20-allocators/ex4_counting.zig.

Solution 
//! Chapter 20, exercise 4: an allocator that counts.
//! Run with:  zig test ex4_counting.zig
//! Goal: make every test pass without changing the tests. Implement the
//! four vtable functions by forwarding to `child` and keeping the tallies.
const std = @import("std");

const Counting = struct {
    child: std.mem.Allocator,
    allocs: usize = 0,
    frees: usize = 0,
    bytes_requested: usize = 0,

    fn allocator(self: *Counting) std.mem.Allocator {
        return .{ .ptr = self, .vtable = &vtable };
    }

    const vtable: std.mem.Allocator.VTable = .{
        .alloc = alloc,
        .resize = resize,
        .remap = remap,
        .free = free,
    };

    fn alloc(ctx: *anyopaque, len: usize, alignment: std.mem.Alignment, ret_addr: usize) ?[*]u8 {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        const p = self.child.rawAlloc(len, alignment, ret_addr);
        if (p != null) {
            self.allocs += 1;
            self.bytes_requested += len;
        }
        return p;
    }

    fn resize(ctx: *anyopaque, memory: []u8, alignment: std.mem.Alignment, new_len: usize, ret_addr: usize) bool {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        return self.child.rawResize(memory, alignment, new_len, ret_addr);
    }

    fn remap(ctx: *anyopaque, memory: []u8, alignment: std.mem.Alignment, new_len: usize, ret_addr: usize) ?[*]u8 {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        return self.child.rawRemap(memory, alignment, new_len, ret_addr);
    }

    fn free(ctx: *anyopaque, memory: []u8, alignment: std.mem.Alignment, ret_addr: usize) void {
        const self: *Counting = @ptrCast(@alignCast(ctx));
        self.frees += 1;
        self.child.rawFree(memory, alignment, ret_addr);
    }
};

test "counts allocs, frees and bytes" {
    var c = Counting{ .child = std.testing.allocator };
    const a = c.allocator();

    const x = try a.alloc(u8, 10);
    const y = try a.alloc(u32, 4);
    try std.testing.expectEqual(@as(usize, 2), c.allocs);
    try std.testing.expectEqual(@as(usize, 26), c.bytes_requested);
    a.free(x);
    a.free(y);
    try std.testing.expectEqual(@as(usize, 2), c.frees);
}

test "a list balances its allocations" {
    var c = Counting{ .child = std.testing.allocator };
    const a = c.allocator();
    {
        var list: std.ArrayList(u64) = .empty;
        defer list.deinit(a);
        var i: u64 = 0;
        while (i < 500) : (i += 1) try list.append(a, i);
    }
    try std.testing.expect(c.allocs > 0);
    try std.testing.expectEqual(c.allocs, c.frees);
}

Only successful allocations are counted, which is why alloc checks the result before incrementing. The child's rawAlloc, rawResize, rawRemap and rawFree are the vtable calls without the type-safe wrapping, which is what a forwarding allocator wants.

Check your understanding

  1. What happens when you call free on memory from an ArenaAllocator?
    AnswerNothing. Arena memory is released all at once by deinit() or reset().
  2. When is an arena the wrong choice?
    AnswerWhen parts of the data need to be freed at different times, when memory must not grow unboundedly, or when a value must outlive the arena (then dupe it elsewhere).
  3. What does reset(.retain_capacity) do differently from deinit()?
    AnswerBoth forget every allocation; reset keeps the chunks so the next round reuses them without going back to the backing allocator, and the arena stays usable.
  4. Why is page_allocator a poor choice for many small strings?
    AnswerEvery allocation is at least one page (16 KiB here) and costs a system call.
  5. What does FixedBufferAllocator do when its buffer is full?
    AnswerReturns error.OutOfMemory, an ordinary error you handle with try or catch.
  6. What is init.gpa in a Debug build, and in a release build?
    AnswerA DebugAllocator with leak checking in Debug; c_allocator if libc is linked or smp_allocator otherwise in release.
  7. What are the four functions in an allocator's vtable?
    Answeralloc, resize, remap and free, each receiving the allocator's state as *anyopaque.
  8. A function takes an allocator and builds a result out of many pieces. Who decides how long the pieces live?
    AnswerThe caller, by choosing which allocator to pass: an arena for "all together", a general-purpose allocator for piece-by-piece freeing.
What you learned.
  • The allocator is chosen by the caller and should match the lifetime of the data.
  • DebugAllocator for development: leaks, double frees and use-after-free are reported with traces. init.gpa is one in Debug.
  • page_allocator is the raw OS source, good as a backing allocator; c_allocator and smp_allocator are the fast general-purpose choices for release.
  • ArenaAllocator frees everything at once; reset(.retain_capacity) makes it a reusable per-frame or per-request allocator.
  • FixedBufferAllocator allocates from an array and fails cleanly when full; stackFallback uses the stack first and a fallback after.
  • One arena per lifetime, process / campaign / frame, is how IRON LEDGER never writes a per-object free.
  • An allocator is a pointer plus four vtable functions; a counting wrapper is thirty lines.
