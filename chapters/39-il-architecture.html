39. The architecture in one picture

In this chapter you meet IRON LEDGER as a whole before you read any of its parts. You will learn the one rule the entire program is built around, see how the source tree enforces that rule, and learn the two doors through which every other part of the program talks to the simulation. By the end you will know where to look for anything.

What you need from earlier chapters. This chapter leans on Chapter 30 (files, imports and modules: every Zig file is a struct, and a module has one root file), Chapter 31 (the build system: addModule, addExecutable, root_module, build options), and Chapter 33 (the std.Io value that all real-world I/O needs in 0.16). If b.addAnonymousImport or init.io look unfamiliar, skim those chapters first. Everything else here is prose and a map.

39.1 What you are about to read

IRON LEDGER is a single-player BattleTech mercenary-company simulator. You are the commander of an outfit, not a pilot: every screen is a roster, a ledger, a map or a report, and battles are resolved by the simulation from the state you prepared beforehand (training, maintenance, supply, morale). The whole thing is about 31,500 lines of Zig 0.16 with no libraries beyond the system's SQLite. It was built in stages over a few weeks by one person and a coding assistant, and its history is visible in the comments: many of them say which stage introduced a rule and why.

That size is the point of Part 5. A 200-line example program cannot show you how a language feels at scale; a 31,000-line one can. Every chapter from here to the end takes one slice of the program, shows you the real code, tells you which functions to open and in what order, and gives you exercises that you carry out inside the repository with the compiler and the test suite as your safety net.

Before you start, run the suite once in a copy of the game so that you know what green looks like:

$ cp -r game /tmp/il && cd /tmp/il
$ zig build test --summary all
Build Summary: 10/10 steps succeeded; 246/247 tests passed (1 skipped)

Work in the copy. The exercises in Part 5 ask you to change the game, and a copy lets you experiment without fear. (The original guide this Part is adapted from was written at an earlier commit with 224 tests; the count has since grown, and a few numbers in the guide's prose have drifted. This book was checked against the source as it stands today, commit 8958001.)

39.2 The source tree

Here is the whole repository at the directory level, with the one distinction that matters marked on the right:

src/
├── domain/     entities and rule tables: person, unit, chassis, contract, hq, tuning …   (pure)
├── sim/        state, the daily tick, commands, queries, battle, medical, personnel …    (pure)
├── econ/       finance, markets, logistics                                               (pure)
├── gen/        company and person generators                                             (pure)
├── persist/    sqlite.zig (C binding) and store.zig (save/load, migrations)              (I/O)
├── tui/        term.zig, screen.zig, app.zig, emblem.zig, png.zig, music.zig, splash.zig, paths.zig  (I/O)
├── root.zig    the `game` module: re-exports everything above except tui/
└── main.zig    the executable: flags, the REPL, the demo, and the hand-off to tui/app.zig
data/
├── chassis.zon  planets.zon  parts.zon
└── tables/      tuning.zon meklab.zon names.zon ranks.zon awards.zon abilities.zon
                 rat.zon factions.zon scenarios.zon terrain.zon difficulty.zon

Four directories are marked pure. That word has a precise meaning here, stated in the game's ARCHITECTURE.md and repeated in CLAUDE.md as a hard rule:

Sim core (src/domain, src/sim, src/econ, src/gen) is pure and deterministic: no I/O, no wall clock, no global mutable state.

Given the same starting seed and the same sequence of player commands, two runs of the simulation produce byte-for-byte identical state. Everything else in the program's design is a consequence of wanting that to be true and wanting it to stay true as the code grows. Keep the rule in mind as you read; each of the next chapters will show you one thing it forces.

39.3 How a directory becomes a promise

A rule in a document is only a wish. What makes this one hold is the module layout in build.zig. Chapter 31 taught you that a Zig program is one or more modules, each a tree of files with a single root. IRON LEDGER has two:

build.zig (trimmed; the real file is heavily commented)
const mod = b.addModule("game", .{
    .root_source_file = b.path("src/root.zig"),
    .target = target,
});
// … the .zon data files are attached to `mod` here (Chapter 40) …
mod.link_libc = true;
mod.linkSystemLibrary("sqlite3", .{});

const exe = b.addExecutable(.{
    .name = "game",
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
        .imports = &.{
            .{ .name = "game", .module = mod },
        },
    }),
});
b.installArtifact(exe);

The library module game is rooted at src/root.zig, and the executable is rooted at src/main.zig, which imports the library by the name given in the .imports list. Now look at what root.zig re-exports:

src/root.zig (the shape; some lines omitted)
//! Module root for the simulation core. See ARCHITECTURE.md.
//! The core is pure and deterministic: no I/O, no wall clock, no globals.

const std = @import("std");

// domain/ — entities
pub const types = @import("domain/types.zig");
pub const person = @import("domain/person.zig");
pub const unit = @import("domain/unit.zig");
pub const chassis = @import("domain/chassis.zig");
pub const tuning = @import("domain/tuning.zig");
// … fifteen more domain files …

// sim/ — state, time, randomness, events, battle resolution
pub const state = @import("sim/state.zig");
pub const tick = @import("sim/tick.zig");
pub const commands = @import("sim/commands.zig");
pub const queries = @import("sim/queries.zig");
pub const cli = @import("sim/cli.zig");
// …

// persist/ — SQLite save files (Stage 11)
pub const sqlite = @import("persist/sqlite.zig");
pub const store = @import("persist/store.zig");

// econ/, gen/ …

test {
    std.testing.refAllDecls(@This());
}

There is no tui line. The terminal client lives outside the game module entirely; it is part of the executable's module, reached from main.zig with @import("tui/app.zig"). That means the simulation cannot import the client even by accident, because the file is not in its module. The dependency points one way.

The purity rule has a second, quieter enforcement that Chapter 33 prepared you for. In Zig 0.16, anything that touches the outside world needs an std.Io value: opening a file, reading the clock, spawning a process. The executable receives one in main and hands it to the client and to the save store. It never hands one to the simulation. A function in src/sim that wanted to read the time would have no io to read it with. As the original guide put it: purity is not a promise in a comment; it is a parameter that is not there.

Try it. In your copy of the game, run 
$ grep -rlE 'std\.Io|std\.posix|std\.fs\.|Clock\.now|std\.time' src/sim src/domain src/econ src/gen
It prints nothing. Now run the same search over src/tui src/persist src/main.zig and you get eight files. That is the boundary, visible from the shell.

One exception is worth knowing about now so it does not surprise you later: persist/ is inside the game module (so tests can round-trip a campaign through SQLite), but it does I/O. It talks to the C library directly rather than through std.Io, which is why the grep above does not flag it. The store is not part of the simulation; it reads a GameState and writes one, and nothing in sim/ imports it.

39.4 The picture

ARCHITECTURE.md draws the layers like this:

┌─────────────────────────────────────────────────────┐
│  Frontends: CLI (REPL, demo) and the terminal client │
└──────────────────────┬──────────────────────────────┘
                       │ Commands in / Queries out
┌──────────────────────▼──────────────────────────────┐
│  Simulation core (pure, deterministic)              │
│   sim/    clock, daily pipeline, events, autoresolve│
│   domain/ person, unit, part, force, contract, hq   │
│   econ/   finance, markets, logistics network       │
│   gen/    company/person/name generation            │
├─────────────────────────────────────────────────────┤
│  data/   static game data loaded from .zon files    │
├─────────────────────────────────────────────────────┤
│  persist/  SQLite save files, schema migrations     │
└─────────────────────────────────────────────────────┘

Read the arrow in the middle carefully, because it names the two doors. A frontend changes the simulation by building a Command value (a tagged union, Chapter 14) and passing it to commands.execute. A frontend reads the simulation by calling a function in queries.zig, which returns plain data: formatted strings plus the IDs a key handler will need. There is a third, smaller door shared by both frontends: cli.parseCommand turns a typed line of text into a Command, so a verb added for the REPL works in the terminal client's : line for free.

Here is that hand-off in the executable's main, which is the only place in the program that sees all three layers at once:

src/main.zig
pub fn main(init: std.process.Init) !void {
    var gs = game.state.GameState.init(init.gpa, .{ .seed = 3025 });
    defer gs.deinit();

    var args = std.process.Args.Iterator.init(init.minimal.args);
    _ = args.next(); // exe name
    var repl = false;
    var tui = false;
    var ascii = false;
    var no_splash = false;
    var no_music = false;
    var data_dir: ?[]const u8 = null;
    var store_arg: ?[:0]const u8 = null;
    while (args.next()) |arg| {
        if (std.mem.eql(u8, arg, "--repl")) repl = true;
        if (std.mem.eql(u8, arg, "--tui")) tui = true;
        if (std.mem.eql(u8, arg, "--ascii")) ascii = true;
        if (std.mem.eql(u8, arg, "--no-splash")) no_splash = true;
        if (std.mem.eql(u8, arg, "--no-music")) no_music = true;
        if (std.mem.eql(u8, arg, "--store")) store_arg = args.next() orelse store_arg;
        if (std.mem.eql(u8, arg, "--data")) data_dir = args.next() orelse data_dir;
    }

    // Without --store the save lives beside the binary in a source tree and
    // in the per-user data directory for an installed copy (tui/paths.zig).
    const store_path = store_arg orelse
        try paths.defaultStore(init.io, init.arena.allocator(), init.environ_map);

    if (tui) {
        try @import("tui/app.zig").run(init.io, init.gpa, init.environ_map, store_path,
            .{ .ascii = ascii, .no_splash = no_splash, .no_music = no_music, .data_dir = data_dir });
    } else if (repl) {
        try runRepl(&gs, init.io, init.gpa, store_path);
    } else {
        try runDemo(&gs);
    }
}

Compare this with the main you wrote in Chapter 32: the same std.process.Init, the same argument iterator, the same pattern of flags. What is new is only the scale of what it hands off to. Notice also where init.io goes: into the client and the REPL, both of which need files and a terminal, and not into GameState.init, which gets an allocator and a seed.

39.5 Four consequences of the one rule

Each of the next chapters is, at bottom, a study of one thing the purity rule forces. Here they are in one place so you can see the shape of Part 5:

  • Randomness is a value inside the state. There is no global random generator. GameState carries a bag of seeded generators, one per subsystem, and every dice roll names the stream it draws from. Chapter 41.
  • Time is an integer. The campaign clock is day_index: u32, days since the campaign began. The calendar date exists too, but only so it can be printed and so that "the first of the month" is easy to detect. Nobody reads a wall clock. Chapter 43.
  • Money is an integer. Every amount is a 64-bit count of C-bills, every multiplier is basis points, and there is not one floating-point number in the rules. Two machines produce the same balance to the C-bill. Chapter 45.
  • The state is one tree with one owner. A single arena allocator owns every allocation a campaign makes and frees them all in one call, so the domain code has no destructors and no use-after-free. Chapter 41.

The payoff for all of it is a single test in Chapter 49: two campaigns, same seed, same script, must hash identically. It is cheap, it runs on every build, and it catches a whole class of bugs (an unordered hash map iteration, a stray PRNG, a wall-clock read) that would otherwise surface as "saved games replay differently after an update".

39.6 A note on reading large code

You will not read all 31,000 lines and you should not try. The files are long because the game is detailed, not because the code is dense: queries.zig is four thousand lines mostly because there are many screens, each of which formats many columns. The skill to practise in Part 5 is navigating: opening a file, finding the top-level declarations with a search for pub fn or pub const, reading one function end to end, and following one call into another file when you need to.

Two habits help. First, every file opens with a //! comment saying what it is and, by house rule, which MekHQ class it mirrors; read that before anything else. Second, the test blocks at the bottom of each file are the best documentation of what the code is for; a test named "tier upgrade: refusals keep the money" tells you the rule and the bug it once had in one line.

Guided reading

Open these in order. Each is short; the whole list is twenty minutes.

  1. ARCHITECTURE.md, sections 1 and 4 only (the design pillars and the layer diagram). Note the phrase "pure and deterministic" and the list of player actions as commands.
  2. CLAUDE.md, the "Hard rules" list. These are the rules the exercises in Part 5 will ask you to respect; most of them will make more sense after the chapter that covers them.
  3. build.zig, skipping the long comments on first read. Find addModule("game", the data_files table, linkSystemLibrary("sqlite3", and the test step. Notice that the test step also depends on the install step: a green test run means the client compiled too, and the comment above it records the day that stopped being true by accident.
  4. src/root.zig, top to bottom. Count the re-exports (there are more than forty) and confirm that none of them mentions tui. Read the small dataProvenance function in the middle: it is the first real function of the codebase you meet, and it uses only things you learned in Chapter 21 and Chapter 23.
  5. src/main.zig, the main function and the small test block above it that pulls the tui/ files into the executable's test build. Skim runDemo to see what a scripted campaign looks like: it is nothing but execute calls and prints.

Exercise 39.1 · Prove the boundary from the shell warm-up

Without reading any code, use grep to find every file in src/ that mentions std.Io or std.posix, and every file that mentions commands.execute. From the two lists, write one sentence describing which directories do I/O and which directories may change the simulation.

Solution 
$ grep -rlE 'std\.Io|std\.posix' src
src/tui/emblem.zig
src/tui/term.zig
src/tui/music.zig
src/tui/app.zig
src/tui/paths.zig

src/sim/…  (a handful of sim files, all inside test blocks)

I/O happens only in src/tui and src/main.zig (plus the C calls in src/persist, which are not std.Io). Outside of tests, the simulation is changed only from main.zig and tui/app.zig, and always through commands.execute. Nearly every hit in src/sim and src/persist is inside a test block driving a small campaign, or in a helper those tests share.

Exercise 39.2 · A test that guards the boundary practice

Add a test at the bottom of src/root.zig that uses reflection (Chapter 27) to check two things: the module root has at least forty public declarations, and it has no declaration named tui. Run zig build test.

Solution 
test "the module root re-exports at least forty namespaces" {
    const decls = @typeInfo(@This()).@"struct".decls;
    try std.testing.expect(decls.len >= 40);
    // The client is not one of them: the core cannot reach the terminal.
    try std.testing.expect(!@hasDecl(@This(), "tui"));
}

@This() is the struct that is root.zig itself (every file is a struct, Chapter 30). @typeInfo(...).@"struct".decls lists its public declarations at compile time, so decls.len is a constant. @hasDecl is the direct way to ask about one name. If someone later adds pub const tui = @import("tui/app.zig"); to the root, this test fails and names the reason.

Exercise 39.3 · Trace one command from the shell to the state practice

Starting from runDemo in src/main.zig, follow the very first execute call (.create_commander) as far as you can into the simulation using only "find the definition" jumps. List the files you pass through, in order, and stop when you reach the function that actually creates the commander.

Solution
  1. src/main.zig: runDemo calls game.commands.execute(gs, .{ .create_commander = … }).
  2. src/sim/commands.zig: execute switches on the union; the .create_commander arm refuses a start year outside 3000 to 3060 (Error.BadYear), sets the calendar year, calls gs.createCommander(c.name, c.origin, c.profession), names the outfit after the commander if it still has the placeholder name, and opens the markets.
  3. src/sim/state.zig: GameState.createCommander refuses a second commander, picks the home world with planet_mod.weightedPickByFaction(&self.rng, origin.key()) (a dice roll from the state's own generator bag, Chapter 41), builds a regional HQ with eight starter facilities, recruits its back-office staff with recruitGenerated, and hands it founding capital through transferFunds.
  4. Along the way it reaches into src/domain/commander.zig (the Faction and Profession enums), src/domain/planet.zig (the star map) and src/domain/hq.zig (the HQ struct and its facilities).

The point of the exercise is the shape of the path: an executable file, then the one execute switch, then a method on GameState, then the domain. You will see that same shape for every command in Chapter 42.

Check your understanding

  1. Name the two modules in build.zig and the root file of each.
    AnswerThe library module game, rooted at src/root.zig, and the executable's module, rooted at src/main.zig, which imports game by name.
  2. Why can code in src/sim not open a file, even if a programmer tried?
    AnswerOpening a file in 0.16 requires an std.Io value. main passes init.io only to the client and the REPL; no function in the simulation core receives one, so there is nothing to call openFile with.
  3. What are the two doors between a frontend and the simulation?
    Answercommands.execute(gs, cmd) to change state, and the functions in queries.zig to read it as formatted rows plus IDs. (cli.parseCommand is a helper that produces commands from text; it does not touch state.)
  4. Where does the terminal client live, and why is that placement significant?
    AnswerIn src/tui/, which is not re-exported by root.zig; it belongs to the executable's module. The simulation therefore cannot import it, so the dependency can only point from client to core.
  5. List the four consequences of the determinism rule that later chapters cover.
    AnswerRandomness lives inside the state as named streams; time is an integer day counter; money is integer C-bills with basis-point multipliers; the state is one tree owned by one arena.
  6. Which test summarises the whole architecture, and what does it assert?
    AnswerThe golden-master test in commands.zig: two campaigns with the same seed and the same command script must produce the same gs.hash().
What you learned.
  • IRON LEDGER is organised around one rule: the simulation core is a pure, deterministic function of its seed and its command history.
  • The rule is enforced by the module layout (tui/ is outside the game module) and by the absence of an std.Io parameter anywhere in the core.
  • Frontends change state only through commands.execute and read it only through queries.*; cli.parseCommand is shared by both frontends.
  • Randomness, time, money and memory ownership are each shaped by the rule; the golden-master test guards it.
  • Read large code by navigating, not by scanning: file header comments and test names tell you what things are for.
