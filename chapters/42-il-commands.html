42. Commands: the only way in

In this chapter you read the one function that is allowed to change a campaign. Every player action is a value of one tagged union, every arm of one switch follows the same three-beat shape, and every refusal is a named error that both frontends turn into a sentence. By the end you will add a command of your own and watch the compiler walk you through every place it must be handled.

What you need from earlier chapters. Chapter 14 (tagged unions, payload captures with |x|, and exhaustive switch), Chapter 16 (error sets, try, catch |err| switch (err), merging sets with ||), Chapter 12 (a result struct whose fields all have defaults), Chapter 11 (tokenising a line with std.mem.tokenizeScalar) and Chapter 8 (expectError).

42.1 One union, one switch

Nothing outside the simulation core mutates GameState except through one function:

pub fn execute(gs: *GameState, cmd: Command) Error!Result

Its argument is a tagged union with 71 variants at the time of writing (the original guide said "about ninety"; the count is easy to check, and Exercise 42.3 pins it). Here is the top of it:

src/sim/commands.zig
pub const Command = union(enum) {
    /// End the turn: advance one day. Turn-based — time only moves here,
    /// and nothing blocks it; decisions wait in the inbox with deadlines.
    advance_day,
    advance_days: u32,
    hire: struct {
        first: []const u8,
        last: []const u8,
        role: person_mod.Role,
    },
    /// Hire a randomly generated candidate (experience rolled on 2d6).
    recruit: person_mod.Role,
    fire: types.PersonId,
    /// Generate a full company: 3 lances of meks with pilots + support tail.
    new_company: []const u8,
    rename_outfit: []const u8,
    rename_force: struct { force: types.ForceId, name: []const u8 },
    /// Attach an emblem image (raw bytes) to a force (ARCH §9.8 identity).
    set_emblem: struct { force: types.ForceId, image: []const u8 },
    /// Character creation: origin picks the starter world (weighted, in the
    /// commander's faction space); profession grants one 2% edge.
    create_commander: struct {
        name: []const u8,
        origin: commander_mod.Faction,
        profession: commander_mod.Profession,
        /// Campaign start year (12C.16): the market, RATs and salvage field
        /// only what exists by then.
        start_year: u16 = 3025,
    },
    // … sixty more, ending with:
    /// Trim a deployed company's field stores to its field plan …
    trim_stock: types.ForceId,
};

The three payload shapes from Chapter 14 are all here. advance_day carries nothing. fire carries one typed ID. hire carries an inline struct, and create_commander's inline struct even has a defaulted field, so a caller may write .{ .create_commander = .{ .name = "Erik", .origin = .CC, .profession = .quartermaster } } and get the year 3025. A command value is data: it can be built by a key handler, parsed from text, stored in an array for a test script, or (in principle) written to a replay file. That is why a union was chosen over a method per action.

The union's doc comments are worth a moment. They are the specification of the game's rules in the player's terms ("time only moves here, and nothing blocks it"), and they sit exactly where a reader looking for the rule will look.

42.2 The error set and the result

Before the switch, two more types:

pub const Error = error{
    UnknownPerson,
    UnknownForce,
    UnknownUnit,
    UnknownChassis,
    NoSuchEvent,
    NoSuchChoice,
    NotADecision,
    CommanderExists,
    NoHomeWorld,
    NoSuchOffer,
    NotACompany,
    CompanyDeployed,
    UnknownPlanet,
    // … eighty named errors in all, ending with:
    UnknownAbility,
    AlreadyLearned,
    /// That term is already at the best the employer will give.
    TermAtCap,
} || std.mem.Allocator.Error;

pub const Result = struct {
    days_advanced: u32 = 0,
    hired: types.PersonId = .none,
    created_force: types.ForceId = .none,
    /// Tons a `trim_stock` sent home.
    tons_moved: u32 = 0,
    /// The hull a `buy_hull_for` bought, and its delivery time (0 = on hand).
    unit: types.UnitId = .none,
    eta_days: u32 = 0,
    /// People a `crew_company` hired (halls plus the astech/medic pools),
    /// and the manning lines it could not fill because no candidate of
    /// that role walked the boards.
    hired_count: u32 = 0,
    still_open: u32 = 0,
    /// `order_part`: false when logistics failed the sourcing roll.
    sourced: bool = true,
    /// `negotiate`: how the round went.
    negotiation: enum { none, improved, hardened, withdrawn } = .none,
    // …
};

Error is an explicit set merged with std.mem.Allocator.Error (Chapter 16), so try gs.log(…) inside an arm, which can fail with OutOfMemory, needs no conversion. Every other error is a refusal with a name a human can read. There is no Error.Failed; the design rule (from ARCHITECTURE.md) is that command validation returns values the UI can explain, and you will see the explaining in 42.5.

Result is the mirror image: every field has a default, so an arm that has nothing to report returns .{}, and an arm that created something fills one field. A caller that does not care writes _ = try execute(…); a caller that does writes (try execute(gs, .{ .new_company = "Alpha" })).created_force. The doc comments on the fields name the command that fills each, which is how you find your way from a result field back to its arm.

42.3 The shape of an arm

The switch itself is next. The first arms are the simplest, and they show the mechanics of a payload capture:

pub fn execute(gs: *GameState, cmd: Command) Error!Result {
    switch (cmd) {
        .advance_day => return advance(gs, 1),
        .advance_days => |n| return advance(gs, n),
        .hire => |h| {
            const id = try gs.hirePerson(h.first, h.last, h.role);
            return .{ .hired = id };
        },
        .recruit => |role| {
            const id = try gs.recruitGenerated(role);
            return .{ .hired = id };
        },
        .fire => |id| {
            const p = gs.person(id) orelse return Error.UnknownPerson;
            // 12C.2: a firing pays half the departure payout; seats open.
            const paid = try @import("personnel.zig").depart(gs, id, .resigned, tuning.person.fire_severance_bp, "severance (fired)");
            if (paid > 0) try gs.log(.rotation, .{ .company = gs.companyOf(p.assigned_force) }, "[personnel] {s} {s} fired — {d} c-bills severance", .{ p.first_name, p.last_name, paid });
            return .{};
        },
        // …

|n| binds the u32 of advance_days; |h| binds the inline struct so h.first works; |id| binds the typed ID. The .fire arm shows the three beats that every non-trivial arm follows: validate (gs.person(id) orelse return Error.UnknownPerson), mutate (depart), report (a log line, then a Result).

Here is the arm the original guide singled out, because its comment records a real bug:

        .upgrade_tier => |hq_id| {
            // Check everything before a c-bill moves: a refused upgrade used
            // to keep the money.
            const h = gs.hqs.getPtr(hq_id) orelse return Error.UnknownHq;
            if (h.tier != .field) return Error.MaxLevel;
            for (h.projects.items) |p| if (p.kind == .tier_upgrade) return Error.ProjectInProgress;
            if (gs.treasuryBalance(.{ .hq = hq_id }) < hq_ops.tier_upgrade_cost) return Error.InsufficientTreasury;
            hq_ops.startTierUpgrade(gs, hq_id) catch |err| switch (err) {
                error.ProjectInProgress => return Error.ProjectInProgress,
                error.MaxLevel => return Error.MaxLevel,
                error.UnknownHq => return Error.UnknownHq,
                error.OutOfMemory => return Error.OutOfMemory,
            };
            try gs.postTreasury(.{ .hq = hq_id }, .{
                .day = gs.clock.day_index,
                .amount = -hq_ops.tier_upgrade_cost,
                .category = .hq_construction,
                .hq = hq_id,
                .note = "regional upgrade",
            });
            return .{};
        },

Four checks, then two effects, then .{}. An earlier version debited first and checked second, so a refused upgrade kept the money; the discipline "all checks, then all effects" is what prevents that class of bug, and the test "tier upgrade: refusals keep the money; a funded field HQ starts the project and pays once" makes sure it stays prevented.

The middle of the arm shows a pattern from Chapter 16 that you will see throughout the file. hq_ops.startTierUpgrade has its own, smaller error set (it is declared !void, so the compiler infers error{UnknownHq, MaxLevel, ProjectInProgress, OutOfMemory} from its body). The arm translates each case into the command layer's Error explicitly with a catch |err| switch (err). Because a switch on an error set is exhaustive, a new failure mode added to startTierUpgrade shows up here as a compile error ("unhandled error"), which is exactly where you want to be told.

42.4 A longer arm: crewing a company

Most arms are ten to thirty lines. Here is a thirty-line one you will meet again in Chapter 50, where a single keypress runs it:

        .crew_company => |company| {
            const f = gs.force(company) orelse return Error.UnknownForce;
            if (f.echelon != .company) return Error.NotACompany;
            if (gs.deploymentContract(company) != null) return Error.CompanyDeployed;
            const personnel = @import("personnel.zig");
            var hired: u32 = 0;
            var still_open: u32 = 0;
            for (personnel.manningNeeds(gs, company)) |n| {
                var have = personnel.manningHave(gs, company, n.role);
                while (have < n.need) : (have += 1) {
                    if (personnel.isPooledRole(n.role)) {
                        // MekHQ hires astechs and medics to complement on
                        // demand: no market, no signing bonus, salary only.
                        const spec = person_gen.generateWithBonus(&gs.rng, n.role, gs.recruitBonus());
                        const id = try gs.hireFromSpec(spec);
                        gs.person(id).?.assigned_force = company;
                        hired += 1;
                    } else if (try hireRoleFromHall(gs, n.role, company)) {
                        hired += 1;
                    } else {
                        still_open += n.need - have;
                        break;
                    }
                }
            }
            _ = try gs.autoAssign(company);
            try gs.log(.decision, .{ .company = company }, "[raise] {s}: {d} hired to fill the manning table ({d} still open — the halls had nobody)", .{ f.name, hired, still_open });
            return .{ .hired_count = hired, .still_open = still_open };
        },

Three validations, then a loop over the fourteen-row manning table (manningNeeds returns a fixed-size array [14]Need), then autoAssign, then a log line and a two-field result. Notice gs.person(id).?.assigned_force = company;: the person was just created by hireFromSpec, so the lookup cannot fail and .? is the honest way to say so (Chapter 15). Notice also that the code looks the person up after hiring rather than keeping a pointer from before, which is the stale-pointer rule from Chapter 41. And notice hireRoleFromHall calling execute recursively with .hire_candidate: an arm may compose other commands, which keeps the signing-bonus accounting in one place.

42.5 Advancing time is a command too

The two arms at the top of the switch call advance, a private function that is the only place the daily tick (Chapter 43) is invoked from:

fn advance(gs: *GameState, days: u32) Error!Result {
    // Turn-based: each day is a turn; nothing interrupts the advance.
    // Decisions wait in the inbox and default at their deadlines — except
    // money (Stage 12): a negative outfit treasury holds the turn until a
    // loan or a sale covers it, and past all credit the outfit folds.
    var result: Result = .{};
    for (0..days) |_| {
        if (gs.bankrupt) return Error.Bankrupt;
        // Couriers already bound for the outfit count: the turn can end
        // while the money is on the road.
        if (gs.funds + gs.inboundToOutfit() < 0) {
            if (gs.funds + gs.liquidationValue() + gs.creditRemaining() < 0) {
                gs.bankrupt = true;
                try gs.log(.finance, .{}, "[bankrupt] the outfit cannot cover {d}: creditors seize what is left", .{gs.funds});
                return Error.Bankrupt;
            }
            return Error.Insolvent;
        }
        try tick.advanceDay(gs);
        result.days_advanced += 1;
    }
    return result;
}

This is where the game's turn structure lives: a day is a turn, the only thing that can stop the clock is a negative treasury, and days_advanced tells the caller how far it got. It is also a good example of a Zig function that returns an error and has partially done its work: if day three of seven is refused with Error.Insolvent, days one and two happened and the state reflects them. The caller learns this from the error, not from a rollback, because the design says time only moves forward.

42.6 From text to command, and from error to sentence

Both frontends build Command values. The terminal client's keys build them directly (try self.exec(.{ .crew_company = co })). Typed text, whether in the REPL or the client's : line, goes through one parser:

src/sim/cli.zig
pub fn parseCommand(verb: []const u8, tokens: *std.mem.TokenIterator(u8, .scalar)) ParseError!?Command {
    const eq = std.mem.eql;
    if (eq(u8, verb, "transfer")) {
        return .{ .transfer = .{ .from = try parseTreasury(try need(tokens.next())), .to = try parseTreasury(try need(tokens.next())), .amount = try num(i64, tokens.next()) } };
    }
    if (eq(u8, verb, "admit")) return .{ .admit = @enumFromInt(try num(u32, tokens.next())) };
    if (eq(u8, verb, "depot")) return .{ .depot = @enumFromInt(try num(u32, tokens.next())) };
    // …
    if (eq(u8, verb, "shares")) {
        return .{ .set_shares_pct = try num(u8, tokens.next()) };
    }
    // …
    return null; // not a verb we know
}

The return type ParseError!?Command reads inside-out: an optional command (null means "not my verb; maybe the frontend knows it") wrapped in a possible parse error (BadArguments, BadSite, BadNumber). The helpers num and need turn a maybe-token into a number or a required string, and @enumFromInt turns the user's typed number into a typed ID at the edge, which is one of the few places that conversion is legitimate (Chapter 13). A verb also needs a row in the verbs list (for tab completion) and in the usage table (for help), and a test checks that every listed verb has a parser branch, so you cannot add one and forget the others.

When execute refuses, the error travels back up to the frontend, and a shared table turns it into a sentence:

pub fn errorText(err: anyerror) []const u8 {
    return switch (err) {
        error.InsufficientTreasury => "not enough money in that treasury — transfer funds first",
        error.MaxLevel => "already at the top: this HQ is regional (or the facility is maxed)",
        error.ProjectInProgress => "a project is already running here — watch PROJECTS",
        error.BadPercent => "a percentage between 0 and 100",
        error.BadYear => "the campaign starts between 3000 and 3060",
        error.CompanyDeployed => "that company is deployed — hire at an HQ hall and `xfer person <id> co:N` to send people out to it",
        // …
        else => @errorName(err),
    };
}

anyerror accepts any error set, and the else arm falls back to the error's name, so a new error is never silent; it just reads as UnknownAbility until someone writes it a sentence. This is the payoff of Error being a set of names rather than one Failed: the same table serves the REPL's stderr and the client's status line.

42.7 The tests

commands.zig ends with about fifty tests, and their style is the style of the whole suite: build the smallest state that exercises the rule, run one command, assert on state. The refusal test for the arm you read above:

test "tier upgrade: refusals keep the money; a funded field HQ starts the project and pays once" {
    var gs = GameState.init(std.testing.allocator, .{ .seed = 1230 });
    defer gs.deinit();
    _ = try execute(&gs, .{ .create_commander = .{ .name = "T", .origin = .LC, .profession = .paymaster } });
    const home = gs.hqs.keys()[0];
    const home_funds = gs.hqs.getPtr(home).?.funds;
    try std.testing.expectError(Error.MaxLevel, execute(&gs, .{ .upgrade_tier = home })); // already regional
    try std.testing.expectEqual(home_funds, gs.hqs.getPtr(home).?.funds);
    // … found a field HQ, empty its till …
    try std.testing.expectError(Error.InsufficientTreasury, execute(&gs, .{ .upgrade_tier = fb }));
    try std.testing.expectEqual(@as(usize, 0), gs.hqs.getPtr(fb).?.projects.items.len);
    // Funded: the project starts and the cost is paid exactly once.
    gs.hqs.getPtr(fb).?.funds = hq_ops.tier_upgrade_cost + 1;
    _ = try execute(&gs, .{ .upgrade_tier = fb });
    try std.testing.expectEqual(@as(types.CBills, 1), gs.hqs.getPtr(fb).?.funds);
    try std.testing.expectError(Error.ProjectInProgress, execute(&gs, .{ .upgrade_tier = fb }));
}

Every expectError is paired with an expectEqual on the money, which is the actual property: not just "it refused" but "it refused and nothing moved". Tests reach into GameState fields directly (gs.hqs.getPtr(fb).?.funds = …) to set up situations; that is allowed in tests precisely because it is not allowed anywhere else.

Guided reading

  1. src/sim/commands.zig, the Command union, all of it. It is two hundred lines of doc comments and is the best single description of what the game lets you do.
  2. The Error set and Result struct just below it.
  3. execute: read the first ten arms in order, then jump to .upgrade_tier, .crew_company, .set_shares_pct and .trim_stock. Note the three beats in each. Then advance and debitPurchase (a four-line helper that is "check, then post").
  4. src/sim/cli.zig: parseCommand (skim the branches, read newlance fully), errorText, verbs, usage, and the two tests at the bottom.
  5. Back in commands.zig, read three tests: "command validation errors", "tier upgrade: refusals keep the money", and "golden master: same seed + same script". You will return to the last one in Chapter 49.

Exercises

Exercise 42.1 · A command from the union to the REPL challenge

Add a command set_morale_all: u8 that sets the morale of every active person to the given value, refusing values over 100 with Error.BadPercent. Add the variant, the arm, a REPL verb morale <0-100> (verb list, parser branch, usage row), and a test. Do it in that order and read every compile error before fixing it.

Solution

Adding the variant alone makes zig build test fail with error: switch must handle all possibilities at execute's switch and note: unhandled enumeration value: 'set_morale_all'. (The two switch (cmd) in main.zig have else arms and are untouched.) The arm, placed next to .set_shares_pct:

        .set_morale_all => |value| {
            if (value > 100) return Error.BadPercent;
            var it = gs.people.iterator();
            while (it.next()) |entry| {
                const p = entry.value_ptr;
                if (p.status == .active) p.morale = value;
            }
            try gs.log(.decision, .{}, "[exercise] morale set to {d} for everyone on the books", .{value});
            return .{};
        },

In cli.zig: "morale", in the verbs array; .{ "morale", "morale <0-100>" }, in the usage table; and a parser branch if (eq(u8, verb, "morale")) return .{ .set_morale_all = try num(u8, tokens.next()) };. If you forget the usage row, the test "every listed verb parses or fails on arguments" fails with usage(v) != null. The test:

test "set_morale_all touches the active only and refuses over 100" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    const a = try gs.hirePerson("A", "One", .mekwarrior);
    const b = try gs.hirePerson("B", "Two", .tech_mek);
    gs.person(b).?.status = .retired;
    try std.testing.expectError(Error.BadPercent, execute(&gs, .{ .set_morale_all = 101 }));
    _ = try execute(&gs, .{ .set_morale_all = 90 });
    try std.testing.expectEqual(@as(u8, 90), gs.person(a).?.morale);
    try std.testing.expectEqual(@as(u8, 50), gs.person(b).?.morale);
}

The retired person keeps the default morale of 50, which checks the .active filter. zig build run -- --repl then accepts morale 75, and so does the terminal client's : line, without either frontend being edited. That is the whole argument for one parser.

Exercise 42.2 · Refusals with expectError warm-up

Write a test proving set_shares_pct refuses 101 with Error.BadPercent and accepts 100, and check what 100 percent becomes in gs.share_profit_bp (read the arm to find the unit).

Solution 
test "shares refuse 101 percent" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    try std.testing.expectError(Error.BadPercent, execute(&gs, .{ .set_shares_pct = 101 }));
    _ = try execute(&gs, .{ .set_shares_pct = 100 });
    try std.testing.expectEqual(@as(types.Bp, 10_000), gs.share_profit_bp);
}

The arm stores @as(types.Bp, pct) * 100: percent to basis points, the unit Chapter 45 explains. expectError takes the error and the expression, not its result; the call happens inside.

Exercise 42.3 · Count the variants warm-up

Write a one-assertion test that pins the number of Command variants using @typeInfo. First guess the number, then print it with std.debug.print inside the test, then replace the print with an expectEqual.

Solution 
test "the command union is large" {
    const n = @typeInfo(Command).@"union".fields.len;
    try std.testing.expectEqual(@as(usize, 71), n);
}

@typeInfo(Command).@"union".fields is the variant list, available at compile time. The number is 71 today; if you did Exercise 42.1 first it is 72. A pinned count is a mild nuisance for whoever adds the next command, which is the point of the exercise rather than a recommendation: the game does not pin it, and you should think about whether you would.

Exercise 42.4 · Find the three beats practice

Open the .found_hq arm (near .upgrade_tier). It calls debitPurchase before gs.foundHq. Is that a violation of "all checks, then all effects"? Read debitPurchase and foundHq's error set and argue either way in three sentences.

Solution

The arm does its own checks first (planet_mod.find, reachable), so by the time it debits, the only ways foundHq can fail are the ones already ruled out (UnknownPlanet, NotReachable) plus OutOfMemory. debitPurchase itself is "check the balance, then post", so it cannot half-succeed. It is therefore not a violation in practice, but it is fragile: if foundHq gained a new failure mode, the exhaustive catch |err| switch would force someone to add an arm and, one hopes, to notice the money had already left. The .upgrade_tier arm avoids the question by posting last; that ordering is the safer habit.

Check your understanding

  1. Why is a player action a value rather than a method call?
    AnswerA value can be built by a key handler, parsed from text, stored in an array for a test script, or logged; one switch then handles all of them identically, and the compiler checks the switch is complete.
  2. What are the three beats of an arm, and which bug does the order prevent?
    AnswerValidate, mutate, report. Doing every check before any effect prevents a refused command from leaving a partial change behind, such as a debited treasury for an upgrade that never started.
  3. What does catch |err| switch (err) { … } buy over try when calling hq_ops.startTierUpgrade?
    AnswerIt translates the helper's smaller error set into the command layer's set explicitly, and because the switch is exhaustive, a new error in the helper becomes a compile error at the arm.
  4. Why does Result give every field a default?
    AnswerSo most arms can return .{} and only the arms with something to report fill a field; callers read the field they care about.
  5. What does ParseError!?Command mean?
    AnswerParsing may fail (bad number, missing argument); if it succeeds it may still yield null, meaning "not a verb this parser knows", which lets the frontend try its own verbs.
  6. What happens if execute refuses on day 3 of advance_days = 7?
    AnswerDays 1 and 2 have already happened and remain; the error (Insolvent or Bankrupt) is returned and no rollback occurs, because time only moves forward.
  7. Why does errorText take anyerror and end with else => @errorName(err)?
    AnswerSo it can be called with errors from any layer and never fails to produce text; an error without a sentence shows its name until someone writes one.
What you learned.
  • All mutation of a campaign goes through commands.execute, one exhaustive switch over a 71-variant tagged union.
  • Every arm validates, then mutates, then reports; refusals are named errors from one merged set, and results are a struct of defaulted fields.
  • Helpers with smaller error sets are translated with an exhaustive catch |err| switch, so new failure modes surface at compile time.
  • Time advances through the same door, and money is the only thing that can hold a turn.
  • One parser (cli.parseCommand) and one error table (cli.errorText) serve both frontends, so adding a verb is a change in one file.
