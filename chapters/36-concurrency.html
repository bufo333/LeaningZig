36. Threads and atomics

In this chapter you will start threads with std.Thread.spawn, wait for them with join, and see exactly what goes wrong when two threads touch the same variable. Then you will fix it three ways: give each thread its own slot, use an atomic, or take a mutex. You will meet std.Io.Group for running a batch of tasks, and learn when a program should not use threads at all.

36.1 Spawn and join

A thread is a second instruction pointer running through your program at the same time as the first, sharing all the same memory. Zig starts one with std.Thread.spawn, which takes a configuration struct (usually empty), a function, and a tuple of arguments for that function. It returns a Thread handle, or an error if the OS refused. join blocks until the thread's function returns.

t1_hello.zig
const std = @import("std");

fn greet(name: []const u8, times: u32) void {
    for (0..times) |i| std.debug.print("{s} {d}\n", .{ name, i });
}

pub fn main() !void {
    const t = try std.Thread.spawn(.{}, greet, .{ "worker", 3 });
    greet("main", 3);
    t.join();
    std.debug.print("done\n", .{});
}
$ zig run t1_hello.zig
main 0
main 1
main 2
worker 0
worker 1
worker 2
done

Run it a few times and the lines interleave differently, or not at all, depending on how the operating system schedules the two threads. That is the first lesson: the order in which threads run is not yours to choose. The only ordering guarantee in this program is that done comes after both, because join waits.

The arguments tuple .{ "worker", 3 } is matched to greet's parameters at compile time, so passing the wrong number or type is a compile error rather than a crash. The values are copied into the new thread; to share something, pass a pointer (next section). Every thread you spawn must eventually be joined (or detached if you truly do not care when it ends); forgetting is a resource leak, and a program that returns from main while threads are still running ends them abruptly.

36.2 The data race

Because threads share memory, two of them can write the same variable. Here four threads each add one to a global counter a hundred thousand times.

t2_race.zig
const std = @import("std");

var counter: u64 = 0;

fn bump() void {
    for (0..100_000) |_| counter += 1;
}

pub fn main() !void {
    var threads: [4]std.Thread = undefined;
    for (&threads) |*t| t.* = try std.Thread.spawn(.{}, bump, .{});
    for (threads) |t| t.join();
    std.debug.print("counter = {d} (wanted 400000)\n", .{counter});
}
$ zig run t2_race.zig
counter = 103977 (wanted 400000)
$ zig run t2_race.zig
counter = 103684 (wanted 400000)

Not 400,000, and a different wrong number every run. counter += 1 is three steps on the machine: read the value, add one, write it back. If thread A reads 50, thread B reads 50, both add one and both write 51, one increment has vanished. With four threads hammering the same cache line, most of them vanish.

This is undefined behaviour, not just a wrong answer. Zig, like C, defines a program with a data race as having no meaning at all. The numbers above are what happened on this machine today; on another CPU or with -O ReleaseFast the compiler may hoist the load out of the loop and print 100000, or anything else. Do not reason about what a race "usually" does. Remove it.

There are three honest ways to remove it, and the rest of the chapter is those three.

36.3 Fix one: do not share

The best synchronisation is none. If every thread writes to its own slot and only the main thread reads the slots after join, there is nothing to race on. This is how nearly all "split the work in N pieces" programs should look.

t5_parts.zig
const std = @import("std");

fn sumChunk(chunk: []const u64, out: *u64) void {
    var s: u64 = 0;
    for (chunk) |v| s += v;
    out.* = s;
}

pub fn main() !void {
    var data: [1000]u64 = undefined;
    for (&data, 0..) |*d, i| d.* = i;

    var parts: [4]u64 = undefined;
    var threads: [4]std.Thread = undefined;
    for (&threads, 0..) |*t, i| {
        t.* = try std.Thread.spawn(.{}, sumChunk, .{ data[i * 250 .. (i + 1) * 250], &parts[i] });
    }
    for (threads) |t| t.join();
    std.debug.print("parts {any}\n", .{parts});
    std.debug.print("total {d}\n", .{parts[0] + parts[1] + parts[2] + parts[3]});
}
$ zig run t5_parts.zig
parts { 31125, 93625, 156125, 218625 }
total 499500

Each thread receives a slice of the input (a view, not a copy) and a pointer to exactly one element of parts. The slices do not overlap and the pointers are distinct, so no two threads ever touch the same byte. join is what makes the main thread's reads of parts safe: joining a thread is a guarantee that everything it wrote is visible afterwards. The pattern generalises: chunk the input, one output slot per chunk, join, reduce.

36.4 Fix two: atomics

Sometimes threads really do need one shared number: a progress counter, a "stop now" flag, an ID generator. For a single machine word, the CPU can do read-modify-write as one indivisible step, and Zig exposes that as std.atomic.Value(T).

t3_atomic.zig
const std = @import("std");

var counter: std.atomic.Value(u64) = .init(0);

fn bump() void {
    for (0..100_000) |_| _ = counter.fetchAdd(1, .monotonic);
}

pub fn main() !void {
    var threads: [4]std.Thread = undefined;
    for (&threads) |*t| t.* = try std.Thread.spawn(.{}, bump, .{});
    for (threads) |t| t.join();
    std.debug.print("counter = {d}\n", .{counter.load(.seq_cst)});
}
$ zig run t3_atomic.zig
counter = 400000

Exactly right, every time. fetchAdd(1, .monotonic) adds one atomically and returns the old value (which we discard with _ =). The methods are load, store, swap, fetchAdd, fetchSub, fetchAnd, fetchOr, cmpxchgStrong and cmpxchgWeak, and each takes a memory ordering as its last argument. .init(0) is the initial value.

The ordering argument answers a question you might not know you were asking: "when this thread sees this atomic change, which of the other writes made before it is it guaranteed to see too?" The choices are .monotonic, .acquire, .release, .acq_rel and .seq_cst. For a beginner, two rules cover almost everything:

  • If the atomic is the only thing shared (a pure counter), .monotonic is enough: you want the arithmetic to be atomic and nothing else.
  • If the atomic announces other data ("the buffer is ready", "please stop"), the writer uses .release and the reader uses .acquire. Together they promise the reader sees everything the writer did before the store.

When in doubt, .seq_cst is the strongest and always correct, merely a little slower. Here is the announcement pattern, a stop flag:

t7_flag.zig
const std = @import("std");

var stop: std.atomic.Value(bool) = .init(false);
var ticks: std.atomic.Value(u32) = .init(0);

fn spin() void {
    while (!stop.load(.acquire)) _ = ticks.fetchAdd(1, .monotonic);
}

pub fn main(init: std.process.Init) !void {
    const t = try std.Thread.spawn(.{}, spin, .{});
    try init.io.sleep(.fromMilliseconds(20), .awake);
    stop.store(true, .release);
    t.join();
    std.debug.print("worker ticked {d} times before it saw the flag\n", .{ticks.load(.seq_cst)});
}
$ zig run t7_flag.zig
worker ticked 10134572 times before it saw the flag

The worker spins reading the flag with .acquire; main sleeps 20 ms and stores true with .release. Without atomics, the compiler would be entitled to read stop once, see false, and loop forever; the atomic load tells it the value can change under its feet.

36.5 Fix three: a mutex

Atomics cover one word. When the shared thing is bigger (a list, a hash map, two fields that must change together), you need a lock. A mutex ("mutual exclusion") is a token only one thread can hold; while a thread holds it, everyone else who asks waits. In 0.16 the mutex lives in std.Io, because waiting for a lock is a blocking operation the I/O layer wants to know about, so lock and unlock take the io value.

t4_mutex.zig
const std = @import("std");

var mutex: std.Io.Mutex = .init;
var total: u64 = 0;
var names: std.ArrayList([]const u8) = .empty;

fn work(io: std.Io, gpa: std.mem.Allocator, name: []const u8, pay: u64) !void {
    mutex.lockUncancelable(io);
    defer mutex.unlock(io);
    total += pay;
    try names.append(gpa, name);
}

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const gpa = init.gpa;
    defer names.deinit(gpa);
    const t1 = try std.Thread.spawn(.{}, work, .{ io, gpa, "Grayson", 1500 });
    const t2 = try std.Thread.spawn(.{}, work, .{ io, gpa, "Clay", 800 });
    t1.join();
    t2.join();
    std.debug.print("total {d}, {d} names\n", .{ total, names.items.len });
}
$ zig run t4_mutex.zig
total 2300, 2 names

The shape to memorise is the pair: lock immediately followed by defer unlock. Whatever happens between them, including an early return or a try that fails, the lock is released. Everything that touches total or names happens inside that window, so the two threads take turns, and the ArrayList's internal pointer juggling is never interrupted half way.

lockUncancelable is the plain blocking form. There is also try mutex.lock(io), which can return error.Canceled if the task is cancelled while waiting; use it inside code that participates in cancellation, and the uncancelable form everywhere else.

Gone in 0.16. std.Thread.Mutex, std.Thread.Pool and std.Thread.WaitGroup no longer exist. The mutex is std.Io.Mutex (initialised with .init, methods take io), and the pool-and-wait-group job is done by std.Io.Group, next. If you see the old names in a tutorial, translate.

Hold locks briefly, and never call out to unknown code while holding one. The classic mistake is thread A holding lock 1 waiting for lock 2 while thread B holds 2 waiting for 1: a deadlock, and both wait forever. One lock per program, held for a few lines at a time, avoids it entirely.

36.6 A group of tasks: std.Io.Group

Spawning and joining threads by hand is fine for four fixed workers. For "run these N things and wait for all of them", 0.16 offers std.Io.Group. You call group.async(io, function, args) once per task and group.await(io) once at the end. The io implementation decides how to run them: the default Threaded implementation you get from main uses a pool of OS threads sized to the machine.

t6_group.zig
const std = @import("std");

fn sumChunk(chunk: []const u64, out: *u64) void {
    var s: u64 = 0;
    for (chunk) |v| s += v;
    out.* = s;
}

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    var data: [1000]u64 = undefined;
    for (&data, 0..) |*d, i| d.* = i;

    var parts: [4]u64 = undefined;
    var group: std.Io.Group = .init;
    for (0..4) |i| group.async(io, sumChunk, .{ data[i * 250 .. (i + 1) * 250], &parts[i] });
    try group.await(io);
    std.debug.print("total {d}\n", .{parts[0] + parts[1] + parts[2] + parts[3]});
    std.debug.print("this machine has {d} cpus\n", .{try std.Thread.getCpuCount()});
}
$ zig run t6_group.zig
total 499500
this machine has 14 cpus

Same work as 36.3, no thread handles to manage. std.Thread.getCpuCount() tells you how many hardware threads exist, which is the natural upper bound on how many chunks are worth making. await returns error.Canceled if the group was cancelled, hence the try. The functions you hand to a group must return void or an error union that includes error.Canceled; plain void, as here, is simplest.

The async story, in one paragraph. Group.async is one corner of a larger design. std.Io in 0.16 also has io.async and io.concurrent, which return a Future you later await, plus cancellation that propagates through them. The point of putting all of this behind the io value is that the same code can run on a thread pool today (std.Io.Threaded) and on an event loop tomorrow, without changing the call sites. This book stops here; the standard library's Io.zig has the reference, and the language keywords async/await from older Zig versions are gone.

36.7 When not to use threads

Threads make a program faster only when there is enough independent work to keep more than one core busy, and they make every program harder to reason about. Some honest guidance:

  • A turn-based simulation does not need them. IRON LEDGER advances one day in a few microseconds. Adding threads would add nothing but the risk of a data race breaking determinism.
  • I/O-bound work rarely needs them. Waiting for a disk or a socket does not use a core. The std.Io design exists so such waiting can overlap without you managing threads.
  • Small inputs do not need them. Spawning a thread costs tens of microseconds; summing a thousand numbers costs less than one. Exercise 36.4 measures this.
  • Anything touching a random generator or a hash map from two threads is wrong until you add a lock, and once you add the lock the threads mostly wait for each other.

The places threads do pay off: big, chunkable, CPU-heavy work (image processing, batch parsing, running many independent simulations for statistics); and keeping a user interface responsive while something slow happens in the background. If your program is neither, single-threaded is not a compromise, it is the right design.

In IRON LEDGER. The simulation core in src/sim/ is single-threaded on purpose: the golden-master test in src/sim/commands.zig demands that the same seed and script always produce the same state hash, and a second thread drawing from the RNG or appending to a list would break that in ways no test could reliably catch. The one place the game reaches for concurrency is the terminal client, where the soundtrack plays in a separate process, not a thread: src/tui/music.zig starts the player with std.process.spawn(io, ...) and reaps it with std.c.waitpid, so the audio can be killed and restarted without any shared memory at all. That is a good rule of thumb: prefer a process when the two halves share nothing, a thread only when they must share memory, and neither when the work is small.

Exercises

Exercise 36.1 · Spawn and join warm-up

Start four workers, each summing its own quarter of 0..1_000_000 into its own slot, join them, and print the total. Name the file: exercises/36-concurrency/ex1_spawn.zig.

Solution 
//! Chapter 36, exercise 1: spawn and join.
//! Run with:  zig run ex1_spawn.zig
//! Goal: start four worker threads, each computing the sum of its own
//! range into its own slot, then join them and add the slots. The
//! per-thread lines may appear in any order. Expected output:
//!   worker 0: 0..250000
//!   worker 1: 250000..500000
//!   worker 2: 500000..750000
//!   worker 3: 750000..1000000
//!   total = 499999500000

const std = @import("std");

fn worker(id: usize, lo: u64, hi: u64, out: *u64) void {
    std.debug.print("worker {d}: {d}..{d}\n", .{ id, lo, hi });
    var s: u64 = 0;
    var i = lo;
    while (i < hi) : (i += 1) s += i;
    out.* = s;
}

pub fn main() !void {
    const n_threads = 4;
    const total_n: u64 = 1_000_000;
    var slots: [n_threads]u64 = undefined;
    var threads: [n_threads]std.Thread = undefined;
    const chunk = total_n / n_threads;
    for (&threads, 0..) |*t, i| {
        t.* = try std.Thread.spawn(.{}, worker, .{ i, i * chunk, (i + 1) * chunk, &slots[i] });
    }
    for (threads) |t| t.join();
    var total: u64 = 0;
    for (slots) |s| total += s;
    std.debug.print("total = {d}\n", .{total});
}

The per-thread lines come out in scheduler order, so they differ between runs, but the total is always 499999500000 because each slot is written by exactly one thread and read only after join.

Exercise 36.2 · A shared counter, done right practice

Write bumpAtomic, using std.atomic.Value(u64), and bumpMutex, using std.Io.Mutex around a plain u64, so that four threads each adding 100,000 produce exactly 400,000. The test file gets its io from std.testing.io. Name the file: exercises/36-concurrency/ex2_counter.zig.

Solution 
//! Chapter 36, exercise 2: a shared counter, three ways.
//! Run with:  zig test ex2_counter.zig
//! Goal: fill in the atomic and mutex versions of `bump` so both tests
//! count exactly 4 * 100_000. The plain version is left as a demonstration
//! of a data race and is not tested (its result is not defined).

const std = @import("std");

const per_thread = 100_000;
const n_threads = 4;

var atomic_count: std.atomic.Value(u64) = .init(0);

fn bumpAtomic() void {
    for (0..per_thread) |_| _ = atomic_count.fetchAdd(1, .monotonic);
}

var mutex_count: u64 = 0;
var mutex: std.Io.Mutex = .init;

fn bumpMutex(io: std.Io) void {
    for (0..per_thread) |_| {
        mutex.lockUncancelable(io);
        defer mutex.unlock(io);
        mutex_count += 1;
    }
}

test "atomic counter is exact" {
    var threads: [n_threads]std.Thread = undefined;
    for (&threads) |*t| t.* = try std.Thread.spawn(.{}, bumpAtomic, .{});
    for (threads) |t| t.join();
    try std.testing.expectEqual(@as(u64, n_threads * per_thread), atomic_count.load(.seq_cst));
}

test "mutex counter is exact" {
    const io = std.testing.io;
    var threads: [n_threads]std.Thread = undefined;
    for (&threads) |*t| t.* = try std.Thread.spawn(.{}, bumpMutex, .{io});
    for (threads) |t| t.join();
    try std.testing.expectEqual(@as(u64, n_threads * per_thread), mutex_count);
}

The atomic version needs no io; the mutex version does, so it is passed as a thread argument. Note std.testing.io: tests are given a working I/O implementation, which is also what you would use to test file code. Try timing both: the mutex version is many times slower, because every increment is a lock and unlock.

Exercise 36.3 · Parallel sum over a slice practice

Write parallelSum(data, n_threads) that splits any slice into n_threads chunks (the last one may be short, and there may be fewer items than threads), sums each on its own thread, and returns the total. Tests compare with a serial sum for 1001 items and 4 or 7 threads, and check a 2-item slice with 8 threads and an empty slice. Name the file: exercises/36-concurrency/ex3_parallel_sum.zig.

Solution 
//! Chapter 36, exercise 3: a parallel sum over a slice.
//! Run with:  zig test ex3_parallel_sum.zig
//! Goal: implement `parallelSum` so it splits `data` into `n_threads`
//! chunks, sums each chunk on its own thread, and returns the total.
//! Handle a slice shorter than n_threads and a remainder chunk.

const std = @import("std");

fn sumChunk(chunk: []const u32, out: *u64) void {
    var s: u64 = 0;
    for (chunk) |v| s += v;
    out.* = s;
}

pub fn parallelSum(data: []const u32, comptime n_threads: usize) !u64 {
    var partial = [_]u64{0} ** n_threads;
    var threads: [n_threads]?std.Thread = [_]?std.Thread{null} ** n_threads;
    const chunk_len = (data.len + n_threads - 1) / n_threads; // ceil
    for (0..n_threads) |i| {
        const lo = @min(i * chunk_len, data.len);
        const hi = @min(lo + chunk_len, data.len);
        if (lo == hi) break; // fewer items than threads
        threads[i] = try std.Thread.spawn(.{}, sumChunk, .{ data[lo..hi], &partial[i] });
    }
    for (threads) |maybe| if (maybe) |t| t.join();
    var total: u64 = 0;
    for (partial) |p| total += p;
    return total;
}

test "matches a serial sum" {
    var data: [1001]u32 = undefined;
    for (&data, 0..) |*d, i| d.* = @intCast(i);
    var serial: u64 = 0;
    for (data) |v| serial += v;
    try std.testing.expectEqual(serial, try parallelSum(&data, 4));
    try std.testing.expectEqual(serial, try parallelSum(&data, 7));
}

test "short slices and empty slices" {
    const two = [_]u32{ 5, 6 };
    try std.testing.expectEqual(@as(u64, 11), try parallelSum(&two, 8));
    const none = [_]u32{};
    try std.testing.expectEqual(@as(u64, 0), try parallelSum(&none, 4));
}

The chunk length is rounded up, so the last chunk absorbs the remainder; @min clamps both bounds to the slice; and an empty chunk means "no more work", so we break and leave the remaining thread handles null. Storing ?std.Thread lets the join loop skip the threads that were never started.

Exercise 36.4 · The same work with Io.Group challenge

Allocate one hundred million u64s, sum them once with eight raw threads and once with an std.Io.Group of eight tasks, and time both with the monotonic clock. Print the CPU count. Then shrink the input to a thousand elements and observe that the timings are dominated by thread start-up. Name the file: exercises/36-concurrency/ex4_group.zig.

Solution 
//! Chapter 36, exercise 4: the same work with std.Io.Group.
//! Run with:  zig run ex4_group.zig
//! Goal: rewrite the parallel sum with an Io.Group instead of raw
//! threads, and time both. Expected output (timings vary):
//!   threads: 4999999950000000 in 30 ms
//!   group:   4999999950000000 in 30 ms
//!   cpus: 14

const std = @import("std");

fn sumChunk(chunk: []const u64, out: *u64) void {
    var s: u64 = 0;
    for (chunk) |v| s += v;
    out.* = s;
}

const n = 100_000_000;
const n_tasks = 8;

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const data = try init.gpa.alloc(u64, n);
    defer init.gpa.free(data);
    for (data, 0..) |*d, i| d.* = i;
    var parts: [n_tasks]u64 = undefined;
    const chunk = n / n_tasks;

    var t0 = std.Io.Clock.now(.awake, io);
    var threads: [n_tasks]std.Thread = undefined;
    for (&threads, 0..) |*t, i| {
        t.* = try std.Thread.spawn(.{}, sumChunk, .{ data[i * chunk .. (i + 1) * chunk], &parts[i] });
    }
    for (threads) |t| t.join();
    var total: u64 = 0;
    for (parts) |p| total += p;
    var t1 = std.Io.Clock.now(.awake, io);
    std.debug.print("threads: {d} in {d} ms\n", .{ total, t0.durationTo(t1).toMilliseconds() });

    t0 = std.Io.Clock.now(.awake, io);
    var group: std.Io.Group = .init;
    for (0..n_tasks) |i| {
        group.async(io, sumChunk, .{ data[i * chunk .. (i + 1) * chunk], &parts[i] });
    }
    try group.await(io);
    total = 0;
    for (parts) |p| total += p;
    t1 = std.Io.Clock.now(.awake, io);
    std.debug.print("group:   {d} in {d} ms\n", .{ total, t0.durationTo(t1).toMilliseconds() });
    std.debug.print("cpus: {d}\n", .{try std.Thread.getCpuCount()});
}

Both versions take about the same time, because the group is a thread pool underneath. The value of the group is not speed but bookkeeping: no handle array, no join loop, and the pool is already sized to the machine. Compare the code of the two halves and notice which one you would rather maintain.

Check your understanding

  1. Why did the plain counter print 103977 instead of 400000, and why is the exact number meaningless?
    Answercounter += 1 is a read, an add and a write; two threads interleaving those steps lose increments. A program with a data race has undefined behaviour, so the value depends on the CPU, the optimiser and luck.
  2. What does join guarantee besides "the thread has finished"?
    AnswerThat everything the thread wrote is visible to the joining thread afterwards. That is what makes reading the per-thread slots after join safe without any atomics.
  3. When is .monotonic ordering enough, and when do you need .release/.acquire?
    Answer.monotonic suffices when the atomic itself is the only shared data (a counter). When the atomic announces other data ("buffer ready", "stop"), the writer stores with .release and the reader loads with .acquire.
  4. Write the idiomatic mutex pair in 0.16.
    Answermutex.lockUncancelable(io); defer mutex.unlock(io); with var mutex: std.Io.Mutex = .init;. Note that std.Thread.Mutex is gone.
  5. Why must a function given to std.Thread.spawn receive a pointer to write its result, rather than returning it?
    AnswerA spawned function may only return void, !void, u8 or noreturn, and join does not hand the value back. Writing through a pointer to a slot the caller owns is how results come back, and join makes the write visible.
  6. What replaced std.Thread.Pool and WaitGroup?
    Answerstd.Io.Group: group.async(io, fn, args) per task and try group.await(io) to wait for all of them. The default Io.Threaded runs them on a thread pool.
  7. Give two reasons IRON LEDGER's simulation stays single-threaded.
    AnswerA day's work is far too small to benefit, and any second thread touching the RNG, the maps or the lists would destroy the determinism the golden-master test guards.
What you learned.
  • std.Thread.spawn(.{}, f, .{args}) starts a thread; t.join() waits and makes its writes visible. Arguments are copied; share by pointer.
  • Two threads writing one variable without synchronisation is a data race: undefined behaviour, not merely a wrong count.
  • Fix it by not sharing (one slot per thread), with std.atomic.Value(T) (load, store, fetchAdd, orderings .monotonic/.acquire/.release/.seq_cst), or with std.Io.Mutex and lockUncancelable/defer unlock.
  • std.Io.Group runs a batch of tasks on the I/O layer's thread pool; std.Thread.getCpuCount() sizes the batch. std.Thread.Mutex, Pool and WaitGroup are gone in 0.16.
  • Use threads for large, chunkable, CPU-bound work; prefer a process when nothing is shared; stay single-threaded when the work is small or must be deterministic.
