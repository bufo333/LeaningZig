44. Queries: the only way out

In this chapter you read the other door. Frontends never walk GameState to draw a screen; they call a query, which returns rows of formatted text plus the IDs a key handler will need, allocated from an arena the caller throws away after drawing. You will read one query end to end, learn the colour markup that lets one query serve two frontends, meet a bug that taught the project a rule, and extend a query yourself.

What you need from earlier chapters. Chapter 23 (format specifiers, especially width and alignment such as {s: <20} and {d: >3}, and allocPrint), Chapter 21 (ArrayListUnmanaged and toOwnedSlice), Chapter 20 (a per-call arena), Chapter 10 and Chapter 11 (slicing and searching strings), Chapter 13 (an enum with a method, used as a filter) and Chapter 27 (inline for over an enum's fields, in personRecord).

44.1 The contract

Every function in src/sim/queries.zig has the same first two parameters:

pub fn people(alloc: Alloc, gs: *GameState, filter: HallFilter) !People
pub fn hqDetail(alloc: Alloc, gs: *GameState, id: types.HqId) ![]const []const u8
pub fn manning(alloc: Alloc, gs: *GameState, company: types.ForceId) ![]ManningRow
pub fn personRecord(alloc: Alloc, gs: *GameState, id: types.PersonId) ![]const []const u8

An allocator and the state, then whatever selects the view. The allocator is never the state's arena. In the terminal client it is a frame arena that is reset before every draw; in a test it is a small arena created for the call; in the REPL it is a temporary arena around one print. The query allocates freely into it (hundreds of small strings for a busy screen) and frees nothing, and the caller drops the whole arena when the screen has been drawn. This is the third lifetime from Chapter 20: not the process, not the campaign, but one frame.

The return value is plain data with no methods and no pointers back into the state: strings already formatted, and typed IDs next to them. The file is 4,000 lines because there are many screens, not because any query is complicated.

44.2 One query, end to end

The People screen's query is a good first read because it is one loop:

src/sim/queries.zig
pub const PersonRow = struct {
    id: types.PersonId,
    text: []const u8,
    // …
};

pub const People = struct {
    header: []const u8,
    rows: []PersonRow,
    total: usize,
    // …
};

/// Everyone on the payroll (active, wounded, missing), filtered by role group.
pub fn people(alloc: Alloc, gs: *GameState, filter: HallFilter) !People {
    var rows: std.ArrayListUnmanaged(PersonRow) = .empty;
    var total: usize = 0;
    var it = gs.people.iterator();
    while (it.next()) |e| {
        const p = e.value_ptr;
        if (p.status == .kia or p.status == .retired or p.status == .resigned or p.status == .released) continue;
        total += 1;
        if (!filter.matches(p.role)) continue;
        if (filter == .wounded and p.status != .wounded) continue;
        if (filter == .unassigned and !isUnassigned(gs, p)) continue;
        const name = try p.rankedName(alloc);
        try rows.append(alloc, .{ .id = p.id, .text = try std.fmt.allocPrint(alloc, "{d: <4} {s: <20} {s: <15} {s: <7} {s: <5} {d: >3} {s} {s} {s: <11} {d: >3} {d: >3} {s: >7}", .{
            @intFromEnum(p.id),                                                             clip(name, 20),
            @tagName(p.role),                                                               @tagName(p.experience()),
            try skillsText(alloc, p),                                                       p.xp,
            try padMk(alloc, "", try stripMarkup(alloc, try statusText(alloc, gs, p)), 18), try padMk(alloc, "", try stripMarkup(alloc, try assignmentText(alloc, gs, p)), 22),
            clip(locationText(gs, p), 11),                                                  p.fatigue,
            p.morale,                                                                       try money(alloc, p.monthlySalary()),
        }) });
    }
    return .{
        .header = "id   name                 role            exp     skill  XP status             assignment             where       fat mor     pay",
        .rows = try rows.toOwnedSlice(alloc),
        .total = total,
    };
}

Walk it. The map iterator visits people in insertion order (Chapter 41), so the roster is stable from frame to frame. The departed are skipped before total is counted, so the header can say "12 of 30" when a filter is on. Then a row is one allocPrint with a long format string: {d: <4} left-aligns the ID in four columns, {s: <20} left-aligns the name in twenty, {d: >3} right-aligns fatigue in three, {s: >7} right-aligns the money. Everything the format string cannot do (clip a long name, strip colour codes before padding, format money with separators) is a small helper at the top of the file: clip, stripMarkup, padMk, money.

The row carries p.id beside its text. That is the second half of the contract: when the cursor is on row seven and the user presses D to fire, the key handler reads rows[7].id and builds .{ .fire = id }. It never has to work out which person row seven was, because the query told it.

The filter is an enum with a method, the pattern from Chapter 13:

pub const HallFilter = enum {
    all,
    combat, // mekwarriors, vehicle crews, aero pilots
    techs, // tech_mek / tech_mechanic / tech_aero / tech_ba / astech
    medical, // doctors, medics
    admin_command,
    admin_logistics,
    admin_transport,
    admin_hr,
    admin_finance,
    other, // infantry, battle armor, everything else
    unassigned, // personnel screen only: no seat, no HQ posting, no company
    wounded, // personnel screen only: anyone hurt, in the medbay or waiting

    pub fn matches(self: HallFilter, role: person_mod.Role) bool {
        return switch (self) {
            .all, .unassigned, .wounded => true,
            .combat => role == .mekwarrior or role == .vehicle_crew or role == .aero_pilot,
            .techs => role == .tech_mek or role == .tech_mechanic or role == .tech_aero or role == .tech_ba or role == .astech,
            .medical => role == .doctor or role == .medic,
            // …
        };
    }
};

The same enum serves the hiring hall and the people screen, and the client cycles it with a key. Because it is an exhaustive enum with a switch, adding a group is a two-line change and the compiler lists the switch.

44.3 Markup: one query, two frontends

Look at statusText's output being passed through stripMarkup above. Query text carries lightweight colour markup: {g}active{/} means "green until the reset", {c} is critical red, {a} amber, {d} dim, {p} purple, {s} selected. The terminal client's screen renders the codes into styles (Chapter 48); the REPL strips them; and inside a fixed-width column they must be removed before padding, or the invisible codes would count as characters and the columns would drift. That is what stripMarkup is for:

/// Remove `{x}` markup tokens (for fixed-width columns).
pub fn stripMarkup(alloc: Alloc, s: []const u8) ![]const u8 {
    var out: std.ArrayListUnmanaged(u8) = .empty;
    var i: usize = 0;
    while (i < s.len) : (i += 1) {
        if (s[i] == '{' and i + 2 < s.len and s[i + 2] == '}' and std.mem.indexOfScalar(u8, "agcsdtp/", s[i + 1]) != null) {
            i += 2;
            continue;
        }
        try out.append(alloc, s[i]);
    }
    return out.toOwnedSlice(alloc);
}

A hand-written scanner over a byte slice, the Chapter 11 kind. There is a trap here that Chapter 23 warned you about: a literal brace inside a format string must be doubled. So in a plain string literal the markup is "{g}active{/}", but inside an allocPrint format it is "{{g}}{s}{{/}}". You can see both forms in personRecord below. Get it wrong and the compiler complains about an invalid format specifier, which is a kinder failure than most template languages give you.

44.4 A longer query: the person record

The r key on the People screen opens a record, built by personRecord. It is eighty lines of out.append(alloc, try std.fmt.allocPrint(alloc, …)); here are the parts that teach something:

pub fn personRecord(alloc: Alloc, gs: *GameState, id: types.PersonId) ![]const []const u8 {
    var out: std.ArrayListUnmanaged([]const u8) = .empty;
    const p = gs.person(id) orelse return out.toOwnedSlice(alloc);
    const day = gs.clock.day_index;
    try out.append(alloc, try std.fmt.allocPrint(alloc, "{{a}}{s} {s} {s}{{/}}{s}  ·  {s} · {s} · {s}{s}", .{
        p.rank.abbrev(), p.first_name, p.last_name,
        if (p.callsign) |c| try std.fmt.allocPrint(alloc, " \"{s}\"", .{c}) else "",
        @tagName(p.role), @tagName(p.experience()), p.rank.name(),
        if (p.rank_pinned) " (pinned — :promote <id> <rank> unpin lets seats decide)" else "",
    }));
    // … status, assignment, unit …
    try out.append(alloc, "");
    try out.append(alloc, "skill               level   next   XP cost");
    inline for (@typeInfo(types.SkillType).@"enum".fields) |f| {
        const st: types.SkillType = @enumFromInt(f.value);
        if (p.skill(st)) |lvl| {
            const primary = st == p.role.primarySkill();
            if (lvl == 0) {
                try out.append(alloc, try std.fmt.allocPrint(alloc, "{s}{s: <19} {d: >5}   mastered{{/}}", .{ if (primary) "{a}" else "", f.name, lvl }));
            } else {
                const cost = person_mod.improveCost(lvl - 1);
                try out.append(alloc, try std.fmt.allocPrint(alloc, "{s}{s: <19} {d: >5} {d: >6} {d: >8}{s}{{/}}", .{ if (primary) "{a}" else "", f.name, lvl, lvl - 1, cost, if (p.xp >= cost) "  {g}affordable{/}" else "" }));
            }
        }
    }
    // … training, abilities, age, loyalty, shares, record, awards, injuries …
    try out.append(alloc, try std.fmt.allocPrint(alloc, "available   {s}", .{if (p.isAvailable(day)) "{g}yes{/}" else "{c}no{/}"}));
    return out.toOwnedSlice(alloc);
}

Three things. First, an unknown ID returns an empty list rather than an error; a screen with nothing to show is not a failure. Second, the skills table is an inline for over the SkillType enum's fields (Chapter 27): the loop is unrolled at compile time, one iteration per skill, and f.name is the skill's name as a compile-time string, so adding a skill to the enum adds a row here with no edit. Third, the if … else "" idiom inside argument tuples: an optional piece of text is an empty string when absent, which keeps every line a single allocPrint.

44.5 The bug that made a rule

The original guide records a bug worth retelling because its fix is a query. The HQ screen once mapped the cursor row to a facility by position, assuming the facility table started on row one. When the tier section above it grew (a field HQ explains how to become regional; a regional one does not), every row shifted and the u key upgraded the wrong facility. The fix:

/// Which facility a row of `hqDetail` names, or null. The tier section
/// above the facility table varies in length (field HQs explain how to
/// become regional), so the HQ screen's `u` reads the cursor through this
/// rather than by position.
pub fn hqFacilityAtRow(alloc: Alloc, gs: *GameState, id: types.HqId, row: usize) !?@import("../domain/hq.zig").FacilityKind {
    const lines = try hqDetail(alloc, gs, id);
    if (row >= lines.len) return null;
    // The table runs from the "facility" header to the next blank line.
    var header: ?usize = null;
    for (lines, 0..) |l, i| if (std.mem.startsWith(u8, l, "facility ")) {
        header = i;
        break;
    };
    const start = (header orelse return null) + 1;
    if (row < start) return null;
    for (lines[start..row + 1]) |l| if (l.len == 0) return null;
    var it = std.mem.tokenizeScalar(u8, lines[row], ' ');
    const tag = it.next() orelse return null;
    return std.meta.stringToEnum(@import("../domain/hq.zig").FacilityKind, tag);
}

It reads the rendered rows back, finds the header, checks the row is inside the table, and parses the first word back into the enum with std.meta.stringToEnum. The return type !?FacilityKind is "may fail to allocate; may be no facility". A test builds an HQ, renders it, and checks that every row maps to the facility it names and the header maps to null. The rule of thumb the project took from it: if a key handler needs to know what a row means, ask a query, never count.

44.6 Queries that return structure

Not every query returns lines. When the client needs to act on numbers, the query returns a struct per row and lets the client format the numbers it needs:

pub const ManningRow = struct {
    role: person_mod.Role,
    have: u32,
    need: u32,
    text: []const u8,
};

pub fn manning(alloc: Alloc, gs: *GameState, company: types.ForceId) ![]ManningRow {
    const personnel = @import("personnel.zig");
    const needs = personnel.manningNeeds(gs, company);
    var out: std.ArrayListUnmanaged(ManningRow) = .empty;
    // … tech-hours needed against tech-hours available …
    for (needs) |n| {
        const have = personnel.manningHave(gs, company, n.role);
        const open = n.need -| have;
        const why = /* … */;
        try out.append(alloc, .{ .role = n.role, .have = have, .need = n.need, .text = try std.fmt.allocPrint(alloc,
            "{s: <16} {d: >5} {d: >5} {s}{d: >5}{{/}}   {{d}}{s}{{/}}",
            .{ @tagName(n.role), have, n.need, if (open > 0) "{c}" else "{g}", open, why }) });
    }
    return out.toOwnedSlice(alloc);
}

n.need -| have is saturating subtraction (Chapter 4): zero when the company has more than it needs, never negative. The row carries have and need as numbers as well as in the text, so the raise-a-company wizard can total them without parsing its own output. You will see this query again in Chapter 50, because it is what redraws after the c key crews a company.

Guided reading

  1. src/sim/queries.zig, lines 1 to about 100: the helpers money, padCells, padMk, clip, planetName, personName. Each is a few lines and you will see them in every query.
  2. status and desk (the status strip and the Desk screen), then people, then personRecord.
  3. hqDetail and hqFacilityAtRow, and the test "the HQ screen's facility rows map back to facilities whatever sits above them" at the bottom of the file.
  4. manning, toe and toeFiltered: the structured kind.
  5. summary and rating: two queries that compute rather than list. rating is the game's reputation formula and is also called by the tick (queries.ratingScore in runFinances), an example of a query being pure enough to use as a rule.

Exercises

Exercise 44.1 · One more line on the record practice

Add a line to personRecord showing this person's salary as a percentage of the outfit's monthly payroll (gs.monthlyPayroll()). Only one file changes. Then write a test that hires a 1,500-a-month mekwarrior and a 400-a-month astech and checks the exact line for the mekwarrior.

Solution
src/sim/queries.zig, in personRecord, before the skills header
    {
        const payroll = gs.monthlyPayroll();
        if (payroll > 0) try out.append(alloc, try std.fmt.allocPrint(alloc, "payroll     {d}% of the outfit's monthly payroll", .{@divTrunc(p.monthlySalary() * 100, payroll)}));
    }
test "the record shows the payroll share" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    const a = arena.allocator();
    const id = try gs.hirePerson("Lori", "Kalmar", .mekwarrior);
    _ = try gs.hirePerson("Clay", "Cluny", .astech);
    const rec = try personRecord(a, &gs, id);
    var found: ?[]const u8 = null;
    for (rec) |line| if (std.mem.startsWith(u8, line, "payroll ")) {
        found = line;
    };
    // 1500 of 1900: seventy-eight percent, truncated.
    try std.testing.expectEqualStrings("payroll     78% of the outfit's monthly payroll", found.?);
}

Integer arithmetic throughout: @divTrunc because CBills is signed (Chapter 45), multiply before dividing to keep the precision, and the payroll > 0 guard because a state with nobody hired would divide by zero. 1500 × 100 / 1900 is 78.94, truncated to 78. Notice the block { … } around the two lines: it scopes payroll so the name cannot collide with anything later in this long function, a habit worth copying in a codebase where shadowing is an error.

Exercise 44.2 · Test a filtered query practice

Write a test for people: hire one mekwarrior and one tech_mek, query with .techs, and assert one row, a total of two, the right id on the row, and that the row text contains the tech's last name. Then query with .all and assert the order matches hiring order.

Solution 
test "the people query filters by role group and keeps ids" {
    var gs = GameState.init(std.testing.allocator, .{});
    defer gs.deinit();
    const pilot = try gs.hirePerson("Grayson", "Carlyle", .mekwarrior);
    const tech = try gs.hirePerson("Clay", "Cluny", .tech_mek);
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    const a = arena.allocator();
    const techs = try people(a, &gs, .techs);
    try std.testing.expectEqual(@as(usize, 1), techs.rows.len);
    try std.testing.expectEqual(@as(usize, 2), techs.total);
    try std.testing.expectEqual(tech, techs.rows[0].id);
    try std.testing.expect(std.mem.indexOf(u8, techs.rows[0].text, "Cluny") != null);

}

The three-line arena setup is the one the original guide called out as appearing in every query test. total counts before the filter and rows after, which is the property the header relies on. The order assertion holds because gs.people is an ordered map.

Exercise 44.3 · Markup round trip warm-up

Write a test that stripMarkup turns "{g}ok{/} now" into "ok now". Then read stripMarkup again and say what it does with "{x}", which is not a colour, and with a lone "{" at the end of a string.

Solution 
test "markup strips to plain text" {
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    try std.testing.expectEqualStrings("ok now", try stripMarkup(arena.allocator(), "{g}ok{/} now"));
}

"{x}" is copied through unchanged, because 'x' is not in "agcsdtp/"; only the eight known codes are treated as markup. A lone '{' at the end is also copied, because the check i + 2 < s.len fails before any out-of-bounds index is attempted. The function is written so that it can never panic on any input, which matters for text that came from a data file or a player.

Check your understanding

  1. Why does a query take an allocator rather than using gs.allocator()?
    AnswerQuery results live for one frame, not for the campaign; allocating them from the campaign arena would leak a screen's worth of strings on every redraw. The caller passes a frame arena it resets after drawing.
  2. Why does PersonRow carry an id?
    AnswerSo a key handler can act on the highlighted row (fire, admit, assign) by reading the ID beside the text instead of re-deriving which person the row was.
  3. What is {{g}} in a format string, and what is {g} in a plain literal?
    AnswerThe same markup token: braces must be doubled inside a format string because { and } are format syntax, while a plain string literal needs no escaping.
  4. Why must markup be stripped before padding a column?
    AnswerThe tokens are invisible when rendered but count as bytes in {s: <18}, so padding a marked-up string yields columns that are too short by three bytes per token.
  5. What went wrong on the HQ screen, and what is the resulting rule?
    AnswerThe key handler mapped cursor rows to facilities by position; when the section above the table changed length, the mapping was off by the difference. Rule: if a key handler needs to know what a row means, ask a query.
  6. How does personRecord list skills without naming any?
    AnswerWith inline for over @typeInfo(types.SkillType).@"enum".fields, which unrolls one iteration per enum variant at compile time and provides each name as a string.
What you learned.
  • Every query takes an allocator and the state and returns plain data: formatted rows with typed IDs beside them, or small structs of numbers plus text.
  • Callers pass a frame arena and reset it after drawing, so query results cost nothing to free.
  • Row text carries {g}…{/} markup that the terminal renders and the REPL strips; braces are doubled inside format strings.
  • A key handler that needs the meaning of a row asks a query (hqFacilityAtRow) rather than counting rows.
  • Reflection (inline for over an enum) keeps tables in step with the types they display.
