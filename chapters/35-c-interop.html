35. Calling C

In this chapter you will call functions from the C standard library and from SQLite without writing a line of C: declaring them with extern fn, matching C's types, handling C strings and opaque handles, and turning C's integer return codes into Zig errors. You will also see @cImport, which reads a C header for you, and export fn, which goes the other way.

35.1 Why this is easy in Zig

Most languages need a "foreign function interface": a binding generator, a wrapper library, some glue in a third language. Zig needs none of that, because Zig's types already include every type C has. A C int is c_int. A C pointer is a Zig pointer. A C string is a pointer to bytes with a zero at the end, and Zig has a type for exactly that. So calling C is a matter of declaring the function with Zig types, and the linker does the rest.

Here is the smallest possible example: two functions from libc.

c1_strlen.zig
const std = @import("std");

extern fn strlen(s: [*:0]const u8) usize;
extern fn getpid() c_int;

pub fn main() void {
    const name: [*:0]const u8 = "Grayson Carlyle";
    std.debug.print("strlen = {d}\n", .{strlen(name)});
    std.debug.print("pid    = {d}\n", .{getpid()});
}
$ zig run -lc c1_strlen.zig
strlen = 15
pid    = 36500

extern fn says "this function exists, somewhere in a library I will link; here is its signature". There is no body. The name must match the C symbol exactly. And -lc on the command line tells Zig to link the C library, which is where strlen and getpid live. (On macOS the system library is always linked, so this particular example happens to work without -lc; on Linux it would fail with an undefined symbol. Always pass -lc when you use libc, so your program is portable.)

The signature is the whole contract, so it has to be right. Zig provides the C integer types as builtins whose size follows the target platform:

The important mental shift is about pointers. In Zig a pointer's type says whether it points to one thing (*T) or to many ([*]T), and whether it can be null (?). C has one pointer type for all of these, so when you declare a C function you are adding information the C header did not have. Choose honestly: if C can hand you NULL, write ?; if it is a string, write the sentinel.

Two more pieces of vocabulary. callconv(.c) on a Zig function says "make this callable the way C expects", which you need whenever C will call your function (a callback). And @cImport/std.c can spare you writing declarations at all; both come later in the chapter.

35.3 A callback: qsort

C's qsort sorts an array of anything, given the element size and a comparison function. It is the classic example of C calling back into your code, and it shows every type from the table at once.

c3_qsort.zig
const std = @import("std");

const Compare = *const fn (?*const anyopaque, ?*const anyopaque) callconv(.c) c_int;
extern fn qsort(base: ?*anyopaque, count: usize, size: usize, cmp: Compare) void;

fn ascending(a: ?*const anyopaque, b: ?*const anyopaque) callconv(.c) c_int {
    const x: *const c_int = @ptrCast(@alignCast(a.?));
    const y: *const c_int = @ptrCast(@alignCast(b.?));
    if (x.* < y.*) return -1;
    if (x.* > y.*) return 1;
    return 0;
}

pub fn main() void {
    var values = [_]c_int{ 1500, 400, 800, 640 };
    qsort(&values, values.len, @sizeOf(c_int), ascending);
    std.debug.print("{any}\n", .{values});
}
$ zig run -lc c3_qsort.zig
{ 400, 640, 800, 1500 }

Read the comparator slowly. C promises to call it with two const void *, so the parameters are ?*const anyopaque. We know they are really pointers to c_int, so we convert: a.? unwraps the optional (a null here would be a bug in qsort), @alignCast asserts the pointer is aligned well enough for a c_int, and @ptrCast changes the pointee type. Both casts are safety-checked in Debug builds. The callconv(.c) after the parameter list is what makes this function acceptable where C expects a function pointer.

The type *const fn (...) callconv(.c) c_int is a pointer to such a function. We give it a name, Compare, only to keep the qsort declaration readable. And &values, a pointer to an array, coerces to ?*anyopaque automatically, because any pointer can become a void *.

35.4 Strings across the border

A C string is a [*:0]const u8: a pointer to bytes, with the promise that a zero byte marks the end. A Zig string is a []const u8: a pointer and a length, no terminator needed. Crossing from one to the other is a small ceremony in each direction.

Zig to C. String literals are secretly [:0]const u8, a slice that also promises the terminator, and they coerce to [*:0]const u8 without a copy. That is why passing "Grayson Carlyle" to strlen just worked. A runtime slice does not carry that promise: to hand one to C you copy it into a buffer and add the zero yourself (Exercise 35.5), or allocate with allocator.dupeZ(u8, s), which does the same on the heap.

C to Zig. Given a [*:0]const u8, std.mem.span walks to the zero and returns a proper slice with a length. From then on it is an ordinary Zig string.

c4_span.zig
const std = @import("std");

extern fn getenv(name: [*:0]const u8) ?[*:0]const u8;

pub fn main() void {
    const raw = getenv("HOME") orelse {
        std.debug.print("HOME is not set\n", .{});
        return;
    };
    const home: []const u8 = std.mem.span(raw);
    std.debug.print("HOME has {d} bytes and starts with '{c}'\n", .{ home.len, home[0] });

    // Going the other way: a Zig string literal is already sentinel-terminated.
    const lit: [:0]const u8 = "campaigns.db";
    const ptr: [*:0]const u8 = lit; // coerces, no copy
    std.debug.print("{s}\n", .{ptr});
}
$ zig run -lc c4_span.zig
HOME has 11 bytes and starts with '/'
campaigns.db

getenv returns NULL when the variable is unset, so the return type is ?[*:0]const u8 and we use orelse. The type system made us think about the missing case, which is precisely what C would not have done.

Who owns the bytes? A string C gives you usually points into C's memory. getenv's result lives as long as the environment; SQLite's column text is valid only until the next step. If you need it later, copy it (allocator.dupe). IRON LEDGER's Stmt.text always copies for this reason.

35.5 Opaque handles and return codes

Most C libraries give you a pointer to some struct they never let you see, and every function returns an int that is zero on success. SQLite is the model citizen of this style, and it is installed on this machine, so we can use the real thing. Three declarations get us open, execute and close:

c8_errors.zig
const std = @import("std");

const Handle = opaque {};
extern fn sqlite3_open(filename: [*:0]const u8, db: *?*Handle) c_int;
extern fn sqlite3_close(db: *Handle) c_int;
extern fn sqlite3_exec(db: *Handle, sql: [*:0]const u8, cb: ?*anyopaque, arg: ?*anyopaque, errmsg: ?*?[*:0]u8) c_int;
extern fn sqlite3_free(p: ?*anyopaque) void;
extern fn sqlite3_libversion() [*:0]const u8;

const SQLITE_OK = 0;

const Db = struct {
    h: *Handle,

    fn open(path: [*:0]const u8) error{SqliteError}!Db {
        var h: ?*Handle = null;
        if (sqlite3_open(path, &h) != SQLITE_OK or h == null) return error.SqliteError;
        return .{ .h = h.? };
    }

    fn close(self: Db) void {
        _ = sqlite3_close(self.h);
    }

    fn exec(self: Db, sql: [*:0]const u8) error{SqliteError}!void {
        var msg: ?[*:0]u8 = null;
        if (sqlite3_exec(self.h, sql, null, null, &msg) != SQLITE_OK) {
            if (msg) |m| {
                std.debug.print("sqlite says: {s}\n", .{m});
                sqlite3_free(m);
            }
            return error.SqliteError;
        }
    }
};

pub fn main() !void {
    std.debug.print("SQLite {s}\n", .{sqlite3_libversion()});
    const db = try Db.open(":memory:");
    defer db.close();
    try db.exec("CREATE TABLE person (name TEXT, salary INTEGER)");
    try db.exec("INSERT INTO person VALUES ('Grayson', 1500)");
    std.debug.print("two statements ran\n", .{});
    db.exec("SELEKT * FROM person") catch |e| std.debug.print("caught {s}\n", .{@errorName(e)});
}
$ zig run -lc -lsqlite3 c8_errors.zig
SQLite 3.51.0
two statements ran
sqlite says: near "SELEKT": syntax error
caught SqliteError

Walk through the shapes:

  • const Handle = opaque {}; declares a type with unknown size and contents. You can have a *Handle and pass it around, but you cannot dereference it or make one yourself. That is exactly what SQLite's sqlite3 * is. Because it is a distinct type, you also cannot pass a statement handle where a database handle belongs; C would let you.
  • sqlite3_open takes an out-parameter, a pointer to a pointer: *?*Handle. We declare var h: ?*Handle = null; and pass &h. After the call, if it succeeded, h is non-null and we unwrap it with h.?.
  • sqlite3_exec's error message is another out-parameter, ?*?[*:0]u8: an optional pointer (we may pass NULL to say "I don't want it") to an optional C string (SQLite may leave it NULL). The message is allocated by SQLite, so we must give it back with sqlite3_free.
  • Every return code is compared with SQLITE_OK, and the wrapper turns "not OK" into error.SqliteError. Above the wrapper, nobody sees a c_int again; they see try db.exec(...).

This is the pattern for every C library: raw extern declarations at the bottom of one file, a thin Zig struct with methods above them that speaks errors and slices, and nothing C-shaped leaking out of that file. If you forget to link the library, the error is clear and comes from the linker, not the compiler:

$ zig run -lc c8_errors.zig
error: undefined symbol: _sqlite3_close
    note: referenced by .../c8_errors_zcu.o:_c8_errors.Db.close
error: undefined symbol: _sqlite3_exec
    ...

35.6 @cImport and std.c: letting the compiler read the header

Writing declarations by hand is fine for a dozen functions, and it keeps your dependency on the C library explicit and reviewable. For a large API, Zig can translate the header for you. @cImport takes a block of @cInclude calls and produces a namespace containing every function, type and macro from those headers:

c7_cimport.zig
const std = @import("std");
const c = @cImport({
    @cInclude("stdio.h");
    @cInclude("math.h");
});

pub fn main() void {
    const root = c.sqrt(2.0);
    _ = c.printf("sqrt(2) = %.4f\n", root);
    std.debug.print("c_int is {d} bits, c_long is {d} bits\n", .{ @bitSizeOf(c_int), @bitSizeOf(c_long) });
}
$ zig run -lc c7_cimport.zig
c_int is 32 bits, c_long is 64 bits
sqrt(2) = 1.4142

This works directly from zig run -lc in 0.16; no build.zig configuration is needed for headers that live in the system include path. (In a build script the equivalent is exe.linkLibC() plus, for third-party headers, exe.addIncludePath.) The translated declarations use C's loose pointer types ([*c]u8, a "C pointer" that may be null and may point to one or many), so you will do a little more casting than with hand-written declarations, but you get the entire header for free. Exercise 35.4 wraps strtol this way.

For libc specifically there is a middle path: std.c already contains hand-written declarations for most of POSIX, with good Zig types.

c5_stdc.zig
const std = @import("std");

pub fn main() void {
    std.debug.print("pid  {d}\n", .{std.c.getpid()});
    std.debug.print("ppid {d}\n", .{std.c.getppid()});
    if (std.c.getenv("SHELL")) |sh| std.debug.print("shell {s}\n", .{sh});
}
$ zig run -lc c5_stdc.zig
pid  36661
ppid 36655
shell /bin/zsh

Not everything is there (strlen is not, for instance, because std.mem covers it), so when a name is missing, declare it yourself. Note also that std.c.getenv is typed to return ?[*:0]u8, and {s} knows how to print a sentinel-terminated pointer.

35.7 The other direction: export

export fn makes a Zig function visible to C under its exact name, with the C calling convention. Compile the file as a library (zig build-lib) and a C program can link against it; or, as here, simply call it from Zig, which is a handy way to test.

c6_export.zig
const std = @import("std");

export fn ledger_apply_bp(amount: i64, bp: i64) i64 {
    return @divTrunc(amount * bp, 10_000);
}

pub fn main() void {
    std.debug.print("{d}\n", .{ledger_apply_bp(1500, 11_000)});
}
$ zig run c6_export.zig
1650

An exported function's parameters and return type must be C-compatible: integers, floats, pointers, extern structs. A Zig slice or error union would not have a C representation, and the compiler will tell you so. This is how IRON LEDGER could one day expose its simulation to a C or Python front end: an exported function per command, taking integers and C strings.

In IRON LEDGER. The game's whole persistence layer stands on src/persist/sqlite.zig: eleven extern fn declarations against SQLite plus two opaque {} handle types, with no header translation. The file is the pattern of 35.5 at full size. Db.open, Db.exec and Db.prepare wrap return codes; Stmt.bind uses @typeInfo (as in Chapter 27) to choose sqlite3_bind_int64, sqlite3_bind_text or sqlite3_bind_null from the Zig type of the value; Stmt.text copies column bytes into an allocator because SQLite's buffer dies on the next step. The constant transient is SQLite's SQLITE_TRANSIENT, the special destructor pointer (void*)-1, spelled as @ptrFromInt(std.math.maxInt(usize)). The linker finds the symbols because build.zig says linkSystemLibrary("sqlite3"), the build-script form of -lsqlite3. The same discipline holds for the terminal: std.posix.tcsetattr for raw mode and std.c.waitpid for the music player are each confined to one file.

Exercise 35.2 · qsort with your comparator practice

Sort an array of i64 salaries with libc's qsort and a comparator written in Zig. Name the file: exercises/35-c-interop/ex2_qsort.zig.

Solution 
//! Chapter 35, exercise 2: qsort with a Zig comparator.
//! Run with:  zig run -lc ex2_qsort.zig
//! Goal: sort an array of salaries with libc's qsort, using a comparator
//! written in Zig with callconv(.c). Expected output:
//!   before: { 1500, 400, 800, 640, 1500, 500 }
//!   after:  { 400, 500, 640, 800, 1500, 1500 }

const std = @import("std");

const CompareFn = *const fn (?*const anyopaque, ?*const anyopaque) callconv(.c) c_int;
extern fn qsort(base: ?*anyopaque, nmemb: usize, size: usize, compar: CompareFn) void;

fn byValue(a: ?*const anyopaque, b: ?*const anyopaque) callconv(.c) c_int {
    const x: *const i64 = @ptrCast(@alignCast(a.?));
    const y: *const i64 = @ptrCast(@alignCast(b.?));
    if (x.* < y.*) return -1;
    if (x.* > y.*) return 1;
    return 0;
}

pub fn main() void {
    var salaries = [_]i64{ 1500, 400, 800, 640, 1500, 500 };
    std.debug.print("before: {any}\n", .{salaries});
    qsort(&salaries, salaries.len, @sizeOf(i64), byValue);
    std.debug.print("after:  {any}\n", .{salaries});
}

The element type changed from c_int to i64, so the size argument (@sizeOf(i64)) and the casts inside the comparator changed with it. Get either wrong and qsort will sort garbage; C checks nothing. The @alignCast is what lets Zig check at least the alignment in Debug builds.

Exercise 35.3 · A tiny SQLite binding challenge

Extend the open/exec/close wrapper into a binding with prepared statements: declare sqlite3_prepare_v2, step, finalize, reset, bind_int64, bind_text, column_int64 and column_text, wrap them in Db and Stmt structs that return Zig errors, insert two people and read them back. Name the file: exercises/35-c-interop/ex3_sqlite.zig.

Solution 
//! Chapter 35, exercise 3: a tiny SQLite binding.
//! Run with:  zig run -lc -lsqlite3 ex3_sqlite.zig
//! Goal: declare the eight SQLite functions needed to open a database,
//! create a table, insert rows with a prepared statement and read them
//! back. Wrap return codes in Zig errors. Expected output:
//!   sqlite 3.51.0
//!   Grayson earns 1500
//!   Clay earns 800
//!   2 rows

const std = @import("std");

const Handle = opaque {};
const StmtHandle = opaque {};

extern fn sqlite3_libversion() [*:0]const u8;
extern fn sqlite3_open(filename: [*:0]const u8, db: *?*Handle) c_int;
extern fn sqlite3_close(db: *Handle) c_int;
extern fn sqlite3_exec(db: *Handle, sql: [*:0]const u8, cb: ?*anyopaque, arg: ?*anyopaque, errmsg: ?*?[*:0]u8) c_int;
extern fn sqlite3_free(p: ?*anyopaque) void;
extern fn sqlite3_prepare_v2(db: *Handle, sql: [*]const u8, nbyte: c_int, stmt: *?*StmtHandle, tail: ?*?[*]const u8) c_int;
extern fn sqlite3_step(stmt: *StmtHandle) c_int;
extern fn sqlite3_finalize(stmt: *StmtHandle) c_int;
extern fn sqlite3_reset(stmt: *StmtHandle) c_int;
extern fn sqlite3_bind_int64(stmt: *StmtHandle, idx: c_int, v: i64) c_int;
extern fn sqlite3_bind_text(stmt: *StmtHandle, idx: c_int, text: [*]const u8, n: c_int, destructor: ?*const anyopaque) c_int;
extern fn sqlite3_column_int64(stmt: *StmtHandle, col: c_int) i64;
extern fn sqlite3_column_text(stmt: *StmtHandle, col: c_int) ?[*:0]const u8;
extern fn sqlite3_errmsg(db: *Handle) [*:0]const u8;

const SQLITE_OK = 0;
const SQLITE_ROW = 100;
const SQLITE_DONE = 101;
const transient: ?*const anyopaque = @ptrFromInt(std.math.maxInt(usize));

pub const Error = error{SqliteError};

pub const Db = struct {
    h: *Handle,

    pub fn open(path: [*:0]const u8) Error!Db {
        var h: ?*Handle = null;
        if (sqlite3_open(path, &h) != SQLITE_OK or h == null) return error.SqliteError;
        return .{ .h = h.? };
    }

    pub fn close(self: Db) void {
        _ = sqlite3_close(self.h);
    }

    pub fn exec(self: Db, sql: [*:0]const u8) Error!void {
        var err: ?[*:0]u8 = null;
        if (sqlite3_exec(self.h, sql, null, null, &err) != SQLITE_OK) {
            if (err) |e| {
                std.debug.print("sqlite: {s}\n", .{e});
                sqlite3_free(e);
            }
            return error.SqliteError;
        }
    }

    pub fn prepare(self: Db, sql: []const u8) Error!Stmt {
        var s: ?*StmtHandle = null;
        const rc = sqlite3_prepare_v2(self.h, sql.ptr, @intCast(sql.len), &s, null);
        if (rc != SQLITE_OK or s == null) {
            std.debug.print("sqlite: {s}\n", .{sqlite3_errmsg(self.h)});
            return error.SqliteError;
        }
        return .{ .h = s.? };
    }
};

pub const Stmt = struct {
    h: *StmtHandle,

    pub fn finalize(self: Stmt) void {
        _ = sqlite3_finalize(self.h);
    }

    pub fn bindInt(self: Stmt, idx: c_int, v: i64) Error!void {
        if (sqlite3_bind_int64(self.h, idx, v) != SQLITE_OK) return error.SqliteError;
    }

    pub fn bindText(self: Stmt, idx: c_int, s: []const u8) Error!void {
        if (sqlite3_bind_text(self.h, idx, s.ptr, @intCast(s.len), transient) != SQLITE_OK)
            return error.SqliteError;
    }

    /// Run an INSERT to completion, then reset so it can be bound again.
    pub fn run(self: Stmt) Error!void {
        const rc = sqlite3_step(self.h);
        if (rc != SQLITE_DONE and rc != SQLITE_ROW) return error.SqliteError;
        _ = sqlite3_reset(self.h);
    }

    /// Advance a SELECT: true while rows remain.
    pub fn next(self: Stmt) Error!bool {
        const rc = sqlite3_step(self.h);
        if (rc == SQLITE_ROW) return true;
        if (rc == SQLITE_DONE) return false;
        return error.SqliteError;
    }

    pub fn int(self: Stmt, col: c_int) i64 {
        return sqlite3_column_int64(self.h, col);
    }

    /// Borrowed: valid only until the next step.
    pub fn text(self: Stmt, col: c_int) []const u8 {
        const p = sqlite3_column_text(self.h, col) orelse return "";
        return std.mem.span(p);
    }
};

pub fn main() !void {
    std.debug.print("sqlite {s}\n", .{sqlite3_libversion()});
    const db = try Db.open(":memory:");
    defer db.close();
    try db.exec("CREATE TABLE person (name TEXT, salary INTEGER)");

    const ins = try db.prepare("INSERT INTO person VALUES (?1, ?2)");
    defer ins.finalize();
    const people = [_]struct { name: []const u8, salary: i64 }{
        .{ .name = "Grayson", .salary = 1500 },
        .{ .name = "Clay", .salary = 800 },
    };
    for (people) |p| {
        try ins.bindText(1, p.name);
        try ins.bindInt(2, p.salary);
        try ins.run();
    }

    const sel = try db.prepare("SELECT name, salary FROM person");
    defer sel.finalize();
    var rows: u32 = 0;
    while (try sel.next()) : (rows += 1) {
        std.debug.print("{s} earns {d}\n", .{ sel.text(0), sel.int(1) });
    }
    std.debug.print("{d} rows\n", .{rows});
}

This is a two-thirds-size copy of the game's binding. The interesting declarations are sqlite3_prepare_v2, which takes the SQL as a pointer plus a byte count (so a Zig slice's .ptr and .len map straight onto it), and sqlite3_bind_text's destructor argument, where transient asks SQLite to copy the bytes. Stmt.next turns the three-valued step (ROW, DONE, or an error) into !bool, which reads naturally in a while (try sel.next()) loop.

Exercise 35.4 · @cImport and strtol practice

Import stdlib.h with @cImport and wrap strtol in a Zig function that returns error.NotANumber when no digits were consumed and error.TrailingGarbage when the string did not end after the number. Name the file: exercises/35-c-interop/ex4_cimport.zig.

Solution 
//! Chapter 35, exercise 4: @cImport and wrapping a C return code.
//! Run with:  zig run -lc ex4_cimport.zig
//! Goal: import <stdlib.h> and <errno.h> with @cImport, wrap strtol in a
//! Zig function that returns an error instead of a sentinel, and print:
//!   "42" -> 42
//!   "  -7" -> -7
//!   "12abc" -> error.TrailingGarbage
//!   "abc" -> error.NotANumber

const std = @import("std");
const c = @cImport({
    @cInclude("stdlib.h");
    @cInclude("errno.h");
});

const ParseError = error{ NotANumber, TrailingGarbage };

/// strtol reports failure by returning 0 and leaving `end` at the start,
/// or by stopping early. Turn both into Zig errors.
fn parseLong(text: [*:0]const u8) ParseError!c_long {
    var end: [*c]u8 = undefined;
    const v = c.strtol(text, &end, 10);
    if (end == @as([*c]u8, @constCast(text))) return error.NotANumber;
    if (end[0] != 0) return error.TrailingGarbage;
    return v;
}

pub fn main() void {
    const inputs = [_][*:0]const u8{ "42", "  -7", "12abc", "abc" };
    for (inputs) |s| {
        if (parseLong(s)) |v| {
            std.debug.print("\"{s}\" -> {d}\n", .{ s, v });
        } else |e| {
            std.debug.print("\"{s}\" -> {s}\n", .{ s, @errorName(e) });
        }
    }
}

strtol's second argument is a char ** out-parameter that receives where parsing stopped. The translated type is [*c][*c]u8, so the local is a [*c]u8 and we pass its address. "Nothing consumed" is end == text, which needs a @constCast because the C signature drops the const. "Not at the end" is end[0] != 0. Both sentinels become errors, which is the whole point of wrapping.

Exercise 35.5 · Sentinel strings both ways practice

Write toC(buf, s), which copies a Zig slice into a buffer and appends the zero, returning [:0]u8 or error.TooLong; fromC(p), which turns a [*:0]const u8 into a slice; and an exported ledger_bp function. No libc is needed, so this one is a zig test. Name the file: exercises/35-c-interop/ex5_span.zig.

Solution 
//! Chapter 35, exercise 5: sentinel strings both ways.
//! Run with:  zig test ex5_span.zig
//! Goal: implement `toC` (copy a Zig slice into a sentinel-terminated
//! buffer for C) and `fromC` (turn a C string back into a slice) and
//! export a C-callable `ledger_bp` function. No libc needed.

const std = @import("std");

/// Copy `s` into `buf` and add the terminating zero. Returns the
/// sentinel-terminated slice, or error.TooLong if it does not fit.
pub fn toC(buf: []u8, s: []const u8) error{TooLong}![:0]u8 {
    if (s.len + 1 > buf.len) return error.TooLong;
    @memcpy(buf[0..s.len], s);
    buf[s.len] = 0;
    return buf[0..s.len :0];
}

/// A C string comes back as a many-item pointer; find its length.
pub fn fromC(p: [*:0]const u8) []const u8 {
    return std.mem.span(p);
}

/// Exported so a C caller could use it: apply basis points to an amount.
export fn ledger_bp(amount: i64, bp: i64) i64 {
    return @divTrunc(amount * bp, 10_000);
}

test "toC adds the sentinel" {
    var buf: [16]u8 = undefined;
    const s = try toC(&buf, "Clay");
    try std.testing.expectEqual(@as(usize, 4), s.len);
    try std.testing.expectEqual(@as(u8, 0), s[4]);
    try std.testing.expectEqualStrings("Clay", s);
}

test "toC refuses when there is no room for the zero" {
    var buf: [4]u8 = undefined;
    try std.testing.expectError(error.TooLong, toC(&buf, "Clay"));
}

test "fromC finds the length" {
    const p: [*:0]const u8 = "Kalmar";
    try std.testing.expectEqualStrings("Kalmar", fromC(p));
    try std.testing.expectEqual(@as(usize, 6), fromC(p).len);
}

test "exported function is callable from Zig too" {
    try std.testing.expectEqual(@as(i64, 1650), ledger_bp(1500, 11_000));
}

The slice syntax buf[0..s.len :0] produces a sentinel-terminated slice and, in Debug builds, checks that buf[s.len] really is zero. The length test (s.len + 1 > buf.len) is the one C programmers forget; Zig makes you write it because the return type promises the sentinel exists.

Check your understanding

  1. What is the Zig type for a C const char * that is a string, and for a char * that is a byte buffer with a separate length?
    Answer[*:0]const u8 for the string (zero-terminated many-item pointer); [*]u8 for the buffer. If either may be NULL, prefix with ?.
  2. Why declare const Handle = opaque {}; instead of using *anyopaque for SQLite's database pointer?
    AnswerBoth are pointers you cannot look inside, but *Handle and *StmtHandle are distinct types, so the compiler stops you passing a statement where a database belongs. *anyopaque would accept anything.
  3. What does callconv(.c) do and when do you need it?
    AnswerIt makes a Zig function use the C calling convention so C code can call it. You need it on callbacks you pass to C (like a qsort comparator); export fn implies it.
  4. What is the difference between -lc and -lsqlite3, and what happens if you forget the second?
    Answer-lc links the C standard library; -lsqlite3 links SQLite. Without it the compile succeeds but the linker reports undefined symbol: _sqlite3_open and friends.
  5. Does @cImport work from zig run in 0.16?
    AnswerYes, with -lc, for headers on the system include path. In build.zig you call linkLibC() and, for other headers, addIncludePath.
  6. You receive a [*:0]const u8 from C and want to store it in a struct for later. What two steps are needed?
    Answerstd.mem.span to get a slice with a length, then allocator.dupe(u8, slice) to copy it into memory you own, because C's buffer may be freed or reused.
  7. Why does IRON LEDGER wrap every c_int return code inside sqlite.zig instead of returning it?
    AnswerSo the rest of the program uses try and Zig error sets, cannot forget to check a code, and never depends on SQLite's constants. All the C-shaped code stays in one file.
What you learned.
  • extern fn name(args) ret; declares a C function; link its library with -lc, -lsqlite3, or linkSystemLibrary in build.zig.
  • C's types map onto c_int, c_long, usize, [*:0]const u8, [*]u8, ?*T, ?*anyopaque; add ? wherever NULL is possible.
  • opaque {} is a type you can point at but never inspect: the right shape for a library handle. Out-parameters are pointers to optionals, *?*Handle.
  • Callbacks C will call need callconv(.c); export fn publishes a Zig function to C.
  • std.mem.span turns a C string into a slice; string literals already coerce to [*:0]const u8; copy anything C hands you if you keep it.
  • @cImport translates headers (works from zig run -lc); std.c has many POSIX functions pre-declared.
  • Wrap return codes into Zig errors in one file per C library, and let nothing C-shaped escape it.
