30. Program structure: files, imports, modules

In this chapter you will split a program across several files and directories, learn the one rule of visibility (pub), discover that every file is secretly a struct, and make sure tests in every file actually run. Nothing here needs a build script yet; that comes in Chapter 31.

30.1 Every file is a struct

You have written const std = @import("std"); at the top of every program. It is time to say what that line does. @import takes a path and returns a type: the struct that the file defines. A Zig source file is the body of a struct declaration with the braces left off. Its top-level const, fn and test are that struct's declarations. std is a type, and std.debug.print is a declaration inside a declaration inside it.

Once you see this, importing your own files is obvious: @import("geometry.zig") is the struct defined by geometry.zig, and you use its public declarations with a dot. Here is a program in three files.

app/geometry.zig

//! Tiny geometry helpers for the import demo.
const std = @import("std");

pub const Point = struct { x: i32, y: i32 };

pub fn manhattan(a: Point, b: Point) u32 {
    return @abs(a.x - b.x) + @abs(a.y - b.y);
}

fn secret() u32 {
    return 42;
}

test "manhattan" {
    try std.testing.expectEqual(@as(u32, 7), manhattan(.{ .x = 0, .y = 0 }, .{ .x = 3, .y = 4 }));
}

app/domain/types.zig

//! Typed IDs shared by the whole program.
pub const PersonId = enum(u32) { _ };
pub const UnitId = enum(u32) { _ };

app/main.zig

const std = @import("std");
const geometry = @import("geometry.zig");
const types = @import("domain/types.zig");

pub fn main() void {
    const a = geometry.Point{ .x = 1, .y = 1 };
    const b = geometry.Point{ .x = 4, .y = 5 };
    std.debug.print("distance {d}\n", .{geometry.manhattan(a, b)});
    const id: types.PersonId = @enumFromInt(7);
    std.debug.print("person {d}\n", .{@intFromEnum(id)});
    std.debug.print("geometry is a {s}\n", .{@typeName(@TypeOf(geometry))});
}
$ cd app && zig run main.zig
distance 7
person 7
geometry is a type

Notice that you ran zig run on main.zig alone and the other two files were found. The path in @import is relative to the importing file, so "domain/types.zig" reaches into a subdirectory. The compiler follows imports from the root file outward and compiles what it finds. There is no list of source files anywhere; the imports are the list.

The last line of output is the proof of the opening claim: @TypeOf(geometry) is type. The value geometry is a type, and geometry.Point is a declaration inside it. This is also why the naming convention is what it is: a file that is used as a namespace gets a lower-case constant (geometry, types), while a file that is used as a type gets a capitalised one (section 30.5).

30.2 pub, and private by default

Zig has one visibility rule. A declaration is private to its file unless it is marked pub. There are no classes with private members, no packages, no friends, no header files. geometry.zig above has a function secret without pub. Try to call it:

priv/main.zig

const geometry = @import("geometry.zig");
pub fn main() void {
    _ = geometry.secret();
}
$ zig run main.zig
main.zig:3:17: error: 'secret' is not marked 'pub'
    _ = geometry.secret();
        ~~~~~~~~^~~~~~~
geometry.zig:10:1: note: declared here
fn secret() u32 {
^~~~~~~~~~~~~~~

The same rule applies to constants (pub const), to nested types, and to the fields of a struct only in the sense that fields are always accessible; visibility is about declarations. A file's public surface is therefore easy to read: search for pub. Everything else is an implementation detail that you can rename or delete without looking at other files.

Design advice. Start with nothing pub and add it when another file needs the name. A file with three pub declarations and twenty private helpers is a well-designed file. A file where everything is pub has no boundary, and reflection (Chapter 27) will also see all of it.

30.3 Naming imports

The constant you bind an import to is your choice, and two conventions cover almost every case:

  • Namespace files (functions and types grouped by topic) get a lower-case name matching the file: const geometry = @import("geometry.zig");, const types = @import("domain/types.zig");.
  • When you only want one thing, take it directly: const Point = @import("geometry.zig").Point;. This is common for types used everywhere.
  • Files that are a type (section 30.5) get a capitalised name: const Counter = @import("Counter.zig");.

Imports are cheap to write and it is normal for a file to start with five or ten of them. Unused imports are not an error (they are lazily analysed), but zig fmt and code review will thank you for removing them.

30.4 A root file that re-exports

As a project grows past a handful of files you want one place that names the whole thing. The convention is root.zig: a file whose only job is to import the others and mark them pub. Anyone who imports root.zig, or the module built from it, sees the entire tree through one door.

tests/root.zig

//! Root of a small module. Tests here reference every file we want tested.
const std = @import("std");
pub const money = @import("money.zig");
pub const roster = @import("roster.zig");

test {
    std.testing.refAllDecls(@This());
}

This is exactly the shape of IRON LEDGER's src/root.zig, which the Ledger box below shows. A re-export costs nothing at run time: pub const money = @import("money.zig"); is a compile-time alias. Directory trees follow the same idea in layers: root.zig imports domain/types.zig, sim/state.zig, persist/store.zig, and each directory groups files that change together.

What about the test block at the bottom? Section 30.7 explains it. First, two smaller facts about imports.

30.5 Cyclic imports are fine

In many languages, file A importing file B while B imports A is either an error or a source of subtle bugs. In Zig it simply works, because imports are lazy: @import gives you a type, and the compiler only analyses the declarations you actually reference, when you reference them.

cyc/a.zig

const std = @import("std");
const b = @import("b.zig");
pub fn ping(n: u32) u32 {
    if (n == 0) return 0;
    return 1 + b.pong(n - 1);
}
pub fn main() void {
    std.debug.print("ping(5) = {d}\n", .{ping(5)});
}

cyc/b.zig

const a = @import("a.zig");
pub fn pong(n: u32) u32 {
    if (n == 0) return 0;
    return 1 + a.ping(n - 1);
}
$ zig run a.zig
ping(5) = 5

The game leans on this: queries.zig imports commands.zig in a test, and commands.zig imports queries.zig for the rating calculation. You should still avoid cycles when a clean layering is possible, because they make the code harder to read, not because the compiler minds.

30.6 @This() and files that are types

If a file is a struct, can it have fields? Yes. Put field declarations at the top level and the file becomes a struct type with those fields, exactly as if you had written const Counter = struct { … }; in another file. Inside such a file you need a way to name the struct you are in, and that is @This().

this/Counter.zig

//! A file that IS a struct: it has fields at the top level.
//! Import it with a capitalised name: `const Counter = @import("Counter.zig");`
count: u32 = 0,
step: u32 = 1,

const Counter = @This();

pub fn bump(self: *Counter) void {
    self.count += self.step;
}

pub fn init(step: u32) Counter {
    return .{ .step = step };
}

this/main.zig

const std = @import("std");
const Counter = @import("Counter.zig");

pub fn main() void {
    var c = Counter.init(5);
    c.bump();
    c.bump();
    std.debug.print("count = {d}\n", .{c.count});
    std.debug.print("size of Counter: {d} bytes\n", .{@sizeOf(Counter)});
}
$ zig run main.zig
count = 10
size of Counter: 8 bytes

@This() returns the innermost struct, enum or union being defined. In a file-as-struct it is the file's type; inside const Stack = struct { … } it is Stack, which is why the idiom const Self = @This(); appears in so many generic types (Chapter 26) where the struct has no name yet. In root.zig above, @This() is the root file itself, handed to refAllDecls.

Fields and top-level code do not mix well. A file with fields cannot have a main that makes sense as a program entry, and its field list comes first by convention. Keep files-as-types small and focused: one type, its methods, its tests.

30.7 Doc comments: //! and ///

Three comment forms exist and they mean different things. // is an ordinary comment. /// directly above a declaration is a doc comment for that declaration; tools and editors pick it up. //! at the very top of a file is a doc comment for the file itself, that is, for the struct the file defines. The Counter.zig file above opens with a //! block, and the contract of this course requires one on every exercise file. A /// that is not followed by a declaration is a compile error, which catches the common mistake of leaving a doc comment on a deleted function.

30.8 Test discovery across files

Here is a trap that catches every new Zig project. Run zig test root_noref.zig on a root file that imports two files full of tests, but never references anything in them:

tests/root_noref.zig

const std = @import("std");
pub const money = @import("money.zig");
pub const roster = @import("roster.zig");
test "root only" {
    try std.testing.expect(true);
}
$ zig test root_noref.zig
1/1 root_noref.test.root only...OK
All 1 tests passed.

One test ran. The tests in money.zig and roster.zig were silently skipped, because of the same laziness that makes cyclic imports work: a file that is imported but never referenced is never analysed, and its tests do not exist. Now the root.zig from section 30.4:

$ zig test root.zig
1/3 root.test_0...OK
2/3 money.test.money...OK
3/3 roster.test.roster...OK
All 3 tests passed.

std.testing.refAllDecls(@This()) is a function that, only while testing, takes the address of every public declaration of the type it is given. Referencing money and roster forces their files to be analysed, and their file-level tests join the run. The anonymous test { … } block gets the name test_0.

But look again at the run: roster.inner.test.inner roster did not appear. refAllDecls goes one level deep; it referenced roster, and roster.zig's own test ran, but a test nested inside the struct inner is only discovered if inner is referenced. Older Zig versions shipped std.testing.refAllDeclsRecursive for this; 0.16 does not. The recursive version is a dozen lines you can keep in your own project:

tests/root_recursive.zig

const std = @import("std");
pub const money = @import("money.zig");
pub const roster = @import("roster.zig");

/// refAllDecls only goes one level deep. This walks nested structs too.
fn refAllDeclsRecursive(comptime T: type) void {
    inline for (comptime std.meta.declarations(T)) |decl| {
        const D = @TypeOf(@field(T, decl.name));
        if (D == type) {
            switch (@typeInfo(@field(T, decl.name))) {
                .@"struct", .@"enum", .@"union", .@"opaque" => refAllDeclsRecursive(@field(T, decl.name)),
                else => {},
            }
        }
        _ = &@field(T, decl.name);
    }
}

test {
    refAllDeclsRecursive(@This());
}
$ zig test root_recursive.zig
1/4 root_recursive.test_0...OK
2/4 money.test.money...OK
3/4 roster.test.roster...OK
4/4 roster.inner.test.inner roster...OK
All 4 tests passed.

It uses std.meta.declarations (reflection again) to visit every public declaration; for those that are types, it recurses. In practice most projects are fine with plain refAllDecls in the root plus a habit of referencing nested namespaces from a file-level test. IRON LEDGER does exactly that, and zig build test reports several hundred tests as a result.

Rule of thumb. If a test you just wrote does not show up in the count, the file it lives in is not referenced. Add it to root.zig, or reference the containing struct from a test that does run.
In IRON LEDGER. The module root game/src/root.zig is a pure table of re-exports, grouped by directory, with the discovery test at the bottom: 
//! Module root for the simulation core. See ARCHITECTURE.md.
//! The core is pure and deterministic: no I/O, no wall clock, no globals.

const std = @import("std");

// domain/ (entities)

pub const person = @import("domain/person.zig");

// …
// sim/ (state, time, randomness, events, battle resolution)

// …
// persist/ (SQLite save files, Stage 11)

Every file below it opens with a //! block naming its MekHQ counterpart, a house rule from the project's CLAUDE.md. The executable in game/src/main.zig never imports these files by path; it writes const game = @import("game"); and reaches game.state.GameState, game.commands.execute and so on through the root. The name "game" is not a file: it is a module declared in build.zig, which is where the next chapter begins.

Exercises

Exercise 30.1 · One program, several files warm-up

The tree exercises/30-program-structure/ex1_split/ has main.zig importing domain/types.zig, domain/pilot.zig and roster.zig. Finish roster.zig (add, get, best) so zig build run prints the best pilot and zig build test passes in every file.

Solution

src/roster.zig

//! A fixed-capacity roster indexed by PersonId.
const std = @import("std");
const types = @import("domain/types.zig");
const Pilot = @import("domain/pilot.zig").Pilot;

pub const Roster = struct {
    slots: [16]Pilot = undefined,
    count: usize = 0,

    pub fn add(self: *Roster, p: Pilot) void {
        self.slots[self.count] = p;
        self.count += 1;
    }

    pub fn get(self: *const Roster, id: types.PersonId) ?*const Pilot {
        if (id.index() >= self.count) return null;
        return &self.slots[id.index()];
    }

    pub fn best(self: *const Roster) ?*const Pilot {
        if (self.count == 0) return null;
        var top: usize = 0;
        for (self.slots[0..self.count], 0..) |p, i| {
            if (p.skill() > self.slots[top].skill()) top = i;
        }
        return &self.slots[top];
    }
};

test "roster" {
    var r = Roster{};
    try std.testing.expect(r.best() == null);
    r.add(Pilot.init("A", 4, 4));
    r.add(Pilot.init("B", 2, 2));
    try std.testing.expectEqualStrings("B", r.best().?.name);
    try std.testing.expect(r.get(@enumFromInt(5)) == null);
}

src/main.zig (the test block)

test {
    // Pull every file's tests into this test binary.
    std.testing.refAllDecls(@This());
    _ = types;
    _ = pilot;
    _ = roster;
}

roster.zig imports domain/pilot.zig with a path relative to itself, and takes just the Pilot type. The test block in main.zig references each import so their tests are discovered; _ = types; is enough on its own for a plain import, and refAllDecls is belt and braces.

Exercise 30.2 · A file that is a struct practice

In exercises/30-program-structure/ex2_counter/, src/Ledger.zig has fields at the top level. Finish apply and nextDay and run zig build test.

Solution

src/Ledger.zig

//! Chapter 30, exercise 2: a file that is a struct.
//! This file has fields at the top level, so @import("Ledger.zig") IS the
//! type. By convention such files are named in CapitalCase.
const std = @import("std");

funds: i64,
day: u32 = 1,
log: std.ArrayList(i64) = .empty,

const Ledger = @This();

pub fn init(funds: i64) Ledger {
    return .{ .funds = funds };
}

pub fn deinit(self: *Ledger, gpa: std.mem.Allocator) void {
    self.log.deinit(gpa);
}

pub fn apply(self: *Ledger, gpa: std.mem.Allocator, delta: i64) !void {
    self.funds += delta;
    try self.log.append(gpa, delta);
}

pub fn nextDay(self: *Ledger) void {
    self.day += 1;
}

test "Ledger is the file" {
    try std.testing.expect(@TypeOf(Ledger.init(0)) == Ledger);
}

const Ledger = @This(); names the file's own type so methods can take *Ledger. The test in main.zig ends with _ = Ledger; so the file's own test is discovered.

Exercise 30.4 · Namespaces inside one file warm-up

A single file: a field-less money struct used as a namespace, a Stack using const Self = @This();, and thisFile() returning the file's own type. File: exercises/30-program-structure/ex4_namespace.zig.

Solution 
//! Chapter 30, exercise 4: namespaces inside one file.
//! Run with:  zig test ex4_namespace.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// A namespace: a struct with no fields, used only to group declarations.
pub const money = struct {
    pub const CBills = i64;
    pub fn fromCbills(n: i64) CBills {
        return n * 100;
    }
    fn hidden() void {}
};

pub const Stack = struct {
    items: [8]u32 = undefined,
    len: usize = 0,

    const Self = @This();

    pub fn push(self: *Self, v: u32) void {
        self.items[self.len] = v;
        self.len += 1;
    }
    pub fn pop(self: *Self) ?u32 {
        if (self.len == 0) return null;
        self.len -= 1;
        return self.items[self.len];
    }
};

/// The file itself is a struct too. This returns it.
pub fn thisFile() type {
    return @This();
}

test "namespace has no size" {
    try std.testing.expectEqual(@as(usize, 0), @sizeOf(money));
    try std.testing.expectEqual(@as(money.CBills, 300), money.fromCbills(3));
}

test "Self works like the type name" {
    var s = Stack{};
    s.push(1);
    s.push(2);
    try std.testing.expectEqual(@as(?u32, 2), s.pop());
    try std.testing.expect(@TypeOf(s) == Stack);
}

test "visibility is per declaration" {
    try std.testing.expect(@hasDecl(money, "fromCbills"));
    try std.testing.expect(@hasDecl(money, "hidden"));
    try std.testing.expect(!@hasDecl(money, "nope"));
}

test "the file is a struct" {
    try std.testing.expect(@typeInfo(thisFile()) == .@"struct");
    try std.testing.expect(@hasDecl(thisFile(), "Stack"));
}

A struct with no fields has size zero and exists only to group names. Note the third test: @hasDecl from inside the same file sees the private hidden, because visibility is about crossing file boundaries.

Check your understanding

  1. What does @import("x.zig") evaluate to?
    AnswerA type: the struct whose declarations are the top-level declarations of x.zig.
  2. How does the compiler know which files belong to a program run with zig run main.zig?
    AnswerIt follows @import from the root file. There is no separate file list.
  3. What is the complete visibility system of Zig?
    Answerpub on a declaration makes it visible to importers; without it the declaration is private to its file.
  4. Is it an error for a.zig to import b.zig while b.zig imports a.zig?
    AnswerNo. Imports are lazy and cycles are allowed, though a clean layering is still easier to read.
  5. When would a file have fields at the top level, and what does @This() return there?
    AnswerWhen the file is one type (conventionally named in CapitalCase). @This() returns that type.
  6. Why did zig test root_noref.zig run only one test?
    AnswerThe imported files were never referenced, so they were never analysed and their tests did not exist. refAllDecls or _ = money; fixes it.
  7. Does std.testing.refAllDeclsRecursive exist in 0.16?
    AnswerNo. Only refAllDecls does; a recursive walk is a few lines with std.meta.declarations.
  8. What is the difference between //! and ///?
    Answer//! documents the file (the struct it defines) and goes at the top; /// documents the declaration immediately below it.
What you learned.
  • A Zig file is a struct; @import returns its type; paths are relative to the importing file and may enter subdirectories.
  • pub is the whole visibility system; everything else is private to its file.
  • Bind namespace imports to lower-case names, type-files to capitalised names, or take a single declaration directly.
  • root.zig re-exports the tree with pub const x = @import("…"); the executable reaches it by module name.
  • Cyclic imports work because analysis is lazy.
  • Files with top-level fields are types; @This() names the enclosing type.
  • //! documents a file, /// a declaration.
  • Tests only run in referenced files: use std.testing.refAllDecls(@This()) in the root, and reference nested namespaces yourself.
