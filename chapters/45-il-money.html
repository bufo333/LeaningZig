45. Money without floats

In this chapter you see how a game whose whole subject is money gets by without a single floating-point number. Every amount is a 64-bit integer, every multiplier is basis points, and money moves in exactly one way: a ledger entry and a treasury balance changing together. You will read that one function, the ledger it feeds, and the summaries built on top, and you will test the rounding rule that makes it all reproducible.

What you need from earlier chapters. Chapter 4 (i64, @divTrunc versus @divFloor, and why signed division must name its rounding), Chapter 5 (why floats are not exact and why that matters for money), Chapter 14 (a small tagged union, Treasury, switched on with payload captures), Chapter 12 (a struct with defaulted fields used as a record), Chapter 21 (a list you only ever append to) and Chapter 27 (an array sized by an enum's variant count).

45.1 Two types and one function

The entire monetary type system of IRON LEDGER is at the top of src/domain/types.zig:

src/domain/types.zig
/// All money is integer C-bills. No floats in the ledger, ever.
pub const CBills = i64;

/// Basis points (1/100 of a percent) for all multiplier math, so payment
/// formulas stay in integer arithmetic. 10_000 bp == ×1.0.
pub const Bp = i64;

pub fn applyBp(amount: CBills, bp: Bp) CBills {
    return @divTrunc(amount * bp, 10_000);
}

test "basis point math stays in integers" {
    try std.testing.expectEqual(@as(CBills, 1_500), applyBp(1_500, 10_000));
    try std.testing.expectEqual(@as(CBills, 900), applyBp(1_500, 6_000));
    try std.testing.expectEqual(@as(CBills, 4_800), applyBp(1_500, 32_000));
}

Both are aliases for i64. The aliases buy readability, not safety: the compiler will happily let you add a Bp to a CBills, and the discipline of not doing so is a house rule enforced by review and by the fact that every multiplier goes through applyBp. A 10 percent markup is applyBp(cost, 11_000). A green pilot's 0.6 salary multiplier is 6_000. An elite pilot's 3.2 is 32_000. The test pins those three.

Why not a f64 and cost * 1.1? Chapter 5 gave the general answer: 0.1 is not representable in binary floating point, so a chain of multiplications drifts, and two machines (or two compiler versions) can drift differently. For a game whose determinism test hashes the treasury balance, "differently" is a failing build. With integers, 1_500 * 6_000 / 10_000 is 900 on every machine ever made.

The one subtlety is rounding. amount * bp is exact in i64 for any amount the game will see (a trillion C-bills times a hundred thousand basis points is far inside 63 bits). The division is where a fraction of a C-bill is lost, and Zig makes you say how: @divTrunc rounds toward zero, so applyBp(-1_500, 6_000) is -900 and applyBp(-1, 5_000) is 0, not -1. @divFloor would give -1 for the latter. Neither is wrong; what would be wrong is not choosing, and Zig does not let you write / on signed integers at runtime for exactly that reason (Chapter 4, and appendix A4 shows the error).

45.2 The ledger

Money is recorded in one place, a list of transactions that only ever grows:

src/econ/finance.zig
pub const Category = enum {
    contract_payment,
    advance,
    salvage,
    battle_loss_comp,
    breach_clawback,
    payroll,
    hardship_pay, // remote-deployment payroll bonus (ARCH §9.6)
    maintenance,
    hull_upkeep, // per-hull monthly carry cost, running or not (ARCH §9.8)
    parts,
    supplies,
    local_supplies, // bought beyond the ring at 2–4× (ARCH §9.6)
    freight,
    unit_purchase,
    unit_sale,
    fabrication, // structural parts made at a regional HQ (ARCH §9.8)
    fund_transfer, // outfit treasury ↔ company local funds (ARCH §9.8)
    hq_construction,
    hq_upkeep,
    transport_charter,
    loan_principal,
    loan_interest,
    event,
    misc,
};

pub const Transaction = struct {
    day: u32,
    amount: types.CBills, // signed: income +, expense −
    category: Category,
    /// Cost/profit center; .none = outfit-level overhead.
    company: types.ForceId = .none,
    /// HQ cost center (Stage 9A).
    hq: types.HqId = .none,
    contract: types.ContractId = .none,
    note: []const u8 = "",
};

pub const Ledger = struct {
    transactions: std.ArrayListUnmanaged(Transaction) = .empty,

    pub fn post(self: *Ledger, alloc: std.mem.Allocator, txn: Transaction) !void {
        try self.transactions.append(alloc, txn);
    }

    pub fn balance(self: *const Ledger) types.CBills {
        var total: types.CBills = 0;
        for (self.transactions.items) |t| total += t.amount;
        return total;
    }

    /// Net for one company over [from_day, to_day] — the monthly P&L view.
    pub fn companyNet(self: *const Ledger, company: types.ForceId, from_day: u32, to_day: u32) types.CBills {
        var total: types.CBills = 0;
        for (self.transactions.items) |t| {
            if (t.company == company and t.day >= from_day and t.day <= to_day) total += t.amount;
        }
        return total;
    }
};

A Transaction is a record: a day, a signed amount, a category, and three typed-ID tags that default to .none. The sign convention is in the comment and nowhere else; income is positive, expense negative, and every caller writes .amount = -cost when spending. The tags are what make the ledger a database rather than a log: "the P&L of Alpha Company for March" is companyNet, a filter over the same list, and "what has this contract paid so far" is another filter. There is no second copy of any total anywhere that could disagree with the list.

Ledger stores no allocator; post takes one, and in the game it is always the campaign arena via gs.allocator(). The two finance tests at the bottom of the file use std.testing.allocator and call ledger.deinit(alloc), which is the only reason that method exists.

45.3 The only way money moves

A ledger on its own would let a balance and its history drift apart. The game prevents that by having exactly one function that does both:

src/sim/state.zig
/// Where money lives (Stage 9A, ARCH §11): the outfit's central treasury,
/// an HQ's funds, or a deployed company's operating fund. Spending resolves
/// where the spender stands — the treasury cannot teleport.
pub const Treasury = union(enum) {
    outfit,
    hq: types.HqId,
    company: types.ForceId,
};

/// Post to the outfit's central treasury (the common case).
pub fn postTransaction(self: *GameState, txn: finance_mod.Transaction) !void {
    try self.postTreasury(.outfit, txn);
}

/// The only way money moves: ledger entry + the named treasury's balance,
/// in lockstep. Balances MAY go negative (obligations don't wait);
/// purchases that should refuse instead call `debitOrRefuse` first.
pub fn postTreasury(self: *GameState, treasury: Treasury, txn: finance_mod.Transaction) !void {
    try self.ledger.post(self.allocator(), txn);
    switch (treasury) {
        .outfit => self.funds += txn.amount,
        .hq => |id| if (self.hqs.getPtr(id)) |h| {
            h.funds += txn.amount;
        },
        .company => |id| if (self.forces.getPtr(id)) |f| {
            f.local_funds += txn.amount;
        },
    }
}

pub fn treasuryBalance(self: *GameState, treasury: Treasury) types.CBills {
    return switch (treasury) {
        .outfit => self.funds,
        .hq => |id| if (self.hqs.getPtr(id)) |h| h.funds else 0,
        .company => |id| if (self.forces.getPtr(id)) |f| f.local_funds else 0,
    };
}

Treasury is the small tagged union the guide mentioned: "which till" is a typed value, and a switch over it is exhaustive, so a fourth kind of treasury would have to be handled in both functions before the program compiled. postTreasury appends to the ledger and then adjusts the one named balance, in that order, in one function, with no early return between them. If post fails (out of memory), the balance is untouched and the error propagates. There is no code path in which one happens without the other.

Read the doc comment's second sentence: balances may go negative. Payroll on the first of the month is posted whether or not the outfit can pay it; the consequence is an insolvent turn (Chapter 42's advance), not a skipped payroll. Purchases that should refuse are a separate, four-line function in commands.zig:

fn debitPurchase(gs: *GameState, treasury: state_mod.Treasury, txn: @import("../econ/finance.zig").Transaction) Error!void {
    if (gs.treasuryBalance(treasury) < -txn.amount) return Error.InsufficientTreasury;
    try gs.postTreasury(treasury, txn);
}

Check, then post. Because txn.amount is negative for a purchase, the comparison is against -txn.amount. This is the "all checks, then all effects" discipline of Chapter 42 in its smallest form.

45.4 Sums with different filters

Every report about money is a pass over the list with a filter. The P&L view is the most general:

src/econ/finance.zig
/// Which entity's books to read (Stage 9A).
pub const EntityFilter = union(enum) {
    all,
    company: types.ForceId,
    hq: types.HqId,

    pub fn matches(self: EntityFilter, t: *const Transaction) bool {
        return switch (self) {
            .all => true,
            .company => |id| t.company == id,
            .hq => |id| t.hq == id,
        };
    }
};

pub const Summary = struct {
    income: types.CBills = 0,
    expenses: types.CBills = 0, // stored positive
    by_category: [category_count]types.CBills = @splat(0),

    pub const category_count = @typeInfo(Category).@"enum".fields.len;

    pub fn net(self: *const Summary) types.CBills {
        return self.income - self.expenses;
    }

    pub fn category(self: *const Summary, cat: Category) types.CBills {
        return self.by_category[@intFromEnum(cat)];
    }
};

/// Summarize [from_day, to_day] for the whole outfit or one entity's books.
pub fn summarize(ledger: *const Ledger, from_day: u32, to_day: u32, filter: EntityFilter) Summary {
    var s: Summary = .{};
    for (ledger.transactions.items) |*t| {
        if (t.day < from_day or t.day > to_day) continue;
        if (!filter.matches(t)) continue;
        s.by_category[@intFromEnum(t.category)] += t.amount;
        if (t.amount >= 0) s.income += t.amount else s.expenses -= t.amount;
    }
    return s;
}

Two things from Part 3 are doing quiet work here. by_category is an array sized by @typeInfo(Category).@"enum".fields.len and indexed by @intFromEnum, so adding a category grows the array and the totals with no other change (Exercise 45.3 confirms it). And @splat(0) fills the array with zeros in the default value. The function itself is a filter and two accumulators, kept separate so a statement can show income and expenses rather than one net number, which is what the Ledger screen draws.

The rest of the money code is variations on this: gs.monthlyPayroll() sums monthlySalary() over active people; a person's salary is applyBp(applyBp(role.baseSalary(), experience.salaryMultBp()), rank.payBp()), three integers multiplied in two steps; a contract's monthly net is base pay through a chain of basis-point terms; a rating letter's pay multiplier is a Bp looked up from a table. There is not a float anywhere in src/econ, and a grep for f64 under src/sim and src/domain finds only the star map's coordinates, which are distances, not money.

45.5 Where a C-bill is lost

With integer division, every multiplication that is not by a whole number loses a fraction, and it is worth knowing where. The rule the code follows is: multiply everything first, divide once, truncate toward zero. applyBp(applyBp(x, a), b) truncates twice, which is a design choice the salary formula accepts: a pilot's pay is computed the same way every payday, so the truncation is consistent, and a C-bill a month is not gameplay. What would be gameplay is a truncation that differs between the amount debited and the amount credited, which is why transferFunds moves one computed amount to both sides rather than computing it twice.

The exercise below asks you to pin the truncation direction in a test, so that anyone who later "fixes" @divTrunc to @divFloor learns from the suite that negative amounts round differently.

Guided reading

  1. src/domain/types.zig, the first twenty lines and the two enums with methods (ExperienceLevel.salaryMultBp, Quality.maintenanceModifier). Note that the multiplier table is in basis points.
  2. src/econ/finance.zig, all of it (162 lines). The two tests at the bottom are the clearest specification of the ledger's semantics.
  3. src/sim/state.zig: Treasury, postTransaction, postTreasury, treasuryBalance, treasuryTags, transferFunds, monthlyPayroll.
  4. src/sim/commands.zig: debitPurchase, then the .transfer, .take_loan and .buy_listing arms to see the check-then-post pattern with different treasuries.
  5. src/domain/person.zig: monthlySalary and severance, two formulas that are nothing but applyBp and @divTrunc.
  6. src/sim/queries.zig: ledger and money (the thousands-separator formatter), to see how integers become the text on the Ledger screen.

Exercises

Exercise 45.1 · Pin the rounding warm-up

Add a test to types.zig that fixes the behaviour of applyBp on negative amounts and on fractions below one C-bill: applyBp(-1_500, 6_000), applyBp(-1, 5_000), applyBp(1, 5_000) and a ten percent markup on 1,500. Predict each value before running.

Solution 
test "basis points truncate toward zero on both signs" {
    try std.testing.expectEqual(@as(CBills, -900), applyBp(-1_500, 6_000));
    try std.testing.expectEqual(@as(CBills, 0), applyBp(-1, 5_000));
    try std.testing.expectEqual(@as(CBills, 0), applyBp(1, 5_000));
    try std.testing.expectEqual(@as(CBills, 1_650), applyBp(1_500, 11_000));
}

Half a C-bill truncates to zero in both directions, which is the @divTrunc behaviour. Had the function used @divFloor, the second case would be -1 and the test would fail, which is the point: the direction is now a documented decision rather than an accident of which builtin someone reached for.

Exercise 45.2 · One till, not the other practice

Write a test in state.zig that creates a commander (which founds an HQ with its own treasury), posts a 1,000 C-bill expense to that HQ with postTreasury, and asserts three things: the HQ's balance fell by exactly 1,000, the outfit's funds did not change, and the ledger grew by one entry. Then use finance.summarize with an .hq filter and check the expense appears.

Solution 
test "an HQ treasury pays and the outfit's does not" {
    var gs = GameState.init(std.testing.allocator, .{ .seed = 3 });
    defer gs.deinit();
    _ = try gs.createCommander("T", .LC, .paymaster);
    const hq = gs.hqs.keys()[0];
    const outfit_before = gs.funds;
    const hq_before = gs.treasuryBalance(.{ .hq = hq });
    const txns = gs.ledger.transactions.items.len;
    try gs.postTreasury(.{ .hq = hq }, .{
        .day = gs.clock.day_index,
        .amount = -1_000,
        .category = .misc,
        .hq = hq,
        .note = "exercise",
    });
    try std.testing.expectEqual(hq_before - 1_000, gs.treasuryBalance(.{ .hq = hq }));
    try std.testing.expectEqual(outfit_before, gs.funds);
    try std.testing.expectEqual(txns + 1, gs.ledger.transactions.items.len);
    const s = finance_mod.summarize(&gs.ledger, 0, 0, .{ .hq = hq });
    try std.testing.expect(s.expenses >= 1_000);
}

Two details. The transaction is tagged with .hq = hq as well as being posted to the .hq treasury: the treasury says whose balance moves, the tag says whose books it is on, and they are usually but not always the same (an HQ can pay for a company's supplies). And the summary is >= 1_000 rather than equal, because founding an HQ already posted its own expenses on day 0; a test should assert what it set up, not what the fixture happened to do.

Exercise 45.3 · Add a category and see what moves practice

Add a charity variant to finance.Category. Before building, predict which files will fail to compile. Build, then write a test that proves Summary already has room for it.

Solution

Nothing fails. Summary.by_category is sized from the enum, summarize indexes it with @intFromEnum, the ledger stores the category as a value, and the save store writes it as its tag name (Chapter 47). No switch over Category exists anywhere in the program; the Ledger screen prints @tagName. The test:

test "a new category needs no other change" {
    try std.testing.expectEqual(@as(usize, Summary.category_count), @typeInfo(Category).@"enum".fields.len);
    var s: Summary = .{};
    s.by_category[@intFromEnum(Category.charity)] = -5;
    try std.testing.expectEqual(@as(types.CBills, -5), s.category(.charity));
}

Contrast this with adding a variant to Command (Chapter 42) or to Effect (Chapter 46), where the compiler lists several switches. Both outcomes are correct: a category is data that flows through, a command is behaviour that must be handled.

Check your understanding

  1. What is applyBp(cost, 11_000)?
    AnswerA ten percent markup: cost * 11_000 / 10_000, truncated toward zero.
  2. Why @divTrunc and not /?
    AnswerCBills is signed and Zig refuses / on runtime signed integers, because truncation and flooring differ on negatives and the programmer must choose.
  3. What two things does postTreasury do, and why in one function?
    AnswerIt appends the transaction to the ledger and adjusts the named treasury's balance. Doing both in one place means the balance and the history can never disagree.
  4. Can a treasury go negative? Where is that refused?
    AnswerYes; obligations like payroll post regardless. Purchases that should refuse go through debitPurchase, which checks the balance first, and a negative outfit treasury holds the turn in advance.
  5. How is "Alpha Company's profit this month" computed?
    AnswerAs a filter over the one transaction list: ledger.companyNet(alpha, from, to) or summarize(…, .{ .company = alpha }), summing entries tagged with that company in the day range.
  6. Why does adding a Category not break any switch?
    AnswerNothing switches on it; totals live in an array sized by the enum and indexed with @intFromEnum, and display uses @tagName.
What you learned.
  • CBills and Bp are both i64; every multiplier is basis points applied by applyBp, which truncates toward zero.
  • The ledger is an append-only list of tagged transactions; every total and report is a filtered sum over it, so there is no second copy to drift.
  • postTreasury is the only function that moves money: one ledger entry and one balance change, together.
  • Balances may go negative by design; refusals are a separate check-then-post step, and insolvency holds the turn.
  • Reflection sizes the per-category totals, so categories are pure data; behaviour-carrying unions are the ones the compiler makes you handle.
