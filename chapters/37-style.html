37. Style, idioms and reading compile errors

In this chapter you will learn how Zig code is expected to look (the formatter, the naming rules, the order of things in a file, the idioms every library uses), and then spend most of the chapter on the skill that matters most day to day: reading what the compiler and the runtime tell you. Six real compile errors, a panic with a stack trace, an error return trace, and the three build modes that decide which checks stay on.

37.1 zig fmt

Zig has one formatting style and a tool that applies it. There is nothing to configure and no argument to have.

before.zig
const std=@import("std");
pub fn main( ) void{
std.debug.print("x\n",.{});}
$ zig fmt --check before.zig
before.zig
$ echo $status
1
$ zig fmt before.zig
before.zig
$ cat before.zig
const std = @import("std");
pub fn main() void {
    std.debug.print("x\n", .{});
}

zig fmt file.zig rewrites the file in place; zig fmt --check lists files that would change and exits non-zero, which is the form you put in a pre-commit hook or CI. Run it on a directory to format everything under it. The style is four-space indent, one statement per line, and a rule you will come to rely on: a trailing comma in any list (.{ a, b, }, struct fields, arguments) makes the formatter put one item per line; removing it makes the formatter put them on one line. That comma is the only formatting decision left to you, and it is a good one.

37.2 Names

The conventions are simple and the standard library follows them without exception, so your code will read as native if you do too.

ThingStyleExamples
Types (structs, enums, unions, and functions that return types)TitleCasePerson, PersonId, ArrayList, fn Stack(comptime T: type) type
Functions and methodscamelCasebaseSalary, advanceDay, readFileAlloc
Variables, constants, fields, parameters, enum tags, error names' fieldssnake_casehired_day, max_roster_size, .mekwarrior
Error valuesTitleCaseerror.UnknownPerson, error.OutOfMemory
Filessnake_case.zig, or TitleCase.zig when the file is a structfinance.zig, rng.zig; ArrayList.zig

A useful consequence: you can tell what an identifier is from its shape. Role.baseSalary is a function on a type; role.base_salary would be a field. Acronyms are treated as words: HqId, not HQID; parseJson, not parseJSON.

37.3 Doc comments and the order of a file

Two kinds of comment carry meaning for tools. //! at the top of a file documents the file itself (that is what every exercise header in this book is). /// immediately before a declaration documents that declaration, and zig build-exe -femit-docs or an editor will show it. Ordinary // comments are for humans reading the code right there.

s_style.zig
//! A file-level doc comment: what this file is for.
const std = @import("std");

/// Money in C-bills. Doc comments (three slashes) attach to the next declaration.
pub const CBills = i64;

/// A person's job.
pub const Role = enum {
    mekwarrior,
    tech,

    pub fn baseSalary(self: Role) CBills {
        return switch (self) {
            .mekwarrior => 1_500,
            .tech => 800,
        };
    }
};

pub const Roster = struct {
    people: std.ArrayList(Role) = .empty,

    const Self = @This();

    pub fn deinit(self: *Self, gpa: std.mem.Allocator) void {
        self.people.deinit(gpa);
    }

    pub fn add(self: *Self, gpa: std.mem.Allocator, role: Role) !void {
        try self.people.append(gpa, role);
    }

    pub fn payroll(self: Self) CBills {
        var total: CBills = 0;
        for (self.people.items) |r| total += r.baseSalary();
        return total;
    }
};

const max_roster_size = 12;

test "payroll" {
    var roster: Roster = .{};
    defer roster.deinit(std.testing.allocator);
    try roster.add(std.testing.allocator, .mekwarrior);
    try roster.add(std.testing.allocator, .tech);
    try std.testing.expectEqual(@as(CBills, 2_300), roster.payroll());
    try std.testing.expect(roster.people.items.len <= max_roster_size);
}
$ zig test s_style.zig
All 1 tests passed.
$ zig fmt --check s_style.zig && echo clean
clean

The file also shows the conventional order, top to bottom: the file doc comment; imports; public types; the functions that belong to each type inside it; free functions; private constants near where they are used; tests at the bottom. Within a struct: fields first, then const Self = @This(); if the struct needs to name itself, then init/deinit, then the rest. None of this is enforced, but every file in the standard library follows it and readers expect it.

37.4 The idioms

You have met each of these in an earlier chapter; here they are together, as the checklist a reviewer would apply.

  • init and deinit. A type that owns resources has a function that creates it and a method that releases them, in that order and with those names. deinit takes *Self (it may need to mutate) and, for unmanaged containers, the allocator that was used.
  • The allocator is the first parameter. fn init(gpa: std.mem.Allocator, ...), list.append(gpa, item). Seeing an allocator in a signature is how you know a function may allocate; not seeing one is how you know it cannot.
  • .empty and .init as starting values. var list: std.ArrayList(T) = .empty;, var mutex: std.Io.Mutex = .init;. A declaration with a type and a leading-dot value, and no allocation until the first use.
  • Self. Inside a struct, const Self = @This(); so methods can say self: *Self and the struct can be renamed without touching every method.
  • defer right after acquire, errdefer for partial construction. The line that gets a resource is immediately followed by the line that gives it back (Chapter 17). errdefer undoes the steps already taken when a later step fails.
  • Errors are values; try is the default. Handle an error where you can do something about it; otherwise try and let the caller decide. Never catch unreachable to silence one.
  • Slices in, slices out. Functions take []const u8, not arrays or pointers to arrays; they return slices of memory the caller owns or was told about.
  • Prefer const. The compiler insists: a var that is never mutated is an error.
  • Pure core, I/O at the edges. Functions that compute take values and return values; the io and the allocator are handed in from main and stay near it. IRON LEDGER's simulation never sees an io.

37.5 Reading compile errors

Zig's compiler is strict, and a beginner's first hour is mostly spent being told no. That is the language doing its job: each of these errors is a bug in another language. Every message has the same anatomy: file:line:column: error: what, then the offending line with a caret under the exact spot, then zero or more note: lines that point at the other half of the story. Read the first error only; later ones are often consequences of it. Here are the six you will hit most.

1. Unused constant or variable.

const std = @import("std");
pub fn main() void {
    const unused = 5;
    std.debug.print("hi\n", .{});
}
$ zig run e1.zig
e1.zig:3:11: error: unused local constant
    const unused = 5;
          ^~~~~~

Zig refuses dead values because they are almost always a mistake (you meant to use it) or leftovers (delete it). If you genuinely need to discard something, say so: _ = unused;. The same rule applies to function parameters (_ = param;) and to a var that is never written, which gets its own message, local variable is never mutated, with the note consider using 'const'.

2. Shadowing.

const std = @import("std");
pub fn main() void {
    const count: u32 = 1;
    for (0..3) |count| {
        std.debug.print("{d}\n", .{count});
    }
}
$ zig run e2.zig
e2.zig:4:17: error: capture 'count' shadows local constant from outer scope
    for (0..3) |count| {
                ^~~~~
e2.zig:3:11: note: previous declaration here
    const count: u32 = 1;
          ^~~~~

In Zig a name means one thing within a function. The note tells you where the other count is; rename one of them. This also applies to a local that shadows a top-level declaration (naming a variable std, for instance).

3. Missing switch case.

const std = @import("std");
const Role = enum { mekwarrior, tech, medic };
fn salary(r: Role) i64 {
    return switch (r) {
        .mekwarrior => 1500,
        .tech => 800,
    };
}
pub fn main() void {
    std.debug.print("{d}\n", .{salary(.medic)});
}
$ zig run e3.zig
e3.zig:4:12: error: switch must handle all possibilities
    return switch (r) {
           ^~~~~~
e3.zig:2:39: note: unhandled enumeration value: 'medic'
const Role = enum { mekwarrior, tech, medic };
                                      ^~~~~
e3.zig:2:14: note: enum 'e3.Role' declared here

This is the error you want. Add a variant to an enum and the compiler lists every switch that needs a new arm. The fix is an arm for .medic, or, if you truly mean "everything else", an else arm (which silences future additions, so use it sparingly).

4. Type mismatch between branches.

const std = @import("std");
fn describe(funds: i64) i64 {
    const bonus: i64 = 100;
    return if (funds > 0) bonus else "broke";
}
pub fn main() void {
    std.debug.print("{d}\n", .{describe(5)});
}
$ zig run e4.zig
e4.zig:4:38: error: expected type 'i64', found '*const [5:0]u8'
    return if (funds > 0) bonus else "broke";
                                     ^~~~~~~

An if used as a value must produce one type from both branches ("peer type resolution"), and here the result is also being returned as i64. The message names the type it wanted and the type it found; *const [5:0]u8 is what a string literal is. When you see an unexpected type in one of these messages, the fix is usually to make both branches the same kind of thing, or to add @as(T, ...) to a literal so the compiler knows what you meant.

5. try in a function that cannot fail.

const std = @import("std");
fn parse(s: []const u8) i32 {
    const n = try std.fmt.parseInt(i32, s, 10);
    return n;
}
pub fn main() void {
    std.debug.print("{d}\n", .{parse("12")});
}
$ zig run e5.zig
e5.zig:3:15: error: expected type 'i32', found 'error{InvalidCharacter,Overflow}'
    const n = try std.fmt.parseInt(i32, s, 10);
              ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
e5.zig:2:25: note: function cannot return an error
fn parse(s: []const u8) i32 {
                        ^~~

The message looks like a type mismatch, and it is: try means "return the error to my caller", and this function's return type i32 has no room for an error. The note says it plainly. Change the return type to !i32, or handle the error right there with catch.

6. Integer overflow at compile time.

const std = @import("std");
pub fn main() void {
    const days: u8 = 200 + 100;
    std.debug.print("{d}\n", .{days});
}
$ zig run e6.zig
e6.zig:3:26: error: type 'u8' cannot represent integer value '300'
    const days: u8 = 200 + 100;
                     ~~~~^~~~~

Both operands are known at compile time, so the sum is computed at compile time, and 300 does not fit in a u8. The compiler refuses rather than wrapping. Widen the type (u16) or reconsider the value. The same computation with runtime values produces the runtime panic in the next section.

37.6 Reading a panic and a stack trace

When a safety check fails at runtime, the program panics: it prints a message, a stack trace, and exits. Here is an index one past the end:

const std = @import("std");
pub fn main() void {
    const items = [_]u8{ 1, 2, 3 };
    var idx: usize = 2;
    idx += 1;
    std.debug.print("{d}\n", .{items[idx]});
}
$ zig run e9.zig
thread 5965804 panic: index out of bounds: index 3, len 3
/.../e9.zig:6:37: 0x102f7dcd3 in main (e9)
    std.debug.print("{d}\n", .{items[idx]});
                                    ^
/opt/homebrew/Cellar/zig/0.16.0_1/lib/zig/std/start.zig:698:59: 0x102f7dbb3 in callMain (e9)
    if (fn_info.params.len == 0) return wrapMain(root.main());
                                                          ^
???:?:?: 0x18a24c4e3 in start (/usr/lib/dyld)

Read it top down. The first line is the message, with the numbers you need (index 3, length 3). Then one frame per function on the call stack, innermost first: the panic happened at e9.zig:6:37 in main, which was called by callMain in the standard library's start code, which was called by the dynamic loader. The frames below your own file are scaffolding; the first frame in a file you wrote is where to look, and the caret is under the exact expression. The other messages of this family are integer overflow, attempt to unwrap null (using .? on a null optional), attempt to use null value, division by zero, reached unreachable code, and attempt to cast negative value to unsigned.

An error return trace looks similar but tells a different story: not where the program stopped, but the path an error travelled before nobody handled it.

const std = @import("std");
fn open(name: []const u8) !u32 {
    if (name.len == 0) return error.EmptyName;
    return 1;
}
fn load(name: []const u8) !u32 {
    const h = try open(name);
    return h * 2;
}
pub fn main() !void {
    const v = try load("");
    std.debug.print("{d}\n", .{v});
}
$ zig run e8.zig
error: EmptyName
/.../e8.zig:3:24: 0x10479199b in open (e8)
    if (name.len == 0) return error.EmptyName;
                       ^
/.../e8.zig:7:15: 0x104791a7f in load (e8)
    const h = try open(name);
              ^
/.../e8.zig:11:15: 0x104791bbf in main (e8)
    const v = try load("");
              ^

The error was created in open, passed through the try in load, passed through the try in main, and main returned it, so the runtime printed it. Each frame is a try or return error.X the error went through. This trace is unique to Zig and costs almost nothing in Debug builds; it is the reason "just try it" is good advice, because when the error finally surfaces you still know where it was born.

37.7 Panicking on purpose: @panic, assert, unreachable

Three tools let you say "this cannot happen", and they mean slightly different things.

@panic("message") stops the program with your message and a stack trace. Use it for a situation the program cannot continue from and that is not the caller's fault to handle: a corrupted data file, an impossible state.

const std = @import("std");

fn withdraw(funds: i64, amount: i64) i64 {
    if (amount > funds) @panic("withdraw: insufficient funds");
    return funds - amount;
}

pub fn main() void {
    std.debug.print("{d}\n", .{withdraw(100, 30)});
    std.debug.print("{d}\n", .{withdraw(100, 300)});
}
$ zig run s_panic.zig
70
thread 5998933 panic: withdraw: insufficient funds
/.../s_panic.zig:4:25: 0x102572faf in withdraw (s_panic)
    if (amount > funds) @panic("withdraw: insufficient funds");
                        ^
/.../s_panic.zig:10:40: 0x102571c67 in main (s_panic)

(In real code this particular case should be an error, error.InsufficientFunds, because the caller can do something about it. A panic is for when nobody can.)

std.debug.assert(condition) documents a promise the caller must keep. If the condition is false, it panics with reached unreachable code and a trace pointing at the assert. The point is the documentation: an assert at the top of a function is a precondition anyone can read. IRON LEDGER's daysInMonth could assert month >= 1 and month <= 12.

unreachable is an expression that says "control never gets here". You have seen it as the else arm of a switch over values the type system does not exclude:

const std = @import("std");

fn dayName(d: u8) []const u8 {
    return switch (d) {
        0 => "Mon", 1 => "Tue", 2 => "Wed", 3 => "Thu", 4 => "Fri", 5 => "Sat", 6 => "Sun",
        else => unreachable,
    };
}

pub fn main() void {
    std.debug.print("{s}\n", .{dayName(2)});
    std.debug.print("{s}\n", .{dayName(9)});
}
$ zig run s_unreachable.zig
Wed
thread 5998793 panic: reached unreachable code
/.../s_unreachable.zig:6:17: 0x1009222ef in dayName (s_unreachable)
        else => unreachable,
                ^

The rule for choosing: if the bad input can come from the outside world (a user, a file, the network), it is an error and the caller handles it. If it can only come from a bug in your own program, it is an assert or unreachable, and you want the loudest possible failure as close to the bug as possible. Exercise 37.3 practises the distinction.

37.8 Debug, ReleaseSafe, ReleaseFast

Every panic in this chapter came from a safety check the compiler inserted: bounds checks on indexing, overflow checks on arithmetic, null checks on .?, and the check that unreachable really is. Whether those checks exist depends on the build mode.

ModeSafety checksOptimisationUse it for
Debug (default)onnonedevelopment, tests, this whole book
ReleaseSafeonfullshipping software; fast and still panics instead of corrupting
ReleaseFastofffullbenchmarks, code you have tested to exhaustion
ReleaseSmallofffor sizeembedded targets, tiny binaries

The same out-of-bounds program under each mode:

$ zig run e9.zig
thread 5965804 panic: index out of bounds: index 3, len 3
...
$ zig run -O ReleaseSafe e9.zig
thread 5969181 panic: index out of bounds: index 3, len 3
...
$ zig run -O ReleaseFast e9.zig
0

ReleaseFast printed 0: it read whatever byte happened to follow the array. No message, no trace, no guarantee it will do the same tomorrow. That is undefined behaviour, and it is why the default for anything you ship should be ReleaseSafe. Likewise unreachable in ReleaseFast is a promise to the optimiser, which will happily delete the branch and any code it can prove leads there.

To build a standalone executable rather than run one: zig build-exe -O ReleaseFast e7.zig writes e7 next to the source. In a build.zig project the same choice is zig build -Doptimize=ReleaseSafe (Chapter 31). You can also change safety for one block with @setRuntimeSafety(false), which is the right granularity for the rare inner loop that needs it.

In IRON LEDGER. The whole repository is zig fmt clean, and its file layout is 37.3 at scale: src/domain/types.zig begins with a //! comment, then pub const CBills = i64;, then typed IDs, then enums with their methods, then tests. The naming table is visible in one line from src/domain/person.zig: types.applyBp(self.role.baseSalary(), self.experience().salaryMultBp()), three camelCase methods on TitleCase types returning a snake_case-typed Bp. The game's Date.daysInMonth uses else => unreachable exactly as in 37.7, and its commands.zig has an Error set of a dozen names (UnknownPerson, NotACompany, CompanyDeployed) for everything a player could ask for and be refused. One project story from the original guide is worth keeping: a column binding was once lost when the formatter reflowed a long argument list and an edit missed the new shape. The round-trip test caught it. Formatting is not cosmetic; a diff you can read is a bug you can see.

Exercise 37.1 · Fix six errors warm-up

The starter contains all six errors from 37.5. Run it, read the first error, fix it, run again, until it prints the five expected lines. Name the file: exercises/37-style/ex1_fix_errors.zig.

Solution 
//! Chapter 37, exercise 1: fix six compile errors.
//! Run with:  zig run ex1_fix_errors.zig
//! Goal: the starter has six errors (unused constant, shadowing, missing
//! switch case, type mismatch, try in a non-error function, comptime
//! overflow). Fix them one at a time, re-running after each. Expected
//! output:
//!   mekwarrior earns 1500
//!   tech earns 800
//!   medic earns 400
//!   parsed 42
//!   days in the year: 365

const std = @import("std");

const Role = enum { mekwarrior, tech, medic };

fn salary(r: Role) i64 {
    return switch (r) {
        .mekwarrior => 1500,
        .tech => 800,
        .medic => 400, // was missing: "switch must handle all possibilities"
    };
}

// was `fn parse(s: []const u8) i32`: try needs an error-union return type
fn parse(s: []const u8) !i32 {
    return try std.fmt.parseInt(i32, s, 10);
}

fn label(funds: i64) []const u8 {
    // was `if (funds > 0) "solvent" else 0`: both branches must agree
    return if (funds > 0) "solvent" else "broke";
}

pub fn main() !void {
    // was `const unused = 5;` with nothing reading it
    const roles = [_]Role{ .mekwarrior, .tech, .medic };
    for (roles) |r| {
        std.debug.print("{s} earns {d}\n", .{ @tagName(r), salary(r) });
    }
    // was `const n = ...; for (...) |n|`: the capture shadowed the constant
    const n = try parse("42");
    std.debug.print("parsed {d}\n", .{n});
    _ = label(n);
    // was `const days: u8 = 365;`: u8 cannot represent 365
    const days: u16 = 365;
    std.debug.print("days in the year: {d}\n", .{days});
}

Each comment marks what was there before. The order in which the compiler reports them can vary with what it analyses first, so always fix the top one and re-run rather than trying to fix all six from one output.

Exercise 37.2 · Rename to the conventions practice

The starter is correct but named like C and Java: c_bills_t, PERSON, GetBaseSalary, HiredDay. Rename everything to Zig convention, add a /// comment to each public declaration, and run zig fmt. The tests check behaviour only, so if they still pass you have not broken anything. Name the file: exercises/37-style/ex2_naming.zig.

Solution 
//! Chapter 37, exercise 2: rename to the conventions.
//! Run with:  zig test ex2_naming.zig
//! Goal: the starter uses C-style and Java-style names. Rename every
//! identifier to Zig convention (TitleCase types, camelCase functions,
//! snake_case values) and add a doc comment to each public declaration.
//! The tests only check behaviour, so the compiler is your reviewer.

const std = @import("std");

/// Money in C-bills. Integer, always.
pub const CBills = i64;

/// A person's job in the company.
pub const Role = enum {
    mekwarrior,
    tech,

    /// Monthly pay before any modifiers.
    pub fn baseSalary(self: Role) CBills {
        return switch (self) {
            .mekwarrior => 1_500,
            .tech => 800,
        };
    }
};

/// One hired person.
pub const Person = struct {
    name: []const u8,
    role: Role,
    hired_day: u32,

    /// True once the person has served at least `min_days`.
    pub fn isVeteran(self: Person, today: u32, min_days: u32) bool {
        return today >= self.hired_day and today - self.hired_day >= min_days;
    }
};

/// Total monthly payroll for a roster.
pub fn monthlyPayroll(people: []const Person) CBills {
    var total: CBills = 0;
    for (people) |p| total += p.role.baseSalary();
    return total;
}

test "payroll adds the roster" {
    const roster = [_]Person{
        .{ .name = "Grayson", .role = .mekwarrior, .hired_day = 0 },
        .{ .name = "Clay", .role = .tech, .hired_day = 3 },
    };
    try std.testing.expectEqual(@as(CBills, 2_300), monthlyPayroll(&roster));
}

test "veteran after enough days" {
    const p: Person = .{ .name = "Lori", .role = .mekwarrior, .hired_day = 10 };
    try std.testing.expect(!p.isVeteran(40, 90));
    try std.testing.expect(p.isVeteran(100, 90));
}

Types became CBills, Role, Person; functions baseSalary, isVeteran, monthlyPayroll; fields hired_day. Nothing else changed, which is the point: convention is free once you know it.

Exercise 37.3 · Assert, unreachable, or error? practice

Implement four small functions, choosing for each impossible case between std.debug.assert, unreachable, an error, or nothing at all because the type already excludes it: daysInMonth(Month), discount(amount, bp) with bp promised to be 0 to 10000, parseMonth(text) from user input, and digitValue(ch) whose callers have already checked isDigit. Name the file: exercises/37-style/ex3_assert.zig.

Solution 
//! Chapter 37, exercise 3: assert, unreachable, or error?
//! Run with:  zig test ex3_assert.zig
//! Goal: implement the three functions, choosing the right tool for each
//! impossible case: `std.debug.assert` for a caller-side contract,
//! `unreachable` for a case the type system already excludes, and an
//! error for input that comes from the outside world.

const std = @import("std");

const Month = enum(u8) { jan = 1, feb, mar, apr, may, jun, jul, aug, sep, oct, nov, dec };

/// Days in a month of a non-leap year. `month` is an enum, so every case
/// is covered: no `else` and no `unreachable` needed at all.
pub fn daysInMonth(month: Month) u8 {
    return switch (month) {
        .jan, .mar, .may, .jul, .aug, .oct, .dec => 31,
        .apr, .jun, .sep, .nov => 30,
        .feb => 28,
    };
}

/// The caller promises `bp` is at most 100 percent. Breaking that promise
/// is a bug in the caller, so we assert rather than return an error.
pub fn discount(amount: i64, bp: i64) i64 {
    std.debug.assert(bp >= 0 and bp <= 10_000);
    return amount - @divTrunc(amount * bp, 10_000);
}

/// Text typed by a user is not a bug when it is wrong; it is an error.
pub fn parseMonth(text: []const u8) error{UnknownMonth}!Month {
    return std.meta.stringToEnum(Month, text) orelse error.UnknownMonth;
}

/// A digit character 0-9 to its value. Callers filter with isDigit
/// first, so anything else is unreachable.
pub fn digitValue(ch: u8) u8 {
    return switch (ch) {
        '0'...'9' => ch - '0',
        else => unreachable,
    };
}

test "days in month" {
    try std.testing.expectEqual(@as(u8, 31), daysInMonth(.jan));
    try std.testing.expectEqual(@as(u8, 28), daysInMonth(.feb));
}

test "discount within contract" {
    try std.testing.expectEqual(@as(i64, 900), discount(1000, 1_000));
    try std.testing.expectEqual(@as(i64, 0), discount(1000, 10_000));
}

test "parseMonth reports bad input as an error" {
    try std.testing.expectEqual(Month.sep, try parseMonth("sep"));
    try std.testing.expectError(error.UnknownMonth, parseMonth("Sept"));
}

test "digitValue" {
    try std.testing.expectEqual(@as(u8, 7), digitValue('7'));
}

daysInMonth takes an enum, so every case is an arm and no else exists. discount asserts its precondition. parseMonth returns an error because text from a user is not a bug. digitValue uses unreachable because its contract says callers filter first. Four impossible cases, four different answers.

The starter runs and panics. Read the trace, find the line, fix the logic (do not remove the check or switch to ReleaseFast). After the first fix it panics again with a different message. Name the file: exercises/37-style/ex4_panic.zig.

Solution 
//! Chapter 37, exercise 4: read the panic, fix the bug.
//! Run with:  zig run ex4_panic.zig
//! Goal: the starter panics with "index out of bounds" and, after you fix
//! that, with "integer overflow". Use the stack trace to find each line,
//! then fix the logic (not the safety check). Expected output:
//!   Grayson: 1500
//!   Lori: 1500
//!   Clay: 800
//!   total 3800
//!   average 1266

const std = @import("std");

const names = [_][]const u8{ "Grayson", "Lori", "Clay" };
const pay = [_]u16{ 1500, 1500, 800 };

pub fn main() void {
    // was `i <= names.len`: one past the end
    var i: usize = 0;
    while (i < names.len) : (i += 1) {
        std.debug.print("{s}: {d}\n", .{ names[i], pay[i] });
    }
    // was `var total: u16 = 0`: 1500 + 1500 + 800 overflows u16
    var total: u32 = 0;
    for (pay) |p| total += p;
    std.debug.print("total {d}\n", .{total});
    std.debug.print("average {d}\n", .{total / pay.len});
}

The first panic is index out of bounds: index 3, len 3 from a <= that should be <. The second is integer overflow from summing three u16s into a u16; the fix is a wider accumulator, not +%, because wrapping would silently give the wrong total.

Check your understanding

  1. What does the trailing comma do in zig fmt?
    AnswerA trailing comma in a list makes the formatter lay it out one element per line; without it the list is collapsed onto one line if it fits. It is the one formatting choice left to the author.
  2. Which of these is misnamed: fn ParseInt, const MaxSize = 5, const person_id: PersonId, error.notFound?
    AnswerAll but the third. Functions are camelCase (parseInt), values are snake_case (max_size), error names are TitleCase (error.NotFound).
  3. The compiler says expected type 'i32', found 'error{InvalidCharacter,Overflow}' on a line with try. What is wrong?
    AnswerThe enclosing function's return type is i32, not an error union, so try has nowhere to send the error. Change it to !i32 or use catch.
  4. In a stack trace, which frame do you look at first?
    AnswerThe topmost frame that is in a file you wrote. Frames above it in the standard library (such as callMain in start.zig) are scaffolding.
  5. What is the difference between a panic's stack trace and an error return trace?
    AnswerA stack trace shows the call chain at the moment the program stopped. An error return trace shows each try or return error.X the error passed through on its way out, from where it was created to where it went unhandled.
  6. A user types a month name that does not exist. assert, unreachable, or error?
    AnswerAn error. Bad input from outside the program is a normal condition to handle. assert and unreachable are for conditions that only a bug in your own code could produce.
  7. What does -O ReleaseFast do to an out-of-bounds index, and which mode should you ship?
    AnswerIt removes the check, so the program reads whatever memory is there: undefined behaviour with no message. Ship ReleaseSafe, which is fully optimised and keeps the checks.
What you learned.
  • zig fmt is the only style; --check for CI; the trailing comma controls one-per-line layout.
  • Names: TitleCase types and errors, camelCase functions, snake_case everything else, snake_case files. //! documents a file, /// a declaration.
  • Idioms: init/deinit, allocator first, .empty/.init, Self, defer after acquire, errdefer for partial construction, try by default, pure core with I/O at the edges.
  • Compile errors have a location, a caret and notes; fix the first one. The six common ones: unused value, shadowing, missing switch case, branch type mismatch, try without an error-union return type, comptime overflow.
  • A panic prints a message and a stack trace; look at the first frame in your own file. An error return trace shows the path an unhandled error travelled.
  • @panic for unrecoverable states, assert for caller contracts, unreachable for cases the code has already excluded, errors for anything from outside.
  • Debug and ReleaseSafe keep safety checks; ReleaseFast removes them and turns bugs into undefined behaviour. Ship ReleaseSafe; benchmark with ReleaseFast; zig build-exe -O ReleaseFast file.zig makes a binary.
