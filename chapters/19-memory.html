19. Memory: stack, heap and allocators

In this chapter you will learn where your program's bytes live, why some values need the heap, and how Zig hands out heap memory: not with a hidden new, but through an allocator you pass around like any other value. You will allocate and free, watch the testing allocator catch a leak, and learn the ownership conventions that tell you, for any slice, whether you must free it.

19.1 Two places to keep a value

Every value your program makes has to live somewhere. Zig gives you two places, and it matters which one you choose.

The stack is a region of memory that grows and shrinks as functions are called and return. When a function starts, it gets a frame on the stack, and every local variable lives in that frame. When the function returns, the frame is discarded, all at once, for free. That is why locals are so cheap and why Chapter 18 warned you never to return a pointer to one: the memory is reclaimed the instant the function ends. Stack frames are also small; a few kilobytes each, a few megabytes in total.

The heap is everything else: a large pool of memory from which you can request a block of any size, keep it as long as you like, across as many function calls as you like, and give it back when you are done. The price is that you have to give it back. Nothing does it for you.

mem2.zig

const std = @import("std");

fn stackBuffer() void {
    var buf: [8]u8 = undefined; // lives in this function's frame
    @memset(&buf, 'z');
    std.debug.print("stack: {s}\n", .{buf});
} // buf is gone here, for free

fn heapBuffer(a: std.mem.Allocator) ![]u8 {
    const buf = try a.alloc(u8, 8); // lives until someone frees it
    @memset(buf, 'h');
    return buf; // fine: the memory outlives this function
}

pub fn main(init: std.process.Init) !void {
    stackBuffer();
    const b = try heapBuffer(init.gpa);
    defer init.gpa.free(b);
    std.debug.print("heap:  {s}\n", .{b});
}
stack: zzzzzzzz
heap:  hhhhhhhh

stackBuffer's array is created and destroyed inside the function. heapBuffer's slice comes from an allocator, is returned to the caller, and the caller frees it. The rule of thumb: use the stack when the size is known at compile time and the value does not need to outlive the function. Use the heap when the size depends on run-time data (a list of pilots read from a file), when the value must outlive the function that made it, or when it is too big for a frame.

19.2 Why Zig has no new

In most languages, heap allocation is invisible. Python makes a list and you never think about where it went. C++ has new and Go has make, but the standard library allocates behind your back all the time. Zig's rule is that nothing allocates unless you hand it an allocator. There is no global heap function. If a function needs heap memory, it takes a parameter of type std.mem.Allocator, and every call site shows it.

This buys three things. You can always see which lines might allocate (and therefore might fail with OutOfMemory, which is an ordinary error you handle with try). You can choose a different strategy for different parts of the program, because the allocator is just a value; Chapter 20 is about that choice. And a library you use can never surprise you with allocation, because it has nowhere to get memory except from you.

The allocator is small, two pointers:

mem9.zig

const std = @import("std");

pub fn main() void {
    std.debug.print("Allocator is {d} bytes: a data pointer and a vtable pointer\n", .{@sizeOf(std.mem.Allocator)});
    inline for (@typeInfo(std.mem.Allocator).@"struct".fields) |f| {
        std.debug.print("  field {s}: {s}\n", .{ f.name, @typeName(f.type) });
    }
}
Allocator is 16 bytes: a data pointer and a vtable pointer
  field ptr: *anyopaque
  field vtable: *const mem.Allocator.VTable

ptr is the concrete allocator's own state, as an untyped pointer. vtable points at its four functions (allocate, resize, remap, free). Every allocator in the standard library, and any you write, is something that can produce this two-pointer value. Passing it by value is cheap, so you pass it everywhere.

19.3 alloc, free, create, destroy, dupe

The allocator interface has a handful of methods you will use constantly. Where does the allocator itself come from? For now, from the init parameter of main: init.gpa is a general-purpose allocator the runtime prepares for you, leak-checked in Debug builds. Section 19.6 shows how to make your own.

mem1.zig

const std = @import("std");

pub fn main(init: std.process.Init) !void {
    const a = init.gpa; // std.mem.Allocator

    // alloc: n values of T, returned as a slice you own
    const hp = try a.alloc(u16, 4);
    defer a.free(hp);
    @memset(hp, 100);
    hp[2] = 37;
    std.debug.print("hp = {any}\n", .{hp});

    // create: one T on the heap, returned as *T
    const Pilot = struct { name: []const u8, skill: u8 };
    const p = try a.create(Pilot);
    defer a.destroy(p);
    p.* = .{ .name = "Ada", .skill = 4 };
    std.debug.print("{s} skill {d}\n", .{ p.name, p.skill });

    // dupe: copy a slice into fresh memory you own
    const greeting = try a.dupe(u8, "hello, commander");
    defer a.free(greeting);
    greeting[0] = 'H';
    std.debug.print("{s}\n", .{greeting});
}
hp = { 100, 100, 37, 100 }
Ada skill 4
Hello, commander
  • a.alloc(T, n) gives you n values of T as a slice []T. The bytes are uninitialised; write before you read. Release with a.free(slice).
  • a.create(T) gives you one T as a pointer *T. Release with a.destroy(ptr).
  • a.dupe(T, slice) allocates a copy of a slice. Release with a.free. This is the way to make a string you own from one you were only lent.

Every one of them can fail with error.OutOfMemory, so every call has a try. And every one of them is paired with a defer on the next line, as Chapter 17 taught. Free with the same allocator you allocated from; mixing allocators is a bug the DebugAllocator will catch loudly.

Free takes the slice, not just the pointer. a.free(hp) receives the whole slice, pointer and length. That is how the allocator knows how much to release without keeping its own size table. Consequently you must free exactly the slice you were given, not a sub-slice of it.

19.5 Ownership: who frees this?

When a function returns a slice, a question arises that never comes up in Python: does the caller now have to free it? Zig has no runtime answer; the answer is a convention, written in the function's doc comment and followed by everyone. Two conventions cover nearly everything.

Caller owns. The function allocates the result with the allocator it was given, and the caller must free it with the same allocator. Any function that takes an Allocator and returns a slice or pointer is almost certainly this. allocPrint, dupe, readFileAlloc: all caller-owns.

Borrowed. The function returns a slice into memory the caller already has. Nothing was allocated; there is nothing to free; the result is only valid as long as the original is. Any function that takes no allocator and returns a slice is this. std.mem.trim, tokenizer.next(), slicing with s[a..b]: all borrowed.

mem6.zig

const std = @import("std");

/// Caller owns the returned slice and must free it with `a`.
fn upperCopy(a: std.mem.Allocator, s: []const u8) ![]u8 {
    const out = try a.alloc(u8, s.len);
    for (s, out) |c, *o| o.* = std.ascii.toUpper(c);
    return out;
}

/// Borrows `s`: returns a slice INTO the caller's memory. Nothing to free.
fn firstWord(s: []const u8) []const u8 {
    const end = std.mem.indexOfScalar(u8, s, ' ') orelse s.len;
    return s[0..end];
}

test "owned vs borrowed" {
    const a = std.testing.allocator;
    const line = "hire steiner now";

    const w = firstWord(line); // borrowed: points into `line`
    try std.testing.expectEqualStrings("hire", w);

    const up = try upperCopy(a, line); // owned: we must free
    defer a.free(up);
    try std.testing.expectEqualStrings("HIRE STEINER NOW", up);
}

A useful habit: if a function returns a slice and takes an allocator, expect to defer free the result. If it does not take an allocator, it could not have allocated, so do not. When you write your own, say which it is in the doc comment; IRON LEDGER's are full of "caller owns" and "borrows from the arena".

Trap: storing a borrowed slice. A borrowed slice is a pointer into someone else's buffer. If you keep it in a struct that outlives that buffer, you have a dangling pointer. When a function receives a []const u8 and needs to keep it, it should dupe it and own the copy. The next example shows the idiom.

mem8.zig

const std = @import("std");

const Roster = struct {
    names: std.ArrayList([]u8),
    a: std.mem.Allocator,

    fn init(a: std.mem.Allocator) Roster {
        return .{ .names = .empty, .a = a };
    }

    fn deinit(self: *Roster) void {
        for (self.names.items) |n| self.a.free(n);
        self.names.deinit(self.a);
    }

    /// Copies `name`, so the caller may reuse its buffer afterwards.
    fn add(self: *Roster, name: []const u8) !void {
        const copy = try self.a.dupe(u8, name);
        errdefer self.a.free(copy);
        try self.names.append(self.a, copy);
    }
};

test "roster owns copies of the names" {
    var r = Roster.init(std.testing.allocator);
    defer r.deinit();

    var scratch: [16]u8 = undefined;
    const n1 = try std.fmt.bufPrint(&scratch, "pilot-{d}", .{1});
    try r.add(n1);
    const n2 = try std.fmt.bufPrint(&scratch, "pilot-{d}", .{2}); // overwrites scratch
    try r.add(n2);

    try std.testing.expectEqualStrings("pilot-1", r.names.items[0]);
    try std.testing.expectEqualStrings("pilot-2", r.names.items[1]);
}
1/1 mem8.test.roster owns copies of the names...OK
All 1 tests passed.

The test deliberately reuses one scratch buffer for both names. If add had stored the slice it was handed instead of a copy, the first name would have been overwritten by the second, and the test would fail. Because add owns copies, deinit must free each one and then the list, which is why Roster remembers its allocator.

19.6 Making an allocator: DebugAllocator

init.gpa is convenient, but you should see what is behind it. std.heap.DebugAllocator is the general-purpose allocator for development. You create one as a variable, ask it for an Allocator value, and call deinit() at the end, which returns .ok or .leak.

mem4.zig

const std = @import("std");

pub fn main() void {
    var gpa_state: std.heap.DebugAllocator(.{}) = .init;
    defer {
        const check = gpa_state.deinit();
        std.debug.print("allocator says: {s}\n", .{@tagName(check)});
    }
    const a = gpa_state.allocator();

    const kept = a.alloc(u8, 32) catch return;
    _ = kept; // never freed on purpose, to see the report
    const freed = a.alloc(u8, 8) catch return;
    a.free(freed);
}

19.7 toOwnedSlice and errdefer free

The common way to build a result of unknown length is to append to an ArrayList and then hand the buffer to the caller with toOwnedSlice. The list gives up its buffer, becomes empty, and the caller owns a plain slice. On the failure path, errdefer frees whatever was built so far. Chapter 21 covers ArrayList in depth; here is the ownership shape.

mem7.zig

const std = @import("std");

/// Builds a list of lines and hands the buffer to the caller.
/// Caller owns the result: free each line, then the slice.
fn summary(a: std.mem.Allocator, funds: u32, pilots: u32) ![][]const u8 {
    var out: std.ArrayList([]const u8) = .empty;
    errdefer {
        for (out.items) |line| a.free(line);
        out.deinit(a);
    }
    try out.append(a, try std.fmt.allocPrint(a, "  {d} c-bills in the treasury", .{funds}));
    try out.append(a, try std.fmt.allocPrint(a, "  {d} pilots on the roster", .{pilots}));
    return out.toOwnedSlice(a);
}

test "toOwnedSlice hands over ownership" {
    const a = std.testing.allocator;
    const lines = try summary(a, 12_000, 4);
    defer {
        for (lines) |line| a.free(line);
        a.free(lines);
    }
    try std.testing.expectEqual(@as(usize, 2), lines.len);
    try std.testing.expectEqualStrings("  4 pilots on the roster", lines[1]);
}

Notice the two levels of ownership: the outer slice, and each string inside it. The caller must free both, inner first. That is a lot of bookkeeping for the caller, which is exactly why the next chapter introduces the arena: with an arena, the caller frees everything with one call and the inner loop disappears.

const std = @import("std");

/// The first `n` square numbers. Caller owns the result and frees it with `a`.
fn squares(a: std.mem.Allocator, n: usize) ![]u32 {

Exercise 19.2 · One struct on the heap practice

Implement Pilot.create, which uses a.create and then dupes the name, and Pilot.destroy, which frees both. The second test uses a failing allocator to make the dupe fail, so the struct must be released by an errdefer. File: exercises/19-memory/ex2_create.zig.

Solution 
//! Chapter 19, exercise 2: one struct on the heap with create/destroy.
//! Run with:  zig test ex2_create.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const Pilot = struct {
    name: []u8,
    skill: u8,

    /// Heap-allocate a Pilot that owns a copy of `name`.
    fn create(a: std.mem.Allocator, name: []const u8, skill: u8) !*Pilot {
        const p = try a.create(Pilot);
        errdefer a.destroy(p);
        p.* = .{ .name = try a.dupe(u8, name), .skill = skill };
        return p;
    }

    /// Free the name, then the struct itself.
    fn destroy(self: *Pilot, a: std.mem.Allocator) void {
        a.free(self.name);
        a.destroy(self);
    }
};

test "create and destroy" {
    const a = std.testing.allocator;
    const p = try Pilot.create(a, "Ada", 4);
    defer p.destroy(a);
    try std.testing.expectEqualStrings("Ada", p.name);
    p.skill -= 1;
    try std.testing.expectEqual(@as(u8, 3), p.skill);
}

test "a failing allocator leaks nothing" {
    // failing_allocator fails the 2nd allocation: the dupe. The errdefer
    // must destroy the already-created struct.
    var failing = std.testing.FailingAllocator.init(std.testing.allocator, .{ .fail_index = 1 });
    try std.testing.expectError(error.OutOfMemory, Pilot.create(failing.allocator(), "Bo", 5));
}

std.testing.FailingAllocator wraps another allocator and fails the allocation at a chosen index. With fail_index = 1, the create succeeds and the dupe fails, exercising exactly the path the errdefer protects. Free in reverse order in destroy: the name, then the struct holding it.

Exercise 19.3 · Find and fix the leak practice

The starter's parseEntry leaks on one error path. Run the tests, read the report, and add the one missing line. File: exercises/19-memory/ex3_leak.zig.

Solution 
//! Chapter 19, exercise 3: find and fix the leak.
//! Run with:  zig test ex3_leak.zig
//! Goal: make every test pass without changing the tests. In the
//! starter, one error path forgets to free; the testing allocator
//! reports it.
const std = @import("std");

/// Reads "name:skill" into a heap copy of the name and a number.
const Entry = struct { name: []u8, skill: u8 };

fn parseEntry(a: std.mem.Allocator, text: []const u8) !Entry {
    const colon = std.mem.indexOfScalar(u8, text, ':') orelse return error.NoColon;
    const name = try a.dupe(u8, text[0..colon]);
    errdefer a.free(name); // the fix: without this, a bad number leaks `name`
    const skill = try std.fmt.parseInt(u8, text[colon + 1 ..], 10);
    return .{ .name = name, .skill = skill };
}

test "good entry" {
    const a = std.testing.allocator;
    const e = try parseEntry(a, "Ada:4");
    defer a.free(e.name);
    try std.testing.expectEqualStrings("Ada", e.name);
    try std.testing.expectEqual(@as(u8, 4), e.skill);
}

test "bad entries leak nothing" {
    const a = std.testing.allocator;
    try std.testing.expectError(error.NoColon, parseEntry(a, "Ada"));
    try std.testing.expectError(error.InvalidCharacter, parseEntry(a, "Ada:four"));
}

The name is duplicated before the number is parsed; if the parse fails, the function returns an error and the caller never sees the name. The errdefer a.free(name) right after the dupe fixes it. This is the constructor pattern from Chapter 17 in its smallest form.

Exercise 19.4 · An owned list of borrowed slices challenge

Write lines(a, text), which returns a caller-owned slice of slices that each borrow from text, using an ArrayList and toOwnedSlice. File: exercises/19-memory/ex4_owned.zig.

Solution 
//! Chapter 19, exercise 4: an owned list of borrowed slices.
//! Run with:  zig test ex4_owned.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Split `text` on newlines. The outer slice is OWNED by the caller
/// (free it with `a`); each inner slice BORROWS from `text`, so there
/// is nothing else to free. Empty lines are skipped.
fn lines(a: std.mem.Allocator, text: []const u8) ![][]const u8 {
    var out: std.ArrayList([]const u8) = .empty;
    errdefer out.deinit(a);
    var it = std.mem.splitScalar(u8, text, '\n');
    while (it.next()) |line| {
        if (line.len == 0) continue;
        try out.append(a, line);
    }
    return out.toOwnedSlice(a);
}

/// Total length of all lines. Borrows everything, allocates nothing.
fn totalLen(ls: []const []const u8) usize {
    var n: usize = 0;
    for (ls) |l| n += l.len;
    return n;
}

test "lines" {
    const a = std.testing.allocator;
    const text = "hire Ada\n\nadvance 3\nquit\n";
    const ls = try lines(a, text);
    defer a.free(ls);
    try std.testing.expectEqual(@as(usize, 3), ls.len);
    try std.testing.expectEqualStrings("advance 3", ls[1]);
    try std.testing.expectEqual(@as(usize, 21), totalLen(ls));
    // borrowed: the line points into `text`
    try std.testing.expect(ls[0].ptr == text.ptr);
}

test "empty text" {
    const a = std.testing.allocator;
    const ls = try lines(a, "");
    defer a.free(ls);
    try std.testing.expectEqual(@as(usize, 0), ls.len);
}

Only the outer slice is allocated; the test proves the inner slices are borrowed by checking that ls[0].ptr == text.ptr. The caller frees one thing. Contrast with summary in section 19.7, where the inner strings were owned too and needed a loop to free.

Check your understanding

  1. When must a value go on the heap rather than the stack?
    AnswerWhen its size is only known at run time, when it must outlive the function that creates it, or when it is too large for a stack frame.
  2. Why does Zig have no global new or malloc?
    AnswerSo that every allocation is visible at the call site (it needs an allocator argument), can fail with an ordinary error, and can use whatever strategy the caller chose.
  3. What does a.free need, and why?
    AnswerThe whole slice, pointer and length, so it knows how much to release. Free exactly what alloc returned, with the same allocator.
  4. How do you know whether to free a slice a function returned?
    AnswerBy convention: if the function took an allocator, the caller owns the result and frees it; if not, the result borrows existing memory and must not be freed.
  5. What does std.testing.allocator do at the end of a test?
    AnswerReports every allocation that was not freed, with the stack trace of where it was allocated, and fails the test.
  6. What does DebugAllocator.deinit() return?
    Answer.ok if everything was freed, .leak otherwise, having printed a report for each leaked block.
  7. What does list.toOwnedSlice(a) do?
    AnswerHands the list's buffer to the caller as a plain slice the caller now owns and must free; the list becomes empty.
What you learned.
  • Stack memory is per function frame, automatic and short-lived; heap memory is requested and must be returned.
  • Nothing allocates without a std.mem.Allocator parameter; the allocator is two pointers passed by value.
  • alloc/free for slices, create/destroy for single values, dupe to own a copy; all can fail with OutOfMemory.
  • std.testing.allocator fails a test that leaks and shows where the leak was allocated.
  • DebugAllocator(.{}) is .init, .allocator(), .deinit() returning .ok or .leak; init.gpa is one, ready made.
  • "Caller owns" when a function takes an allocator and returns a slice; "borrowed" when it does not. dupe what you need to keep.
  • toOwnedSlice transfers a list's buffer to the caller; errdefer frees partial work on failure.
