40. Data: ZON files become typed tables

In this chapter you see how IRON LEDGER keeps its numbers out of its code. Every balance constant, every mek design and every planet lives in a .zon file that the compiler type-checks against a Zig struct at build time. You will read the mechanism end to end, from build.zig to a rules formula, break it on purpose to see what the compiler says, and add a knob of your own.

What you need from earlier chapters. Chapter 28 (ZON: a struct literal in a file, imported with @import and given a type by the declaration that receives it), Chapter 31 (build options with b.option, and addAnonymousImport), Chapter 12 (struct fields with and without defaults), and Chapter 27 for the last section, where a test walks a struct's fields with @typeInfo and inline for. Chapter 15's ?*const T return type appears in the catalogue lookup.

40.1 The problem the data layer solves

A management game is mostly numbers: what a mekwarrior is paid, how far an HQ's influence reaches, how many days paperwork takes, how likely a rare part is to appear on a market. The first version of IRON LEDGER had these as constants scattered through the code with // TUNE comments. That is fine for a prototype and bad for a game, because balancing means changing the numbers often and a modder cannot change them at all.

The obvious fix in most languages is a config file parsed at start-up: JSON, TOML, whatever. That buys flexibility and costs safety. A misspelled key becomes a default silently; a string where a number belongs becomes a crash on turn 40. Zig offers a third option that Chapter 28 introduced: a data file in the language's own literal syntax, imported at compile time, type-checked against a struct. IRON LEDGER uses it for all fourteen of its tables. The rule in CLAUDE.md is blunt: static game data belongs in data/*.zon, not hardcoded.

40.2 One knob, end to end

Take one number and follow it. Here is the top of the tuning table:

data/tables/tuning.zon
// Tuning knobs (Stage 12.17). Typed against domain/tuning.zig `Tuning` at
// comptime. Money in C-bills, multipliers in basis points (10_000 = ×1).
// The formulas live beside their subsystems; this file only holds the
// numbers they were built on, so play-testing edits land here.
.{
    .hq = .{
        .influence_ly = .{ .field = 15, .regional = 60, .brigade = 90 }, // ARCH §9.2
        .influence_per_comms_ly = 10,
        .influence_per_spaceport_ly = 5,
        .paperwork_base_days = 21,
        .paperwork_min_days = 5,
        .paperwork_days_per_admin_level = 3,
        .upgrade_cost_per_level = .{ .mek_bay = 800_000, .warehouse = 400_000, .hospital = 500_000,
            .mess = 150_000, .training_ground = 300_000, .hiring_hall = 200_000,
            .comms = 600_000, .spaceport = 1_200_000 },
        .warehouse_tons_per_level_sq = 200, // 200 / 800 / 1800 / 3200 / 5000
        .upkeep = .{ .field = 10_000, .regional = 25_000, .brigade = 60_000 },
        .founding_funds = 1_000_000,
        .found_field_hq_cost = 500_000,
        .sale_pct = 40,
    },
    .logistics = .{
        .ly_per_jump = 30,
        .recharge_days = 7,
        // …
    },
    // … network, market, person, medical, battle, rating, contract …
}

It is exactly the anonymous struct literal syntax you used for .{ .year = 3025 } in Chapter 12, with nothing around it. Comments are allowed. Underscores in numbers are allowed. Nested literals are allowed. What is not here is any hint of a type; the file does not know what it is describing.

The type is on the Zig side:

src/domain/tuning.zig
//! Tuning tables: every balance constant the sim reads, loaded at comptime
//! from data/tables/tuning.zon (Stage 12.17, closing the "// TUNE" debt).
//! Mirrors MekHQ `campaign/CampaignOptions` — knobs, not rules; the
//! formulas stay legible in the modules that use them. The ZON file is
//! type-checked against `Tuning` at compile time: a missing or misspelled
//! field is a build error, not a silent default.

const std = @import("std");
const types = @import("types.zig");

pub const Tuning = struct {
    hq: struct {
        influence_ly: struct { field: u32, regional: u32, brigade: u32 },
        influence_per_comms_ly: u32,
        influence_per_spaceport_ly: u32,
        paperwork_base_days: u32,
        paperwork_min_days: u32,
        paperwork_days_per_admin_level: u32,
        upgrade_cost_per_level: struct { mek_bay: types.CBills, warehouse: types.CBills, /* … */ },
        warehouse_tons_per_level_sq: u32,
        upkeep: struct { field: types.CBills, regional: types.CBills, brigade: types.CBills },
        founding_funds: types.CBills,
        found_field_hq_cost: types.CBills,
        sale_pct: u32,
    },
    logistics: struct {
        ly_per_jump: u32,
        recharge_days: u32,
        // …
    },
    // …
};

/// The live table.
pub const t: Tuning = @import("tuning_zon");

The last line is the whole mechanism. @import("tuning_zon") returns the file's value; declaring the constant as : Tuning forces the compiler to coerce that anonymous literal to the Tuning struct, field by field, at compile time. A field in the file that the struct does not have is an error. A field the struct has that the file lacks (and that has no default) is an error. A string where a u32 belongs is an error. And they are errors with line numbers in the .zon file, as you will see in a moment.

Then the rules code reads the value as a plain constant. Here is the founding-capital line from GameState.createCommander (Chapter 41), where tuning is @import("../domain/tuning.zig").t:

self.transferFunds(.outfit, .{ .hq = id }, tuning.hq.founding_funds, 0) catch {};

No lookup, no parsing, no getOrDefault. tuning.hq.founding_funds is an i64 known at compile time, so the optimiser treats it exactly like the literal 1_000_000 it replaced.

40.3 What the compiler says when you get it wrong

The claim "a wrong field is a build error" is easy to make and worth checking. In your copy of the game, misspell one field in the ZON file (fatigue_tired to fatigue_tierd, say) and build:

$ zig build test
data/tables/tuning.zon:108:26: error: unexpected field 'fatigue_tierd'
        .fatigue_tierd = 30,
                         ^~
src/domain/tuning.zig:398:31: note: imported here
pub const t: Tuning = @import("tuning_zon");
                              ^~~~~~~~~~~~

Now put a string where a number belongs (.paperwork_base_days = "21"):

data/tables/tuning.zon:10:32: error: expected type 'u32'
        .paperwork_base_days = "21",
                               ^~~~

Both point at the data file, both name the field, and neither lets the game build. Compare with what a runtime config parser would do with the same two mistakes: the first would probably be ignored, the second would crash the first time the value was used. That is the trade the ZON approach makes: the data is baked into the binary (you cannot edit it without rebuilding), and in exchange the binary can never disagree with it.

40.4 How the file gets its name

The string "tuning_zon" is not a path. It is a name that build.zig attaches to the module, and this indirection is what makes mod support cheap:

build.zig
const data_dir = b.option([]const u8, "data", "Directory overlaying data/*.zon and data/tables/*.zon (mod support)");
const DataFile = struct { import_name: []const u8, rel: []const u8 };
const data_files = [_]DataFile{
    .{ .import_name = "chassis_zon", .rel = "chassis.zon" },
    .{ .import_name = "planets_zon", .rel = "planets.zon" },
    .{ .import_name = "parts_zon", .rel = "parts.zon" },
    .{ .import_name = "tuning_zon", .rel = "tables/tuning.zon" },
    .{ .import_name = "meklab_zon", .rel = "tables/meklab.zon" },
    .{ .import_name = "names_zon", .rel = "tables/names.zon" },
    .{ .import_name = "ranks_zon", .rel = "tables/ranks.zon" },
    .{ .import_name = "awards_zon", .rel = "tables/awards.zon" },
    .{ .import_name = "abilities_zon", .rel = "tables/abilities.zon" },
    .{ .import_name = "rat_zon", .rel = "tables/rat.zon" },
    .{ .import_name = "factions_zon", .rel = "tables/factions.zon" },
    .{ .import_name = "scenarios_zon", .rel = "tables/scenarios.zon" },
    .{ .import_name = "terrain_zon", .rel = "tables/terrain.zon" },
    .{ .import_name = "difficulty_zon", .rel = "tables/difficulty.zon" },
};
var overlaid = std.ArrayList([]const u8).empty;
for (data_files) |f| {
    var path: std.Build.LazyPath = b.path(b.fmt("data/{s}", .{f.rel}));
    if (data_dir) |dir| {
        const candidate = b.pathJoin(&.{ dir, f.rel });
        const exists = if (std.fs.path.isAbsolute(candidate))
            std.Io.Dir.accessAbsolute(b.graph.io, candidate, .{})
        else
            b.build_root.handle.access(b.graph.io, candidate, .{});
        if (exists) |_| {
            path = if (std.fs.path.isAbsolute(candidate)) .{ .cwd_relative = candidate } else b.path(candidate);
            overlaid.append(b.allocator, f.rel) catch @panic("OOM");
        } else |_| {}
    }
    mod.addAnonymousImport(f.import_name, .{ .root_source_file = path });
}
// What the binary can say about its data (settings screen, REPL banner).
const build_options = b.addOptions();
build_options.addOption(?[]const u8, "data_dir", data_dir);
build_options.addOption([]const []const u8, "data_overlays", overlaid.items);
mod.addImport("build_options", build_options.createModule());

Read the loop slowly; it is ordinary Zig running inside the build script, which is itself an ordinary Zig program (Chapter 31). For each of the fourteen files it computes a path, defaulting to data/…. If the user passed -Ddata=mymod and a file exists at the same relative path under that directory, the path is swapped. Then addAnonymousImport binds the name to whichever path won. The simulation code says @import("tuning_zon") and never learns which file it got.

Two smaller things to notice. The build script itself uses the 0.16 I/O API (b.graph.io, std.Io.Dir.accessAbsolute) to test for the file, because the build runner is a real program with real I/O. And the last four lines create a second tiny module, build_options, whose contents are values computed here: the data directory and the list of files it overlaid. root.zig imports it as build_info and uses it in dataProvenance to print "mod mymod: 1 file overlaid (tables/tuning.zon)" on the settings screen. That is how a binary can say where its numbers came from.

Try it. Run zig build --help in the game directory and find the two lines 
  -Ddata=[string]              Directory overlaying data/*.zon and data/tables/*.zon (mod support)
  -Dbundle-music=[bool]        Copy data/music into the install prefix (large)
Zig generated that help text from the b.option calls; nobody wrote it twice.

40.5 A catalogue: rows with defaults

The tuning table is one big struct. The design catalogue is a slice of small ones, and it shows the other half of the idea: fields with defaults let a row leave out what does not apply to it.

src/domain/chassis.zig
pub const Chassis = struct {
    key: []const u8, // variant designation, e.g. "SHD-2H"
    name: []const u8, // "Shadow Hawk"
    tonnage: u8,
    bv: u16, // BV2 — autoresolve base strength (ARCH §7)
    cost: types.CBills,
    rarity: types.Rarity, // market appearance tier (ARCH §9.8)
    /// First year the design is in service (12C.16, MekHQ `introYear`);
    /// the market, RATs and salvage only field what exists in the campaign year.
    intro_year: u16 = 2400,
    kind: unit.UnitKind = .mek,
    // Construction facts (Stage 10 MekLab; meks only, defaults for others).
    walk_mp: u8 = 0,
    jump_mp: u8 = 0,
    heat_sinks: u8 = 10,
    armor_half_tons: u16 = 0,
    // Transport facts (Stage 12.15; dropships/jumpships only, TRO:3025).
    mek_bays: u8 = 0,
    asf_bays: u8 = 0,
    vehicle_bays: u8 = 0,
    cargo_tons: u32 = 0,
    collars: u8 = 0,
    loadout: []const LoadoutSlot,

    pub fn engineRating(self: *const Chassis) u32 {
        return @as(u32, self.tonnage) * self.walk_mp;
    }

    pub fn weightClass(self: *const Chassis) WeightClass {
        return switch (self.tonnage) {
            0...35 => .light,
            36...55 => .medium,
            56...75 => .heavy,
            else => .assault,
        };
    }
};

pub const catalog: []const Chassis = @import("chassis_zon");

pub fn find(key: []const u8) ?*const Chassis {
    for (catalog) |*c| {
        if (std.mem.eql(u8, c.key, key)) return c;
    }
    return null;
}

Six fields have no default and must be present in every row: key, name, tonnage, bv, cost, rarity, plus the loadout slice. Everything else may be omitted, so a vehicle row need not state jump_mp and a mek row need not state collars. Here is one of the 97 rows:

data/chassis.zon (one row)
.{ .key = "SHD-2H", .name = "Shadow Hawk", .tonnage = 55, .bv = 1064, .cost = 4_672_315,
   .rarity = .common, .walk_mp = 5, .jump_mp = 3, .heat_sinks = 12, .armor_half_tons = 19,
   .loadout = .{
    .{ .slot = "lt.ac5.1", .part = "ac5", .class = .weapon },
    .{ .slot = "rt.lrm5.1", .part = "lrm5", .class = .weapon },
    .{ .slot = "ra.mlas.1", .part = "mlas", .class = .weapon },
    .{ .slot = "hd.srm2.1", .part = "srm2", .class = .weapon },
    .{ .slot = "lt.ammo_ac5.1", .part = "ammo_ac5", .class = .ammo },
    .{ .slot = "rt.ammo_lrm.1", .part = "ammo_lrm", .class = .ammo },
    .{ .slot = "ct.ammo_srm.1", .part = "ammo_srm", .class = .ammo },
} },

Note .rarity = .common and .class = .weapon: enum literals in a data file. The compiler resolves them against types.Rarity and unit.SlotClass because the struct says those are the field types, so a typo like .commom is a build error too. (If you compare this row with the original guide, the cost has changed; the catalogue was re-priced from the sourcebooks after the guide was written. The data moved and the code did not need to.)

The lookup function find is the pattern from Chapter 15: it returns ?*const Chassis, a maybe-pointer into the constant table, and null for an unknown key. Callers write chassis.find(u.chassis_key) orelse … or if (chassis.find(key)) |c| …. There is no error type because "not in the catalogue" is an ordinary outcome, not a failure.

40.6 What the type system cannot check, tests do

The compiler checks shape: fields, types, enum names. It cannot check meaning: that the part key "ac5" in a loadout exists in the parts catalogue, that every entry in a house's random assignment table names a mek of the stated weight class, or that a design's tonnage adds up under the construction rules. Those are cross-file facts, and the game checks them with tests that run against the data:

src/domain/part.zig
test "every chassis loadout part resolves in the part catalog" {
    const chassis = @import("chassis.zig");
    for (chassis.catalog) |c| {
        for (c.loadout) |slot| {
            try std.testing.expect(find(slot.part) != null);
        }
    }
    for (component_keys) |k| try std.testing.expect(find(k) != null); // the fabrication guarantee
}
src/domain/rat.zig
test "every RAT entry names a catalogue mek of the right class; every house has all four classes" {
    try std.testing.expect(table.len >= 6);
    for (table) |row| {
        inline for (.{ chassis.WeightClass.light, .medium, .heavy, .assault }) |class| {
            const pool = row.pool(class);
            try std.testing.expect(pool.len > 0);
            for (pool) |key| {
                const c = chassis.find(key) orelse {
                    std.debug.print("RAT {s}: unknown design {s}\n", .{ row.faction, key });
                    return error.TestUnexpectedResult;
                };
                try std.testing.expect(c.kind == .mek);
                if (c.weightClass() != class) {
                    std.debug.print("RAT {s}: {s} is {s}, listed as {s}\n", .{ row.faction, key, @tagName(c.weightClass()), @tagName(class) });
                    return error.TestUnexpectedResult;
                }
            }
        }
    }
    // …
}

Two habits from Chapter 8 appear here. A test that loops over data prints which row failed before returning error.TestUnexpectedResult, because "expect failed" on its own would send you hunting through 97 rows. And the loops are cheap: the whole catalogue is a compile-time constant, so these tests cost microseconds and nobody is tempted to skip them.

This is why docs/modding.md tells a modder to run zig build test -Ddata=mymod rather than just zig build. The build proves the mod has the right shape; the tests prove its rows refer to each other correctly. In the exercises you will see that the tuning table has an even stronger check: a test that visits every field, however deeply nested, without naming any of them.

40.7 The tuning sanity test

You met this function in Chapter 27 as an example of reflection. Now read it as its authors use it:

src/domain/tuning.zig
fn checkPositive(comptime T: type, value: T, comptime name: []const u8) !void {
    switch (@typeInfo(T)) {
        .int => |info| {
            // Signed knobs (deltas, scores) may be zero or negative by design.
            if (info.signedness == .signed) return;
            if (value <= 0) {
                std.debug.print("tuning field {s} must be positive\n", .{name});
                return error.BadTuning;
            }
            if (std.mem.endsWith(u8, name, "_bp") and value > 100_000) {
                std.debug.print("tuning field {s} is over 100000 basis points\n", .{name});
                return error.BadTuning;
            }
        },
        .@"struct" => |info| inline for (info.fields) |f| try checkPositive(f.type, @field(value, f.name), name ++ "." ++ f.name),
        else => {},
    }
}

test "every tuning value is positive and every basis-point knob is sane" {
    try checkPositive(Tuning, t, "t");
}

test "spot checks against the values the formulas were built on" {
    try std.testing.expectEqual(@as(u32, 60), t.hq.influence_ly.regional);
    try std.testing.expectEqual(@as(u32, 6), t.battle.mounts_per_ammo_ton);
    try std.testing.expectEqual(@as(types.Bp, 1_200), t.finance.loan_rate_bp);
    try std.testing.expectEqual(@as(types.CBills, 2_000), t.logistics.freight_per_ly);
}

The recursion is on types, not on values: for a struct it calls itself once per field with the field's type, the field's value (read with @field), and a dotted name built with ++, all at compile time. At runtime what remains is a flat list of integer comparisons, one per unsigned knob. Add a field to Tuning and it is covered with no change to the test, which is exactly what the first exercise asks you to confirm.

The second test is the reverse: four values pinned by hand. It exists so that a mod which changes the numbers the formulas were tuned around fails loudly under zig build test -Ddata=…, and so that an accidental edit to the stock file is noticed.

Guided reading

  1. build.zig: the block from const data_dir = b.option( to mod.addImport("build_options", …). Match each import_name to the Zig file that imports it (grep for _zon" under src/domain and src/gen).
  2. src/domain/tuning.zig: skim the Tuning struct to see how the knobs are grouped by subsystem, then read the three declarations at the bottom: t, checkPositive, and the two tests.
  3. data/tables/tuning.zon next to it. Pick any three knobs and grep the source for their names to find the formula that uses each. You will find that every use is a plain field access.
  4. src/domain/chassis.zig top to bottom (186 lines). Note the four lookup helpers after find (ofWeightClass, ofKind, scoutPool, availableIn) and how each filters the constant slice. Then the tests: the first checks shape facts the compiler cannot (positive BV, unique keys).
  5. src/domain/part.zig, src/domain/rat.zig, src/domain/scenario.zig, src/domain/planet.zig: read only the tests. Each is a cross-file check of the kind described in 40.6.
  6. docs/modding.md: the table of files and the "Rules of the road". It is written for modders, which makes it the clearest statement of what each table holds.

Exercises

Exercise 40.1 · Break it on purpose warm-up

In your copy of the game, make three separate edits to data/tables/tuning.zon, building after each and writing down the first line of the error: (a) misspell a field name; (b) delete a field entirely; (c) change .rarity_target's .common value to "7". Undo each edit before the next.

Solution

(a) error: unexpected field 'fatigue_tierd', pointing at the line in the ZON file. (b) data/tables/tuning.zon:92:16: error: missing field 'fatigue_tired', pointing at the opening .{ of the .person block, with a note saying where the file was imported (src/domain/tuning.zig:398). (c) error: expected type 'u8' (or whatever the field's integer type is), pointing at the string. In all three cases the game does not build, which is the behaviour the design promises. Notice that (b) is reported at the struct literal rather than at the missing line, because there is no missing line to point at.

Exercise 40.2 · Add a knob practice

Add a new tuning knob person.exercise_bonus_xp with the value 5. It needs a field in the Tuning struct and a value in the ZON file. Then write a test in tuning.zig that reads it back. Before running the tests, predict whether checkPositive will cover the new field, and check your prediction by temporarily setting the value to 0.

Solution
src/domain/tuning.zig, inside the person struct
    person: struct {
        weekly_hours: u16,
        exercise_bonus_xp: u32,
        // …
data/tables/tuning.zon, inside .person
    .person = .{
        .weekly_hours = 40,
        .exercise_bonus_xp = 5,
        // …
src/domain/tuning.zig, at the bottom
test "the new knob is on the table" {
    try std.testing.expectEqual(@as(u32, 5), t.person.exercise_bonus_xp);

With the value 0, zig build test prints tuning field t.person.exercise_bonus_xp must be positive and the sanity test fails: checkPositive found the new field through @typeInfo without anyone telling it. The dotted name in the message was built at compile time with ++. Set it back to 5 and everything is green.

Exercise 40.3 · A cross-file check of your own practice

Add a test to src/domain/chassis.zig asserting that every design of kind .mek has at least one loadout slot of class .weapon. Use the pattern from 40.6: loop the constant catalogue, skip rows that do not apply, count, expect.

Solution 
test "every mek carries at least one weapon" {
    for (catalog) |c| {
        if (c.kind != .mek) continue;
        var weapons: u32 = 0;
        for (c.loadout) |slot| if (slot.class == .weapon) {
            weapons += 1;
        };
        try std.testing.expect(weapons > 0);
    }
}

It passes against the stock data. Two details: c.kind is a defaulted field, so rows that omit it read as .mek; and the one-line for … |slot| if (…) { … }; form needs the trailing semicolon because the whole for is a statement whose body is an if expression. If you want the failure message to name the offending design, print c.key before returning error.TestUnexpectedResult, as the RAT test does.

Exercise 40.4 · A mod that changes one number challenge

Create a directory mymod/tables/, copy tuning.zon into it, and change the regional influence radius from 60 to 61 light-years. Build and test with -Ddata=mymod. Which test notices, and why is that the right test to notice? Then run the game's REPL with the same option and find where it reports the overlay.

Solution 
$ mkdir -p mymod/tables && cp data/tables/tuning.zon mymod/tables/
$ sed -i '' 's/.regional = 60, .brigade = 90/.regional = 61, .brigade = 90/' mymod/tables/tuning.zon
$ zig build test -Ddata=mymod
error: 'domain.tuning.test.spot checks against the values the formulas were built on' failed:
       expected 60, found 61
Build Summary: … 1 failed

The spot-check test is the one that notices, and it is the right one: the shape is still valid (so the build succeeds and checkPositive is happy), but a formula somewhere was tuned around 60, and the test exists to say so. A modder who intends the change edits or skips that test; an accidental edit gets caught. The REPL banner prints the result of root.dataProvenance: mod mymod: 1 file overlaid (tables/tuning.zon). The values came from build_options, which the build script computed in the loop you read in 40.4.

Check your understanding

  1. What gives a ZON file its type?
    AnswerThe declaration that receives it: pub const t: Tuning = @import("tuning_zon"); coerces the anonymous literal to Tuning at compile time.
  2. Where is the string "tuning_zon" connected to a real file?
    AnswerIn build.zig, by mod.addAnonymousImport(f.import_name, .{ .root_source_file = path }), where path is either data/tables/tuning.zon or the same relative path under the -Ddata directory.
  3. Which mistakes in a data file does the compiler catch, and which does it not?
    AnswerIt catches shape errors: unknown fields, missing fields without defaults, wrong types, unknown enum literals. It cannot catch cross-file meaning, such as a loadout naming a part that is not in parts.zon; tests do that.
  4. Why can a vehicle row omit jump_mp?
    AnswerBecause Chassis.jump_mp has a default (= 0). Fields with defaults may be omitted from any struct literal, ZON included.
  5. What does find return for an unknown key, and why is that not an error?
    Answernull, because the return type is ?*const Chassis. "Not in the catalogue" is an ordinary outcome the caller handles with orelse or if, not a failure to propagate.
  6. Why does checkPositive take comptime T: type rather than using @TypeOf(value)?
    AnswerBoth would work for the top call, but the recursion needs to pass f.type explicitly for each field, and marking the parameter comptime guarantees the switch (@typeInfo(T)) is resolved while compiling, so only the integer checks survive to runtime.
  7. How does the binary know which files a mod overlaid?
    Answerbuild.zig records them in a generated build_options module (addOptions), which root.zig imports as build_info and formats in dataProvenance.
What you learned.
  • Every table in IRON LEDGER is a .zon struct literal imported by name and coerced to a Zig struct at compile time; the struct is the schema.
  • Shape errors (unknown field, missing field, wrong type, bad enum literal) fail the build with a line number in the data file.
  • build.zig binds each import name to a path, which is how -Ddata=<dir> overlays files without the simulation knowing.
  • Rows with defaulted fields let one struct describe meks, vehicles, fighters and ships.
  • Cross-file facts are checked by tests that loop over the constant data and name the failing row; a reflective test covers every tuning knob automatically.
