4. Integers and arithmetic

In this chapter you will learn Zig's integer types and how to choose one, what happens when arithmetic overflows and the three operators Zig gives you for it, why signed division needs a builtin, how to convert between integer types on purpose, and how bit operators and shifts work. Along the way you will see your first runtime panic.

4.1 Widths and signedness

An integer type in Zig is a letter and a number: u for unsigned or i for signed, then the number of bits. u8 holds 0 to 255. i8 holds -128 to 127. u32 holds 0 to about four billion; i64 holds plus or minus about nine quintillion. The number can be anything from 1 to 65535, so u3 and i7 are real types, though in practice you use 8, 16, 32 and 64.

widths.zig
const std = @import("std");

pub fn main() void {
    const a: u8 = 255;
    const b: i8 = -128;
    const c: u16 = 65_535;
    const d: i32 = -2_147_483_648;
    const e: u64 = 18_446_744_073_709_551_615;
    const f: u3 = 7; // three bits: 0..7
    const g: usize = 42;
    std.debug.print("{d} {d} {d} {d} {d} {d} {d}\n", .{ a, b, c, d, e, f, g });
    std.debug.print("usize is {d} bits on this machine\n", .{@bitSizeOf(usize)});
    std.debug.print("u8 max {d}, i8 min {d}, i8 max {d}\n", .{
        std.math.maxInt(u8), std.math.minInt(i8), std.math.maxInt(i8),
    });
}
$ zig run widths.zig
255 -128 65535 -2147483648 18446744073709551615 7 42
usize is 64 bits on this machine
u8 max 255, i8 min -128, i8 max 127

Two types stand apart. usize is an unsigned integer as wide as a memory address on the machine you compile for: 64 bits on any modern computer. It is the type of every array index, length, and count in the standard library, and you will use it constantly from Chapter 9 on. Its signed twin isize is rarer. std.math.maxInt(T) and minInt(T) give the limits of any integer type.

Choosing a width is part of design. A tonnage that is never above 100 fits a u8; a day count fits a u32; money that can be negative and large is an i64. Smaller types save memory in arrays and make invalid values impossible to store. Larger types avoid overflow. When unsure, u32 or i64 is a reasonable default, and usize for anything that indexes memory.

4.2 Literals

An integer literal can be written in four bases, and underscores can be placed anywhere inside it for readability.

literals.zig
const std = @import("std");

pub fn main() void {
    const decimal = 9_626_000;
    const hex = 0xFF;
    const binary = 0b1010_1010;
    const octal = 0o755;
    const char = 'A'; // a character literal is a comptime_int too
    std.debug.print("{d} {d} {d} {d} {d}\n", .{ decimal, hex, binary, octal, char });
    std.debug.print("{x} {b} {o} {c}\n", .{ hex, binary, octal, char });
}
$ zig run literals.zig
9626000 255 170 493 65
ff 10101010 755 A

0x is hexadecimal, 0b binary, 0o octal. A character in single quotes, 'A', is also an integer literal whose value is the character's code (65 for A), which is why it can be printed with {d} or with {c}. As Chapter 3 explained, all of these are comptime_int until they meet a concrete type, and they must fit that type:

toobig.zig
const std = @import("std");

pub fn main() void {
    const a: u8 = 256;
    std.debug.print("{d}\n", .{a});
}
$ zig run toobig.zig
toobig.zig:4:19: error: type 'u8' cannot represent integer value '256'
    const a: u8 = 256;
                  ^~~

The same message appears if you put a negative literal into an unsigned type: type 'u8' cannot represent integer value '-1'. Both are caught before the program runs.

4.3 Overflow, and your first panic

A u8 holds at most 255. What happens when you add 10 to 250?

overflow.zig
const std = @import("std");

pub fn main() void {
    var armor: u8 = 250;
    armor += 10;
    std.debug.print("{d}\n", .{armor});
}
$ zig run overflow.zig
thread 12345 panic: integer overflow
overflow.zig:5:11: 0x10000abcd in main (overflow)
    armor += 10;
          ^

The program stops with a panic. This is the runtime, not the compiler: the program built and started, and then the addition on line 5 produced a value that does not fit, and Zig's safety check caught it. A panic prints a message, the source location, and a stack trace, then exits with a failure status. The full trace continues into the standard library's start.zig; the transcript cuts it there, and you can too when reading one.

Compare this with C, where the same addition silently gives 4, and with Python, where integers grow without bound. Zig's position is that overflow in ordinary arithmetic is nearly always a bug, so in Debug and ReleaseSafe builds it is checked and stops the program. In ReleaseFast builds the check is removed and the result is undefined, which is why you test in Debug.

When the operands are known at compile time, the same overflow is reported even earlier:

overflow_comptime.zig
const std = @import("std");

pub fn main() void {
    const armor: u8 = 250;
    const more = armor + 10;
    std.debug.print("{d}\n", .{more});
}
$ zig run overflow_comptime.zig
overflow_comptime.zig:5:24: error: overflow of integer type 'u8' with value '260'
    const more = armor + 10;
                 ~~~~~~^~~~

That is why the first example used a var and a separate +=: to make the value a runtime one, so you could see the runtime check. The compiler folds constant arithmetic whenever it can, and reports what it finds.

4.4 Wrapping and saturating operators

Sometimes overflow is what you want. A hash function multiplies numbers expecting the high bits to fall off. An 8-bit counter is meant to roll over. A count that must never go below zero should stop at zero rather than crash. Zig has separate operators for these cases, so the intent is visible in the source.

wrapsat.zig
const std = @import("std");

pub fn main() void {
    var armor: u8 = 250;
    const wrapped = armor +% 10;
    const saturated = armor +| 10;
    std.debug.print("wrapped {d}, saturated {d}\n", .{ wrapped, saturated });

    armor = 3;
    std.debug.print("3 -% 5 = {d}, 3 -| 5 = {d}\n", .{ armor -% 5, armor -| 5 });
    std.debug.print("200 *% 2 = {d}, 200 *| 2 = {d}\n", .{ @as(u8, 200) *% 2, @as(u8, 200) *| 2 });
    var i: i8 = 127;
    i +%= 1;
    std.debug.print("i8 127 +%= 1 -> {d}\n", .{i});
}
$ zig run wrapsat.zig
wrapped 4, saturated 255
3 -% 5 = 254, 3 -| 5 = 0
200 *% 2 = 144, 200 *| 2 = 255
i8 127 +%= 1 -> -128
OperatorNameOn overflow
+ - *plainpanic in Debug and ReleaseSafe; undefined in ReleaseFast
+% -% *%wrappingwraps around modulo 2bits: 250 +% 10 is 4
+| -| *|saturatingclamps to the type's minimum or maximum: 250 +| 10 is 255

All three have assignment forms: +=, +%=, +|=. The saturating subtraction -| is the one you will use most, because "how many more do we need" is naturally need -| have, zero when there is already enough, and never a negative number stored in an unsigned type. Read the wrapping example for signed types too: i8 127 +% 1 is -128, the way the bits work in hardware.

Try it. Change +% and +| in wrapsat.zig to plain + and run it. Then make the type u16 and run it again; the panic disappears because 260 fits. Choosing the width is the first line of defence against overflow, and the operators are the second.

4.5 Division: four builtins

For unsigned integers, / divides and % gives the remainder, both rounding toward zero, and there is nothing to decide. For signed integers there is a genuine choice: -17 divided by 5 is -3 remainder -2 if you round toward zero, or -4 remainder 3 if you round toward negative infinity. Languages disagree (C does the first, Python the second), and each answer is right for some problems. Zig refuses to guess:

signed_slash_rt.zig
const std = @import("std");

pub fn main() void {
    var n: i32 = -17;
    n -= 0;
    const d: i32 = 5;
    std.debug.print("{d}\n", .{n / d});
}
$ zig run signed_slash_rt.zig
signed_slash_rt.zig:7:34: error: division with 'i32' and 'i32': signed integers must use @divTrunc, @divFloor, or @divExact
    std.debug.print("{d}\n", .{n / d});
                               ~~^~~

So you say which you mean:

division.zig
const std = @import("std");

pub fn main() void {
    const a: u32 = 17;
    const b: u32 = 5;
    std.debug.print("unsigned: {d} / {d} = {d}, remainder {d}\n", .{ a, b, a / b, a % b });

    const n: i32 = -17;
    const d: i32 = 5;
    std.debug.print("@divTrunc(-17, 5) = {d}\n", .{@divTrunc(n, d)});
    std.debug.print("@divFloor(-17, 5) = {d}\n", .{@divFloor(n, d)});
    std.debug.print("@rem(-17, 5) = {d}\n", .{@rem(n, d)});
    std.debug.print("@mod(-17, 5) = {d}\n", .{@mod(n, d)});
    std.debug.print("@divExact(20, 5) = {d}\n", .{@divExact(@as(i32, 20), 5)});
}
$ zig run division.zig
unsigned: 17 / 5 = 3, remainder 2
@divTrunc(-17, 5) = -3
@divFloor(-17, 5) = -4
@rem(-17, 5) = -2
@mod(-17, 5) = 3
@divExact(20, 5) = 4
  • @divTrunc(a, b) rounds toward zero. Its matching remainder is @rem, which has the sign of a.
  • @divFloor(a, b) rounds toward negative infinity. Its matching remainder is @mod, which has the sign of b and is therefore never negative for a positive divisor. Use @mod for "day of the week" style wrap-around on values that can go negative.
  • @divExact(a, b) asserts that the division has no remainder and panics if it does. Use it when a remainder would mean a bug.

If the operands happen to be compile-time constants, the compiler lets / through, because there is no ambiguity about a number it can see. With runtime signed values you must use a builtin, and the error message lists them. The same holds for % on signed values: "signed integers and floats must use @rem or @mod".

Division by zero is a panic in the same family as overflow:

$ zig run divzero.zig
thread 12345 panic: division by zero
divzero.zig:6:35: 0x10000abcd in main (divzero)
    std.debug.print("{d}\n", .{10 / d});
                                  ^

4.6 Mixing types: peer type resolution

Arithmetic between two different integer types is allowed when one can hold every value of the other; the result takes the wider type. This is called peer type resolution, and it also explains what happens when a literal meets a typed value.

mixed.zig
const std = @import("std");

pub fn main() void {
    const a: u8 = 200;
    const b: u32 = 100_000;
    const sum = a + b; // peer type resolution: u8 + u32 -> u32
    std.debug.print("{d} is a {s}\n", .{ sum, @typeName(@TypeOf(sum)) });

    const c: i32 = -5;
    const d: u8 = 3;
    const e = c + d; // i32 + u8 -> i32
    std.debug.print("{d} is a {s}\n", .{ e, @typeName(@TypeOf(e)) });

    const lit = a + 1; // u8 + comptime_int -> u8
    std.debug.print("{d} is a {s}\n", .{ lit, @typeName(@TypeOf(lit)) });
}
$ zig run mixed.zig
100200 is a u32
-2 is a i32
201 is a u8

A u8 plus a u32 is a u32. An i32 plus a u8 is an i32, because every u8 value fits in an i32. A u8 plus a literal stays a u8, because the literal takes on the concrete type next to it, and it would be an error if the literal did not fit.

When neither type contains the other, there is no safe answer and the compiler stops:

mixed_bad.zig
const std = @import("std");

pub fn main() void {
    const a: u32 = 5;
    const b: i32 = -3;
    const c = a + b;
    std.debug.print("{d}\n", .{c});
}
$ zig run mixed_bad.zig
mixed_bad.zig:6:19: error: type 'u32' cannot represent integer value '-3'
    const c = a + b;
                  ^

A u32 cannot hold -3 and an i32 cannot hold 4 billion, so u32 + i32 has no type both sides fit. The message here names the literal because b was compile-time known; with runtime values the message is "incompatible types". Either way the fix is the same: convert one side explicitly, which is the next section.

The same rule governs plain assignment. Widening is free; narrowing is refused:

narrowing.zig
const std = @import("std");

pub fn main() void {
    const big: u32 = 300;
    const small: u8 = big;
    std.debug.print("{d}\n", .{small});
}
$ zig run narrowing.zig
narrowing.zig:5:23: error: type 'u8' cannot represent integer value '300'
    const small: u8 = big;
                      ^~~

4.7 Casts that say what they mean

Zig has no single "cast" operator. It has several builtins, each doing one specific thing to the bits, so a reader can see which one you chose and why.

casts.zig
const std = @import("std");

pub fn main() void {
    const wide: u32 = 200;
    const narrow: u8 = @intCast(wide); // fits, ok
    std.debug.print("intCast: {d}\n", .{narrow});

    const big: u32 = 0x1234_5678;
    const low: u8 = @truncate(big); // keeps the low 8 bits
    std.debug.print("truncate: 0x{x}\n", .{low});

    const signed: i8 = -1;
    const bits: u8 = @bitCast(signed); // same 8 bits, read as unsigned
    std.debug.print("bitCast: {d}\n", .{bits});

    const small: u8 = 7;
    const widened = @as(u32, small) * 1_000_000; // widen before multiplying
    std.debug.print("as: {d}\n", .{widened});
}
$ zig run casts.zig
intCast: 200
truncate: 0x78
bitCast: 255
as: 7000000
BuiltinWhat it doesIf the value does not fit
@as(T, x)gives x the type T using the normal coercion rules (widening, literals)compile error
@intCast(x)converts to the target type, keeping the numeric valuepanic in Debug
@truncate(x)keeps only the low bits that fit the targethigh bits are dropped, silently and on purpose
@bitCast(x)reinterprets the same bits as another type of the same sizesizes must match, else compile error

Notice that @intCast, @truncate and @bitCast do not take the target type as an argument. They get it from context: the declared type of the variable they are assigned to, or the parameter type they are passed as. When there is no context, wrap them in @as: @as(u8, @intCast(x)). This looks odd for a week and then becomes natural.

@as(u32, small) * 1_000_000 in the example is the idiom for "widen before multiplying". Written as small * 1_000_000 it would try to compute in u8 and fail at compile time because the literal does not fit. Widening first makes the multiplication happen in u32.

And @intCast is a checked cast: it promises the value fits, and in Debug builds the promise is verified.

intcast_fail.zig
const std = @import("std");

pub fn main() void {
    var wide: u32 = 200;
    wide += 100;
    const narrow: u8 = @intCast(wide);
    std.debug.print("{d}\n", .{narrow});
}
$ zig run intcast_fail.zig
thread 12345 panic: integer does not fit in destination type
intcast_fail.zig:6:24: 0x10000abcd in main (intcast_fail)
    const narrow: u8 = @intCast(wide);
                       ^
Which one? If you want the same number in a different width, @intCast. If you want the low byte of a bigger number, @truncate. If you want to look at the bits of a signed number as unsigned, or a float as an integer, @bitCast. If the compiler would already allow the conversion and you only need to pin the type, @as. If you are casting to make an error go away and cannot say which of these you mean, stop and work out where the types should have matched.

4.8 Bit operators and shifts

Integers are bits, and Zig has the usual operators for working on them directly: & and, | or, ^ exclusive or, ~ not, << shift left, >> shift right.

bits.zig
const std = @import("std");

pub fn main() void {
    const a: u8 = 0b1100_1010;
    const b: u8 = 0b1010_0101;
    std.debug.print("a     = {b:0>8}\n", .{a});
    std.debug.print("b     = {b:0>8}\n", .{b});
    std.debug.print("a & b = {b:0>8}\n", .{a & b});
    std.debug.print("a | b = {b:0>8}\n", .{a | b});
    std.debug.print("a ^ b = {b:0>8}\n", .{a ^ b});
    std.debug.print("~a    = {b:0>8}\n", .{~a});
    std.debug.print("a << 1 = {b:0>8}\n", .{a << 1});
    std.debug.print("a >> 2 = {b:0>8}\n", .{a >> 2});

    const flags: u8 = 0;
    const with_bit_3 = flags | (1 << 3);
    std.debug.print("set bit 3: {b:0>8}, is set? {}\n", .{ with_bit_3, (with_bit_3 & (1 << 3)) != 0 });
}
$ zig run bits.zig
a     = 11001010
b     = 10100101
a & b = 10000000
a | b = 11101111
a ^ b = 01101111
~a    = 00110101
a << 1 = 10010100
a >> 2 = 00110010
set bit 3: 00001000, is set? true

The {b:0>8} format from Chapter 2 prints all eight bits so the columns line up. Shifting left by one doubles a number and drops the top bit; shifting right by one halves it. The last two lines show the classic flag idiom: flags | (1 << n) turns bit n on, flags & ~(1 << n) turns it off, and (flags & (1 << n)) != 0 tests it.

Shifts have a rule that surprises everyone once. The shift amount must be a type just wide enough to express every valid shift for the value's width. A u8 can be shifted by 0 to 7, which needs 3 bits, so the amount must be a u3:

shift_amount.zig
const std = @import("std");

pub fn main() void {
    const value: u8 = 1;
    var amount: u8 = 3;
    amount += 1;
    std.debug.print("{d}\n", .{value << amount});
}
$ zig run shift_amount.zig
shift_amount.zig:7:41: error: expected type 'u3', found 'u8'
    std.debug.print("{d}\n", .{value << amount});
                                        ^~~~~~
shift_amount.zig:7:41: note: unsigned 3-bit int cannot represent all possible unsigned 8-bit values

The reason is that shifting a u8 by 8 or more is undefined in hardware, and the type of the amount makes that impossible to write. Literal amounts are fine because the compiler can see them fit; a runtime amount has to be narrowed:

shift_amount_ok.zig
const std = @import("std");

pub fn main() void {
    const value: u8 = 1;
    var amount: u8 = 3;
    amount += 1;
    const shifted = value << @intCast(amount); // amount becomes a u3
    std.debug.print("{d}\n", .{shifted});
    std.debug.print("{s}\n", .{@typeName(std.math.Log2Int(u8))});
}
$ zig run shift_amount_ok.zig
16
u3

std.math.Log2Int(T) names the correct shift type for any integer type T, which is handy in generic code. For a u32 it is u5, for a u64 it is u6.

4.9 Small helpers

Three builtins and one library function cover most of the remaining integer chores:

minmax.zig
const std = @import("std");

pub fn main() void {
    const fatigue: u8 = 95;
    const add: u8 = 20;
    const capped = @min(100, fatigue + add);
    std.debug.print("capped {d}\n", .{capped});
    const clamped = std.math.clamp(@as(i32, -7), 0, 10);
    std.debug.print("clamped {d}\n", .{clamped});
    std.debug.print("abs {d}\n", .{@abs(@as(i32, -42))});
}
$ zig run minmax.zig
capped 100
clamped 0
abs 42

@min and @max take any number of arguments of any numeric type and use peer type resolution on them. std.math.clamp(x, lo, hi) pins a value into a range. @abs gives the absolute value; note that its result for a signed type is the matching unsigned type, because the absolute value of the most negative i32 does not fit in an i32.

In IRON LEDGER. The game never stores money in a float. Every amount is a CBills = i64, and every multiplier is an integer number of basis points, so that the same campaign replays to the C-bill on any machine (game/src/domain/types.zig): 
/// Integer C-bills. Never floats in financial or rules math.
pub const CBills = i64;
/// Basis points: 10_000 = ×1.
pub const Bp = i64;

pub fn applyBp(amount: CBills, bp: Bp) CBills {
    return @divTrunc(amount * bp, 10_000);
}
A 10 percent markup is applyBp(cost, 11_000), and the rounding direction is written down in the source as @divTrunc. The other two operators from this chapter are all over the code as well. The random number generator seeds its streams with a wrapping multiply that is meant to overflow (game/src/sim/rng.zig): seed ^ (0x9E3779B97F4A7C15 *% (i + 1)). And every "how many are still needed" is a saturating subtraction, such as const gap = n.need -| personnel.manningHave(gs, f.id, n.role); in game/src/econ/contract_market.zig, which is zero when the slot is filled and never a negative count. Chapter 45 follows the money through the whole program.

Exercise 4.1 · Pick a width warm-up

Five constants are declared without types, each with a comment describing its range. Add the smallest integer type that fits each one, choosing signed or unsigned correctly. The tests check bit widths and signedness. Name the file: exercises/04-integers/ex1_widths.zig.

Solution 
//! Chapter 04, exercise 1: pick the smallest integer type that fits.
//! Run with:  zig test ex1_widths.zig
//! Goal: make every test pass by changing only the type annotations.
const std = @import("std");

const armor_points: u8 = 255; // 0..255, never negative
const temperature: i8 = -40; // -40..40
const day_index: u16 = 40_000; // 0..65535
const funds: i64 = -3_000_000_000; // can be hugely negative
const bit_flags: u3 = 0b101; // exactly three flags

test "each value fits and the width is minimal" {
    try std.testing.expectEqual(8, @bitSizeOf(@TypeOf(armor_points)));
    try std.testing.expectEqual(8, @bitSizeOf(@TypeOf(temperature)));
    try std.testing.expectEqual(16, @bitSizeOf(@TypeOf(day_index)));
    try std.testing.expectEqual(64, @bitSizeOf(@TypeOf(funds)));
    try std.testing.expectEqual(3, @bitSizeOf(@TypeOf(bit_flags)));
}

test "signedness" {
    try std.testing.expectEqual(.unsigned, @typeInfo(@TypeOf(armor_points)).int.signedness);
    try std.testing.expectEqual(.signed, @typeInfo(@TypeOf(temperature)).int.signedness);
    try std.testing.expectEqual(.signed, @typeInfo(@TypeOf(funds)).int.signedness);
}

@bitSizeOf and @typeInfo(...).int.signedness are reflection builtins from Chapter 27; here they simply let the tests look at the types you chose. The tests compare against bare literals like 8, which works because @bitSizeOf returns a comptime_int.

Exercise 4.2 · Overflow arithmetic practice

Four small functions use plain operators and the tests make them overflow, so running the file panics. Replace each operator with the wrapping or saturating form that the function's comment calls for. Name the file: exercises/04-integers/ex2_overflow.zig.

Solution 
//! Chapter 04, exercise 2: overflow arithmetic.
//! Run with:  zig test ex2_overflow.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Add `heal` armor points but never exceed 255.
fn repair(armor: u8, heal: u8) u8 {
    return armor +| heal;
}

/// Take `hit` points of damage but never go below zero.
fn damage(armor: u8, hit: u8) u8 {
    return armor -| hit;
}

/// An 8-bit counter that is meant to roll over from 255 back to 0.
fn tick(counter: u8) u8 {
    return counter +% 1;
}

/// Mix a seed the way a hash would: the multiplication is meant to overflow.
fn mix(seed: u64, i: u64) u64 {
    return seed ^ (0x9E3779B97F4A7C15 *% (i + 1));
}

test "repair saturates at 255" {
    try std.testing.expectEqual(@as(u8, 255), repair(250, 10));
    try std.testing.expectEqual(@as(u8, 60), repair(50, 10));
}

test "damage saturates at 0" {
    try std.testing.expectEqual(@as(u8, 0), damage(3, 5));
    try std.testing.expectEqual(@as(u8, 40), damage(50, 10));
}

test "tick wraps" {
    try std.testing.expectEqual(@as(u8, 0), tick(255));
    try std.testing.expectEqual(@as(u8, 8), tick(7));
}

test "mix does not panic and differs per index" {
    const a = mix(3025, 0);
    const b = mix(3025, 1_000_000_000);
    try std.testing.expect(a != b);
}

Armor repair and damage saturate; a rollover counter and a hash mix wrap. The point of having three operators is that the choice is written in the code where a reader can see it, rather than living in your head.

Exercise 4.3 · Basis points and signed division practice

Implement applyBp (scale by basis points, rounding toward zero), weekOf (which week a day index falls in, correct for negative days), and dayOfWeek (0 to 6, never negative). Each needs a different division builtin. Name the file: exercises/04-integers/ex3_division.zig.

Solution 
//! Chapter 04, exercise 3: basis points and signed division.
//! Run with:  zig test ex3_division.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const CBills = i64;
const Bp = i64;

/// Scale `amount` by `bp` basis points (10_000 = x1), rounding toward zero.
fn applyBp(amount: CBills, bp: Bp) CBills {
    return @divTrunc(amount * bp, 10_000);
}

/// Which week (starting at 0) a day index falls in, for negative days too.
/// Day -1 is the last day of week -1, not week 0.
fn weekOf(day: i32) i32 {
    return @divFloor(day, 7);
}

/// Day of the week, 0..6, for negative days too.
fn dayOfWeek(day: i32) i32 {
    return @mod(day, 7);
}

test "applyBp" {
    try std.testing.expectEqual(@as(CBills, 1_100), applyBp(1_000, 11_000));
    try std.testing.expectEqual(@as(CBills, 500), applyBp(1_000, 5_000));
    try std.testing.expectEqual(@as(CBills, -33), applyBp(-100, 3_333));
    try std.testing.expectEqual(@as(CBills, 33), applyBp(100, 3_333));
}

test "weekOf" {
    try std.testing.expectEqual(@as(i32, 0), weekOf(6));
    try std.testing.expectEqual(@as(i32, 1), weekOf(7));
    try std.testing.expectEqual(@as(i32, -1), weekOf(-1));
    try std.testing.expectEqual(@as(i32, -1), weekOf(-7));
    try std.testing.expectEqual(@as(i32, -2), weekOf(-8));
}

test "dayOfWeek" {
    try std.testing.expectEqual(@as(i32, 6), dayOfWeek(6));
    try std.testing.expectEqual(@as(i32, 0), dayOfWeek(7));
    try std.testing.expectEqual(@as(i32, 6), dayOfWeek(-1));
    try std.testing.expectEqual(@as(i32, 0), dayOfWeek(-7));
}

applyBp is the game's own function and uses @divTrunc, so a negative amount rounds toward zero just as a positive one does. weekOf needs @divFloor so that day -1 lands in week -1, and dayOfWeek needs @mod so the result is never negative. Try swapping them and watch which tests fail.

Exercise 4.4 · A flag set practice

Write set, clear, isSet and count for an 8-bit flag set using only bit operators. The bit index parameter is a u3; think about why. Name the file: exercises/04-integers/ex4_bits.zig.

Solution 
//! Chapter 04, exercise 4: a bit-flag set for unit status.
//! Run with:  zig test ex4_bits.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

const damaged: u3 = 0;
const low_ammo: u3 = 1;
const pilot_injured: u3 = 2;

/// Return `flags` with bit `bit` turned on.
fn set(flags: u8, bit: u3) u8 {
    return flags | (@as(u8, 1) << bit);
}

/// Return `flags` with bit `bit` turned off.
fn clear(flags: u8, bit: u3) u8 {
    return flags & ~(@as(u8, 1) << bit);
}

/// Is bit `bit` on in `flags`?
fn isSet(flags: u8, bit: u3) bool {
    return (flags >> bit) & 1 == 1;
}

/// How many bits are on?
fn count(flags: u8) u8 {
    return @popCount(flags);
}

test "set and test" {
    var f: u8 = 0;
    f = set(f, low_ammo);
    try std.testing.expect(isSet(f, low_ammo));
    try std.testing.expect(!isSet(f, damaged));
    try std.testing.expectEqual(@as(u8, 0b010), f);
}

test "clear" {
    var f: u8 = 0b111;
    f = clear(f, pilot_injured);
    try std.testing.expectEqual(@as(u8, 0b011), f);
    f = clear(f, pilot_injured); // clearing twice is harmless
    try std.testing.expectEqual(@as(u8, 0b011), f);
}

test "count" {
    try std.testing.expectEqual(@as(u8, 0), count(0));
    try std.testing.expectEqual(@as(u8, 3), count(0b111));
    try std.testing.expectEqual(@as(u8, 8), count(0xFF));
}

The u3 parameter is exactly the shift-amount type for a u8, so 1 << bit compiles without a cast. The @as(u8, 1) is needed because a bare literal shifted by a runtime amount has no width to shift within. @popCount counts set bits directly; a loop that tests each bit is the other valid answer.

Exercise 4.5 · Four casts challenge

Four functions each need exactly one cast builtin: widen two u8 values before multiplying, take the low byte of a u32, reinterpret an i8 as a u8, and narrow a usize to a u16. Pick @as, @truncate, @bitCast or @intCast for each based on what the doc comment says. Name the file: exercises/04-integers/ex5_casts.zig.

Solution 
//! Chapter 04, exercise 5: casts that mean what they say.
//! Run with:  zig test ex5_casts.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

/// Total tonnage of a lance of `count` units at `each` tons, as a u32.
/// Both inputs are u8, so the product must be widened before multiplying.
fn lanceTonnage(count: u8, each: u8) u32 {
    return @as(u32, count) * @as(u32, each);
}

/// The low byte of a 32-bit colour value (the blue channel of 0xRRGGBB).
fn blue(rgb: u32) u8 {
    return @truncate(rgb);
}

/// Reinterpret the bits of a signed byte as unsigned, without changing them.
fn rawByte(x: i8) u8 {
    return @bitCast(x);
}

/// Convert an index (usize) into a u16 row number. Callers promise it fits.
fn rowNumber(index: usize) u16 {
    return @intCast(index);
}

test "lanceTonnage does not overflow" {
    try std.testing.expectEqual(@as(u32, 400), lanceTonnage(4, 100));
    try std.testing.expectEqual(@as(u32, 65_025), lanceTonnage(255, 255));
}

test "blue keeps the low byte" {
    try std.testing.expectEqual(@as(u8, 0x56), blue(0x123456));
    try std.testing.expectEqual(@as(u8, 0xFF), blue(0x0000FF));
}

test "rawByte keeps the bits" {
    try std.testing.expectEqual(@as(u8, 255), rawByte(-1));
    try std.testing.expectEqual(@as(u8, 128), rawByte(-128));
    try std.testing.expectEqual(@as(u8, 5), rawByte(5));
}

test "rowNumber narrows" {
    try std.testing.expectEqual(@as(u16, 12), rowNumber(12));
    try std.testing.expectEqual(@as(u16, 65_535), rowNumber(65_535));
}

Each cast leaves a different mark. @truncate says "I only want the low bits", @bitCast says "same bits, different label", @intCast says "this fits, check me". Use the wrong one and either the compiler objects (@bitCast between sizes) or a test fails (@intCast where truncation was wanted panics on 0x123456).

Check your understanding

  1. What range does an i8 hold, and a u8?
    Answeri8: -128 to 127. u8: 0 to 255.
  2. What happens when var a: u8 = 250; a += 10; runs in a Debug build?
    AnswerA runtime panic, "integer overflow", with the file and line. In ReleaseFast the result would be undefined.
  3. What do 250 +% 10 and 250 +| 10 give for u8?
    Answer4 (wrapping) and 255 (saturating).
  4. Why is a / b an error for runtime signed integers?
    AnswerRounding toward zero and rounding toward negative infinity give different answers for negatives, so Zig makes you choose @divTrunc, @divFloor, or @divExact.
  5. What is the type of x + y when x: u8 and y: u32? And when x: u32 and y: i32?
    Answeru32 in the first case. The second is a compile error: neither type can hold all values of the other.
  6. What is the difference between @intCast and @truncate?
    Answer@intCast keeps the numeric value and panics in Debug if it does not fit. @truncate keeps only the low bits and never panics.
  7. What type must the shift amount have in x << n when x is a u32?
    Answeru5, because valid shifts are 0 to 31. Use @intCast(n) on a wider runtime value.
  8. Why does IRON LEDGER store money as i64 rather than f64?
    AnswerInteger arithmetic is exact and identical on every machine, so a campaign replays to the C-bill; percentages are done with integer basis points and @divTrunc.
What you learned.
  • Integer types are u/i plus a bit width; usize is the index type; literals accept 0x, 0b, 0o, and underscores.
  • Plain arithmetic panics on overflow in Debug builds; +% wraps and +| saturates, with matching - and * forms.
  • Signed division and remainder need @divTrunc/@rem or @divFloor/@mod; division by zero panics.
  • Mixed types resolve to the wider one when it contains the other; otherwise you cast explicitly.
  • @as coerces, @intCast converts with a check, @truncate drops high bits, @bitCast reinterprets bits; the target type comes from context.
  • Bit operators are & | ^ ~ << >>; a shift amount must be the narrow type that fits every valid shift.
