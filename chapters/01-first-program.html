1. Installing Zig and your first program

In this chapter you will install the Zig 0.16 compiler, write a hello-world program by hand, run it three different ways, and read it line by line until every character in it makes sense. You will also meet the three shapes a Zig main function can take and learn why they differ.

1.1 What Zig is

Zig is a general-purpose programming language in the C tradition. Programs compile to native machine code, run without a virtual machine or a runtime, and manage their own memory. If you have used Python or JavaScript, the biggest change is that there is nothing between your code and the machine: no interpreter, no garbage collector, no exception system. If you have used C, the biggest change is that Zig removes the parts of C that cause most bugs (undefined behaviour is caught in debug builds, integer overflow panics rather than silently wrapping, and the preprocessor is gone) and adds compile-time code execution, a proper module system, built-in tests, and a cross-compiler that can build for any target from any machine.

Three of Zig's slogans will come up again and again in this book, so here they are once:

  • No hidden control flow. When you read a line of Zig, what it does is what it says. A function call is written as a call. Nothing runs behind your back, so there are no exceptions that unwind through your code and no destructors that fire when a scope ends. Cleanup is written explicitly with defer (Chapter 17).
  • No hidden memory allocation. Nothing in the language or the standard library allocates memory unless you hand it an allocator. This is why Zig programs can run on tiny devices and why IRON LEDGER can free its entire campaign with one call.
  • Errors are values. A function that can fail says so in its return type, and the caller must do something about it. The compiler makes forgetting impossible.

Zig is still a young language and its standard library changes between releases. This book is written for version 0.16. Tutorials on the web written for 0.11, 0.13, or 0.14 will show you functions that no longer exist. When in doubt, trust the compiler in front of you, not a blog post.

1.2 Installing the compiler

Zig ships as a single folder containing one executable, zig, and its standard library. There is nothing to configure.

macOS. If you use Homebrew, one command does it:

$ brew install zig

Linux and Windows. Go to https://ziglang.org/download/, download the archive for your platform (for example zig-x86_64-linux-0.16.0.tar.xz or zig-x86_64-windows-0.16.0.zip), unpack it somewhere permanent such as your home folder, and add that folder to your PATH. On Linux that usually means one line in ~/.bashrc or ~/.zshrc:

export PATH="$HOME/zig-x86_64-linux-0.16.0:$PATH"

On Windows, open Edit environment variables for your account and add the unpacked folder to Path. Many Linux distributions also package Zig, but the packaged version is often old; the download from ziglang.org is the reliable route.

Check it. Open a new terminal and ask the compiler for its version:

$ zig version
0.16.0

If you see 0.16.0 (a suffix such as 0.16.0-dev.123 is fine too), you are ready. If you see an older number, you have an old install somewhere on your PATH; find it with which zig on macOS and Linux or where zig on Windows and remove it.

An editor. Any text editor works. VS Code with the Zig Language extension, or any editor that speaks the language server zls, gives you error underlines as you type. The book never depends on an editor feature, so use what you like.

1.3 A folder and a file

Make a folder for the book's programs and go into it. Every command in Part 0 assumes you are inside this folder.

$ mkdir ~/zig-book
$ cd ~/zig-book

Now create a file called hello.zig in that folder and type the following into it. Type it rather than pasting: five lines is short enough, and your fingers will learn the shape of a Zig file.

hello.zig
const std = @import("std");

pub fn main() void {
    std.debug.print("Hello, world!\n", .{});
}

Save the file. The extension .zig matters; the compiler will not look at anything else.

1.4 Running it: zig run

The quickest way to run a single file is zig run:

$ zig run hello.zig
Hello, world!

The first run takes a few seconds while the compiler builds the standard library's pieces that your program uses; later runs are cached and fast. zig run compiles your file into an executable in a cache folder, runs it, and shows you the output. It is the command you will use most in Part 0.

If you mistype something, the compiler tells you where. Delete the second argument to print so the line reads std.debug.print("Hello, world!\n"); and run again:

$ zig run hello.zig
hello.zig:4:14: error: expected 2 argument(s), found 1
    std.debug.print("Hello, world!\n");
    ~~~~~~~~~^~~~~~
<zig>/lib/std/debug.zig:307:5: note: function declared here
pub fn print(comptime fmt: []const u8, args: anytype) void {
~~~~^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Read that from the top. hello.zig:4:14 is the file, the line, and the column. Then the word error: and a sentence. Then the offending line with a marker under the spot. Then a note: showing the declaration of the function you called wrongly, in this case in the standard library's debug.zig. Nearly every Zig error has this shape: location, message, source line, and notes. Put the argument back before going on.

1.5 Building an executable: zig build-exe

zig run hides the executable. When you want a file you can copy somewhere and run later, use zig build-exe:

$ zig build-exe hello.zig
$ ls -la hello
-rwxr-xr-x  1 john  staff  1873176 Sep  9 10:29 hello
$ ./hello
Hello, world!

The compiler wrote a native executable called hello (hello.exe on Windows) into the current folder, and running it prints the same line. It is 1.8 megabytes because a debug build carries symbol tables and safety checks; a release build (zig build-exe -O ReleaseSmall hello.zig) is a few kilobytes. You do not need release builds until much later; the debug build is the one that catches your mistakes.

Real projects with many files use a third command, zig build, driven by a script called build.zig. That is Chapter 31. For now, one file and zig run is all you need.

1.6 One formatter: zig fmt

Zig has exactly one code style, and the compiler ships the tool that enforces it. Write the hello program badly on purpose:

ugly.zig
const std=@import("std");
pub fn main() void{
std.debug.print("Hello, world!\n",.{}); }

It runs fine, because the compiler does not care about whitespace. Now ask zig fmt to fix it in place:

$ zig fmt ugly.zig
ugly.zig
$ cat ugly.zig
const std = @import("std");
pub fn main() void {
    std.debug.print("Hello, world!\n", .{});
}

zig fmt prints the name of each file it changed and rewrites it: four-space indentation, spaces around =, one statement per line, the closing brace on its own line. It will also add a trailing comma to a multi-line list and reflow the list one item per line, which is how the long argument lists in this book got their shape. There is no configuration, so every Zig codebase in the world looks the same, and code review never argues about style.

Two habits worth forming now: run zig fmt . (with a dot, meaning the current folder) before you consider any file finished, and run zig fmt --check . to list files that need formatting without changing them. IRON LEDGER's test suite refuses to pass if zig fmt --check src/ finds anything.

1.7 The anatomy of hello world

Here is the program again, and then one paragraph per line.

const std = @import("std");

pub fn main() void {
    std.debug.print("Hello, world!\n", .{});
}

const std = @import("std"); brings the standard library into the file under the name std. Three things are happening. @import is a builtin function: anything starting with @ is part of the language rather than something defined in a library, and there are about a hundred of them (Appendix A1 lists them). @import("std") returns a value, the whole standard library as one big struct. And const std = … binds that value to a name that cannot be reassigned. You could call it anything, but every Zig file on Earth calls it std, so do that. A file that does not print, read files, or use any library code does not need this line.

pub fn main() void { declares a function. fn introduces it, main is its name, the empty parentheses say it takes no parameters, and void is its return type: it gives nothing back. pub makes the function visible outside this file. The program's entry point must be pub, because the code that starts your program lives in the standard library and has to be able to see main from there. Leave pub off and the compiler says so:

$ zig run hello.zig
<zig>/lib/std/start.zig:697:43: error: 'main' is not marked 'pub'
    const fn_info = @typeInfo(@TypeOf(root.main)).@"fn";
                                      ~~~~^~~~~
hello.zig:3:1: note: declared here
fn main() void {
^~~~~~~~~~~~~~
<zig>/lib/std/start.zig:638:20: note: called inline here
    return callMain(argv[0..argc], env_block);
           ~~~~~~~~^~~~~~~~~~~~~~~~~~~~~~~~~~
<zig>/lib/std/start.zig:590:38: note: called inline here
    std.process.exit(callMainWithArgs(argc, argv, envp));
                     ~~~~~~~~~~~~~~~~^~~~~~~~~~~~~~~~~~

Notice where the error is reported: inside the standard library's start.zig, the file that calls your main, with a note pointing back at your declaration. You will occasionally see errors located in library code like this; the note is the part to read.

std.debug.print("Hello, world!\n", .{}); is a function call. std.debug is a namespace inside the standard library, print is a function in it, and it takes two arguments: a format string and a list of values to substitute into it. The format string here has no placeholders, so the list is empty. The \n at the end is an escape sequence meaning a newline; without it the next thing printed would land on the same line. The semicolon ends the statement, as in C or JavaScript, and it is not optional.

.{} is the piece that puzzles everyone. It is an empty anonymous struct literal, which is Zig's way of writing "a bundle of values whose type the callee will figure out". Because print may be given any number of values of any type, it cannot declare a fixed parameter list, so it takes one parameter that is a bundle. With no values the bundle is .{}; with one value it is .{name}; with two, .{ a, b }. You will write .{} thousands of times, and Chapter 2 is entirely about what goes inside it.

Finally the closing brace ends the function body. Zig uses braces for blocks and does not care about indentation; zig fmt cares for you.

Try it. Add a second line to main that prints your name using a placeholder: std.debug.print("Welcome, {s}. The company is yours.\n", .{"Commander"});. Run it. Then remove the \n from the first line and run it again to see the two lines collide.
name.zig
const std = @import("std");

pub fn main() void {
    const name = "Commander";
    std.debug.print("Welcome, {s}. The company is yours.\n", .{name});
}
$ zig run name.zig
Welcome, Commander. The company is yours.

1.8 Three shapes of main

The main you wrote returns void and takes nothing. That is the simplest form, and it is enough for every program in Part 0. But you will see two other forms in real code, including in IRON LEDGER, so here they are.

Form 1: pub fn main() void. No parameters, cannot fail. The program exits with status 0 when main returns. Use it for small programs that only compute and print.

Form 2: pub fn main() !void. The exclamation mark makes the return type an error union: the function returns either nothing or an error. This lets you write try inside main to propagate failures, which Chapter 16 covers properly. If an error escapes from main, the program prints it and exits with status 1:

hello_err.zig
const std = @import("std");

pub fn main() !void {
    std.debug.print("about to fail\n", .{});
    return error.SomethingWentWrong;
}
$ zig run hello_err.zig
about to fail
error: SomethingWentWrong
hello_err.zig:5:5: 0x10000abcd in main (hello_err)
    return error.SomethingWentWrong;
    ^

The first line is your print. Then the runtime reports the error by name and shows where it was returned. The last line of the transcript, cut here, is a stack trace into the standard library. Try it and check the exit status: echo $? prints 1.

Form 3: pub fn main(init: std.process.Init) !void. This is new in 0.16 and it is the form every real program uses. The single parameter, conventionally called init, is a struct that the runtime fills in before calling you. It carries an allocator (init.gpa), an I/O context (init.io), the command-line arguments, and the environment. Anything that touches the outside world, which means writing to standard output, reading a file, or asking the time, needs the init.io value. Here is the standard-output version of hello world:

hello_stdout.zig
const std = @import("std");

pub fn main(init: std.process.Init) !void {
    var buf: [1024]u8 = undefined;
    var w = std.Io.File.stdout().writer(init.io, &buf);
    const out = &w.interface;
    try out.print("Hello from stdout, {d}\n", .{42});
    try out.flush();
}
$ zig run hello_stdout.zig
Hello from stdout, 42

Do not worry about the middle four lines yet. Chapter 2 takes them apart, and Part 4 explains the design behind std.Io. What matters now is the pattern: a program that only needs to show you something uses std.debug.print and Form 1; a program that produces output meant to be captured, piped, or saved uses a real writer and Form 3. IRON LEDGER's main is Form 3.

Trap: old tutorials. Code written for Zig 0.13 or 0.14 obtains standard output with std.io.getStdOut().writer(). That function does not exist in 0.16 and the compiler will tell you no field named 'getStdOut'. When a snippet from the web will not build, check its Zig version before you check your typing. Appendix A3 lists the old and new forms side by side.

1.9 What just happened, in order

It helps to have a picture of the pipeline, because the error messages refer to its stages. When you type zig run hello.zig:

  1. The compiler parses hello.zig into a tree. Syntax errors (a missing semicolon, an unbalanced brace) stop it here.
  2. It analyses the tree, starting from main and following every reference. Only code that is reachable from main gets checked, which is why a typo in a function you never call can go unnoticed until you call it. Type errors, unused variables, and missing arguments stop it here.
  3. It generates machine code for your target, links it with the pieces of the standard library you used, and writes an executable to its cache.
  4. It runs that executable, passing through any arguments you gave after the file name, and shows you its output.

When something goes wrong at stage 1 or 2, you get a compile error and no program runs. When it goes wrong at stage 4, you get a runtime panic with a stack trace, which you will see for the first time in Chapter 4. Keeping the two apart is the beginning of reading Zig's messages well.

In IRON LEDGER. The game's entry point is game/src/main.zig, and its main is Form 3: pub fn main(init: std.process.Init) !void. The first thing it does is build the game state from the allocator the runtime handed it, then it walks the command-line arguments looking for flags such as --tui and --repl: 
pub fn main(init: std.process.Init) !void {
    var gs = game.state.GameState.init(init.gpa, .{ .seed = 3025 });
    defer gs.deinit();

    var args = std.process.Args.Iterator.init(init.minimal.args);
    _ = args.next(); // exe name
    var repl = false;
    var tui = false;
    while (args.next()) |arg| {
        if (std.mem.eql(u8, arg, "--repl")) repl = true;
        if (std.mem.eql(u8, arg, "--tui")) tui = true;
        // …
    }
Every piece of that will be familiar by the end of Part 1: defer in Chapter 17, the while … |arg| capture in Chapter 15, std.mem.eql in Chapter 11. The file also starts with a //! comment, a doc comment for the whole file; the game's house rule is that every file opens with one.

Exercises

Exercise 1.1 · Hello, by hand warm-up

Without looking at the chapter, write a complete program that prints Hello, world! and a newline, then run it with zig run and format it with zig fmt. The starter file contains only the import line. Name the file: exercises/01-first-program/ex1_hello.zig.

Solution 
//! Chapter 01, exercise 1: hello, world by hand.
//! Run with:  zig run ex1_hello.zig
//! Expected output (on stderr):
//!   Hello, world!
const std = @import("std");

pub fn main() void {
    std.debug.print("Hello, world!\n", .{});
}

Four things must be present: the pub, the name main, a return type, and the empty argument bundle .{}. Forget any one of them and the compiler names the problem; the missing-pub and missing-argument errors are both shown in this chapter.

Exercise 1.2 · Three lines, three values warm-up

The starter declares a company name, a commander name, and a unit count. Print them on three lines exactly as the header comment shows, using {s} for text and {d} for the number. The file does not compile until every constant is used. Name the file: exercises/01-first-program/ex2_roster.zig.

Solution 
//! Chapter 01, exercise 2: three lines, one placeholder each.
//! Run with:  zig run ex2_roster.zig
//! Expected output (on stderr):
//!   Company: Grey Death Legion
//!   Commander: Carlyle
//!   Units: 4
const std = @import("std");

pub fn main() void {
    const company = "Grey Death Legion";
    const commander = "Carlyle";
    const units: u32 = 4;
    std.debug.print("Company: {s}\n", .{company});
    std.debug.print("Commander: {s}\n", .{commander});
    std.debug.print("Units: {d}\n", .{units});
}

Each print call takes one placeholder and a one-element bundle .{value}. The reason the starter refuses to compile is Zig's unused-constant rule, which Chapter 3 explains: declaring a value and never using it is an error, not a warning.

Exercise 1.3 · The stdout version practice

The starter is a Form 3 program that writes to standard output, but when you run it nothing appears. Work out why (the chapter mentions it), fix it, and add a second line that prints The answer is 42. using a {d} placeholder. Confirm the output really goes to stdout by running zig run ex3_stdout.zig 2>/dev/null, which hides stderr. Name the file: exercises/01-first-program/ex3_stdout.zig.

Solution 
//! Chapter 01, exercise 3: the same greeting, written to stdout.
//! Run with:  zig run ex3_stdout.zig
//! Expected output (on stdout, so `zig run ex3_stdout.zig 2>/dev/null` still shows it):
//!   Hello from stdout!
//!   The answer is 42.
const std = @import("std");

pub fn main(init: std.process.Init) !void {
    var buf: [1024]u8 = undefined;
    var w = std.Io.File.stdout().writer(init.io, &buf);
    const out = &w.interface;
    try out.print("Hello from stdout!\n", .{});
    try out.print("The answer is {d}.\n", .{42});
    try out.flush();
}

The missing piece is try out.flush();. The writer collects text in the 1024-byte buffer you gave it and only hands it to the operating system when the buffer fills or when you flush. A program that returns from main without flushing throws away whatever is still in the buffer. std.debug.print has no buffer, which is why it never needs a flush; Chapter 2 goes into the trade-off.

Check your understanding

  1. What does zig run hello.zig do that zig build-exe hello.zig does not?
    AnswerIt runs the program after compiling it, and it keeps the executable in a cache folder instead of writing it next to your source file. build-exe only compiles, and leaves the executable in the current folder.
  2. Why must main be marked pub?
    AnswerThe code that starts your program lives in the standard library (start.zig) and calls main from outside your file. Without pub the function is private to the file and the library cannot see it.
  3. What is .{} in std.debug.print("hi\n", .{});?
    AnswerAn empty anonymous struct literal: the bundle of values to substitute into the format string. It is empty because the string has no placeholders.
  4. What does the ! in pub fn main() !void mean?
    AnswerThe return type is an error union: main returns either nothing or an error. If an error escapes, the runtime prints its name and exits with status 1.
  5. Which form of main does a program need if it wants to write to standard output, and why?
    Answerpub fn main(init: std.process.Init) !void. Writing to stdout in 0.16 needs the I/O context init.io, which only arrives through that parameter, and the try on the write and flush needs the ! return type.
  6. What does zig fmt --check . do?
    AnswerIt lists every file in the current folder that is not formatted the standard way and exits with an error if there are any, without modifying anything. Without --check, zig fmt rewrites the files.
What you learned.
  • Zig is a compiled systems language with no hidden control flow, no hidden allocation, and errors as values; this book is for version 0.16.
  • Install with brew install zig on macOS or the archive from ziglang.org elsewhere; confirm with zig version.
  • zig run compiles and runs one file; zig build-exe writes an executable; zig fmt is the single formatter.
  • Hello world is an import, a pub fn main, and one std.debug.print call whose second argument is the value bundle .{}.
  • main comes in three shapes: void, !void, and (init: std.process.Init) !void; the last one is what real programs use.
  • A compile error names file, line, column, message, and notes; learn to read it top to bottom.
