28. ZON: data files as code

In this chapter you will move a table of numbers out of your source and into a .zon file, import it with a declared type so the compiler checks every entry, and see exactly what happens when the file is wrong. You will also parse ZON at run time with std.zon.parse, write it back with std.zon.stringify, and read the build.zig.zon that every project carries.

28.1 What ZON is

ZON stands for Zig Object Notation. It is not a new language: it is the subset of Zig you already use to write literals. An anonymous struct literal .{ .a = 1 }, an anonymous list .{ 1, 2, 3 }, numbers, strings, booleans, null, and enum literals such as .common. A ZON file contains exactly one such value and nothing else: no const, no functions, no expressions like 2 + 3, no references to other names. Comments are allowed.

Here is a small table of balance knobs in that form. Save it as tuning.zon.

tuning.zon

// Tuning knobs. Typed against `Tuning` in tuning.zig at compile time.
.{
    .person = .{
        .fatigue_tired = 30,
        .exhausted_fatigue = 70,
        .turnover_target = 3, // 2d6 < 3 + flags
    },
    .market = .{
        .fab_cost_bp = 12_000,
        .fab_days = 14,
    },
}

If you have used JSON, the mapping is direct: braces become .{ }, keys become .name =, and you gain three things JSON lacks: comments, numeric underscores like 12_000, and enum literals. If you have used TOML or YAML, ZON is stricter and smaller; there is one way to write everything, and zig fmt formats it.

28.2 Importing a ZON file with a declared type

The remarkable part is how you load it. You do not open the file at run time. You @import it, the same builtin you use for other source files, and assign the result to a constant with an explicit type. The compiler reads the file while compiling, treats it as a literal, and coerces it to that type.

typed.zig

const std = @import("std");

pub const Tuning = struct {
    person: struct { fatigue_tired: u8, exhausted_fatigue: u8, turnover_target: u8 },
    market: struct { fab_cost_bp: u32, fab_days: u32 },
};

pub const t: Tuning = @import("tuning.zon");

pub fn main() void {
    std.debug.print("tired at {d}, exhausted at {d}\n", .{ t.person.fatigue_tired, t.person.exhausted_fatigue });
    std.debug.print("fab: {d} bp over {d} days\n", .{ t.market.fab_cost_bp, t.market.fab_days });
}
$ zig run typed.zig
tired at 30, exhausted at 70
fab: 12000 bp over 14 days

Yes, that is plain zig run on a single file with the .zon sitting next to it. No build script is needed as long as the data file lives in the same directory as the source, or below it. The constant t is an ordinary Tuning value that exists in the compiled binary; reading t.market.fab_days costs the same as reading any other constant, and there is nothing to parse when the program starts.

The type annotation is what makes it safe. Without : Tuning, the import would still work, but the value would be an anonymous struct and any typo in the file would only surface where a field is used, if at all. With the annotation, the whole file is checked against the whole struct at the point of import, once, for every build.

28.3 What the compiler catches

Let us break the file on purpose. First a misspelled field name (turnover_targt):

$ zig run bad.zig
bad.zon:2:82: error: unexpected field 'turnover_targt'
    .person = .{ .fatigue_tired = 30, .exhausted_fatigue = 70, .turnover_targt = 3 },
                                                                                 ^
bad.zig:8:31: note: imported here
pub const t: Tuning = @import("bad.zon");
                              ^~~~~~~~~

Then a value that does not fit its field (exhausted_fatigue is a u8) and a string where a number belongs:

$ zig run bad2.zig
bad2.zon:2:60: error: type 'u8' cannot represent integer value '300'
    .person = .{ .fatigue_tired = 30, .exhausted_fatigue = 300, .turnover_target = 3 },
                                                           ^~~
bad2.zig:8:31: note: imported here
pub const t: Tuning = @import("bad2.zon");

Each error points at the line and column in the data file, with a note showing which import pulled it in. A missing field without a default is reported the same way. Compare this with a JSON config loaded at start-up: the typo is discovered by a player, perhaps hours into a campaign, when the game reads a field that is not there. Here it is discovered by the person who made the typo, seconds later, before the program even links.

The first error stops the file. The compiler reports the first problem in a ZON file and stops. If your file has three mistakes you will fix them one at a time. That is still far better than finding them one at a time at run time.

28.4 Lists of records, with defaults

Tables are usually lists of rows. In ZON a list is an anonymous tuple, .{ row, row, row }, and it coerces to a slice of the row type. Struct fields with default values need not be written in every row, which keeps a catalogue readable.

designs.zon

.{
    .{ .key = "SHD-2H", .name = "Shadow Hawk", .tonnage = 55, .rarity = .common, .jump_mp = 3 },
    .{ .key = "AS7-D", .name = "Atlas", .tonnage = 100, .rarity = .rare },
    .{ .key = "LCT-1V", .name = "Locust", .tonnage = 20, .rarity = .common, .walk_mp = 8 },
}

designs.zig

const std = @import("std");

pub const Rarity = enum { common, uncommon, rare };
pub const Design = struct {
    key: []const u8,
    name: []const u8,
    tonnage: u32,
    rarity: Rarity,
    walk_mp: u8 = 4,
    jump_mp: u8 = 0,
};

pub const catalog: []const Design = @import("designs.zon");

pub fn find(key: []const u8) ?Design {
    for (catalog) |d| if (std.mem.eql(u8, d.key, key)) return d;
    return null;
}

pub fn main() void {
    std.debug.print("{d} designs\n", .{catalog.len});
    for (catalog) |d| {
        std.debug.print("{s:<8} {s:<12} {d:>3}t walk {d} jump {d} {s}\n", .{ d.key, d.name, d.tonnage, d.walk_mp, d.jump_mp, @tagName(d.rarity) });
    }
    if (find("AS7-D")) |atlas| std.debug.print("Atlas weighs {d}\n", .{atlas.tonnage});
}

test "every key is unique" {
    for (catalog, 0..) |a, i| {
        for (catalog[i + 1 ..]) |b| {
            try std.testing.expect(!std.mem.eql(u8, a.key, b.key));
        }
    }
}

test "tonnage is a multiple of 5 between 20 and 100" {
    for (catalog) |d| {
        try std.testing.expect(d.tonnage >= 20 and d.tonnage <= 100 and d.tonnage % 5 == 0);
    }
}
$ zig run designs.zig
3 designs
SHD-2H   Shadow Hawk   55t walk 4 jump 3 common
AS7-D    Atlas        100t walk 4 jump 0 rare
LCT-1V   Locust        20t walk 8 jump 0 common
Atlas weighs 100
$ zig test designs.zig
1/2 designs.test.every key is unique...OK
2/2 designs.test.tonnage is a multiple of 5 between 20 and 100...OK
All 2 tests passed.

The declared type is []const Design, so the tuple of three anonymous structs becomes a slice of three Design values, and the Atlas row gets walk_mp = 4 and jump_mp = 0 from the defaults. The enum literal .rare is checked against Rarity; write .legendary and the build fails.

The two tests show the second half of the pattern. The type system checks shape: field names, field types, enum tags. It cannot check meaning: that keys are unique, that tonnage is in the BattleTech range. So you write tests over the imported table, and because the table is a compile-time constant, those tests run on the real data every time. IRON LEDGER's data tests work this way: every loadout part must exist in the parts catalogue, every random-assignment entry must name a real design.

28.5 Where the file may live

@import resolves paths relative to the importing file, and subdirectories are fine: @import("data/tables/tuning.zon") works with zig run. What does not work is reaching upward. A file outside the directory tree of the root source file is refused:

$ cd inner && zig run outside.zig
outside.zig:8:31: error: import of file outside module path
pub const t: Tuning = @import("../tuning.zon");
                              ^~~~~~~~~~~~~~~

The rule is the same for .zig files: a module is a directory tree with one root, and imports cannot escape it. Projects that keep data beside the source tree (data/ next to src/, as IRON LEDGER does) solve this in build.zig: addAnonymousImport binds a file anywhere on disk to a name, and the code writes @import("tuning_zon"). Section 28.9 shows the minimum version and Chapter 31 explains the build script in full.

28.6 Parsing ZON at run time

Sometimes the data is not known when you compile: a user's settings file, a save game, a mod dropped into a folder. For that there is std.zon.parse. It takes the target type, an allocator, the text, an optional diagnostics object and an options struct, and returns a value of the type or error.ParseZon.

The text must be sentinel-terminated ([:0]const u8), because the parser is the compiler's own tokenizer and it wants a zero byte at the end. String literals already have one; text read from a file needs allocator.dupeZ. There are two entry points:

  • std.zon.parse.fromSlice(T, gpa, source, diag, options) for types that contain no pointers (plain numbers, enums, booleans, fixed arrays, nested structs of those). The result needs no freeing.
  • std.zon.parse.fromSliceAlloc(T, gpa, source, diag, options) for types with slices or strings. Free the result with std.zon.parse.free(gpa, value), or simpler, parse into an arena and free everything at once.

runtime_nopointer.zig

const std = @import("std");

const Point = struct { x: i32, y: i32 };

pub fn main(init: std.process.Init) !void {
    const p = try std.zon.parse.fromSlice(Point, init.gpa, ".{ .x = 3, .y = -4 }", null, .{});
    std.debug.print("({d}, {d})\n", .{ p.x, p.y });
}
$ zig run runtime_nopointer.zig
(3, -4)

runtime.zig

const std = @import("std");

const Config = struct {
    seed: u64 = 3025,
    difficulty: enum { easy, normal, hard } = .normal,
    autosave: bool = true,
    company_name: []const u8 = "Unnamed",
};

pub fn main(init: std.process.Init) !void {
    const gpa = init.gpa;
    const source: [:0]const u8 =
        \\.{ .seed = 42, .difficulty = .hard, .company_name = "Kell Hounds" }
    ;
    var diag: std.zon.parse.Diagnostics = .{};
    defer diag.deinit(gpa);
    const cfg = std.zon.parse.fromSliceAlloc(Config, gpa, source, &diag, .{}) catch |err| {
        std.debug.print("could not parse config: {s}\n{f}", .{ @errorName(err), diag });
        return err;
    };
    defer std.zon.parse.free(gpa, cfg);
    std.debug.print("seed={d} difficulty={s} autosave={} name={s}\n", .{ cfg.seed, @tagName(cfg.difficulty), cfg.autosave, cfg.company_name });

    const broken: [:0]const u8 = ".{ .seed = 42, .difficulty = .impossible }";
    var diag2: std.zon.parse.Diagnostics = .{};
    defer diag2.deinit(gpa);
    _ = std.zon.parse.fromSliceAlloc(Config, gpa, broken, &diag2, .{}) catch |err| {
        std.debug.print("second parse failed: {s}\n{f}", .{ @errorName(err), diag2 });
    };
}
$ zig run runtime.zig
seed=42 difficulty=hard autosave=true name=Kell Hounds
second parse failed: ParseZon
1:31: error: unexpected enum literal 'impossible'
1:31: note: supported: 'easy', 'normal', 'hard'

Three things to notice. Defaults in the struct apply to fields the text omits, exactly as with @import. The Diagnostics value, printed with the {f} specifier, produces the same quality of message the compiler gives, including the list of accepted enum tags. And options is a struct with two useful fields: ignore_unknown_fields (default false, so a typo is an error) and free_on_error.

Use an arena for parsed data. A parsed Config whose company_name came from the text owns heap memory, while one that kept the default points at a string literal. std.zon.parse.free knows the difference in practice, but the simplest robust habit is to parse with an ArenaAllocator and deinit the arena when you are done, as Exercise 28.2 does.

28.7 @embedFile: bytes in the binary

Between "checked at compile time" and "parsed at run time" there is a third option. @embedFile("path") reads a file while compiling and gives you its bytes as a constant, sentinel-terminated string. The file is baked into the executable, so nothing needs to exist on disk when the program runs, but the bytes are not interpreted: you parse them yourself.

embed.zig

const std = @import("std");

const Point = struct { x: i32, y: i32 };
const raw = @embedFile("point.zon");

pub fn main(init: std.process.Init) !void {
    std.debug.print("embedded {d} bytes: {s}", .{ raw.len, raw });
    const p = try std.zon.parse.fromSlice(Point, init.gpa, raw, null, .{});
    std.debug.print("parsed ({d}, {d})\n", .{ p.x, p.y });
    const typed: Point = @import("point.zon");
    std.debug.print("imported ({d}, {d})\n", .{ typed.x, typed.y });
}
$ zig run embed.zig
embedded 20 bytes: .{ .x = 7, .y = 9 }
parsed (7, 9)
imported (7, 9)

The same file is used both ways so you can see the difference: @embedFile gives raw text that fromSlice then parses (its sentinel makes it directly acceptable), while @import gives a finished value. Use @embedFile for things that are not ZON at all, such as a test image or a shader; IRON LEDGER embeds a small PNG for its decoder's tests.

28.8 Writing ZON

The reverse direction is std.zon.stringify.serialize(value, options, writer). It walks the value with reflection (Chapter 27) and writes valid ZON to any *std.Io.Writer. The default output is formatted the way zig fmt would format it; .{ .whitespace = false } gives one compact line.

stringify.zig

const std = @import("std");

const Save = struct { day: u32, funds: i64, name: []const u8, roster: []const u8 };

pub fn main(init: std.process.Init) !void {
    var buf: [512]u8 = undefined;
    var w = std.Io.File.stdout().writer(init.io, &buf);
    const s = Save{ .day = 12, .funds = -3_500, .name = "Kell Hounds", .roster = "ABC" };
    try std.zon.stringify.serialize(s, .{}, &w.interface);
    try w.interface.writeAll("\n");
    try w.interface.flush();
}
$ zig run stringify.zig
.{
    .day = 12,
    .funds = -3500,
    .name = "Kell Hounds",
    .roster = "ABC",
}

Because the output is a legal ZON literal, it can be read back by std.zon.parse at run time or even by @import if you commit it as a source file. Exercise 28.3 makes a round trip.

28.9 build.zig.zon: the file every project has

You have already met one ZON file without being told: build.zig.zon, which zig init generates beside build.zig. It is the package manifest, and it is parsed by the compiler with a declared type just like your tuning table. Trimmed of its comments, the 0.16 version looks like this:

.{
    .name = .init,
    .version = "0.0.0",
    .fingerprint = 0xc674e47417e230d0, // Changing this has security and trust implications.
    .minimum_zig_version = "0.16.0",
    .dependencies = .{
        // .example = .{ .url = "https://…/foo.tar.gz", .hash = "…" },
        // .local = .{ .path = "foo" },
    },
    .paths = .{
        "build.zig",
        "build.zig.zon",
        "src",
    },
}
  • .name is an enum literal, not a string: the package's identifier.
  • .fingerprint is generated once and never changed; it is how the toolchain recognises a package across versions.
  • .dependencies maps names to either a url plus hash or a local path. zig fetch --save <url> fills entries in for you.
  • .paths lists what belongs to the package when it is fetched by someone else.

Everything you learned about ZON applies: comments are fine, a misspelled key is an error with a line number, and the file is checked before any build step runs.

28.10 Data beside the source: a first look at addAnonymousImport

To import a file from outside the source tree, build.zig can name it. Here is the smallest project that does so. The full meaning of every line waits for Chapter 31; for now, focus on the two lines marked with the import name.

proj/build.zig

const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    // -Ddata=<dir> overlays data/tuning.zon from another directory (a "mod").
    const data_dir = b.option([]const u8, "data", "Directory overlaying data/*.zon");

    const exe = b.addExecutable(.{
        .name = "tables",
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/main.zig"),
            .target = target,
            .optimize = optimize,
        }),
    });

    var tuning_path: std.Build.LazyPath = b.path("data/tuning.zon");
    if (data_dir) |dir| tuning_path = .{ .cwd_relative = b.pathJoin(&.{ dir, "tuning.zon" }) };
    exe.root_module.addAnonymousImport("tuning_zon", .{ .root_source_file = tuning_path });

    b.installArtifact(exe);

    const run_cmd = b.addRunArtifact(exe);
    const run_step = b.step("run", "Run the app");
    run_step.dependOn(&run_cmd.step);

    const tests = b.addTest(.{ .root_module = exe.root_module });
    const test_step = b.step("test", "Run tests");
    test_step.dependOn(&b.addRunArtifact(tests).step);
}

proj/src/main.zig

const std = @import("std");

pub const Tuning = struct {
    person: struct { fatigue_tired: u8, exhausted_fatigue: u8, turnover_target: u8 },
    market: struct { fab_cost_bp: u32, fab_days: u32 },
};

/// The live table: whichever file build.zig bound to the name "tuning_zon".
pub const t: Tuning = @import("tuning_zon");

pub fn main() void {
    std.debug.print("fab_days = {d}\n", .{t.market.fab_days});
}

test "fab days is at least a week" {
    try std.testing.expect(t.market.fab_days >= 7);
}
$ zig build run
fab_days = 14
$ zig build run -Ddata=mymod
fab_days = 7
$ zig build test --summary all
Build Summary: 3/3 steps succeeded; 1/1 tests passed
test success
+- run test 1 pass (1 total) 229ms MaxRSS:2M
   +- compile test Debug native success 979ms MaxRSS:263M

The source file says @import("tuning_zon"), a name with no path and no extension. The build script decides which file that name means: data/tuning.zon normally, or mymod/tuning.zon when the user passes -Ddata=mymod. The simulation code neither knows nor cares. This is the mechanism behind IRON LEDGER's mod support, and it is why the modding guide tells you to run zig build test -Ddata=mymod: the same data tests run against your replacement tables.

28.11 Why compile-time data beats JSON for game tables

It is worth stating the trade-off plainly, because "just use JSON" is the default in most ecosystems.

JSON parsed at start-upZON imported at compile time
Typos found when the field is read, maybe neverTypos found at the import, with a line number
Needs a parser, an allocator and error handling at run timeNo run-time cost at all; the value is a constant
Types are whatever the parser guesses (every number is a double)Types are whatever your struct says (u8, CBills, an enum)
Comments are not allowedComments are allowed
Data can change without rebuildingChanging data means rebuilding
Tests need fixtures that mirror the real fileTests run over the real table

The last row of the left column is the one real advantage of run-time data, and it is exactly why the game keeps both tools: balance tables that ship with the binary are ZON imported at compile time, while player settings and mod overlays that must vary after the build go through std.zon.parse or the build option. Choose by asking "who changes this, and when?"

In IRON LEDGER. Every table the simulation reads is a ZON file under game/data/, bound by name in build.zig and imported with a declared type. The tuning table opens like this (game/data/tables/tuning.zon): 
// Tuning knobs. Typed against domain/tuning.zig `Tuning` at comptime.
.{
    .hq = .{
        .influence_ly = .{ .field = 15, .regional = 60, .brigade = 90 },
        .paperwork_base_days = 21,
        .upgrade_cost_per_level = .{ .mek_bay = 800_000, .warehouse = 400_000, /* … */ },
    },
    .person = .{
        .fatigue_tired = 30,
        .exhausted_fatigue = 70,
        .turnover_target = 3, // 2d6 < 3 + flags
        // …
    },
}
and game/src/domain/tuning.zig gives it a shape and a name: pub const t: Tuning = @import("tuning_zon");. The design catalogue works the same way, one struct per row with defaults so a vehicle need not state mek-only fields; a row of game/data/chassis.zon reads .{ .key = "SHD-2H", .name = "Shadow Hawk", .tonnage = 55, .bv = 1064, .cost = 4_701_800, .rarity = .common, .walk_mp = 5, .jump_mp = 3, … }. The 97 designs, 234 systems and every knob are type-checked on every build, and the data tests in the same files check what types cannot.

Exercise 28.1 · A typed design catalogue warm-up

A small project with src/designs.zon next to src/designs.zig. Fill in weightClass, find and countByRarity and make the data tests pass with zig build test inside exercises/28-zon/ex1_designs/. (It is a directory exercise because the checker needs the .zon beside the source.)

Solution

src/designs.zig

//! Chapter 28, exercise 1: a typed design catalogue from a .zon file.
//! Run with:  zig build test   (inside exercises/28-zon/ex1_designs/)
//! Goal: fill in `Design`, import the catalogue, and make every test pass.
const std = @import("std");

pub const Rarity = enum { common, uncommon, rare };

pub const Design = struct {
    key: []const u8,
    name: []const u8,
    tonnage: u32,
    rarity: Rarity,
    walk_mp: u8 = 4,
    jump_mp: u8 = 0,

    pub fn weightClass(self: Design) []const u8 {
        if (self.tonnage <= 35) return "light";
        if (self.tonnage <= 55) return "medium";
        if (self.tonnage <= 75) return "heavy";
        return "assault";
    }
};

pub const catalog: []const Design = @import("designs.zon");

pub fn find(key: []const u8) ?Design {
    for (catalog) |d| if (std.mem.eql(u8, d.key, key)) return d;
    return null;
}

pub fn countByRarity(r: Rarity) usize {
    var n: usize = 0;
    for (catalog) |d| if (d.rarity == r) {
        n += 1;
    };
    return n;
}

test "catalogue has four designs" {
    try std.testing.expectEqual(@as(usize, 4), catalog.len);
}

test "defaults fill in unspecified fields" {
    const whm = find("WHM-6R").?;
    try std.testing.expectEqual(@as(u8, 4), whm.walk_mp);
    try std.testing.expectEqual(@as(u8, 0), whm.jump_mp);
    try std.testing.expectEqual(@as(u8, 8), find("LCT-1V").?.walk_mp);
}

test "find and weight classes" {
    try std.testing.expectEqualStrings("assault", find("AS7-D").?.weightClass());
    try std.testing.expectEqualStrings("medium", find("SHD-2H").?.weightClass());
    try std.testing.expect(find("nope") == null);
}

test "rarity counts" {
    try std.testing.expectEqual(@as(usize, 2), countByRarity(.common));
    try std.testing.expectEqual(@as(usize, 1), countByRarity(.rare));
}

test "every key is unique and every tonnage is a multiple of 5" {
    for (catalog, 0..) |a, i| {
        try std.testing.expect(a.tonnage % 5 == 0);
        for (catalog[i + 1 ..]) |b| try std.testing.expect(!std.mem.eql(u8, a.key, b.key));
    }
}

The .zon file has rows with and without walk_mp; the defaults in Design fill the gaps, which the second test checks.

Exercise 28.2 · Parse a config at run time practice

Write load(arena, source) that parses a Config with std.zon.parse.fromSliceAlloc, printing diagnostics on failure. File: exercises/28-zon/ex2_runtime.zig.

Solution 
//! Chapter 28, exercise 2: parse ZON at run time with std.zon.parse.
//! Run with:  zig test ex2_runtime.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

pub const Difficulty = enum { easy, normal, hard };

pub const Config = struct {
    seed: u64 = 3025,
    difficulty: Difficulty = .normal,
    autosave: bool = true,
    company_name: []const u8 = "Unnamed Company",
};

/// Parse `source` into a Config. Strings inside the result live in `arena`,
/// so the caller frees everything by resetting the arena. On a parse error,
/// print the diagnostics to stderr and return error.ParseZon.
pub fn load(arena: std.mem.Allocator, source: [:0]const u8) !Config {
    var diag: std.zon.parse.Diagnostics = .{};
    defer diag.deinit(arena);
    return std.zon.parse.fromSliceAlloc(Config, arena, source, &diag, .{}) catch |err| {
        std.debug.print("config error: {f}", .{diag});
        return err;
    };
}

test "full config" {
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    const cfg = try load(arena.allocator(),
        \\.{ .seed = 42, .difficulty = .hard, .autosave = false, .company_name = "Kell Hounds" }
    );
    try std.testing.expectEqual(@as(u64, 42), cfg.seed);
    try std.testing.expectEqual(Difficulty.hard, cfg.difficulty);
    try std.testing.expect(!cfg.autosave);
    try std.testing.expectEqualStrings("Kell Hounds", cfg.company_name);
}

test "defaults apply to missing fields" {
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    const cfg = try load(arena.allocator(), ".{ .seed = 7 }");
    try std.testing.expectEqual(@as(u64, 7), cfg.seed);
    try std.testing.expectEqual(Difficulty.normal, cfg.difficulty);
    try std.testing.expectEqualStrings("Unnamed Company", cfg.company_name);
}

test "bad enum literal is a parse error" {
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    try std.testing.expectError(error.ParseZon, load(arena.allocator(), ".{ .difficulty = .brutal }"));
}

test "unknown field is a parse error" {

Exercise 28.3 · Round trip practice

Serialize a Roster with std.zon.stringify.serialize (pretty and compact) and parse it back. File: exercises/28-zon/ex3_roundtrip.zig.

Solution 
//! Chapter 28, exercise 3: serialize a value to ZON and read it back.
//! Run with:  zig test ex3_roundtrip.zig
//! Goal: make every test pass without changing the tests.
const std = @import("std");

pub const Pilot = struct { name: []const u8, gunnery: u8, piloting: u8 };
pub const Roster = struct { day: u32, funds: i64, pilots: []const Pilot };

/// Render `value` as ZON text into `buf`; return the written slice.
/// `pretty` chooses multi-line Zig style; false gives one compact line.
pub fn toZon(buf: []u8, value: anytype, pretty: bool) ![]u8 {
    var w = std.Io.Writer.fixed(buf);
    try std.zon.stringify.serialize(value, .{ .whitespace = pretty }, &w);
    return w.buffered();
}

/// Parse ZON text back into a Roster, allocating from `arena`.
/// The text must be sentinel-terminated: copy it with allocator.dupeZ first.
pub fn fromZon(arena: std.mem.Allocator, text: []const u8) !Roster {
    const z = try arena.dupeZ(u8, text);
    return std.zon.parse.fromSliceAlloc(Roster, arena, z, null, .{});
}

test "round trip" {
    var arena = std.heap.ArenaAllocator.init(std.testing.allocator);
    defer arena.deinit();
    const pilots = [_]Pilot{
        .{ .name = "Kell", .gunnery = 3, .piloting = 4 },
        .{ .name = "Ana", .gunnery = 5, .piloting = 5 },
    };
    const before = Roster{ .day = 12, .funds = -3_500, .pilots = &pilots };
    var buf: [1024]u8 = undefined;
    const text = try toZon(&buf, before, true);
    try std.testing.expect(std.mem.indexOf(u8, text, ".name = \"Kell\"") != null);
    const after = try fromZon(arena.allocator(), text);
    try std.testing.expectEqual(before.day, after.day);
    try std.testing.expectEqual(before.funds, after.funds);
    try std.testing.expectEqual(@as(usize, 2), after.pilots.len);
    try std.testing.expectEqualStrings("Ana", after.pilots[1].name);
    try std.testing.expectEqual(@as(u8, 5), after.pilots[1].gunnery);
}

test "pretty and compact forms" {
    var buf: [256]u8 = undefined;
    const p = Pilot{ .name = "X", .gunnery = 1, .piloting = 2 };
    try std.testing.expectEqualStrings(
        ".{\n    .name = \"X\",\n    .gunnery = 1,\n    .piloting = 2,\n}",
        try toZon(&buf, p, true),
    );
    try std.testing.expectEqualStrings(".{.name=\"X\",.gunnery=1,.piloting=2}", try toZon(&buf, p, false));
}

fromZon has to copy the text with dupeZ because the parser demands a zero terminator, and a slice returned by buffered() has none.

Exercise 28.4 · A mod overlay challenge

Finish build.zig in exercises/28-zon/ex4_overlay/ so that @import("tuning_zon") resolves to data/tuning.zon normally and to <dir>/tuning.zon with -Ddata=<dir>. Verify with zig build run -Ddata=mods/hardcore and zig build test.

Solution

build.zig

const std = @import("std");

pub fn build(b: *std.Build) void {
    const target = b.standardTargetOptions(.{});
    const optimize = b.standardOptimizeOption(.{});

    // zig build -Ddata=mods/hardcore  overlays data/tuning.zon
    const data_dir = b.option([]const u8, "data", "Directory overlaying data/tuning.zon");

    const mod = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .target = target,
        .optimize = optimize,
    });
    var tuning: std.Build.LazyPath = b.path("data/tuning.zon");
    if (data_dir) |dir| tuning = b.path(b.pathJoin(&.{ dir, "tuning.zon" }));
    mod.addAnonymousImport("tuning_zon", .{ .root_source_file = tuning });

    const exe = b.addExecutable(.{ .name = "overlay", .root_module = mod });
    b.installArtifact(exe);

    const run_step = b.step("run", "Print the live tuning table");
    run_step.dependOn(&b.addRunArtifact(exe).step);

    const tests = b.addTest(.{ .root_module = mod });
    const test_step = b.step("test", "Validate the tuning table");
    test_step.dependOn(&b.addRunArtifact(tests).step);
}

b.option returns an optional; when it is present we build a different LazyPath and hand it to addAnonymousImport under the same name.

Check your understanding

  1. Can a ZON file contain 2 * 3 or refer to a constant defined elsewhere?
    AnswerNo. ZON is literals only: no expressions, no names, no code.
  2. What does the type annotation in const t: Tuning = @import("tuning.zon"); buy you?
    AnswerThe compiler coerces the literal to Tuning at the import, so unknown fields, missing fields without defaults, and out-of-range values are build errors with line numbers in the data file.
  3. Does plain zig run main.zig support @import("data.zon")?
    AnswerYes, as long as the file is in the same directory as main.zig or below it. Paths that leave the root file's directory are refused.
  4. When do you need fromSliceAlloc rather than fromSlice?
    AnswerWhen the target type contains pointers or slices, such as strings. fromSlice asserts at compile time that no allocation is needed for the result.
  5. Why must the source given to std.zon.parse be [:0]const u8?
    AnswerThe parser reuses the compiler's tokenizer, which expects a zero byte terminator. Use dupeZ for text read from a file; @embedFile and string literals already have one.
  6. What is the difference between @embedFile("x.zon") and @import("x.zon")?
    Answer@embedFile gives the raw bytes as a constant string; @import gives the parsed, type-checked value.
  7. How does a source file import a data file that lives outside its directory tree?
    Answerbuild.zig binds it to a name with module.addAnonymousImport("name", .{ .root_source_file = path }), and the source writes @import("name").
  8. Name one thing types cannot check about a table, and how the game checks it.
    AnswerUniqueness of keys, references between tables, or ranges like "tonnage is a multiple of 5". Tests over the imported constant check those, on the real data, every build.
What you learned.
  • ZON is the literal subset of Zig: anonymous structs and lists, numbers, strings, booleans, null, enum literals, comments.
  • const t: T = @import("file.zon") loads a file at compile time and type-checks it; errors point into the data file.
  • Lists of rows coerce to []const Row, and struct defaults fill omitted fields.
  • Imports may go into subdirectories but never above the root file; addAnonymousImport in build.zig binds outside files to a name.
  • std.zon.parse.fromSlice / fromSliceAlloc parse ZON at run time from a sentinel-terminated string, with optional Diagnostics; parse into an arena.
  • @embedFile bakes raw bytes into the binary; std.zon.stringify.serialize writes ZON back out.
  • build.zig.zon is the package manifest, itself a ZON file with name, version, fingerprint, dependencies and paths.
  • Compile-time data trades "change without rebuilding" for "every mistake is a build error"; game balance tables want the latter.
